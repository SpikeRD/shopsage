# 需求变更台账（docs/changes/）

> 本目录是 ShopSage 的**需求变更**入口：一条变更一个文件，编号 `NNN-短横线标题.md`（`NNN` 三位递增，不复用、不删除）。
> 本文件同时是**变更流程规范**（怎么走、什么状态、怎么收口）和 **agent 协作提示词模板**（把流程交给 agent 执行时，直接复制第 6 节）。
> 与既有文档的分工：
>
> | 目录 | 回答的问题 | 变更时要不要动 |
> |---|---|---|
> | `docs/architecture.md` | 系统**蓝图**（技术栈、模块边界、数据模型） | 变更**被接受后**同步（蓝图必须与现状一致） |
> | `docs/modules/N.*.md` | 每个模块的**开发 + 测试**文档（8 段模板） | 变更**被接受后**回写对应模块的相关段 |
> | `docs/runbook/N.*-runbook.md` | 「怎么做、怎么确认做对了」的实操手册 | 变更引入新命令/新坑时**必须**补 |
> | `issues/` | 实测撞到、当场不修的问题（现象/根因/判据） | 变更过程中新发现的问题记这里，不塞进变更单 |
> | **`docs/changes/`** | **「原来是什么 → 改成什么 → 为什么 → 怎么做」** | 本次变更的**唯一权威描述** |

## 1. 流程（五步，不许跳步）

```
① 提出（用户口述改动点）
   → 我在 docs/changes/ 建 NNN-xxx.md，逐条追问歧义，写成「需求变更说明书」
② 定稿（用户确认）
   → 状态置 `已定稿`；此时**只改文档，不写代码**
③ 拆任务（把说明书翻译成可执行步骤）
   → 文件内 §6 任务拆解（按依赖排序，每条含：改哪个文件、验收判据、跑哪条命令）
④ 开发（按拆解改代码）
   → 每完成一条就在 §6 打勾，并回填证据（命令 + 输出）
⑤ 收口（回归 + 回写蓝图）
   → 全量回归；同步 architecture.md / modules 文档 / runbook；状态置 `已完成`
```

**两条铁律：**

1. **先文档后代码**。变更说明书定稿（②）之前，不动任何业务代码。
2. **可验证**。每条变更必须落到「跑什么命令 → 看到什么输出算过」，不接受「感觉改好了」。

## 2. 状态取值

| 状态 | 含义 |
|---|---|
| `草稿` | 正在讨论，需求还在变，**不要动代码** |
| `已定稿` | 需求冻结，§6 任务拆解已确认，可以开工 |
| `开发中` | 已开始改代码，§6 逐条打勾 |
| `已完成` | 代码 + 测试 + 文档回写全部收口 |
| `已搁置` | 明确不做（**保留文件**，写明搁置原因，方便日后翻账） |

## 3. 与模块文档的关系

变更**不**直接改写模块文档当草稿；先在变更单里定稿，开发完成后再把结论回写到模块文档对应段落并链接回本变更单编号：

```markdown
> 变更来源：[docs/changes/001-xxx.md](../changes/001-xxx.md)
```

## 4. 变更单结构（`_TEMPLATE.md` 八节）

新建时复制 [`_TEMPLATE.md`](_TEMPLATE.md)，按下表把提示词要求的 7 项内容落到对应小节（**缺节即视为未完成**）：

| 提示词要求（第 6 节阶段 2） | 变更单落点 |
|---|---|
| 1. 变更背景与现状 | §1 变更动机（现状 / 问题 / 不改的代价） |
| 2. 变更目标 + 验收标准（逐条编号、可执行验证） | §2 变更点 + §4 验收判据 |
| 3. 影响面分析（模块/文件/接口/数据结构/配置/依赖） | §2 变更点 + §5 影响面自检 |
| 4. 技术方案 + ≥1 个备选方案对比与取舍理由 | §3 方案设计（3.1 目标方案 / 3.2 备选与取舍） |
| 5. 不做什么（显式排除项，防范围蔓延） | §2 变更点「不改的」行 + §3.2 舍弃理由 |
| 6. 风险与回滚方式 | §3.3 兼容性与迁移（含回滚方式） |
| 7. 实施步骤拆解 + 自测计划（具体命令与预期结果） | §6 任务拆解 + §4 验证命令列 + §7 实测证据 |

> §8「遗留与后续」不在提示词 7 项之内，但凡是本次没做/顺带发现的问题，一律记到 `issues/` 并在此链接，不许塞进本次范围。

## 5. 流程与提示词阶段的对应

| 台账五步（第 1 节） | Agent 提示词阶段（第 6 节） |
|---|---|
| ① 提出 | 阶段 0 · 边界确认 → 阶段 1 · 需求澄清（问答） |
| ② 定稿 | 阶段 2 · 先写文档（硬门禁） |
| ③ 拆任务 | 阶段 2 产出文档的 §6（确认后方可开工） |
| ④ 开发 | 阶段 3 · 开发 |
| ⑤ 收口 | 阶段 4 · 自测（强制取证）→ 阶段 5 · 交付汇报 |

## 6. Agent 协作提示词模板

> 用途：让 agent 按「问答澄清 → 先写文档 → 再开发 → 自测取证」的顺序推进需求变更，避免它猜需求、跳过设计、口头声称"改好了"。
> 完整原文另存于 [`代码需求变更提示词模板.md`](代码需求变更提示词模板.md)，本节为同一内容，便于一处查阅。

### 6.1 使用方式

1. 复制下面「模板正文」整段。
2. 替换 `{{ }}` 占位符（需求初稿、项目路径等）。
3. 粘贴给 agent。之后**不要替它补全细节**——让它主动来问你，这正是模板要的效果。
4. 若只是想快速跑小改动，用 6.3 的「精简版」。

### 6.2 模板正文（可直接复制）

```text
你是本次代码需求变更的执行 agent。请严格按下面 5 个阶段推进，禁止跳阶段、禁止并行。

================ 阶段 0 · 边界确认 ================
先只做一件事：读懂现状，不要写任何代码。
- 阅读我给出的需求初稿：{{需求初稿}}或文本
- 相关仓库/目录：{{项目路径}}
- 只读探索，输出你对现状的理解（关键文件、现有实现方式、可能的落点）
- 如果你发现需求初稿里存在术语歧义、目标冲突、或与现有实现矛盾，直接列出来

================ 阶段 1 · 需求澄清（问答） ================
规则（严格执行）：
1. 用编号提问，每轮最多 {{每轮问题数=5}} 个问题。
2. 每个问题必须给出 2–4 个候选答案，并标注「推荐：X」及一句理由。不要问开放式大题。
3. 严禁在信息不足时自行假设然后开工。信息不足就继续问下一轮。
4. 当我的回答是"随你/你决定/都行"时：采用你的推荐项，并把它记入「假设与风险」清单，最后汇报时必须复述。
5. 遇到需求内部矛盾，必须显式指出让我裁决，不许静默选一种解释。
6. 澄清完成的门槛——以下 6 项全部明确后才可进入阶段 2：
   a) 变更目标（要达成什么可观察的效果）
   b) 范围边界（动哪些模块，明确不碰哪些）
   c) 验收标准（可执行、可判定，不是"运行正常"这类空话）
   d) 兼容性约束（接口/数据/配置是否必须向后兼容）
   e) 交付形式（只改代码？要不要迁移脚本、文档、开关）
   f) 时间/优先级取舍（若必须在质量与速度间取舍，倾向哪边）
7. 每轮问答结束后，用 3–5 行复述你当前的理解，确认无偏差再继续。
8. 澄清轮次上限 {{轮次上限=4}} 轮；达到上限仍有缺口时，停下来告诉我缺口是什么，由我决定是否继续。

================ 阶段 2 · 先写文档（硬门禁） ================
在收到我明确确认之前，一个字的业务代码都不许写。

产出文档：{{文档路径=docs/changes/NNN-标题.md}}
必须包含以下 7 节，缺节即视为未完成（落点见 README 第 4 节）：
1. 变更背景与现状（现在的行为是什么，为什么不够）
2. 变更目标 + 验收标准（逐条编号，每条都可执行验证）
3. 影响面分析（模块 / 文件 / 对外接口 / 数据结构 / 配置项 / 依赖）
4. 技术方案，以及与至少 1 个备选方案的对比和取舍理由
5. 不做什么（显式排除项，防止范围蔓延）
6. 风险与回滚方式
7. 实施步骤拆解 + 自测计划（自测计划要列出具体命令与预期结果）

文档写完后停下，把文档贴出来（或给出路径）等我确认。
我确认前不得进入阶段 3；我提出修改则改完再确认。

================ 阶段 3 · 开发 ================
- 严格按已确认文档实施，不扩大范围。
- 若开发中发现必须扩范围：立即停下，重新走阶段 1–2，不许"顺手一起改了"。
- 小步推进，每一步都要处于可验证状态。
- 不重构与本次变更无关的代码；发现无关问题记入"遗留问题"而非当场动手。
- 输出改动清单：文件 → 改了什么 → 为什么改。

================ 阶段 4 · 自测（强制取证） ================
- 必须真实运行代码/命令，并贴出原始输出。禁止"应该没问题""理论上可行"这类无证据断言。
- 对照阶段 2 的验收标准逐条核对，输出表格：
  | 验收标准 | 验证方式（命令/步骤） | 实测结果 | 结论(通过/失败/未验证) |
- 覆盖面至少包含：正常路径、边界值、异常/非法输入、原有功能回归。
- 测试失败时：要么修复后重测并说明，要么明确标注"未解决 + 原因"，不得隐瞒或淡化。
- 明确区分「我改了」与「我验证了」——前者不算完成。

================ 阶段 5 · 交付汇报 ================
固定格式，按此输出：
1. 结论：完成 / 部分完成 / 受阻（受阻须说明卡在哪）
2. 改动清单
3. 自测结果表（阶段 4 那张）
4. 未解决项与遗留问题
5. 需要我决策的点
6. 假设与风险复述（含阶段 1 记录的"你决定"项）

================ 全局禁令 ================
- 不许跳阶段，不许用"我先实现着，文档后面补"。
- 不许在澄清完成前写业务代码。
- 不许伪造、编造、美化测试结果。
- 不许把"代码写完了"当成"任务完成了"。
- 不确定就说不确定，宁可多问一句。

现在开始：执行阶段 0。
```

### 6.3 精简版（小改动速用）

```text
按四步走，逐步停下等我确认，禁止跳步：
1) 只读现状，用编号提问澄清需求（每题给候选答案+推荐项），信息不足就继续问，不要猜。
2) 写变更文档（背景/目标+可验证验收标准/影响面/方案取舍/不做什么/风险/自测计划），我确认后才动代码。
3) 按文档改，不扩大范围，输出改动清单。
4) 自测：真实运行并贴原始输出，按验收标准逐条给通过/失败表格，区分"改了"和"验证了"。
需求：{{需求描述}}
项目：{{路径}}
```

### 6.4 可调参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `每轮问题数` | 5 | 调小更省事，调大收敛更快 |
| `轮次上限` | 4 | 防止无限提问；到顶要求它列出缺口 |
| `文档路径` | docs/changes/… | 也可改成先口头方案、确认后再落文档 |
| 门禁强度 | 强制 | 想快可放宽阶段 2，但阶段 4 自测建议始终保留 |
| 自测强度 | 冒烟 + 回归 | 高风险变更可加"全量测试 + 手工验证步骤" |

### 6.5 为什么这样设计

- **问答带候选答案**：开放式提问会让 agent 把澄清责任推回给你；给选项能把决策成本降到最低，同时暴露它的理解偏差。
- **"你决定"必须记账**：口语化的授权最容易被 agent 当成"无需再提"，记入假设清单可在交付时暴露分歧。
- **文档作为门禁而非产物**：写文档的真正作用是强制它在动手前把影响面和验收标准想清楚。
- **自测要求原始输出**：这是唯一能区分"真的跑过"和"编了个结论"的手段。
- **显式"不做什么"**：需求变更最大的风险是范围蔓延，而不是写不出来。
