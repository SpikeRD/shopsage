# 需求变更台账（docs/changes/）

> 本目录是 ShopSage 的**需求变更**入口：一条变更一个文件，编号 `NNN-短横线标题.md`（`NNN` 三位递增，不复用、不删除）。
> 与既有文档的分工：
>
> | 目录 | 回答的问题 | 变更时要不要动 |
> |---|---|---|
> | `docs/architecture.md` | 系统**蓝图**（技术栈、模块边界、数据模型） | 变更**被接受后**同步（蓝图必须与现状一致） |
> | `docs/modules/N.*.md` | 每个模块的**开发 + 测试**文档（8 段模板） | 变更**被接受后**回写对应模块的相关段 |
> | `docs/runbook/N.*-runbook.md` | 「怎么做、怎么确认做对了」的实操手册 | 变更引入新命令/新坑时**必须**补 |
> | `issues/` | 实测撞到、当场不修的问题（现象/根因/判据） | 变更过程中新发现的问题记这里，不塞进变更单 |
> | **`docs/changes/`** | **「原来是什么 → 改成什么 → 为什么 → 怎么做」** | 本次变更的**唯一权威描述** |

## 流程（五步，不许跳步）

```
① 提出（用户口述改动点）
   → 我在 docs/changes/ 建 NNN-xxx.md，逐条追问歧义，写成「需求变更说明书」
② 定稿（用户确认）
   → 状态置 `已定稿`；此时**只改文档，不写代码**
③ 拆任务（把说明书翻译成可执行步骤）
   → 文件内 §6 任务拆解（按依赖排序，每条含：改哪个文件、验收判据、跑哪条命令）
④ 开发（按拆解改代码）
   → 每完成一条就在 §6 打勾，并回填证据（命令 + 输出）
⑤ 收口（回归 + 回写蓝图）
   → 全量回归；同步 architecture.md / modules 文档 / runbook；状态置 `已完成`
```

**两条铁律：**

1. **先文档后代码**。变更说明书定稿（②）之前，不动任何业务代码。
2. **可验证**。每条变更必须落到「跑什么命令 → 看到什么输出算过」，不接受「感觉改好了」。

## 与模块文档的关系

变更**不**直接改写模块文档当草稿；先在变更单里定稿，开发完成后再把结论回写到模块文档对应段落并链接回本变更单编号：

```markdown
> 变更来源：[docs/changes/001-xxx.md](../changes/001-xxx.md)
```

## 状态取值

| 状态 | 含义 |
|---|---|
| `草稿` | 正在讨论，需求还在变，**不要动代码** |
| `已定稿` | 需求冻结，§6 任务拆解已确认，可以开工 |
| `开发中` | 已开始改代码，§6 逐条打勾 |
| `已完成` | 代码 + 测试 + 文档回写全部收口 |
| `已搁置` | 明确不做（**保留文件**，写明搁置原因，方便日后翻账） |
