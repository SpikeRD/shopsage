# llm — LLM 接入层（LiteLLM 多模型路由 / 重试 / 熔断 / embedding 双后端）

## 1. 职责

统一封装对 LLM 的调用：多模型路由、自动降级、重试、熔断、token/成本计量。
所有 Agent 一律通过这里调模型，**不允许各处直接 `openai.chat.completions`**。

职责里还有一条容易被忽略、但必须在这里收口的：**embedding**。
它可能花钱（API 后端）、一定是延迟的一部分，而且**换模型会改变向量维度与向量空间**
（第 10 步 rag 的 `vector(n)` 列依赖它）。所以它和对 chat 模型一样，需要**单一出口 + 单一配置源**。

> ⚠️ 本模块横跨两个阶段：**第 5 步只做基础接入（单模型调通 + 429 退避重试 + `embed()`）**；
> **熔断器 + 多模型降级 + Langfuse 回调留到第 13 步（加固）**。见下方「开发步骤」。

## 2. 对外接口

```python
from app.llm import llm_call, embed, LLMResponse, LLMError, PermanentLLMError, RetryableLLMError

# ── chat ──（第 5 步已落地；fallback_models 属第 13 步，见「接口演进」）
resp: LLMResponse = await llm_call(
    messages=[...],
    model="deepseek/deepseek-flash",   # None = 用 config 的 llm_primary
    max_retries=3,                     # 总尝试 = 1 + max_retries
    timeout=30.0,
)
resp.content, resp.model, resp.total_tokens, resp.cost_usd, resp.latency_ms

# ── embedding ──（两种后端同一个签名：API 或本地，由 config 的 embedding_backend 决定）
vecs: list[list[float]] = await embed(texts=["退货政策是什么"])          # 后端/模型都读 config
vecs = await embed(texts=["..."], model="BAAI/bge-m3")                 # 显式指定（本地后端时是 HF 名）

# ── 错误只有两个语义，调用方按它决定「稍后重试」还是「别再试」 ──
try:
    ...
except PermanentLLMError:   # 参数错/鉴权/模型名错/维度不符 → 别重试、别重排队列
    ...
except RetryableLLMError:   # 持续 429/5xx/超时 → 可带延迟重排（第 12 步 queue）
    ...
```

### 接口演进（写清楚「现在没有」与「什么时候有」）

| 接口 | 状态 | 说明 |
|---|---|---|
| `llm_call(messages, model=None, *, max_retries, timeout, **kwargs)` | ✅ 已实现 | 返回 `LLMResponse`（不是 litellm 原始对象，理由见第 4 节第 5 条） |
| `embed(texts, model=None, *, max_retries, timeout)` | ✅ 已实现 | 两后端同名同签名；**保序** + 条数校验 + 可选维度守卫 |

| 熔断器开/半开状态查询 | ⏳ 第 13 步 | `errors.is_retryable()` 已经是它的输入信号，接线时不用改分类逻辑 |

## 4. 关键设计决策

1. **LiteLLM 做统一门面**：一套接口调 OpenAI/DeepSeek/Anthropic/本地模型，模型名切换不改业务代码。
2. **fallback 链 = 主备模型**：主模型 429/5xx/超时 → 自动降级备用模型或小模型，「质量可降级、可用性不降」（A3）。
3. **指数退避 + jitter**：429 限流时 `min(2^n, cap)` 秒退避 + 随机抖动，避免多副本同时重试形成风暴（A1）。
4. **熔断器**：连续失败 N 次直接快速失败一段时间，保护下游模型不被打爆，也避免用户长等。
5. **对返回「我们自己的结构」而不是 litellm 原始对象**：`LLMResponse` 让 token/成本口径只有一处
   （否则每个 Agent 各写一份 `response.usage.*`，第 11/13 步的「统一计费」无处落脚）。
   代价是丢掉 `response.id` 这类透传信息，第 13 步接 Langfuse 时在 `LLMResponse` 上加字段即可。
6. **密钥按用途分层，一把钥匙只服务一条路径**（**本步新增的硬约定**）：

   | 用途 | 字段 | 为什么不共用 |
   |---|---|---|
   | 主模型 | `llm_api_key` | — |
   | **降级模型** | **`llm_fallback_api_key`**（+ 可选 `llm_fallback_api_base`） | 降级链**天生跨厂商**（A3 的意义就在这）：拿 A 家的 key 打 B 家端点必然 401，而降级时刻正是主模型已经不可用的时候，此刻失败＝直接对用户报错。此外还带来**故障隔离**（主 key 被限流/超额时备路径仍可用）、**独立轮换**、**账单可归属**。**凭据解析必须绑定「最终要打哪个模型」**，不能在函数入口解析一次 |
   | embedding | `embedding_api_key`（留空则复用 `llm_api_key`） | embedding 端点常与主模型不同厂商；允许复用，但**厂商不同就必须单独配** |

   两条配套校验：`llm_fallback` 非空而 `llm_fallback_api_key` 为空 → **prod 启动即失败**（dev 告警）；
   两把 key **相同**时告警（不是错误，但意味着没有故障隔离）。

7. **embedding 支持两种后端，但只有一个出口**：

   | | `embedding_backend=litellm`（默认） | `embedding_backend=local` |
   |---|---|---|
   | 实现 | `litellm.aembedding` | `SentenceTransformer.encode`（经 `asyncio.to_thread`） |
   | 密钥/成本 | `embedding_api_key`，按 token 计费 | 无密钥、无边际成本、**文本不出网** |
   | 代价 | 文本出网、受厂商配额限制 | 可选依赖 ~2 GB、首次要下权重、要管设备/内存、**维度与向量空间随模型变** |

   选本地的正当理由只有三条：**合规（文本不许出网）/ 完全离线 / 调用量极大且成本敏感**。
   不要因为「本地免费」就默认切：它会把权重下载、离线预置、线程与设备这些**运维面**问题引进来，
   而 API 后端根本没有这些问题。**无论哪种后端都走同一个 `embed()`**，调用方（rag/cache）不感知差异。

8. **维度守卫而不是「静默容忍」**：`embedding_dim` 填了就强校验，不符直接抛 `PermanentLLMError`。
   因为换模型最坏的情况不是「报错」而是**维度恰好相同但向量空间不相容**——检索看起来正常、
   实际全是乱码结果，评测掉分时你会先去怀疑 prompt。换后端（API↔本地）**必然**属于这种情况。

## 5. 核心技术点（要懂为什么）

- **为什么退避要加 jitter**：无抖动时，所有失败请求在同一时刻重试，会瞬间打爆模型形成「惊群」；随机抖动把重试错开。
- **fallback 的判断边界**：只有「限流/超时/5xx」这类**可恢复错误**才降级；「参数错误/鉴权失败/内容违规」不应降级（降了也没用，还掩盖 bug）。
- **主备模型的成本/质量权衡**：主模型质量高、贵；备模型便宜、快、质量略低。降级时保留原问题上下文，让备模型也能答到及格线。
- **统一计费**：每次调用记录 `model / tokens / cost / latency`，汇入 Langfuse（`11.observability.md`），成本优化靠它。
- **凭据是「按模型」解析的，不是「按函数入口」解析的**：`used_model` 会在降级时从主模型切成备模型，
  所以取 key 必须发生在「最终打哪个模型定了之后」。在入口解析一次，就会在降级那一刻拿主模型的钥匙去开备模型的门 ——
  必然 401，而 401 被判为不可恢复，于是**降级链在最需要它的时刻失效**（第 4 节第 6 条、runbook §8.1）。
- **同一个 `embed()` 后面可以是两种完全不同的实现**：API（按 token 计费、文本出网、可能 429）与
  本地 sentence-transformers（零边际成本、文本不出网、吃本机 CPU/内存）。**调用方不需要知道是哪一种** ——
  这正是「把 embedding 也收进统一门面」换来的东西：换后端不改 rag/cache 一行代码，
  但要付出「维度/向量空间随实现而变」的代价，所以必须有维度守卫（第 4 节第 8 条）。
- **`encode()` 是同步阻塞调用**：在 async 服务里不丢进线程就会阻塞事件循环 —— 症状是
  「并发一上来**所有**接口都慢」，极易误判成数据库或队列问题。同类陷阱适用于任何
  「同步 CPU 密集 + async 框架」的组合（第 4 节第 7 条、runbook §7.3.2）。
