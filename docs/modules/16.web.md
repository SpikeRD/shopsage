# web — Next.js 前端（对客 / 对内 / 管理台三个入口）

> 🔁 **变更 001 把这一层从「粘贴令牌」改成了「真登录」**（详见 [docs/changes/001](../changes/001-account-login-and-admin-console.md)）：
> ① `/login` 从**粘贴令牌**改为**账号 + 口令**（`POST /api/auth/login`），粘贴令牌收进「开发模式」折叠区；
> ② 新增 `/admin` 管理台（开账号 / 停用启用 / 改角色 / 重置口令）；
> ③ **入口由服务端算好**（登录响应的 `entry` 字段）—— 前端不再猜「哪个角色进哪个界面」；
> ④ 三个入口各一把钥匙（`shopsage.token.customer/.internal/.admin`），**互不覆盖**；
> ⑤ 新增 `web/src/lib/session.ts`：存一对令牌 + **快过期时自动续期**（访问令牌只有 30 分钟）。

## 1. 职责

提供演示用的三个前端入口：对客（聊天问答）、对内（数据查询/报表）、管理台（账号管理），负责调用后端 API、WebSocket 流式渲染、展示溯源与图表。**是演示层，不是核心逻辑**。

## 2. 对外接口

```text
/            # 对客入口（聊天框）
/internal    # 对内入口（员工数据查询/报表）
/admin       # 管理台入口（变更 001：账号管理）
/login       # 登录（变更 001：账号 + 口令；开发模式可粘贴令牌）
/citation    # 出处原文（溯源能点开才叫溯源）
```

## 3. 依赖

- `next`（App Router）+ TypeScript
- 后端 `9.api.md`（`POST /api/chat` + `WS /api/chat/stream` + **`POST /api/auth/*`** + **`/api/admin/*`**）
- 图表渲染（接 `6.tools.md` 的 `chart` spec）

## 4. 关键设计决策

1. **三个入口靠角色切换，而非三套前端**：登录后按服务端返回的 `entry` 显示界面（呼应 `4.security.md` 的三档权限）。
2. **流式渲染**：WebSocket 逐段接收，打字机效果，首 token 快（B2）。
3. **溯源可视化**：RAG 回答底部展示「来源文档 + 片段」，可点击跳转（`10.rag.md` 溯源）。
4. **前端不做业务判断**：所有权限/越权判断在后端，前端只做展示。
5. **入口分流只有一处真相**（变更 001）：`entry` 由服务端算（`accounts.entry_for_role`），
   前端 `defaultEntry()` 只在「手粘令牌、服务端没给 entry」时兜底。
   副本必然漂移，而漂移的症状是「登录成功却停在空白页」。
6. **刷新失败必须清干净**（变更 001）：`ensureFreshToken()` 在刷新 401 时把访问令牌与刷新令牌
   **一起清掉**。留下半条会话的症状是「一直转圈，然后莫名其妙跳登录页」。
7. **导航是客户端组件**（变更 001）：`app/layout.tsx` 是服务端组件，而登录态在 `localStorage`
   —— 在 layout 里直接读会渲染出「未登录」快照并与客户端水合结果打架。
   所以按角色渲染入口的那部分抽成 `components/TopNav.tsx`（`"use client"`）。

## 5. 核心技术点（要懂为什么）

- **SSR 与流式的关系**：这里流式走 WebSocket 而非 SSE，因为要双向（用户可中断、可追问），且后端已是 WS 流式（`9.api.md`）。
- **图表 spec 解耦**：后端返回结构化 spec，前端用 ECharts/Recharts 渲染，换绘图库不改后端（`6.tools.md`）。
- **令牌解码不验签**（`lib/auth.ts`）：浏览器没有密钥，`decodeJwtPayload()` 只做 base64 解码。
  所以它**只能决定渲染哪个界面**，绝不能决定「能不能拿到这行数据」—— 后者要服务端验签后的结果。
- **`sub` 是主体标识串**（变更 001）：`c2` / `e1`，**不是**数字 user_id。
  `session.userId` 存的就是它（`readSession` 直接透传 `claims.sub`）。
- **同一秒内 JWT 是确定性的**：所以「刷新过没有」**不能**靠比较新旧令牌字符串来判断
  （`web/tests/session.test.ts` 里专门记了这条，并改用可区分的事实验证）。

## 6. 开发步骤

1. `npx create-next-app` 初始化 `web/`。
2. 写对客聊天页：接 `WS /api/chat/stream`，流式渲染 + 溯源展示。
3. 写对内页：接 `/api/chat`，展示数据表格 + 图表。
4. 接 JWT 登录，按 role 渲染入口。
5. 写 `web/Dockerfile` + 接入 `2.infra.md` 的 compose。
6. **变更 001**：`lib/session.ts`（一对令牌的存储 + 自动续期）、`login/page.tsx`（账号登录表单）、
   `admin/page.tsx`（管理台）、`components/TopNav.tsx`（按角色渲染导航）。

```bash
npx next build          # 构建通过
# 手工/组件测试
```

> ⚠️ 本步的**实际落地**与上面四条有一处差异（有意为之）：本仓不引浏览器自动化依赖，
> 所以「组件测试」拆成两层，各自回答不同的问题（runbook §7.1）：
>
> | 层 | 命令 | 覆盖 |
> |---|---|---|
> | 纯逻辑（离线，**119 条**） | `cd web; npm test` | 帧时序 / 出处解析 / 图表适配 / 角色分流 / 子协议与错误信封 / **会话存储与刷新续期（变更 001 新增 14 条）** |
> | 真链路（**10 条**） | `node tests/run-live.mjs` | 真 WS 帧序列 + 首帧 <1s / 真出处（且能点开原文）/ 真 `chart_spec` / 4401 / `/api/kb` 越权拦截 |
>
> 真链路用例用的是**浏览器里同一份客户端代码**（`src/lib/stream.ts`），
> 而不是另写一个测试专用客户端（那份「干净」的客户端会因为跟真客户端写得不一样而给出虚假的安全感）。
>
> ⚠️ **变更 001 在本机跑真链路时踩到一个环境坑**：`node tests/run-live.mjs` 会**挂住不退出** ——
> 它用 `spawn(..., stdio: ["ignore","pipe","pipe"])` 去跑 `uv run python -m scripts.dev_token --json`，
> 而受限环境下子进程管道不可用时，它的 `capture()` **既不 error 也不 close**，于是永久挂住
> （该文件注释里记的是「会 EPERM 直接失败」，那是另一个变体）。
> 绕法（**不改任何文件**）：直接用 `node --test tests/live/live.test.ts`，
> 令牌从 `SHOPSAGE_TOKEN_CUSTOMER` / `SHOPSAGE_TOKEN_INTERNAL` / `SHOPSAGE_TOKEN_EXPIRED` 传入
> —— `live.test.ts` 本来就支持这条路。
