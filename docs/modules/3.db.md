# db — 数据访问层（SQLAlchemy 模型 / 连接池 / 读写分离 / 权限）

## 1. 职责

统一封装对 PostgreSQL 的访问：ORM 模型、连接池、以及「对客 / 对内」两条权限路径的数据库视角。
是 Text-to-SQL 和所有数据查询的**唯一入口**，业务代码不直接裸写连接。

> 🛠 **实操手册**：[`docs/runbook/3.db-runbook.md`](../runbook/3.db-runbook.md) —— 建库/扩展校验、连接串方言与连接池、
> Alembic 迁移（含可重复执行的回环验证）、种子数据、行级过滤与池上限的证据怎么跑、怎么回填，都在那里。
> 本文讲「是什么、为什么」，手册讲「怎么点、怎么确认做对了」。直接接着做：[`2.infra-runbook.md`](../runbook/2.infra-runbook.md)（第 2 步起依赖栈）。

## 3. 依赖

- `SQLAlchemy 2.x`（ORM + Core）+ `psycopg`（**本仓走同步路径**：`create_engine` / `SessionLocal` /
  `get_db`；异步方案 `asyncpg` / `create_async_engine` 属未来可选项，见 runbook §2.1）
- `pgvector`（向量检索，见 `10.rag.md`，同库不同表/扩展）
- 读取 `config` 的 `database_url`

## 4. 关键设计决策

1. **一张业务库装下关系数据 + 向量数据**：pgvector 是 PostgreSQL 扩展，知识库向量和业务表同库，省一套独立向量库（小企业够用，架构第 2 节）。
2. **读写分离是「能力」，不是「必须一开始就上」**：先单库，用 `get_read_engine` / `get_write_engine` 两个入口预留切换点；负载上来再挂只读副本改连接串即可（架构第 8 节）。
3. **行级过滤只有一处真相：SQL 层，且只写在 `app/db/queries.py` 里**（`WHERE user_id = :当前用户`）。
   - **不是**应用层 `if` 过滤：应用层过滤＝先查出全部再截断，既慢又可能在中途泄露。
   - **也不是**由只读视图负责行过滤：过滤若同时存在于视图与查询封装，就会出现「视图已过滤 / 应用忘了过滤」
     两个假设互相掩护，反而削弱 D1。数据库层的**纵深防御留给只读角色**（见下一条），不留给视图。
4. **只读角色/只读连接：第 4 步（`4.security.md`）再做，第 3 步先留好切换点。**
   `get_read_engine()` / `get_write_engine()` 两个入口已经就位（第 2 条），接只读 DSN 即可切换。
   第 3 步**不**建 `v_customer_orders` 视图、**不**建 `shopsage_readonly` 角色——理由、触发条件与第 4 步
   要做的清单见 [`3.db-runbook.md`](../runbook/3.db-runbook.md) §5.3「决策记录」。
5. **连接池显式设上限**：`pool_size` + `max_overflow` + `pool_pre_ping=True`，防止连接被打爆（C1）。

## 5. 核心技术点（要懂为什么）

- **`pool_pre_ping=True`**：每次借连接前先 ping，踢掉因网络/超时失效的连接，避免「从池里拿到死连接」。
- **连接池参数怎么估**：`pool_size ≈ 每 worker 并发 SQL 数`，`max_overflow` 是峰值临时额度；设太大拖垮库，太小排队。
- **行级过滤为什么必须在 SQL 层而非应用层**：应用层过滤 = 先查出全部再截断，既慢又可能泄露；`WHERE user_id=...` 由数据库保证只返回本用户数据，是防越权的最后一道闸。
  ⚠️ 但「在 SQL 层」≠「写进视图」：本项目把过滤**只**放在 `app/db/queries.py` 的封装里（一处真相），
  由 `assert_row_filtered()` 编译期断言 + 库侧 queryid 锚定证据双保险；视图方案会制造第二处真相，不采用。
- **`sessionmaker` 的 `expire_on_commit=False`**：提交后对象仍可用，避免异步上下文里反复触发刷新。

## 6. 开发步骤

1. 在 **VMware-Linux 虚拟机**上用 `infra/docker-compose.dev.yml` 起 `postgres` + 启用 `pgvector` 扩展（见 `2.infra.md` §2、§3.1；本机 Windows 无 Docker，不要在开发机上试）。
2. 写 `app/db/base.py`（DeclarativeBase）+ 8 张业务表的模型（字段、索引、外键）。
3. 写 `session.py`：`create_engine`（带池参数）、`SessionLocal`、`get_db` / `get_read_engine` / `get_write_engine`。
4. 用 Alembic 建迁移：`alembic init` → 生成首版 → `alembic upgrade head`。
5. 写 `scripts/seed.py`：插入模拟用户/订单/商品/库存/工单/员工数据（电商场景演示必需）。
6. 写**行级过滤的查询封装**（纯 SQL 层过滤，不经视图）：`get_orders_for_customer(user_id)` 等，
   并要求每个出口都过 `assert_row_filtered()`——把「必须带 WHERE」变成可执行检查。

> 📌 **第 6 步的口径修正（与实现同步）**：原文写的是「只读视图 + 行级过滤」的封装，但**只读视图第 3 步没有做**，
> 且按设计决策第 3/4 条**不该由视图承担行过滤**。本步实际交付的是 `app/db/queries.py`（编译期断言覆盖全部
> `get_*` 出口）+ 库侧 `pg_stat_statements` 的 queryid 锚定证据；视图与只读角色推迟到第 4 步，见
> [`3.db-runbook.md`](../runbook/3.db-runbook.md) §5.3「决策记录」。
