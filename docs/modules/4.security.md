# security — SQL 白名单 / 越权拦截 / 脱敏 / 鉴权（旗舰模块）

> 🔁 **变更 001 改了本模块的三件事**（详见 [docs/changes/001](../changes/001-account-login-and-admin-console.md)）：
> ① 新增**账号服务** `accounts.py`（登录认证与账号生命周期，口令散列升级为 Argon2id）；
> ② 令牌声明从「裸 user_id」改为「**主体 + 世代号**」（`sub=c7/e1`、`stype`、`sid`、`aid`、`ver`）；
> ③ `policy.ROLE_MAX_SENSITIVITY` 补上 `admin`（此前缺失 ⇒ 管理员**什么都看不到**，一个已存在的 bug）。
> ⚠️ 升级后**旧令牌一律失效**（没有 `aid`/`ver`），需要重新登录。

## 1. 职责

本项目**最大的亮点模块**。负责在 LLM 生成 SQL 到真正执行之间，以及执行结果返回用户之前，做两层安全闸：
**执行前**（SQL 静态校验 + 权限校验）和**执行后**（敏感字段脱敏 + 输出合规）。
只做「拦截」，不做「生成 SQL」。

变更 001 起还负责**「凭据 → 身份」这一层**：`accounts.py` 回答「这组账号口令对应哪个账号」，
`auth.py` 回答「这条令牌是谁、有没有被改过」。两者的分工不能混：
前者要查库（账号状态会变），后者是纯凭据解析（被限流中间件等多条不查库的路径复用）。

## 3. 依赖

- `sqlglot`（把 SQL 解析成 AST，才能可靠地做白名单/危险操作检测，而不是靠字符串匹配）
- `PyJWT`（JWT 鉴权）+ **`argon2-cffi`**（变更 001：口令散列；旧的 `sha256$` 值仍可验）
- 读 `config` 的 `JWT_SECRET`
- 被 `agents/data.py`（执行前）、`agents/synthesis.py`（执行后）、`api/`（鉴权与账号接口）调用

## 4. 关键设计决策

1. **用 AST 而不是正则校验 SQL**：正则挡不住大小写/注释/子查询/换行绕过；`sqlglot` 解析成抽象语法树后，能可靠地判断「有没有 DROP/DELETE」「是不是只 SELECT」「WHERE 在哪」。
2. **读写路径分离**（架构第 6 节）：读路径 = 允许 NL→SQL 但**只读白名单**；写路径 = 工单/退款走**预定义的 service API**，绝不走 LLM 动态生成 SQL。这是防「LLM 被诱导执行写操作」的根本设计。
3. **白名单 + 黑名单双管**：黑名单拦 `DROP/DELETE/UPDATE/INSERT/TRUNCATE`，白名单限制「只能查哪些表、哪些列」，缺一不可——黑名单会被新语法绕过，白名单防「查了不该查的表」。
   `accounts` 在专门的 `NEVER_IN_SQL_WHITELIST` 里（有断言钉住）：它存的是 `password_hash`。
4. **越权分两种路径**：对客 = 行级过滤（只能查自己的 user_id）；对内 = RBAC（按 role 分级，普通员工看不了财务级数据）；管理 = `PERM_ADMIN` 权限点。
5. **脱敏放在「结果返回前」而非「存储时」**：库里存真值，输出时按角色脱敏，兼顾业务需要与隐私。
6. **令牌的 `sub` 带主体类别**（变更 001）：`c{user_id}` / `e{emp_id}`。
   理由是 `thread_id` 由主体派生，而员工在 `users` 表里**没有行** ——
   若沿用裸 `emp_id`，员工 `emp_id=7` 与客户 `user_id=7` 会派生同一个会话桶
   （两个不同的人落进同一份 checkpoint，那不是越权读一行数据，而是读到别人上一轮的原话）。
7. **「凭据表」与「业务表」分开**（变更 001）：账号是独立一张 `accounts` 表，
   而不是给 `users`/`employees` 各加口令列。后者会让登录分叉成两条路径，
   而「客户侧加了口令校验、员工侧忘了加」这种故障不会有任何报错。

## 5. 核心技术点（要懂为什么）

- **为什么「禁止无 WHERE 全表扫描」**：既防越权（一条 SQL 拖走全表），也防性能事故（全表扫描拖垮库，C1）。实现：AST 里找 SELECT 的 WHERE 节点，缺失即拒。
- **行数限制（`LIMIT`）**：强制注入/校验 `LIMIT <= N`，防止单条查询返回百万行。
- **行级过滤怎么注入**：对客请求解析出 `user_id` 后，把 `WHERE user_id = :uid` 作为**绑定参数**拼进 SQL 或包一层子查询，而不是字符串拼接（防注入）。
- **脱敏规则**：手机 `138****1234`、地址只到区级、员工分级（低级别看不了高敏感列）。用「字段→规则」映射表，可扩展。
- **JWT 为什么放鉴权**：无状态、可水平扩容（架构第 8 节），每个请求自带身份，API 多副本无需共享 session。
- **令牌世代号（`ver`）为什么必须有**（变更 001）：令牌无状态 ⇒ 光改库里的行不会让已发出的令牌失效。
  只查 `status` 能挡住登录，但**挡不住已经发出去的 refresh 令牌继续换 access**。
  `ver` 与 `status` 在同一次查表里取回，成本为零，却把「停用 / 改密 / 改角色」三种作废场景一次解决。
- **为什么鉴权路径刻意不做缓存**：缓存会把「立即生效」退回「延迟生效」——
  而那正是这条决策要消灭的窗口。代价是每请求一次主键点查，已在变更单里显式接受。

## 6. 开发步骤

1. 写 `app/security/sql_guard.py`：`validate_sql()` 用 sqlglot 解析 → 校验只读 → 校验表/列白名单 → 校验有 WHERE → 校验 LIMIT。
2. 写 `app/security/masking.py`：`mask_phone` / `mask_address` / `mask_pii`（按字段规则 + 角色）。
3. 写 `app/security/rbac.py`：`require_role` / `require_permission` 装饰器 + 角色→权限表。
   ⚠️ 角色解析顺序：**身份对象优先**（`Actor.role`），关键字参数 `role=` 最后 ——
   否则一个叫 `role` 的 Query 筛选参数会被当成调用者身份（变更 001 实测踩到，见 §7）。
4. 写 `app/security/auth.py`：JWT 签发/校验 + `get_current_user` 依赖 + 口令散列（Argon2id）。
5. 写 `app/security/accounts.py`（变更 001）：认证、建号、停用、改角色、重置口令 + 两条自我保护规则。
6. 写 `tests/security/`：越权攻击用例 + 注入攻击用例（见下），**全部要能跑通并被拦截**。
