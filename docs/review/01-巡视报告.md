## 4. 我定的整理计划（含每条裁决）

### 4.1 总体思路

1. **代码是真相，文档是解释**：所有"是什么"的陈述先落到代码行号，再决定正文写什么。
2. **一份输入一份精简件**：`docs/` 下每个"有信息量"的文档 → `consolidated/` 下 1 篇（4 段结构：目的 / 关键结论 / 待办 / 来源）。
3. **重复内容只留一处**：runbook 与 modules 大量互相引用同一段原理，精简件只保留"这个模块是什么、坑在哪、证据在哪"，原理集中到 `architecture/` 与 `tech-stack/`。
4. **超大文档一律拆分**：>300 行的输入按主题拆成多个文件，不用一个文件塞 1500 行。

### 4.2 精简件的组织方式

| 目录 | 文件 | 拆分规则 |
|---|---|---|
| `consolidated/modules/` | `01-config.md` … `16-web.md` | 1:1 对应 `docs/modules/N.*.md`，每篇 ≤ 300 行 |
| `consolidated/runbook/` | 按**主题簇**合并，不按原文件 1:1 | 见下表 |
| `consolidated/changes/` | `001`、`002`、`003` 各一篇 + `README-流程.md` | 保留"为什么改/改成什么/证据在哪" |
| `consolidated/issues/` | `001-010.md` 一篇台账 + 关键条目单独展开 | 台账表 + 3 条最值钱的（003/007/009） |
| `consolidated/kb/` | `kb-语料清单.md` | 8 份语料只做清单与用途说明（它们是数据不是文档） |

**runbook 合并表**（20 个输入、合计 17,264 行 → 7 个精简件）：

| 精简件 | 吸收的原始文档 | 为什么不 1:1 |

### 4.4 证据策略

- **行号**：一律写 `文件:行号`（相对仓库根），行号按当前工作区版本；不写"大约"。
- **测试数**：`README.md` 里的 `1846 passed` 等是**跑过的历史快照**，本次未执行（S2），一律标注为"文档声称"，不当作事实断言。
- **⚠️ 的判定**：只有"代码和文档都无证据"才标 ⚠️；"代码有、文档旧"归 R1 异常清单，不标 ⚠️。
