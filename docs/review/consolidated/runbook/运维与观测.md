# 运行手册 · 运维与观测（观测 / 队列 / MCP）

> 吸收：`docs/runbook/11.observability-runbook.md`（1012）、`12.queue-runbook.md`（1620）、`15.mcp-runbook.md`（1035）→ 本文。

## 目的

请求路径之外的"旁边那三套"：**看得见**（观测）、**扛得住**（队列）、**接得上**（MCP）。

## 关键结论

### A. 观测：三层证据链

| 层 | 组件 | 判据 |
|---|---|---|
| 指标 | `shopsage_*` 17+ 项，`/metrics` 文本格式 0.0.4 | `curl /metrics \| grep shopsage_agent_duration` 有桶 |
| 链路 | OTEL span，命名 `node.*` / `tool.*` / `llm.*` / `retrieval.*` / `sql.*` | 一次问答在 trace 里是一棵树，根 span 包住整个请求 |
| LLM 记录 | Langfuse 4.x（没配密钥 = 关闭，零开销） | `langfuse_handler().enabled` 为 True 且能看到 trace |

三条"必须"：

1. **根 span 必须包住整个请求** —— HTTP 由 `ApiMiddleware` 开，**WebSocket 要自己开**（`app/api/chat.py:457`）。
2. **属性白名单**：只有 `ALLOWED_ATTRIBUTES` 里的键能进 span（`app/observability/tracing.py:104`），prompt 原文永远进不去。
3. **分位数只能从桶里算**（`app/observability/metrics.py`），不在应用层算直方图。

### B. 队列：入队 → 重试 → 死信 → 重放

| 环节 | 判据 | 依据 |
|---|---|---|
| 入队 | `POST /api/tasks` → 202 + `job_id`，且同键重投 `created=false` | `app/api/tasks.py:139`、`app/queue/jobs.py:253` |
| 重试 | 按函数分级的 `RetryPolicy`，退避有 jitter | `app/queue/jobs.py:169` |
| 死信 | `queue_dead_letters` 表有行 = 有任务失败到最后一步 | `app/queue/store.py:124` |
| 重放 | `replay_plan()` 生成新 job | `app/queue/core.py:486` |
| 健康 | `arq --check app.queue.worker.WorkerSettings`（容器 healthcheck 用的就是它） | `docker-compose.yml:103` |

> **死信表 0 行是健康形态**，不是"没接上"。

### C. MCP：薄壳 + 两条身份边界

| 项 | 值 | 依据 |
|---|---|---|
| SDK | mcp **2.x**，`MCPServer`（不是 `FastMCP`） | `app/mcp/server.py:95` |
| 工具 | `sql_query` / `retrieve_knowledge` / `create_ticket` / `build_chart` | `app/mcp/tools.py:59-62` |
| 策略 | `MCP_POLICY=customer` 强制行级过滤；`internal` 放开 | `app/mcp/settings.py:58-60` |
| 归因 | `caller = mcp:<tool>` | `app/mcp/sync_calls.py:52` |
| 纪律 | MCP 层**不许** import `app.api` / `fastapi` / `uvicorn` / `starlette` | `docs/runbook/15.mcp-runbook.md` §2.4 |

## 待办 / 已知边界

- ⚠️ `otel-collector` 在生产是 `--profile tracing` 可选启动；默认不落 trace。
- ⚠️ 队列深度指标只在 worker 进程里采集（`app/queue/worker.py:351`），worker 未起时为空。
- ⚠️ Grafana 宿主端口两套形态不同：开发栈 3000、生产栈 3001。

## 坑（各手册最值钱的几条）

| 坑 | 后果 |
|---|---|
| 只埋业务节点、忘了 WS 根 span | trace 分不清是哪一轮 |
| span 属性里塞 prompt | 基数爆炸 + 泄漏面 |
| 把 `arq --check` 的成功当"任务能跑" | 它只证明 worker 连上了 Redis |
| 给 MCP 传与请求身份不符的 `user_id` | 被 `check_params_match_identity` 拒（这是设计） |
| 用 `-m app.mcp.server` 与 `-m app.mcp` 行为不一致 | 两个入口是同一个 `main()`，不该有差异 |
