# 运行手册 · 前端

> 吸收：`docs/runbook/16-web-runbook.md`（1458 行）→ 本文。

## 目的

把 Next 前端在**开发期**（两个进程）与**生产期**（容器）都跑起来，并给出"页面能开但功能坏"的分诊路径。

## 关键结论

### A. 起法（三种）

```bash
# ① 开发：后端 + 前端两个进程
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000   # ⚠️ 不要加 --reload（本机实测起不来）
cd web && npm install --ignore-scripts && npm run dev     # → http://127.0.0.1:3000

# ② 生产镜像（容器里）
docker compose -f docker-compose.yml --project-directory . up -d --build web

# ③ 指向别的后端（构建期！）
NEXT_PUBLIC_API_BASE=http://<host>:8000 npm run build
```

### B. 三条"打开方式"规则

1. **只用 `http://127.0.0.1:3000` / `http://localhost:3000`**。`next dev` 打印的 `Network: <网卡IP>:3000` **不在跨源白名单**，照它打开会"页面能开、WS 一直连不上"（症状极像后端坏了）。
2. `NEXT_PUBLIC_API_BASE` 是**构建期**变量：改了必须重启 `npm run dev` 或重建镜像。
3. WebSocket **不走 Next 路由层**（`rewrites` 不代理 WS 升级），浏览器直连后端 —— 所以后端必须 `--host 0.0.0.0`。

### C. 分诊表

| 症状 | 先查什么 | 不要做什么 |
|---|---|---|
| `Failed to fetch`（**无状态码**） | 进程起了吗 / 跨源被拦？跑 `uv run python -m scripts.check_web_cors` | ❌ 不要去重签令牌 |
| 页面能开、WS 连不上 | 打开的地址是否在白名单 / `NEXT_PUBLIC_API_BASE` 是否指到了前端自己 | ❌ 不要先怀疑后端 |
| 登录后立刻掉线 | 刷新令牌续期（`web/src/lib/session.ts:231`） | — |
| 管理台停用/改角色失败 | CORS 有没有 `PATCH`（`issues/005`） | — |
| 答案说"无法处理"但出处齐全 | 可能是语义缓存命中导致护栏误判（`issues/009`） | ❌ 别只看 citations |

### D. 测试

```bash
cd web
npm test              # 离线用例（node --test，不连后端）
npm run typecheck
npm run build
node tests/run-live.mjs          # 真链路（需后端在跑）
node scripts/admin-create-evidence.mjs   # 真浏览器取证（会改演示库！）
```

## 坑（`16-web-runbook.md` §10.1 里最容易咬人的）

| # | 坑 | 修法 |
|---|---|---|
| 1 | `npm install` 带生命周期脚本 | 必须 `--ignore-scripts` |
| 2 | 用 `Network:` 地址打开 | 用 `127.0.0.1` |
| 3 | 改了 `NEXT_PUBLIC_API_BASE` 只重启 | 要重新 build |
| 4 | 灌完全量回归后语料变空 | 重跑 `scripts.load_knowledge_base` |
| 5 | `--reload` 起不来后端 | 不要加，改完手动重启 |
| 6 | `citations` 非空就当"答出来了" | 要看 `flow_state=delivered`（`issues/009` 的教训） |
