# 运行手册 · 安全与账号

> 吸收：`docs/runbook/4.security-runbook.md`（683 行）→ 本文。
> 设计原理见 `../modules/04-security.md`，本文只讲**怎么验、怎么排障**。

## 目的

四个边界的**操作侧**：SQL 守卫怎么手工试、只读角色怎么建与怎么重放授权、脱敏表怎么改、JWT 怎么抽、注入语料怎么试。

## 关键结论

### A. 两条"方向相反"的白名单（最容易记混）

| 层 | 策略 | 放行条件 |
|---|---|---|
| **表** | 默认拒绝 | 表名在 `policy.ALLOWED_TABLES` 里（8 张业务表） |
| **列** | 默认放开 | 列**不在** `policy.PROTECTED_COLUMNS[表]` 里（登记的是 PII/审计列） |

方向相反是有意的：表可以穷举（就 8 张），列会随业务天天变 —— 对列用"默认拒绝"会把正常查询全误杀。
（依据：`docs/runbook/4.security-runbook.md:54-61`、`app/security/policy.py:20-48`）

### B. 一把铁律：行级过滤的唯一真相只有一处

**`app/db/queries.py` 是唯一生成 `WHERE user_id = ...` 的地方**；`app/security/rbac.py` 只做**校验**（拒绝"身份与请求的 user_id 对不上"），**不生成**那段 WHERE。
理由：过滤一旦有两处，`assert_row_filtered()` 那条"裸查询一律拍死"的判据就失效了。

### C. 最硬的证据：只读角色"读得到、写不了"

```bash
# 建 / 修只读角色（幂等）
uv run python -m scripts.db_readonly
# 验收：8 张表可读 + 6 类写操作被数据库拒绝
uv run python -m scripts.db_readonly --verify
```

判据（代码侧）：`get_read_engine() is get_write_engine()` 必须为 `False`；端到端 `SELECT current_user` 必须是 `shopsage_readonly`。
（`app/db/session.py:97-103`、`docs/runbook/6.tools-runbook.md` §2.5）

### D. ⚠️ 迁移回滚之后必须重放授权（最容易忘的一条）

表级授权挂在**表对象（OID）**上。`alembic downgrade base` 会 `DROP TABLE`，授权随之消失；`upgrade head` 建回来的是**全新的表** —— 只读角色于是"看着配好了、其实一张表都读不了"。

实测症状：`tests/test_db_queries.py` 全线红，报
`psycopg.errors.InsufficientPrivilege: permission denied for table orders`。

```bash
uv run python -m scripts.db_readonly --regrant-only
# 期望：已重放授权：shopsage_readonly ← SELECT on employees, order_items, orders, products, refunds, stock_movements, tickets, users
```

自动化版：`tests/test_db_migrations.py` 的迁移回环用例末尾调用 `regrant()`（幂等）。
（依据：`docs/runbook/4.security-runbook.md:369-400`、`scripts/db_readonly.py:361-364`）

### E. ⚠️ 已知残余风险：应用角色仍是超级用户

`scripts/db_readonly.py --downgrade-superuser` 在本机**没能生效**：
`permission denied to alter role / DETAIL: The bootstrap user must have the SUPERUSER attribute`。
原因是 PostgreSQL 要求执行者**在改动之后仍然**满足条件，而"摘掉自己的 SUPERUSER"恰好让它不再满足 —— **超级用户无法自我降级**。

影响：开发库里 `shopuser` 仍是 `SUPERUSER` + `BYPASSRLS`。**不影响**"只读角色写不进去"这条验收（那是数据库真实行为），但它是**残余风险**：应用凭据一旦泄露，攻击者不受权限约束。
（依据：`docs/runbook/4.security-runbook.md:402-428`）

### F. 三个常见排障动作

| 我想… | 命令 / 做法 |
|---|---|
| 看一条 SQL 会不会被拦 | `validate_sql(sql)` 直接调（`app/security/sql_guard.py:82`） |
| 改表白名单 / 高敏列 / 角色等级 | 改 `app/security/policy.py`（**唯一真相**） |
| 加一个敏感字段的脱敏规则 | 改 `app/security/masking.py` 的 `FIELD_RULES`（`:127`） |
| 抽一个 JWT 看看 | `scripts/dev_token.py`（`--account admin`） |
| 试一条注入语料 | `app/security/guardrail.py:110` 的 `scan(text)` |

## 待办 / 已知边界

- **应用角色是超级用户**（上面 §E）：属基础设施变更，本仓只记录、未动手。生产必须换成最小权限角色。
- ⚠️ 是否启用 `ALTER DEFAULT PRIVILEGES` 让新表自动带只读授权：本仓**刻意不用**（理由见原文 :397-400），但这是"忘跑命令 vs 隐式授权"的取舍 → 与 `03-待确认清单.md` Q-08 同类，暂不单列。
- `payment_method` 全员打码（`issues/008`）的修复不在本手册范围。

## 坑（原文 §7.1 的"十个新坑"里最值得记的）

| 坑 | 后果 | 依据 |
|---|---|---|
| 以为 `mask_pii` 对所有字段都生效 | 只有 `FIELD_RULES` 里登记的字段有规则，其余按值模式扫描兜底 | `app/security/masking.py:127-150` |
| 以为注入检测是防线 | 它是**减速带**：正则 + 归一化只能挡住已知写法 | `docs/runbook/4.security-runbook.md` §4.5 |
| 升级只读角色后忘了重放授权 | 见 §D | — |
| 用超级用户验证"写不进去" | 只读角色写不进去 ≠ 应用写不进去（应用是超级用户） | §E |
| 改完 policy 不跑 `tests/security` | 白名单与列保护是**双向断言**的，不跑就不知道哪头破了 | `tests/security/test_sql_whitelist.py` |
