# 运行手册 · 服务链路（一次问答经过的五层）

> 吸收：`docs/runbook/5.llm-runbook.md`（1325）、`6.tools-runbook.md`（828）、`7.agents-runbook.md`（1081）、`8.graph-runbook.md`（1039）、`9.api-runbook.md`（947）→ 本文。

## 目的

一条消息从浏览器到回答要穿过 **api → graph → agents → tools → llm/rag**。本文只给"每一层的入口、判据、最容易错的一处"，详细原理见 `../tech-stack/`。

## 关键结论

### 五层速查

| 层 | 入口 | 向外提供 | 判据 |
|---|---|---|---|
| api | `app/api/main.py:141 create_app` | HTTP + WS | `/health` 200 且 `components` 全 ok |
| graph | `app/graph/builder.py:95 build_graph` → `compile_graph` | 一张可 `ainvoke` 的图 | `graph.get_graph()` 的边表 == 预期拓扑 |
| agents | `app/agents/*_node()` | 每个节点 `(state) -> dict` | 6 个节点可独立调用（不需要整图） |
| tools | `app/tools/__init__.__all__` | 27 个函数 | 只读查询返回行数 ≤ 上限；写操作幂等 |
| llm / rag | `app/llm/client.py:381`、`app/rag/retriever.py:491` | `llm_call` / `embed` / `hybrid_search` | 429 会退避重试；检索带 citations |

### 一次请求的完整链路（代码依据）

```
WS 握手：子协议 shopsage.v1 + bearer.<token>  → accept → 限流
  ↓ skeleton 帧（立刻发，首字节）
run_turn(graph, entry_state(actor, msg), thread_id="c{uid}:{session}")
  ↓ guardrail_input（零 token，注入检测）
  ↓ router（LLM 分类 → route ∈ {data, rag, analysis, ticket, refund, final}；注入权限）
  ↓ data / rag / analysis / refund_request
  ↓ synthesis（三套角色模板；命中缓存直接用）
  ↓ guardrail_output（LLM 判定有没有编造）
  ↓ node 帧 × N → answer 帧 → done 帧
```

### 每层最容易错的一处

| 层 | 最容易错 | 依据 |
|---|---|---|
| api | 限流要**三处登记**（middleware / scope / DEFAULT_RULES），漏一处额度不生效 | `app/api/middleware.py:57-84` |
| api | `POST /api/chat/approve` **已删除** | `app/api/chat.py:369-386` |
| graph | 条件边目标映射的**键必须是节点名**（不是 route 名） | `app/graph/builder.py:178-214` |
| graph | `durability="sync"` 漏了 → 崩溃后没有断点 | `app/graph/builder.py:89` |
| agents | 权限只在 router 注入一次，后面节点**不许**再判身份 | `app/agents/state.py:238-288` |
| agents | 对客 SQL 的 `uid` 绑定值由**程序覆写**，不采信模型 | `app/agents/data.py:420-433` |
| tools | 行数上限有**两层**，参数化 `LIMIT :n` 只有执行层拦得住 | `app/tools/sql_executor.py:111` |
| llm | 4xx 参数错**不重试**（重试只会更慢） | `app/llm/errors.py:46-56` |
| rag | 换 embedding 后端必须重建索引 + 重标定缓存阈值 | `app/cache/settings.py:86-91` |

### 排障顺序（从外到内）

1. `GET /health` → 看 `components` 里哪个依赖红；
2. `POST /api/chat` 带令牌 → 拿 `request_id`，`grep` 日志；
3. 同一问题走 `WS /api/chat/stream` → 看 `node` 帧停在哪个节点；
4. 停在哪一层就去那一层的 runbook 章节（`7.agents` / `6.tools` / `5.llm`）。
