## 1. 复现（真浏览器，不是「照着代码猜」）

### 1.1 复现脚本

`web/.probe/browser-create-v3.mjs` —— 用 CDP 驱动无头 Chrome **真的**：
导航到 `/login` → 用 React 的原生 setter 填受控输入 → 点「登录」→
在 `/admin` 填开号表单 → 点「开账号」→ 抓**请求/响应**、**页面提示**、**表单残留**。

> 为什么不只跑 `curl`：`curl` 只能证明「后端会 422」，
> 而用户报的是**页面**的问题 —— 中间还隔着表单校验、错误渲染、草稿清理三段代码。
> 实测证明这三段里有两段是坏的（见 §2）。

### 1.2 修复前（`password="pass1234"`，8 位）

```text
表单属性： { label: "初始口令", minLength: -1, required: false, type: "password" }   ← 没有任何约束

点击「开账号」 -> ok
POST http://127.0.0.1:8000/api/admin/accounts -> HTTP 422
请求体: {"identifier":"probe-affypn","password":"pass1234","role":"customer",
         "subject_type":"customer","subject_id":6,"status":"active"}

页面渲染出来的提示： ERROR: 请求参数不合规（HTTP 422，request_id=0340062fd0dd401d）

失败后表单还剩什么： {"identifier":"","password":"","subjectId":"", ...}   ← 全被清空了
```

### 1.3 后端那条请求的确切原因

`web/.probe/backend-422.py`（直接打管理接口，绕过前端）：

```text
口令 1 位  (1)  -> HTTP 422  detail.fields=[{loc:[body,password], msg:"String should have at least 12 characters"}]
口令 8 位  (8)  -> HTTP 422  同上
口令 11 位 (11) -> HTTP 422  同上
口令 12 位 (13) -> HTTP 201  ✅
```

**判据**：口令 ≥ 12 位就能建（201）；< 12 位必然 422，且**页面上不会说「口令太短」**。

## 2. 三个缺陷（同一个根因的三层表现）

见 [`issues/004`](../issues/004-admin-cannot-create-account.md)。摘要：

| # | 缺陷 | 实测证据 |
|---|---|---|
| ① | 前端**完全不知道**口令策略 | 口令框 `minLength=-1`、无文案；`create()` 只判「非空」 |
| ② | 422 的 `detail.fields` **被丢掉** | 后端明说 `password: at least 12 characters`，页面只显示「请求参数不合规」 |
| ③ | 失败后**无条件清空表单** | 实测 `identifier/password/subjectId` 全空 |
| ④ | （修 ①③ 时一并发现）成功提示**被自己清掉** | 见 §4.3 |

④ 是修复过程中新发现的：`load()` 开头 `setNotice(null)`，而 `run()` 原先
「先设成功提示、再 `load()`」—— 于是**开号成功时页面一片空白**。
「成功」与「什么都没发生」在界面上长得一样，管理员只能去列表里数行数。

## 3. 修复

| 文件 | 改动 |
|---|---|
| `web/src/lib/password.ts`（新增） | 口令策略的前端镜像：`MIN_PASSWORD_LENGTH = 12`、`passwordProblem()`、`fieldProblemText()` |
| `web/src/app/(app)/admin/page.tsx` | 口令框加 `minLength` + 规则文案；建号/重置都先 `passwordProblem()`；`describe()` 加 422 字段级分支；`run()` 返回布尔；成功才清空表单；**成功提示移到 `load()` 之后** |
| `web/tests/password.test.ts`（新增） | 10 条防回归用例（含跨语言常量比对与源码级接线断言） |

### 3.1 为什么只镜像「长度」而不抄整份后端策略

后端 `validate_password_strength` 还有一份**弱口令黑名单**。前端**刻意不抄**：

* 那是一个会持续增长的集合，抄一份必然漂移；
* 漂移的后果是「前端说没问题、后端拒」—— 比不抄更糟（又回到「不知道为什么失败」）。

所以前端只镜像**会静默变化的数字**（长度）+ 两条一眼可判的规则（全空白、与标识相同），
**后端始终是权威**：它仍拒绝时，缺陷 ② 的字段级文案会把原因说清楚。

### 3.2 长度常量不许两处各写一个数

`web/tests/password.test.ts` 的**第一条**用例直接去读
`app/security/accounts.py` 的 `MIN_PASSWORD_LENGTH` 并比对 —— 只改一侧就红：

```text
✔ ★前端的口令长度下限必须等于后端 `accounts.MIN_PASSWORD_LENGTH`（防数字漂移） (1.83ms)
```

```text

tests/eval/test_eval_live.py      -> 同理（它的 rag_live 用例没被 skip）
```

⚠️ 注意**第二处是一处测试装置缺口**：`tests/rag/conftest.py` 里有一段

## 7. 第二个问题：管理台「停用 / 改角色」CORS 预检 400（issues/005）

用户报的是**刷新管理台时**同样的 `Failed to fetch`，Console 里多了一句决定性的：

```text
Access to fetch at 'http://127.0.0.1:8000/api/admin/accounts/15' from origin 'http://127.0.0.1:3000'
has been blocked by CORS policy: Response to preflight request doesn't pass access control check:
It does not have HTTP ok status.
```

### 7.1 复现（两条 curl 并排，差别一眼可见）

```text
# ① 管理台真正用的方法：PATCH
OPTIONS /api/admin/accounts/15   Origin: http://127.0.0.1:3000   ACRM: PATCH
-> HTTP/1.1 400 Bad Request
   access-control-allow-methods: GET, POST, OPTIONS
   Disallowed CORS method                       ← 预检被拒，真正的 PATCH 根本不会发出

# ② 对照：POST（简单方法）是通的
OPTIONS /api/chat                Origin: http://127.0.0.1:3000   ACRM: POST
-> HTTP/1.1 200 OK
```

路由实际用到的方法（`create_app().openapi()` 实测）：

```text
GET    6 条   /api/auth/me, /api/admin/accounts, ...
PATCH  1 条   /api/admin/accounts/{account_id}      ← 不在 allow_methods 里
POST   7 条   /api/auth/login, /api/chat, ...
```

### 7.2 真浏览器验收（`web/scripts/admin-patch-evidence.mjs`）

**修复后（全部通过 7 条）**：

```text
PASS  管理员登录后落在 /admin
PASS  在列表里找到一个可停用的非管理员账号并点了「停用」  {"identifier":"test","before":"active"}
PASS  浏览器为 PATCH 自动发出了预检（OPTIONS + ACRM=PATCH），且它是 200
      OPTIONS http://127.0.0.1:8000/api/admin/accounts/15 (ACRM=PATCH) -> 200
PASS  点「停用」后该行状态由 active 变为 disabled       停用前=active 停用后=disabled
PASS  浏览器的 PATCH 请求真的发出去了                  1 条 PATCH …/accounts/15 -> 200
PASS  PATCH 的响应是 200（不是 CORS 失败 / 无状态码）
PASS  页面上没有出现「请求没有到达后端 / Failed to fetch」
```

**把修复撤掉后重跑（复现出用户报的原话，5 条失败）**：

```text
FAIL  浏览器为 PATCH 自动发出了预检（OPTIONS + ACRM=PATCH），且它是 200
      OPTIONS …/accounts/15 (ACRM=PATCH) -> 400  ← Disallowed CORS method
FAIL  点「停用」后该行状态由 active 变为 disabled       停用前=active 停用后=active
FAIL  浏览器的 PATCH 请求真的发出去了                  实际捕到 0 条 PATCH
FAIL  PATCH 的响应是 200                              []
FAIL  页面上没有出现「请求没有到达后端 / Failed to fetch」
      通知区：请求没有到达后端（没有状态码）：多半是后端没起或跨源被拦。
              原始错误：TypeError: Failed to fetch          ← 与用户截图逐字一致
```

> ⚠️ **取证脚本本身踩过一个坑（写下来免得后人重走）**：
> 第一版用页面里的 `fetch(url, {method:"OPTIONS", headers:{"Access-Control-Request-Method":"PATCH"}})`
> 去「手工发预检」，结果永远拿到 **405**。真因：
> `Origin` / `Access-Control-Request-Method` / `Access-Control-Request-Headers`
> 都是**禁止由脚本设置的请求头**，浏览器会把它们丢掉 ——
> 那条 OPTIONS 退化成一个**普通 OPTIONS**，CORSMiddleware 不当作预检，请求落到路由上 → 405。
> **真正的预检只能由浏览器在跨源 `PATCH` 之前自动发出**，
> 要断言它就必须用 CDP 的 Network 域去读那条自动请求。

### 7.3 服务端反向断言（`tests/api/test_cors.py`）

新增 `test_every_route_method_is_allowed_by_cors`：从 OpenAPI schema 取**路由实际用到的方法**，
断言它们都在 CORS 的 `allow_methods` 里。实测能抓到（把 `PATCH` 删回去即红）：

```text
FAILED tests/api/test_cors.py::test_every_route_method_is_allowed_by_cors
  AssertionError: 这些方法被路由用到、但 CORS 没放通：['PATCH']
    —— 浏览器会先发预检，预检被 400 拒 → 那条请求根本不会发出
      （症状：页面上 `Failed to fetch` 且**没有状态码**，后端日志里一条请求都没有）
```

> ⚠️ 该用例第一版用「遍历 `app.routes` 取方法」，结果**一条 API 路由都没枚举到** ——
> Starlette 1.7 把 `include_router` 的结果包成 `_IncludedRouter`，外层遍历只能看到
> `/docs` 那几条内置路由，于是「PATCH 不在白名单里」这个 bug **照样绿**。
> 改用 `create_app().openapi()`（FastAPI 生成的权威视图）才对。

### 7.4 线上排障提示

预检结果会被浏览器缓存 **10 分钟**（`access-control-max-age: 600`）。
所以修好后端之后，**已经失败过的那个页面不会立刻恢复** —— 需要硬刷新。
这不是 bug，但不知道的人会误判成「改了没用」。

修改清单见 [`issues/005`](../issues/005-cors-missing-patch-method.md) 的「修复」章。

## 8. 第三个问题：管理台「改角色」提示成功但没生效（issues/006）

用户报：「修改账户的角色实际上没有生效，但是前端提示修改成功」。

### 8.1 复现（真浏览器，一次就抓住）

`web/scripts/admin-role-evidence.mjs` 把用户的动作（在下拉框里选 `manager`）重放一遍，
同时抓**请求体**、**后端权威值**、**页面提示语**：

```text
改角色 = customer -> manager

PATCH /api/admin/accounts/10
请求体: {"role":"customer"}          ← 发的是**旧值**
status: 200

页面提示：OK: 成功 已把 probe-role-1 的角色改为 manager（在途令牌已失效）。
后端里 probe-role-1 的 role = customer          ← 根本没改
```

**判据（本题最关键的一点）**：请求体里的角色等于**列表里的旧值**，
而后端返回 **200** —— 这不是「后端拒绝」，是「前端发的就是『什么都不改』」。

> 顺带确认：**后端是好的**。直接用 `curl` 发 `PATCH {"role":"manager"}` → 200 且真变了。
> 所以服务端用例永远测不出这个 bug（它们直接构造正确的请求体，从没经过「从 DOM 读值」这一步）。

### 8.2 根因：受控 `select` 的值在异步 thunk 执行前被回滚

用同一个浏览器把 `<select>` 的值随时间打出来（决定性证据）：

```text
change 同步 = manager     ← 只有这一瞬间 DOM 的值是对的
microtask   = customer    ← 已被 React 回滚成旧值
t+0         = customer
t+50ms      = customer
```

机制：用户选 `manager` → `onChange` 触发 → 里面的 `run()` 第一句 `setNotice(null)`
调度了一次重渲染 → 这次渲染时 `account.role` **还是旧值**（列表尚未重新拉取）
→ React 按受控语义把 DOM 的值**写回** `customer`。

而两处求值时机不同，于是**自相矛盾**：

| 求值时机 | 读到 | 结果 |
|---|---|---|
| 提示语（`run()` 的**实参**，同步求值） | `manager` | 说「已改为 manager」 |
| 请求体（**thunk** 异步执行时求值） | `customer` | PATCH 发原角色 = 什么都没改 |

后端收到与当前值相同的 `role` → `update_account` 里 `str(row.role) != str(role)` 为假
→ 不修改、不自增 `token_version` → 返回 200 当前记录 → 前端提示成功。

> 📌 后端「值没变就不写」的短路**是正确的**（避免无谓地作废在途令牌把用户踢下线）——
> 不要去改它。坏的只有「前端在错误的时机读了 DOM 的值」。

### 8.3 修复与验收

在 `onChange` 的**同步阶段**把值取出（`const nextRole = event.target.value;`），
提示语与请求体从此读同一个值。撤掉修复重跑即复现：

```text
FAIL  PATCH 请求体里的 role 等于用户选的值（manager）
      实际请求体 = {"role":"customer"}   ← 发的是旧值（等于什么都没改）
FAIL  后端里 probe-role-1 的角色**真的**变成了 manager      实际 role=customer
FAIL  列表里显示的角色也变成了 manager
```

装回修复后 **6 条全过**：

```text

PASS  后端里 probe-role-1 的角色**真的**变成了 manager     实际 role=manager entry=internal
```
