### 1.2 本步唯一的结构变更：两张写表加幂等键

```powershell
uv run alembic upgrade head
# 实测输出：
#   INFO  [alembic.runtime.migration] Running upgrade 1d0329d8d747 -> 29d823809e4f,
#         add idempotency key to tickets and refunds
```

库侧确认（**约束形状**比迁移文件更重要：它才是幂等的真正执行者）：

```powershell
uv run python -c @"
from sqlalchemy import text
from app.db.session import engine
with engine.connect() as conn:
    for r in conn.execute(text(\"select conrelid::regclass as tbl, conname, pg_get_constraintdef(oid) as def from pg_constraint where conname like '%idempotency%' order by 1\")):
        print(tuple(r))
"@
# 实测输出：
#   ('tickets', 'uq_tickets_user_id_idempotency_key', 'UNIQUE (user_id, idempotency_key)')
#   ('refunds', 'uq_refunds_user_id_idempotency_key', 'UNIQUE (user_id, idempotency_key)')
```

三条设计口径（写在迁移文件的 docstring 里，这里给「为什么」）：

1. **幂等的落点是数据库约束**：写操作走 `INSERT ... ON CONFLICT DO NOTHING`，
   而不是「先 SELECT 再 INSERT」。后者在并发重投（第 12 步队列重放、用户连点两次）时
   两个请求会同时查到空、同时插入 —— 这个窗口在单线程测试里**永远测不出来**。
2. **唯一性是复合的 `(user_id, idempotency_key)`**：单列全局唯一会开出一条**越权读取通道** ——
   用户 B 只要撞上用户 A 用过的键，就会「幂等命中」到 A 的那一行，拿到 A 的 `ticket_id`。
   带上 `user_id` 等于给键加了命名空间。
3. **列可空且无默认值**：第 3 步的种子数据（8 张工单、8 张退款）留空即可；
   PostgreSQL 的唯一约束允许多个 NULL，留空的行不会互相冲突。
   （⚠️ 若哪天把这一列改成 `NOT NULL`，种子脚本与历史数据都要跟着处理。）

> 📌 **本步不改只读角色的授权**：加列不需要重新 `GRANT`（`GRANT SELECT ON TABLES` 覆盖全部列）。
> 但 `tests/test_db_migrations.py::test_migration_round_trip_is_repeatable` 会 `downgrade base` →
> `upgrade head`（**DROP 表再重建**，表级授权随之消失），它末尾照旧调 `scripts.db_readonly.regrant()`
> 重放授权 —— 与 [`4.security-runbook.md`](4.security-runbook.md) §3.4 同一条纪律。

## 2. 只读 SQL 执行器（C1 的执行侧 / D1 的静态层）

### 2.1 四道处理，缺一不可

| # | 处理 | 拦什么 / 解决什么 | 对应问题清单 |
|---|---|---|---|
| ① | `validate_sql(sql, max_rows=…)` **二次校验** | 写语句、多语句、无 WHERE、白名单外表/列、危险函数、超行数 | D1、C1 |
| ② | 强制 `get_read_engine()`（只读 DSN） | 即使校验被绕过，写操作在**库层**报权限错误 | D1 兜底 |
| ③ | 流式游标 + `fetchmany(上限 + 1)` 截断 | 结果行数硬上限；防内存/带宽/连接被拖爆 | C1 |
| ④ | `audit_tool_call` | 谁、什么时候、查了什么、返回几行 —— **被拒的调用也记** | D1/D2 证据 |

### 2.2 为什么是「二次」校验（`6.tools.md` §5 第 1 条）

`agents/data.py`（第 7 步）已经调过一次 `validate_sql`，这里**再验一遍**，理由不是重复劳动：

* 工具会被 `mcp/`（第 15 步）与其他代码路径**直接调用**，那些路径不经过 agent；
* 安全校验一旦依赖「调用者的自觉」，每加一个入口就多一次漏检的机会；
* 二次校验的代价是**微秒级纯内存操作**，而漏检的代价是越权读库。

> ⚠️ 二次校验**不能**替代只读角色：前者是「这段 SQL 长什么样」，后者是「这条连接能干什么」。
> 两者正交，缺任何一个都不成立（[`4.security-runbook.md`](4.security-runbook.md) §3 有对照表）。

### 2.3 行数上限的两层：校验层「声明」+ 执行层「兜底」

这是本模块最值得理解的一处机制，因为**上限其实有两层，而只有第二层拦得住参数化 LIMIT**：

| 层 | 位置 | 对手 | 行为 |
|---|---|---|---|
| ① 校验层 | `sql_guard._check_limit()` | `LIMIT 999999`（字面量） | 超 `policy.MAX_ROWS`（200）**直接拒绝**（`limit_too_large`）；参数化 LIMIT 只能**声明**上限（`limit_clamped=True`），文本原样保留 |
| ② 执行层 | `sql_executor.clamp_bound_limit()` | `LIMIT :n`（绑定值运行期才定） | 把绑定值夹到 `上限 + 1`，再 `fetchmany(上限 + 1)`：**多取一行**只用于判定 `truncated`，永不返回给调用方 |

为什么执行层要夹到「上限 **+ 1**」而不是上限：不多取那一行，就永远分不清
「数据刚好 200 行」与「被截到 200 行」—— 前者是事实，后者是我们要告诉调用方的事。

为什么不能只靠 `fetchmany` 截断：那样客户端只拉 200 行（带宽保住了），
但数据库仍然会为 `LIMIT 1000000000` 真去准备十亿行（**C1 要防的正是这个**）。
夹绑定值才是「在库侧也收住」。

### 2.4 手工试一条 SQL（最常用的排障动作）

```powershell
# ── 执行位置：Windows 开发机，仓库根 ──
uv run python -c @"
from app.tools import execute_readonly_query
from app.security.sql_guard import SQLSecurityError

print('① 正常查询（参数化 LIMIT + 绑定）')
rows, meta = execute_readonly_query(
    'SELECT order_id, status, total_amount FROM orders WHERE user_id = :uid ORDER BY order_id LIMIT :n',
    {'uid': 1, 'n': 5000}, caller='agent:data')
print('   rows =', len(rows), '| 首行 =', rows[0])
print('   meta =', {k: meta[k] for k in ('row_count','truncated','declared_limit','limit_clamped','bound_limit_clamped','rows_cap','tables','duration_ms')})

print()
print('② 写语句被拦（SQLSecurityError，按规则名）')
for sql in ['DELETE FROM orders', 'SELECT 1; DROP TABLE orders', 'UPDATE orders SET status = 1 WHERE order_id = 1']:
    try:
        execute_readonly_query(sql, caller='agent:data')
        print('   !! 未拦', sql)
    except SQLSecurityError as e:
        print(f'   BLOCK[{e.rule}] {sql}')

print()
print('③ 行数截断（上限 3，SQL 里写的是 LIMIT :n = 100000）')
rows, meta = execute_readonly_query(
    'SELECT order_id FROM orders WHERE user_id = :uid ORDER BY order_id LIMIT :n',
    {'uid': 1, 'n': 100000}, max_rows=3, caller='test')
print('   rows =', len(rows), '| truncated =', meta['truncated'], '| bound_limit_clamped =', meta['bound_limit_clamped'])

print()
print('④ 走的是只读角色（current_user 直查）')
rows, _ = execute_readonly_query('SELECT current_user AS db_user', caller='test')
print('   current_user =', rows[0]['db_user'])
"@
```

```
   BLOCK[multiple_statements] SELECT 1; DROP TABLE orders
   BLOCK[not_read_only] UPDATE orders SET status = 1 WHERE order_id = 1

③ 行数截断（上限 3，SQL 里写的是 LIMIT :n = 100000）
   rows = 3 | truncated = True | bound_limit_clamped = True

④ 走的是只读角色（current_user 直查）
   current_user = shopsage_readonly
```

**判读口诀**：先看 `rule`（被哪条规则拦的），再看 `truncated` 是**数据事实**还是**被截断**。
`declared_limit=200 / limit_clamped=True / bound_limit_clamped=True` 三个字段一起看就能回答
「上限是谁定下来的」：校验层声明的、还是执行层夹的。

> 💡 `rows[0]` 里的 `Decimal('2745.98')` 是**故意保留**的：执行器不在这一层做 JSON 化。
> 金额要参与比较、时间要参与计算，顺手 `float()`/`str()` 会让下游拿到「看起来一样、算起来不一样」的数据。
> JSON 化是**出口**的事（图表 §4.2 就是那个出口）。

### 2.5 「真的走了只读引擎吗」的两条证据

```powershell
# ① 应用侧：读引擎与写引擎不是同一个对象
uv run python -c "from app.db.session import engine, get_read_engine; print(get_read_engine() is engine)"
# 实测：False

# ② 端到端：工具查到的 current_user 就是只读角色
uv run python -c "from app.tools import execute_readonly_query; rows, _ = execute_readonly_query('SELECT current_user AS db_user', caller='test'); print(rows[0]['db_user'])"
# 实测：shopsage_readonly
```

`tests/test_tools_sql_executor.py::test_sql_executor_runs_on_read_only_engine` 是它的自动化版。
⚠️ 没配 `DATABASE_READ_URL` 的环境（读写同库）里，这条用例会 **skip 并说明原因**，
而不是假绿 —— 「读路径其实是写角色」这种状态必须看得见。

### 2.6 异常口径：安全异常**原样抛**，数据库异常才翻译

| 异常 | 谁抛 | 调用方怎么处置 | 第 9 步映射 |
|---|---|---|---|
| `SQLSecurityError`（带 `rule` / `sql`） | `security.sql_guard` | 把 `rule` 一起回喂给 LLM 让它改 SQL（第 7 步） | 400 |
| `PermissionDenied`（带 `role` / `missing`） | `security.rbac` | 告诉用户「你没这个权限」 | 403 |
| `ToolContractError` | `app/tools/errors.py` | 参数写错了，别重试，改调用 | 400 |
| `RetryableToolError` | `app/tools/errors.py` | 可以稍后重试（第 12 步队列延迟重投） | 503 + 重试 |
| `PermanentToolError` | `app/tools/errors.py` | 不要重试（含业务拒绝，如「订单状态不支持退款」） | 409 / 422 |

**为什么安全异常不包装进 `ToolError`**：它们带着 `rule` / `missing` 字段，
第 9 步要靠它区分 400 与 403；包一层就丢了这两个字段，HTTP 响应会退化成「500 未知错误」，
排障从「看规则名」退化成「翻日志」。

### 3.2 三条纪律

1. **失败也留痕**：审计包住**参数校验与权限判定**，越权/写语句尝试照旧落一条 WARNING。
   ⚠️ 实测踩过：第一版把权限判定放在 `audit_tool_call` **外面**，
   于是越权用例抛了 `PermissionDenied`、日志里却一条记录都没有 —— 见 §9.1 坑 5。
2. **打码必须递归**：`mask_pii` 只按**顶层字段名**判规则，而 SQL 的绑定参数都在 `params` 子字典里。
   实测漏过一次：`{"params": {"phone": "13812341234"}}` 原样进了日志 —— 见 §9.1 坑 4。
3. **只有一种写法**：审计一律走 `audit_tool_call`（契约测试用源码检查钉住，§7）。

### 3.3 `caller` 的约定取值

| 取值 | 谁在用 |
|---|---|
| `agent:data` / `agent:rag` / `agent:analysis` | 第 7 步的 Agent 节点 |
| `api:chat` / `api:ticket` | 第 9 步的 FastAPI 路由 |
| `mcp:sql_query` / `mcp:create_ticket` | 第 15 步的 MCP 薄壳 |
| `script:…` | 运维脚本 / 一次性修复 |
| `test` | 测试 |

约定本身**不做强校验**（只要求非空）：它是给人看的检索键，
真正的约束在「入口必须显式传入」这一点上（缺了就拒绝执行）。

## 4. 图表工具（返回 spec 而不是图片）

### 4.1 spec 的形状（前端契约）

```json
{
  "schema": "shopsage.chart/v1",
  "type": "bar",
  "title": "订单状态分布",
  "x": {"field": "status", "label": "status"},
  "series": [{"name": "order_id", "field": "order_id", "type": "bar"}],
  "data": [{"status": "delivered", "order_id": 28.0}],
  "meta": {"audit_id": "tc-…", "source_rows": 7, "points": 7, "truncated_points": false,
           "null_values": 0, "sorted_by": "order_id", "descending": true, "warnings": []}
}
```

`schema` 版本号是给前端与 MCP 客户端用的：改结构时不必靠「猜版本」，按版本号分支即可。

### 4.2 JSON 化的两个实测陷阱

* **`Decimal`（金额列）**：`json.dumps(Decimal('1299.00'))` 直接 `TypeError`。
  图表里转成 `float`（只要比例关系）；**精确金额的比对回原始 `rows`**（那里还是 `Decimal`）。
* **`datetime`（timestamptz）**：转 ISO-8601 字符串，前端 `new Date(...)` 能直接解析。

⚠️ 这两个转换只发生在**被声明的列**上：没画进图里的列不进 payload（见 4.3）。

### 4.3 载荷最小化（安全侧的考虑）

`data` 里**只带 `x` 与 `series` 声明的列**，其余列一律丢弃。
图表数据经常被前端缓存、贴进工单、打进日志 —— 把整行（可能含手机号/地址）带出去，
等于给「脱敏出口」开了个后门。列没声明要画，就不该出现在图里。

### 4.4 「没有数据」≠「参数写错」

| 情况 | 行为 | 为什么 |
|---|---|---|
| `rows` 为空 | 返回**空图** + `meta.warnings` | 这是**数据状况**，调用方该回答「暂无数据」，报错就没法回答了 |
| 列名写错 / 类型不存在 / 饼图配多系列 | 抛 `ToolContractError`（报错里带**可用列**） | 这是**调用方写错了**，早炸才能让第 7 步的「报错回喂 LLM」有效 |
| 系列列出现非数值 | 抛 `ToolContractError` | 把 `'N/A'` 悄悄当 0 画出一条假曲线，比报错危险得多 |
| 值是 `NULL` | 原样保留 + 计入 `null_values` | NULL 是数据事实，不做 0 填充（0 填充会伪造出「这天是 0 元」） |
| 行数超过 `max_points`（默认 50，绝对上限 200） | 截断 + `truncated_points=True` + 警告 | 图不是数据导出通道，但截断必须**说出来** |

## 5. 检索工具（只返回**带溯源**的结果）

### 5.1 契约与注入点（第 10 步落地前的标准做法）

`retrieve_docs(query, top_k=5, *, search=None, min_score=None, caller)`：

| 参数 | 说明 |
|---|---|
| `query` | 用户问题（空 → `ToolContractError`） |
| `top_k` | 期望条数，**夹到 `1..20`**（LLM 要「Top 500」时不能让上下文/成本一起爆，E2） |
| `search` | 检索后端（`Searcher`）；`None` = 用 `app/rag/retriever.py::hybrid_search`（第 10 步） |
| `min_score` | 相似度下限（阈值口径属第 10 步，这里只负责过滤生效） |
| `caller` | 审计字段（必填） |

**`search=` 这个注入点不是为了测试才加的**：第 10 步交付前，
第 8/9 步要跑通「router → rag → synthesis」的骨架，中间那条检索链可以先注入临时实现；
第 10 步落地后把它删掉即可（默认后端会自动生效）。

### 5.2 溯源是硬约束（不是「尽量带上」）

`source` 为空（或文本为空）的命中**一律丢弃**，并打一条 WARNING + 计数进审计。
理由：合成 Agent（第 7 步）回答时附的是 `doc.source`；放行一条没有出处的片段，
模型就会引用一段**无法核对**的内容 —— 看起来像有出处，实际是把幻觉洗白了。
宁可少给一条，也不给一条查不到出处的。

⚠️ 对应的测试是**一正一反**两条：只断言「返回的都有来源」的话，
一个「把所有命中都丢光」的实现也能通过。

### 5.3 排序与过滤

统一按 `score` 降序输出（第 10 步换成 RRF 融合分或 rerank 分时，上层看到的顺序语义不变），
`min_score` 之下丢弃；两者都会计入审计的 `details.dropped`（`no_source` / `empty_text` / `below_min_score`）——
「检索返回 0 条」有两种完全不同的成因，分不清就等于没有可观测性。

## 6. 写路径（唯一副作用出口：工单 / 退款）

### 6.1 为什么写路径要有独立设施

`write_path.py` 提供三样共用零件，避免 `ticket.py` / `refund.py` 各写一份、各错一处：

1. **写会话**（`write_session`，绑定写引擎）：读路径的 `get_read_engine()` 在这里**不许出现** ——
   「读写分离」在代码层面就是「两个引擎入口不许混用」（§11 ② 用 grep 钉住）。
2. **幂等插入**（`insert_once`）：`INSERT ... ON CONFLICT DO NOTHING` + 回查既有行。
3. **幂等键校验**（`validate_idempotency_key`）：非空、≤64 字符、字符集受限
   （允许空白/换行的键会让「同一个键」有多种等价写法，幂等随之失效）。

⚠️ 这三样**不对外导出**（不在 `app/tools/__init__.py` 的 `__all__` 里）：
「能拿到一个写会话」不该是工具层的公共 API —— 那等于给「绕过预定义函数直接写库」开了口子。

### 6.2 幂等落在数据库约束上，不落在应用层 `if`

```
create_ticket() ──► INSERT INTO tickets (...) VALUES (...)
                        ON CONFLICT (user_id, idempotency_key) DO NOTHING
                        RETURNING ticket_id
                     ├─ 拿到 id      → created = True（本次新建）
                     └─ 没拿到 id    → 键已存在 → 回查既有行（幂等命中）→ created = False
```

「先 SELECT 再 INSERT」为什么不行：查询与插入之间的窗口就是竞态。
并发重投（第 12 步队列重放、用户连点两次）时两条都会插入成功，而**单线程测试永远是绿的**。

### 6.3 幂等键为什么必须是复合唯一

| 方案 | 后果 |
|---|---|
| `UNIQUE (idempotency_key)` 单列全局 | 用户 B 用了用户 A 用过的键 → **幂等命中到 A 的那一行**，拿到 A 的 `ticket_id`。幂等机制自己变成一条越权读取通道 |
| `UNIQUE (user_id, idempotency_key)` 复合（本仓） | 键按主体加了命名空间：不同用户的相同键互不干扰，各自建单 |

实测口径见 §6.6 ① 与 `tests/test_tools_ticket.py::test_same_key_different_users_are_isolated`
（同一键、两个用户 → 两张工单、库里 2 行，各归各的）。

### 6.4 工单工具

```python
create_ticket(user_id, ticket_type, *, idempotency_key, caller, role="customer",
              assignee_id=None, session=None) -> TicketRef
get_ticket_status(ticket_id, *, caller, requester_user_id=None, session=None) -> TicketRef | None
```

* `TicketRef = (ticket_id, user_id, type, status)`，**刻意不含 `created` 标志**：
  幂等的语义是「同一键的多次调用返回同一个结果」，带一个每次都变的标志位，`k1 == k2` 就不成立。
  「本次是新建还是命中」在**审计字段** `details.created` 里（§6.6 ② 有实测）。
* 权限在工具内校验（`PERM_WRITE_TICKET`）：第 7/9/15 步都从同一个门口进，不依赖调用方自觉。
* 对客查状态（给了 `requester_user_id`）查到别人的工单 → `PermissionDenied`（**403 语义**，
  不是假装 404）：越权尝试必须在审计与指标里**看得见**；
  代价是给了调用方一个「这个 id 存在」的判定 —— 这是一次有意的取舍，写在函数 docstring 里。

### 6.5 退款工具（业务规则 + 职责分离 + 行锁）

```python
create_refund_request(user_id, order_id, amount, *, idempotency_key, caller,
                      role="customer_service", reason=None, session=None) -> RefundRef
get_refund_status(refund_id, *, caller, requester_user_id=None, session=None) -> RefundRef | None
```

四条护栏，缺一个都会出事：

| 护栏 | 规则 | 出事的样子 |
|---|---|---|
| **职责分离（SoD）** | `customer` **没有** `write:refund`（见 `rbac.ROLE_PERMISSIONS`）：对客只能建工单，退款由客服/主管发起 | 客户自己点退款 → 一线少了第二个人复核 |
| **归属校验** | 订单必须属于该 `user_id`，否则 `PermissionDenied`（越权留痕） | 拿别人的订单号退款 |
| **额度校验** | `金额 ≤ 订单金额 − 已申请退款`（不含 `rejected`），且**对订单行加锁** | 两笔并发退款各自读到同样的余额 → 退超 |
| **状态校验** | 只有 `shipped` / `delivered` 可退；其余 → `RefundNotAllowed`（业务拒绝） | 给还没发货的订单退款 |

金额一律走 `Decimal` 两位小数；`float` 入参走 `Decimal(str(x))` 而不是 `Decimal(x)` ——
后者会把 `0.1` 的二进制近似尾巴（`0.1000000000000000055…`）带进账里。

> ⚠️ **行锁是并发正确性的唯一保障，而单线程用例证明不了它的效果**（没有第二个事务来撞）。
> 能证明的是「这句 SQL 确实带 `FOR UPDATE`，且发在 INSERT 之前」——
> `tests/test_tools_refund.py::test_refund_takes_a_row_lock_on_the_order` 用
> SQLAlchemy 的 `before_cursor_execute` 事件抓真实语句来断言这一点。
> 真正的并发验证属第 19 步压测（两个事务同时退同一订单）。

## 9. 故障速查

| 症状 | 最可能的原因 | 怎么确认 | 修法 |
|---|---|---|---|
| `SQLSecurityError[missing_where]`：明明只想查全部订单 | 守卫要求**带 FROM 的 SELECT 必须有 WHERE**（防全表扫描 + 防越权拖库） | 看 `e.rule` | 补真实过滤条件；「看全部」要走对内路径而不是去掉 WHERE（§9.1 坑 1） |
| `SQLSecurityError[limit_too_large]` | 字面量 LIMIT 超过 200 | 报错里带两个数字 | 改小，或用**参数化** LIMIT（执行层会夹到上限） |
| `truncated` 一直是 `False`，但结果明显不全 | 数据本来就不到上限（**数据事实**），或被字面量 LIMIT 提前截断 | 看 `meta`：`row_count` / `rows_cap` / `declared_limit` | 要全量请分页；不要指望 `truncated` 替你把「数据就这么多」说清 |
| `truncated=True` 但行数等于上限 | 正常行为：多取的一行只用于判定，永不返回 | 看 `row_count == rows_cap` | 无需修，调用方据此分页 |
| `bound_limit_clamped=True` | 绑定进 `LIMIT :n` 的值超过上限，被执行层夹到 `上限 + 1` | 看 `meta` | 正常（这是 C1 的兜底），但说明调用方想要的比允许的多 |
| 参数化 LIMIT 传了 `10**9`，库还是被压住了 | 夹取只对**最外层 LIMIT 的占位符**（`:n`）生效；把 LIMIT 拼进字符串、或写在子查询里的 LIMIT 不受保护 | `limit_placeholder_name(sql)` 是否返回了参数名 | 用 `:n` 占位符 + 参数绑定，不要拼字符串 |
| 审计里看不到某次调用 | ① `caller` 为空（调用被拒，且拒之前无 caller 可记）；② logger 被别处配置过 | `audit_records(caplog.records)` 是否为空 | 传非空 `caller`；给 `app.tools.audit` 配 handler（§3.1 的捕获写法） |
| 审计里参数是 `***`，看不到值 | 打码生效（PII / 密钥字段） | 看 `redacted_args` 的路径 | 正常行为；要排查就看**字段路径**而不是值 |
| 审计日志里出现完整手机号 | 参数在**嵌套结构**里（`params.phone`）而打码只做了顶层 | 看 `redacted_args` 是否为空 | 已修（递归打码，§9.1 坑 4）；自建工具时不要绕过 `audit_tool_call` |
| 图表返回空图（`data: []` + warnings）/ 检索返回 0 条 | **数据为空，不是错误** | 看 `meta.warnings` 或审计 `details.dropped` | 这不是异常：如实告诉用户「暂无数据」；若检索侧丢的是无源命中，去修第 10 步的 metadata |

### 9.1 实现期间撞到的十个坑（实测，含修法）

**坑 3–10 是本轮真的卡住过的地方**（有的已修在仓库里，有的属于认知修正）。

#### 坑 1：`6.tools.md` §7 的示例 SQL `SELECT * FROM orders` 会被守卫拦下

文档的截断用例写的是 `execute_readonly_query("SELECT * FROM orders")`，
而本仓的守卫对「带 FROM 但无 WHERE」的查询一律拒绝（`missing_where`，防全表扫描 + 防越权拖库）。
**照抄这条 SQL，你拿到的是 `SQLSecurityError` 而不是 `truncated=True`。**

- ✅ 正确写法（本仓用例）：带 WHERE，并用**参数化 LIMIT** 把「超上限」这件事交到执行层：
  `SELECT order_id FROM orders WHERE user_id = :uid ORDER BY order_id LIMIT :n` + `{'n': 100000}` + `max_rows=3`。
- 顺带说明：`SELECT *` 在 `orders` 上**不会**撞 `star_on_protected_table`（`orders` 没有高敏列），
  但 `SELECT * FROM users` 会 —— 两条规则是分开的。

#### 坑 2：`6.tools.md` §2 的接口清单里没有「退款」，但 §4/§8 要求它

文档 §4 第 1 条把写操作写成「建工单、**退款**」，§8 的验收是「工单/**退款**幂等（A2）」，
而 §2 的接口只列了 `create_ticket` / `get_ticket_status`。

- ✅ 处理：本步补了 `refund.py`（`create_refund_request` / `get_refund_status`），
  在 §1.3 记录了这处有意差异，并把 A2 的两半（工单 + 退款）都写进验收（§10）。
- 教训：**文档的「接口清单」与「验收标准」不一致时，按验收标准做**，
  然后把差异写回手册 —— 悄悄按清单做，验收时会发现「退款那条勾不上」。

#### 坑 3：`ON CONFLICT DO NOTHING` + `RETURNING` 拿不到行才是**正确**路径

第一直觉会写成 `db.execute(stmt).scalar_one()`，期望它总能拿到 id。
实测：幂等命中时（键已存在）`RETURNING` **什么都不返回**，`scalar_one()` 直接抛 `NoResultFound`。

- ✅ 修法：`scalar_one_or_none()`；`None` 就是「幂等命中」的信号，接着按 `(user_id, key)` 回查既有行。
- 实测：第一次 → `9`；第二次 → `None`；回查 → `9`。

#### 坑 4：审计打码**必须递归**，只打顶层会让 `params.phone` 原样进日志

`app.security.masking.mask_pii()` 按**顶层字段名**判规则，而 SQL 的绑定参数天然躺在
`params` 这个子字典里。第一版 `redact_args()` 只过顶层，跑出来的真实日志里躺着完整的
`"phone": "13812341234"` —— **而那时用例是全绿的**（因为用例也只测了顶层参数）。

- ✅ 修法：`_redact_nested()` 对 dict 递归、对 list 逐项递归，并把命中路径记成 `params.phone`
  这样的**路径**（而不是只记字段名）。
- 补的用例：`test_nested_arguments_are_redacted_too`。
- 教训：**「日志里到底出现了什么」只能靠真的跑一遍看输出**，不能靠「我打了码」这个信念 ——
  这条坑就是这么发现的（原本只是去采证据）。

#### 坑 5：权限判定写在审计块**外面** → 越权尝试一条日志都没有

第一版 `create_ticket()` 的顺序是「先校验参数与权限，再进 `with audit_tool_call(...)`」。
后果：越权用例抛出 `PermissionDenied` 时，审计里**一条记录都没有** ——
而 D1 的证据链要的恰恰是「谁在什么时候试图越权」。

- 实测症状：`test_permission_denied_is_audited` 报 `IndexError`（`audit_records(...)[-1]` 取不到元素）。
- ✅ 修法：审计包住**参数校验与权限判定**（只有 `caller` 本身的合法性没法被审计 —— 没有 caller 就没有「谁」）。
- 教训：**审计要包住「整个调用」，而不是「成功的那一半」**。

#### 坑 6：数据库的值不是 JSON 值（`Decimal` / `datetime`）

`execute_readonly_query` 返回的 `rows` 里，金额是 `Decimal('2745.98')`、时间是 `datetime`。
把它们直接塞进 `json.dumps`（图表、HTTP、MCP 都会这么干）会 `TypeError`。

- ✅ 修法：图表工具出口统一 `_jsonable()`（`Decimal → float`、时间 → ISO-8601）；
  而 SQL 执行器**刻意不转**（下游要算、要比）。
- 教训：JSON 化是**出口**的职责，不是「顺手在取数时就做掉」的事。

#### 坑 7：只靠 `fetchmany` 截断 ≠ 库被打不下

只限制客户端取多少行，`LIMIT 1000000000` 仍然会让数据库真去准备十亿行。
校验层对**字面量** LIMIT 能拦（`limit_too_large`），但参数化 LIMIT 的值在运行期才定 —— 它看不穿。

- ✅ 修法：执行层夹绑定值到「上限 + 1」（`bound_limit_clamped=True`），
  再配 `stream_results=True` 的服务端游标逐批取。
- 实测：`{'n': 100000}` + `max_rows=3` → `rows=3, truncated=True, bound_limit_clamped=True`。

#### 坑 8：退款的额度要按「**剩余**可退额度」算，不是订单总额

第一版用例按「订单总额」构造金额，实测直接红：

```
RefundNotAllowed: 退款金额 70.50 超过订单 4 的剩余可退额度 28.20（订单金额 141.00 减去已申请的退款）
```

演示数据里本来就有被种子退款占掉额度的订单（重灌种子后是 141.00 − 42.30 = 98.70）。

- ✅ 修法：测试助手 `find_refundable_order()` **从库里**算出 `remaining` 一起返回，
  用例按它构造金额；判据也改成 `remaining`（这才是实现真正校验的东西）。
- 教训：**用例的失败原因必须与用例名对得上** —— 这条红如果被当成「代码坏了」，就会去改对的实现。

#### 坑 9：`RetryableToolError` 与「业务拒绝」是两件事，别混成一个异常

「订单状态不支持退款」既不是可重试错误，也不是「参数写错了」。混进 `ToolContractError`
会让第 7 步的 agent 把「等货到再退」误判成「我的参数有问题」，回喂给 LLM 一通乱改。

- ✅ 修法：`refund.py` 定义 `RefundNotAllowed(PermanentToolError)`；
  契约错误（枚举/形状）与业务拒绝分开，两者都不重试，但**处置方式不同**。

#### 坑 10：测试写库必须能收尾，否则演示库会越跑越乱

工单/退款用例会真的插行（假实现测不出唯一约束与 `ON CONFLICT`）。第一版没有清理，
跑几轮之后 `tickets` / `refunds` 的行数就与种子数据对不上了，
`scripts/db_check.py --check` 的观感也变了。

- ✅ 修法：测试统一用 `test-tools-` 前缀命名幂等键，`cleanup_tool_rows()` 前后各清一次；
  手动演示用 `runbook-demo-` 前缀（§6.6 末尾就带了清理段）。
- 实测：收尾后 `tickets 残留 0 / 共 8`、`refunds 残留 0 / 共 8`。
