三条铁律：

1. **入队路径里不干活**。`POST /api/tasks` 只做三步：校验 → 算幂等键 → 投。
   不查库、不调模型、不做 embedding —— 「长任务秒级返回 job_id」这条验收在实现上只等于这一件事。
2. **死信先落盘，任务才允许离开队列**（`core.execute_job` 的顺序）。反了就会出现
   「Redis 里没有、死信表里也没有」的窗口 —— 那就是**静默丢任务**，而验收写的是「零任务丢失」（§5.2）。
3. **幂等键是稳定派生，不是随机数**（`jobs.derive_key`）。用 uuid/时间戳当键等于「每次都是新请求」，
   重投一次就真的跑两遍（§5.4、§10.1 坑 9）。

另一条（本步最贵的一条）：**arq 的 `max_tries` 必须 = 最大重试额度 + 1**。
它不是「多给一次机会」，而是「让额度用尽的那一次**能进到我们的函数里**」——
写错的症状是「一切正常，只有死信队列永远是空的」（§10.1 坑 1）。

### 1.0 本步的链路（一次入队 + 四条收场 + 一个人工入口）

```
  客户端
    │  POST /api/tasks        （第 12 步新增：202 + job_id，不阻塞）
    ▼
┌─ app/api/tasks.py ─────────────────────────────────────────────────────────┐
│  鉴权 → scope="tasks"（10 次/分钟）→ dispatch_enqueue(kind, queue=...)      │
└───────────────────────────────┬───────────────────────────────────────────┘
                                │  tasks.enqueue_*（校验 → 算幂等键 → 投）
                                ▼
┌─ Redis（arq）──────────────────────────────────────────────────────────────┐
│  arq:job:<job_id>     任务数据                                             │
│  arq:shopsage:default 队列（ZSET，score = 到点时间）                        │
│  arq:retry:<job_id>   第几次尝试（INCR，从 1 开始）                         │
│  arq:result:<job_id>  结果（TTL 24h）                                      │
└───────────────────────────────┬───────────────────────────────────────────┘
                                │  worker 取任务（独立进程，可单独扩缩、单独重启）
                                ▼
┌─ app/queue/worker.py：bridge_job ─────────────────────────────────────────┐
│  ctx = {job_id, job_try, enqueue_time}  ──►  core.execute_job              │
│                                              │                            │
│        ① 成功 ───────────────────────────────┼─► succeeded（记指标）       │
│        ② 可恢复 + 还有额度 ──────────────────┼─► retry_planned(defer)      │
│        ③ 可恢复 + 额度用尽 ──────────────────┼─► 先写死信 → dead_letter     │
│        ④ 不可恢复（参数错 / 代码 bug）────────┼─► 先写死信 → dead_letter     │
└──────────────────────────────────────────────┼────────────────────────────┘
                                               ▼
                        queue_dead_letters（Postgres）：完整失败现场
                                               │
                        scripts/queue_replay.py│（人工兜底：--list / --job-id / --all）
                                               ▼
                        重放复用原幂等键 → 成功 → 死信被标 replayed_ok（列表收敛）
```

**每个环节「拦得住什么 / 拦不住什么」**（与 [`8.graph-runbook.md`](8.graph-runbook.md) §1.0 同口径）：

| 环节 | 拦得住 | 拦不住 / 需要别的环节 |
|---|---|---|
| `check_payload`（入队前自检） | 缺 `user_id`/`thread_id`/`message` 这类**形状错**（立刻 422） | 「值不对」（例如 user_id 指向不存在的用户）→ 那是任务内部的事 |
| 幂等键（`derive_key` / 显式 key） | 客户端重发、worker 重投、人工重复点击造成的**重复执行** | 「任务跑完之后同一个键再投」会真的再跑一次（§5.6 的边界） |
| `classify`（错误分类） | 用一层归并判定**该不该重投** | 「下游到底好没好」——退避只能给机会，不能保证 |
| `attempts` + 退避 | 把「一直撞墙」变成「撞几次就停」 | 下游彻底挂掉（那是可用性告警的事） |
| 死信表 | 失败**不再静默消失**，且人能查 / 能筛 / 能标记 | 「谁来处理」——这是流程问题，不是代码问题 |
| `replay_plan` 复用原键 | 重放两次只跑一次（写路径副作用不重复，A2） | 「原始输入是错的」——那要 `--rerun` 显式再跑一次 |
| `scale_hint()`（背压） | 一句话的扩容提示（积压 / 最老死信） | 它不是自动扩缩容输入（那要延迟分位数，第 11 步的指标） |

### 1.3 三条任务的重试策略（谁重试几次、为什么）

```powershell
uv run python -c @"
from app.queue.jobs import policy_summary
for name, item in policy_summary().items():
    print(name, item['attempts'], item['base_delay'], item['max_delay'], item['jitter'], item['delays'])
"@
```

```
shopsage.run_report 3 2.0 120.0 0.2 [1.8321, 3.4913]
shopsage.run_agent_turn 2 5.0 60.0 0.2 [4.4363]
shopsage.rebuild_knowledge_base 5 30.0 600.0 0.2 [34.0552, 55.7521, 122.3507, 265.1652]
```

> ⚠️ `delays` 里的数字**每次抽样都不同**（生产策略带 ±20% 抖动，见 `RetryPolicy.jitter`）——
> 它们只是「第一次重投大概等多久」的示意。要确定性的数字请用 `RetryPolicy.jitless()`（用例里就是这么断言的）。
> 读法：`run_report` 是 3 次尝试（首次 + 2 次重投），退避 ≈2s → ≈4s（封顶 120s）。

| 任务 | attempts | base_delay | 为什么是这个数 |
|---|---|---|---|
| `shopsage.run_report` | **3** | 2s | 读多写少的批处理：重试便宜，失败多是限流 / 瞬时不可用 |
| `shopsage.run_agent_turn` | **2** | 5s | 一轮 Agent 要花多次模型调用（C1 成本）：第二次还改不好的，第三次也一样 |
| `shopsage.rebuild_knowledge_base` | **5** | 30s | 长（几分钟）、贵（每次全文 embedding）、但**幂等**：值得多等几轮，别落到人工队列 |
| （未登记的任务） | **1** | 0s | 见 `policy_for`：没登记策略的任务多半还没想过「失败了怎么办」，对它重试等于用真实流量做实验 |

**退避公式**：`delay(n) = min(base * 2^(n-1), max) * U(1-jitter, 1+jitter)`，
其中 `n = 1` 是**首次失败之后**那次延迟；`n >= attempts` 时返回 **0**（调用方应当先 `should_retry`）——
返回一个大数会让「判定写反」这类 bug 变成一次「等了五分钟才发现」的排障。

> ⚠️ 抖动是**对称**的（`jitter=0.2` → 0.8x~1.2x），不是只向下抖：
> 只向下抖会让实际退避总比配置的短，那是另一类「配置与行为不一致」。
> 断言精确退避（1s → 2s → 4s）的用例用 `RetryPolicy.jitless()`；
> 生产策略一律带抖动（`jobs.DEFAULT_POLICIES`，三条都是 `jitter=0.2`）。

**`MAX_ATTEMPTS = max(attempts) + 1`**：

```powershell
uv run python -c "from app.queue.worker import MAX_ATTEMPTS, WorkerSettings; from app.queue.jobs import DEFAULT_POLICIES; print('最大额度 =', max(p.attempts for p in DEFAULT_POLICIES.values())); print('arq max_tries =', MAX_ATTEMPTS, '| WorkerSettings.max_tries =', WorkerSettings.max_tries)"
# 实测：最大额度 = 5
#       arq max_tries = 6 | WorkerSettings.max_tries = 6
```

为什么是 6 而不是 5 —— **读 arq 0.28 的 `Worker.run_job` 源码得到的结论**（§10.1 坑 1）。

## 2. 入队（API 契约与「秒级返回」的实现）

### 2.1 三个接口的形状

| 接口 | 状态码 | 响应里最关键的是什么 | 为什么 |
|---|---|---|---|
| `POST /api/tasks` | **202 Accepted** | `job_id` + **`created`** | 202 = 「已受理、还没完成」；200 会让客户端以为拿到了结果，而它拿到的只是一个**凭据** |
| `GET /api/tasks/{job_id}` | 200 / 404 | `status` + `result` + `dead_letter` | 越权按 **404** 处理（不确认资源是否存在，与 `api/errors.py` 口径一致） |
| `GET /api/tasks/queue` | 200 / 503 | `depth` / `deferred` / `dead_letters` / `scale_hint` | 给人看的读数，不是自动扩缩容输入 |

['POST'] /tasks
['GET'] /tasks/{job_id}
```

> 顺序即语义：`/tasks/queue` **必须**排在 `/tasks/{job_id}` 之前。
> 反了的话 `GET /api/tasks/queue` 会命中「查某个任务」那条路由（把 `queue` 当成一个 job_id），
> 返回 **200 + `status="not_found"`** —— 状态码完全正常，只有响应形状不对，
> 所以钉这条的用例断言的是**响应里有 `depth` / `scale_hint`、且没有 `status`**
> （`tests/api/test_tasks.py::test_queue_status_endpoint_is_reachable`）。

**请求体（`TaskRequest`）刻意缺三样东西**：

| 缺什么 | 理由 |
|---|---|
| `user_id` / `role` | 身份只能来自已验签的令牌 —— 结果归属判定（越权 → 404）要用它 |
| `thread_id` | 客户端能自己指定 `thread_id` 就等于能**推进别人的会话**（`8.graph-runbook.md` §4.4 同一件事） |
| 强制的 `idempotency_key` | 不传时服务端按「任务名 + user_id + 规范化参数」派生稳定键；「忘了传就自己拼个 uuid」是最容易犯的错 |

**错误映射**（每一处都对应「谁该被修」）：

| 情况 | HTTP | 谁的问题 |
|---|---|---|
| Redis 连不上（`QueueUnavailable`） | **503 + `Retry-After: 30`** | 可用性问题：调用方等一会儿重试就好，**不是** 500（500 会让人去查代码） |
| 入参 / 幂等键非法（`ValueError`：例如 agent 缺 `message`、键含空格） | **422** | 调用方能自己修 |
| `kb_rebuild` 由非内部角色提交 | **403** | 越权（知识库重建影响所有人的检索结果）。⚠️ 这个判断在 `app/api/tasks.py` 里，**不在** `schemas` 里：写在 schemas 的第一版抛 `PermissionError` → 500（把一个权限问题报成「服务端未知错误」，见 §10.1 坑 15） |
| 请求体里出现 `user_id` / `thread_id`（`extra="forbid"`） | **422** | 身份与会话键只能来自令牌/服务端派生 |
| 延迟超过 30 天 | **422** | 更远的定时任务该用 cron（`MAX_DEFER_SECONDS`） |
| 查别人的 `job_id` | **404** | 不确认资源是否存在（与 `api/errors.py` 同一口径） |

### 2.2 幂等：`created` 这一个字段回答两个问题

```powershell
uv run python -c @"
import asyncio
from app.queue.jobs import FUNC_REPORT
from app.queue.tasks import enqueue_report
from tests.queue.fake_queue import MemoryJobQueue

async def main():
    q = MemoryJobQueue()
    q.runners[FUNC_REPORT] = q.make_runner(FUNC_REPORT, lambda p: {'ok': True})
    a = await enqueue_report(user_id=2, title='本月', queue=q)
    b = await enqueue_report(user_id=2, title='本月', queue=q)
    print('第一次:', a.summary())
    print('第二次:', b.summary())
    print('job_id 相同 =', a.job_id == b.job_id)

asyncio.run(main())
"@
```

```
第一次: 已入队：report job_id=q_report:u2:95e0237f83b5b22929a5d1b3
第二次: 幂等命中（未重复入队）：report job_id=q_report:u2:95e0237f83b5b22929a5d1b3
job_id 相同 = True
```

* `job_id` —— 「**凭据**」：查状态用它、重放用它、日志里对齐用它；
* `created` —— 「**要不要重新等**」：`False` 表示这个幂等键之前已经投过，客户端不该再等一个新任务；
  而**上游在重复投递**这件事本身是值得看趋势的信号（`metrics.py` 给 `TOOL_OUTCOME` 的那段注释
  就是为「幂等命中率」留的：一直命中说明保护在工作，但那是**故障的信号**，不是成功）。

**幂等键的三条派生规则**（`jobs.py` 的模块 docstring）：

| 情形 | 键的形状 | 为什么 |
|---|---|---|
| 调用方显式给 key | 归一后原样用 | 「我知道这次请求的业务幂等键」（与上游单据号对齐、图侧的 `chat:<thread>:<轮次>`） |
| 调用方没给 | `<kind>:u<id>:<sha256 前 24 位>` | 参数用 `sort_keys` + 紧凑分隔符规范化 —— 否则 `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 会派生出两个键 |
| —— | **永不用随机数 / 时间戳** | 那等于「每次都算新请求」 |

```powershell
uv run python -c @"
from app.queue.jobs import derive_key, FUNC_REPORT
print(derive_key(function=FUNC_REPORT, user_id=2, params={'title': '本月', 'row_limit': 10}) ==
      derive_key(function=FUNC_REPORT, user_id=2, params={'row_limit': 10, 'title': '本月'}))
"@
# 实测：True（键序不影响结果 —— 这一条是「重投一次不会跑两遍」的前提）
```

> ⚠️ 幂等键的字符集是**显式 ASCII 白名单**（字母 / 数字 / `_` / `-` / `.` / `:`，上限 64 字符），
> 非法输入**抛错**而不是静默清洗。两个理由都写在 `normalize_key` 的 docstring 里：
> ① `"a b"` 与 `"ab"` 会被清成同一个键 = 两个请求的内容互相顶替（比拒绝入队难查得多）；
> ② `str.isalnum()` 会放中文进来（`"键".isalnum()` 是 `True`），而这些字符在 Redis key、
> 日志、URL 里的表现各不相同。

**`job_id` 为什么要有 `q_` 前缀**：arq 的 job_id 会进 redis key（`arq:job:<id>`、`arq:result:<id>`），
而调用方的 key 可能是任意字符串。加一层前缀 + 只允许安全字符，让「key 长什么样」不成为 Redis 行为的一部分。
它还让重放能算出原键：`DeadLetterRecord.replay_key` = `job_id` 去掉 `q_` 前缀。

### 2.3 「秒级返回」的实现方式（以及它的证据）

`12.queue.md` §8 第 1 条要的是「长任务秒级返回 job_id」。实现上它**只**意味着一件事：
入队路径里不做任何「干活」的事（不查库、不调模型、不做 embedding）。

`scripts/queue_demo.py --scenario submit` 是这条验收的可执行版本（阈值 200ms，实测 **0.2ms**，内存后端）：

```powershell
uv run python -m scripts.queue_demo --scenario submit
```

```
队列后端 = memory | 场景 = submit
==============================================================================
场景 1：长任务入队 — 秒级返回 job_id（API 不阻塞）
==============================================================================
     入队耗时 = 0.2ms（阈值：< 200ms 才算「秒级」）
     job_id = q_report:u2:405ed0ea84692d6c385fa36e
     状态   = queued（deferred 的延迟任务不走立即队列）
  ✅ 入队 0.2ms，返回 job_id（worker 还没开始跑）
==============================================================================
汇总
==============================================================================
  通过 1/1 个场景
```

> ⚠️ 内存后端的 0.2ms 说明的是「**入队路径本身没有干活**」，不是「生产也是 0.2ms」。
> 生产多出来的是 Redis 的往返（`RedisJobQueue.enqueue` 里**两次**：一次状态预检查 + 一次 `enqueue_job`）。
> 真 Redis 的实测（`--backend redis --scenario submit`，Windows → Linux VM 跨主机，Redis 7.4.11）：
> 「冷启动」（第一次连接、要建池 + TCP + 握手）**4.0ms**，同一个进程里再投 **0.9ms** ——
> 两者都离 200ms 阈值三个数量级。所以「秒级返回」这条验收在真依赖上也是成立的。

**为什么要有一次「状态预检查」**（多一次 Redis 往返买来的东西）：
arq 的「重复 `_job_id` 返回 `None`」**只覆盖「队列项还在」的情形**（实测源码：
`enqueue_job` 在 key 已存在时 `return None`，见 `arq/connections.py`）。
而任务跑完并从队列移除之后，同一个 `_job_id` 是**可以再次入队**的 ——
于是「同一个幂等键投两次」在任务已经跑完时会真的跑第二次，
对客路径上那意味着重复的模型调用与潜在的重复副作用。
所以 `enqueue()` 的顺序是：**先查 `Job.status()`** → 在队列里 / 在跑 / 排在延迟队列里就直接返回「已存在」→ 再投。

## 3. worker：内核结论怎么变成 arq 的动作

### 3.1 `bridge_job` 的两个可观察行为

| 内核结论 | 桥的动作 | 为什么 |
|---|---|---|
| `retry_planned(defer)` | `raise arq.worker.Retry(defer=<内核算的秒数>)` | 退避策略只有一处真相；桥**不许**自己拍一个延迟 |
| `dead_letter` | **先落盘**，然后 `raise outcome.error` | 死信已经留痕了；再抛是为了让 arq 的重试计数与失败指标也对上 —— 否则监控里这次显示「成功」 |

> 「退避策略配了但不生效」（另一种「看起来正常」的故障，见 §10.1 坑 7）。

**排障时认这两行 arq 日志**（实测自 `arq/worker.py` 的源码格式）：

```
  1.80s ↻ shopsage.run_report:q_report:u2:xxxx retrying job in 2.14s     ← 重投（defer_score 就是我们算的延迟）
  6.20s ! shopsage.run_report:q_report:u2:xxxx max retries 6 exceeded    ← arq 那一档保险生效（正常情况下不该看到）
```

`↻` 是重投、`!` 是失败 —— 第一条出现的次数就是「重投了几次」，
而它应当与 `shopsage_queue_retries_total` 对得上（对不上说明有人在别处绕过内核重投了）。

**payload 为什么裹一层 `{"payload": ...}`**（`bridge_job` 的入参形状）：

```
{"payload": {...任务自己的入参...}, "kind": "report", "user_id": 2}
```

arq 的 job 参数是**位置参数 + 关键字参数**，把任务入参直接铺开会与任务签名绑死，
而「任务签名改了、队列里还有旧任务」这件事在发布时必然发生
（症状是 `TypeError: got an unexpected keyword argument`，任务全部进死信）。
多一层字典让「任务入参的演进」不需要动传输层。

| 配置 | 取值 | 为什么是这个数 |
|---|---|---|
| `queue_name` | `arq:shopsage:default` | 它**本身就是 Redis 的 ZSET key**（arq 把队列名直接当 key 用，实测 `arq.constants.default_queue_name == 'arq:queue'`），所以不再叠前缀；多环境共用实例时靠它隔离 |
| `max_tries` | **6** | = 最大额度 5 + 1（§10.1 坑 1） |
| `job_timeout` | 300s | 没有超时的长任务会永久占住一个 worker 槽位，而积压会给出「加 worker」的**错误**建议（加了也不够，槽位是被卡住的） |
| `keep_result` | 86400s | 24 小时够「第二天回来捞结果」；长任务的返回值可能很大，不能无限堆 |
| `max_jobs` | **4**（不是 arq 的 10） | 长任务多是 IO + 模型调用，C1（成本）怕的是「一次打太多模型」 |
| `poll_delay` | 0.5s | arq 的默认值；队列里没活时它就是 worker 的空转频率 |
| `cron_jobs` | `dead_letter_watch` 每分钟 | 保留任务：**它不进业务队列**，也不受业务 `max_tries` 影响 |

> ⚠️ `registered_functions()` 用 `func(..., timeout=..., keep_result=...)` 包装每个任务，
> 但**刻意不在这里覆盖 `max_tries`** —— 因为它由 `WorkerSettings.max_tries` 统一给。
> 实测 arq 的取值顺序是
> `max_tries = self.max_tries if function.max_tries is None else function.max_tries`：
> 一旦某个 `Function` 上写了 `max_tries`，它就会**静默压过**全局那一档，
> 而全局那一档正是「比最大额度多一档」的实现处。这条注释在 `registered_functions` 里。

| 检查 | 不做会怎样 |
|---|---|

| 每个任务都有重试策略 | 未登记策略的任务只有 1 次机会（静默地不重试） |

| 任务名带命名空间前缀 | 没有前缀的名字（例如 `run_report`）在同一个 Redis 里很容易与别的项目撞名 |

### 3.3 内存队列：为什么它可以当「生产代码」跑

`tests/queue/fake_queue.py` 复刻了 arq 的五条关键语义，然后**用生产的 `worker.bridge_job`
执行任务**（`MemoryJobQueue.drain` 直接调它）。这不是「假实现」，它是**换掉传输层**：

| 语义 | arq（Redis） | `MemoryJobQueue` |
|---|---|---|
| 重复 `_job_id` 入队 | `enqueue_job` 返回 `None`，**不覆盖**已有任务 | `enqueue()` 返回 `created=False` |
| `defer_by` 延迟 | 写进 ZSET 的 score，worker 到点才取 | `run_at` 时间戳，`drain()` 只取到点的 |
| `job_try` | `INCR arq:retry:<id>`，从 1 开始 | `JobRecord.try_no`，从 1 开始 |
| `Retry(defer=秒)` | 任务留在队列里、score 推后 | 重排 `run_at`，`try_no += 1` |
| `max_tries` 判定 | `job_try > max_tries` → **函数不被调用** | **同一条判据**（复用它才能复现那个坑） |

> ⚠️ `drain()` 是「跑一遍 worker」，**不是**「等它跑完」：它只在**当前时刻**已经到点的任务上
> 各跑一次。要推进时间就 `advance(seconds)` —— **显式的时间旅行**比 `sleep` 快且不 flaky。
> 「重试 → 死信」的三轮之所以能被确定性验完，靠的就是 `advance(5.0)`，而不是等 2 秒 + 4 秒。

> ⚠️ 「重放成功 → 关掉死信」这条行为，内存队列**直接调用生产的那一个钩子**
> （`resolve_replayed` → `worker.after_job_end_hook`），而不是复刻一份逻辑：
> 内存队列没有 arq 的生命周期钩子，而复刻一份就是两处真相。

### 4.3 `ON CONFLICT DO UPDATE` 而不是 `DO NOTHING`（列白名单）

`store.record()` 用 PG 方言的 `insert(...).on_conflict_do_update(...)`，
且**只允许覆盖失败现场那几列**（`_REWRITABLE`）：`function / kind / payload / attempts /
error_type / error_message / error_traceback / retryable / policy / enqueued_at / failed_at / user_id`。

`resolution` / `replay_count` / `replayed_job_id` / `resolved_at` **绝不覆盖**。

| 写法 | 后果 |
|---|---|
| `DO NOTHING` | 「任务被重投后第二次失败」的现场（attempts 变大、错误变了）**静默消失** |
| `DO UPDATE` 全列 | 一次重复写入会把「已经人工重放成功」抹掉，死信重新出现在待处理列表里 |
| **`DO UPDATE` + 白名单（本实现）** | 失败现场更新、人工状态保留 |

> `to_record()` 才能统一吃「真库的行」与「内存 store 的对象」。见 §10.1 坑 3。

### 4.4 三个刻意的设计决定

1. **`job_id` 唯一 + 列白名单**（见 §4.3）；
2. **`resolution` 是文本 + `resolved_at`，不是布尔位**：收场方式不止一种
   （`replayed_ok` / `replayed_failed` / `wont_fix` / `manual_fix`，`queue_replay.py` 的 `RESOLUTIONS` 是白名单），
   布尔位会逼着后来的人往别处记「怎么处理的」；
3. **`payload` / `policy` 用 JSONB**：payload 要能被**原样喂回**（重放的输入），
   policy 要能回答「当时用的是哪套退避」（策略改了之后回看旧记录仍然说得通）。

还有一条实现口径：**每个方法一次短事务**，不持有长驻 `Session` ——
worker 是长跑进程，长事务会让 PostgreSQL 的 autovacuum 无法回收，
而死信表只在失败时写，本该是最干净的表。`replay_count` 的 +1 发生在 `resolve()` 里
（而不是「发起重放」时）：语义是「这条死信被真正推进过一次」，
发起时 +1 会让「入队失败」也算进去，而那时任务其实没跑。

## 5. 失败收场与人工重放（本步最核心的机制）

### 5.1 四条收场路径（每一条对应 `12.queue.md` 的一句验收）

| 情况 | 内核结论 | 死信？ | 为什么 |
|---|---|---|---|
| 成功 | `succeeded` | ❌ | 顺带记指标与耗时（`shopsage_queue_jobs_total` / `shopsage_queue_job_seconds`） |
| 可恢复错误 + 还有额度 | `retry_planned(defer)` | ❌ | 进死信会让死信被噪音灌满，人工兜底的入口就没人看了 |
| 可恢复错误 + 额度用尽 | `dead_letter` | ✅ **先落盘** | A1：失败变成**可见、可人工兜底的事件** |
| 不可恢复错误（参数错 / 代码 bug） | `dead_letter` | ✅ **先落盘** | 重试无意义，但**必须留痕** |

「不可恢复错误」的处置是最容易被写反的一处（`core.py` 的铁律二）：
**不重投队列**（否则同一个错误被犯 N 次、还会把重试额度浪费掉），
但也**不能直接抛出去** —— arq 会把它记成 job failed 并把任务从队列里删掉，
从此没有任何地方知道「有一个任务永久失败了」。所以这一类的收场是
「**先写死信（可见、可重放），再把异常抛给 arq**（让重试计数与失败指标也对上）」。

### 5.2 「死信先落盘」的顺序为什么是铁律

反过来的两种顺序都会制造「静默丢任务」：

```
❌ 先让任务离开队列（抛给 arq → 删掉）再写死信：
   窗口 = 写库失败 / 进程被杀 → Redis 里没有、死信表里也没有 → 任务从此不存在

✅ 先写死信（拿到 written=True）→ 再决定去向：
   即使后续动作失败，失败现场已经在人能查的地方了
```

`_write_dead_letter` 在写不进去时**不抛**（只返回 `False`），理由写在它的 docstring 里：
此刻已经在失败路径上，再抛一个「写死信失败」会**盖掉原始错误**（排障时最想看到的那个），
而且 arq 会把两次失败混成一次。所以它只返回 False，由 `execute_job` 吼出来：

```
ERROR app.queue.core: 死信落盘失败，任务 q_xxx 只存在于 Redis 的失败结果里（重放脚本找不到它）：原因=exhausted
```

### 5.3 死信里的每一列都救过某一次排障

| 字段 | 回答的问题 |
|---|---|
| `job_id` | 这是哪个任务（也是重放的幂等键） |
| `function` / `kind` / `payload` | **重放时怎么把它再跑一遍** |
| `attempts` | 试了几次（区分「一次就永久失败」与「三次都恢复不了」） |
| `error_type` / `error_message` | 出了什么错（可聚类：「全是 429」还是「全是 KeyError」） |
| `error_traceback` | 出错在**哪一行** —— **只有这里能看到**，因为 arq 的失败结果会过期 |
| `retryable` | 「运气不好」还是「代码坏了」（决定该不该重放） |
| `policy` | 当时用的是哪套策略（策略改了之后回看旧记录仍然说得通） |

```powershell
uv run python -m scripts.queue_replay --show <job_id>      # 完整现场（含 traceback）
uv run python -m scripts.queue_replay --list               # 待处理的（按失败时间升序）
uv run python -m scripts.queue_replay --list --all         # 连已处理的一起看
```

> ⚠️ `--list` 空的时候会打印「没有待处理的死信 —— 人工兜底队列是空的（**健康形态**）」。
> 这句话是刻意写的：一个空列表最容易被读成「工具坏了」。

> ⚠️ **`--all` 是「修饰」，不是「重放动作」**（这里修过一次，值得记下来）：
> 第一版把它放进 argparse 的互斥组，于是最自然的写法 `--list --all`
> 直接报 `argument --all: not allowed with argument --list`。修正后的语义：
>
> | 写法 | 含义 |
> |---|---|
> | `--list`（或什么都不给） | 只列**待处理**的 |
> | `--list --all` / `--list --include-resolved` | 连**已处理**的一起列（多一列「状态」） |
> | `--all` 单独 | 仍然是**列表**（不是「重放全部」） |
> | `--all --dry-run` / `--all --limit 5` | **批量重放**（先失败的先来，先干跑） |
> | `--job-id <id>` | 单条重放 |
>
> 不变式：**「重放」永远需要显式指定范围**。一个手滑的 `--all` 就把整批死信真跑一遍，
> 是最容易造成二次事故的形态；`tests/queue/test_queue_replay_cli.py` 用参数组合用例钉住这些语义
> （含「`--list --all` 必须被接受」这条回归）。

### 5.4 重放：默认复用原幂等键（A2 的落点）

`core.replay_plan(entry)` 只做**纯计算**（不产生副作用，所以能单测、能干跑），两个刻意的决定：

1. **默认复用原幂等键** → 重放两次只会跑一次（写路径的副作用不会重复，A2）；
2. **允许一次显式重跑**（`key_suffix`）：键变成 `<原键>:retry2`（后缀递增），
   于是「同一条死信被点了几次」在 Redis 的 job_id 上是**看得见**的。
   它只由 `scripts/queue_replay.py --rerun` 触发，**不是默认行为**。
   ⚠️ 后缀同样要过 `normalize_key`（有 64 字符上限），所以不能无限叠加 ——
   达到上限时抛错并要求人工处理（一个被重放 100 次的任务该被修，而不是再点一次）。

重放的 payload 里会被塞两个键：`dlq_key`（原死信的 job_id）与 `replay_of`。
`dlq_key` 是「成功之后谁去把那条死信关掉」的凭据 ——
任务成功时 `worker.after_job_end_hook` 据此把它标成 `replayed_ok`（并记下重放用的 job_id）。

```powershell
uv run python -m scripts.queue_replay --all --dry-run      # 只看会重放什么，不动手
uv run python -m scripts.queue_replay --job-id <job_id>    # 重放一条
uv run python -m scripts.queue_replay --all --limit 5      # 批量（先失败的先来）
uv run python -m scripts.queue_replay --resolve <id> --as wont_fix   # 不重放，只标记已处理
```

**四个刻意的行为**（`scripts/queue_replay.py` 的 docstring）：

| 行为 | 为什么 |
|---|---|
| 默认只列不跑（含「`--all` 单独出现」） | 重放会真的执行任务（可能调模型、可能写库）；一个「直接跑全部」的工具最容易造成二次事故 |
| 默认复用原幂等键 | 「点两次」只跑一次；要真再跑一遍必须显式 `--rerun` |
| `--as` 的取值是白名单 | 自由文本的 `resolution` 会让「这条死信怎么收场的」变成一次人工考古 |
| `--all` 是**修饰**而不是动作 | 否则 `--list --all`（最自然的读法）会被 argparse 拒掉；语义随动作变化，见 §5.3 的表 |

> ⚠️ 这个脚本**不启动 worker**：它只把任务重新投进队列。真正执行要有一个在跑的
> `uv run arq app.queue.worker.WorkerSettings` 进程 —— 投完立刻 `--list` 看到的是
> 「已重放、等 worker 执行」（`replayed_job_id` 已写上、`resolution` 还是空的）。

> ⚠️ 「关掉死信」这一步容易被漏。少了它，死信列表永远不收敛，
> 「有死信躺着」这条告警会一直响 —— 而那正是 A1 失效的形态。

### 5.5 重放修不了什么（先想清楚再点重放）

| 情形 | 重放有用吗 | 为什么 |
|---|---|---|
| 下游抖了一下 / 限流（`RetryableToolError`） | ✅ 有用 | 多半第二次就过了 |
| 进程被杀 / 部署重启 | ✅ 有用 | 任务留在队列里，重投即可（`CancelledError` 由 arq 按可重试处理） |
| 参数写错 / 业务规则不允许（`PermanentTaskError`） | ❌ 没用 | **修好参数再 `--rerun`**，否则每次重放都是同一个错误 |
| 代码有 bug（`KeyError` / `TypeError`） | ❌ 没用 | 同一个输入必然同样失败 —— 修代码，然后 `--rerun` |
| 「任务已经成功跑完了，同一个幂等键又投了一次」 | ❌ 这是**设计** | 「已完成」与「排队中」是两种状态（§5.6） |

### 5.6 幂等的边界：同一个键什么时候会真的再跑一次

这一条**必须搞清楚**，否则会把「幂等键 = 永不再跑」写进文档：

```
队列里 / 正在跑 / 排在延迟队列里 → 再投是幂等命中（created=False）
已收场（成功 or 死信）          → 队列项已经没了 → 再投会**真的再跑一次**
```

* 内存队列的 `enqueue` 只看「队列项还在不在」（`_TERMINAL_STATUSES`），所以
  「已完成 → 再投 → 再跑一次」在内存里**直接发生**：
  `test_idempotent_enqueue_does_not_run_twice` 的第三条断言就是这个（`count_calls == 2`，
  第三次 `created=True`），它刻意把这个边界钉住，免得将来有人以为「幂等键 = 永不再跑」；
* 真 Redis 会多挡一次：`RedisJobQueue.enqueue` 先查状态，只有 `not_found` / `complete`
  时才继续投 —— 即「已完成」**也会**被再投一次，被挡住的是
  「还在队列里 / 正在跑 / 排在延迟队列里／状态未知」。

> 「为什么 `complete` 不再挡」以及「重复 `_job_id` 到底怎么表现」这两件事
> **需要真 Redis 才能验**（`Job.status()` 与 `arq:result:*` 的 TTL 时序）。
> 本机已验（Redis 7.4.11），两条证据：

```

```

判定顺序（**顺序即语义**，`core.classify` 的 docstring 逐条写了理由）：

1. `RetryTask` → 可重试（任务自己要求的，最权威）；
2. `PermanentTaskError` / `PermanentToolError` / 永久型 `LLMError` / `ToolContractError` → **不可**重试；
3. `RetryableToolError` / `RetryableLLMError` → 可重试；
4. 其余 `ToolError` / `LLMError` → 不可重试（两层的默认方向都是「保守」）；
5. **没见过的异常** → 不可重试。

**第 5 条是最容易被写反的一处**：`KeyError` / `TypeError` / `ValueError` 这类
「代码有 bug / 参数写错」的异常重投 100 次结果一样，只会让同一个 bug 被犯 100 次、
把重试额度耗光，让真正「运气不好」的任务排在它后面。
**代码坏了要有人看见，而死信队列就是那个「看见」的地方。**

> ⚠️ `asyncio.CancelledError` 在 Python 3.8+ 继承 `BaseException`，**不会**走到 `classify`
> （arq 自己按「可重试」处理 worker 关停时的取消）—— 这是要的：部署重启不该把一个任务判成永久失败。

**`classify` 为什么只做「归并」**：`app/tools/errors.py` 与 `app/llm/errors.py` 已经分别定义了
「可重试」的白名单（第 5、6 步），队列这一层用 `is_permanent` / `is_retryable` 归并它们，
**不重新发明一套分类**。顺序与 `app/llm/errors.py` 保持一致：先排显式永久，再看白名单。

**`RetryTask` 为什么不直接用 `RetryableToolError`**：任务自己最清楚「等多久合适」
（限流头里就写着 `Retry-After`）。内核把「该不该重试」（由错误类型决定）与
「等多久」（由任务提示 + 退避策略决定）分开，于是「任务知道得更准」时不必去改全局策略。
`_defer_for()` 就是这条分工的实现：`RetryTask.defer` 优先，否则用策略算出的退避。

## 7. 可观测性（队列的 gauge + counter + 队列现状接口）

### 7.1 为什么队列需要 `gauge()` 这个**新写入口**

第 11 步只留了 `counter()` / `observe()`，而队列的「现在积压多少」既不是累计量也不是耗时：

| 语义 | 方法 | 写成别的会得到什么 |
|---|---|---|
| 「发生了 N 次」（只增） | `counter()` | —— |
| 「一次花了多久」 | `observe()` | —— |
| **「现在是多少」（可升可降）** | **`gauge()`** | 用 `counter()` 记积压 → `rate()` 之后变成「积压**增长速率**」，**看起来像一条合法曲线**，而「现在积压多少」永远答不出来 |

所以第 12 步给 `observability.Metrics.gauge()` 与 `api.metrics.MetricsRegistry.gauge()`
各加了一个写入口，并把 `MetricsRegistry.snapshot()` 的返回**追加**了第三个键 `gauges`
（不是替换 —— `counters` / `histograms` 是既有调用方在用的读口）。

```powershell
uv run python -c @"
from app.observability.metrics import Metrics
m = Metrics()
m.gauge('shopsage_queue_depth', 7.0)
m.counter('shopsage_queue_jobs_total', {'function': 'shopsage.run_report', 'kind': 'report', 'status': 'succeeded'})
snap = m.snapshot()
print('gauges   =', snap['gauges'])
print('counters =', {k: v for k, v in snap['counters'].items() if 'queue' in k})
"@
```

```
gauges   = {'shopsage_queue_depth': 7.0}
counters = {'shopsage_queue_jobs_total{function="shopsage.run_report",kind="report",status="succeeded"}': 1.0}
```

> ⚠️ 上面这条命令**故意只写一个 gauge**：它同时是 `snapshot()` 分型的证据 ——
> `snapshot()["gauges"]` 里只有 gauge、`snapshot()["counters"]` 里只有 counter。
> 实现上靠的是「问 collector 的 `metric.type`」，**不是靠名字后缀猜**
> （`shopsage_queue_depth` 与 counter 的名字形状可以一模一样，猜错的后果是
> 「当前积压」被读成「累计入队数」，而两条曲线看起来都很正常 —— 见 §10.1 坑 11）。
> `render()` 出来的文本长这样（`gauge` 没有 `_total` 后缀，因为它是瞬时值）：
>
> ```
> shopsage_queue_depth 7.0
> shopsage_queue_dead_letter_pending 2.0
> shopsage_queue_jobs_total{function="shopsage.run_report",kind="report",status="succeeded"} 1.0
> ```

> ⚠️ `gauge()` 还顺手丢掉 `NaN` / `inf`：`prometheus_client` 对它们会写出一行
> Prometheus **无法解析**的文本，整个 scrape 失败，而调用方那边完全看不出问题。

### 7.2 队列的指标（三个 gauge + 四个 counter + 一个直方图）

| 指标 | 类型 | 谁写 | 回答的问题 |
|---|---|---|---|
| `shopsage_queue_depth` | **gauge** | `GET /api/tasks/queue`、`worker.record_queue_gauges`（启动时） | **现在**积压多少（等 worker 取的条数） |
| `shopsage_queue_dead_letter_pending` | **gauge** | `worker.dead_letter_watch`（cron，每分钟） | 人工兜底这条路径上堆了多少活 |
| `shopsage_queue_dead_letter_oldest_seconds` | **gauge** | 同上 | 最老的一条躺了多久 —— **这个才值得告警** |
| `shopsage_queue_jobs_total` | counter | `core.execute_job`（成功路径） | 成功了几笔（按 `function` / `kind` / `status`） |
| `shopsage_queue_job_failures_total` | counter | `core.execute_job`（失败路径） | 失败了几笔（带 `retryable` 标签） |
| `shopsage_queue_retries_total` | counter | `core.execute_job`（计划重投时） | 重投了几次 |
| `shopsage_queue_dead_letter_total` | counter | `core._write_dead_letter` | 进死信几笔（带 `reason=exhausted\|permanent`） |
| `shopsage_queue_job_seconds` | histogram | `core.execute_job`（成功路径） | 单任务耗时（→ 分位数） |

> ⚠️ **`_record_depth` 刻意什么都不写**（`value=None` 时直接返回，只留了一个 extension point）。
> 每次任务结束时**不知道**真实积压（那要问 Redis），而一个「猜出来的深度」比没有深度更糟：
> 它会让扩容决策建立在假数字上。真实深度由 `RedisJobQueue.depth()` 在有 Redis 连接的地方写。

> ⚠️ **死信的两个 gauge 里，「最老的一条躺了多久」才是告警项**：条数多可能只是刚发生一批抖动
> （一次下游故障就能造出几十条），而「最老的躺了三天」意味着**人工兜底这条路径根本没人在走**（A1 失效）。
> `DEAD_LETTER_ALERT_SECONDS = 86400`，超过它 `dead_letter_watch` 会打一条 ERROR。
> 指标名字的常量在 `observability/metrics.py`（`QUEUE_DEPTH` / `QUEUE_DLQ_PENDING` / `QUEUE_DLQ_OLDEST`），
> 第 11 步只留了 `QUEUE_DEPTH` 一个，本步把三个都接上。

> ⚠️ 指标标签里塞 traceback 会让**基数爆炸**（每一条 traceback 都是一条新时间序列），
> 所以 `summarize_error()` 只给**一行摘要**（60 字符），全文进死信表的 `error_traceback`。
> 两处的需求不同，所以是两个出口。

### 7.3 `GET /api/tasks/queue`：背压信号的出口（以及它不是什么）

```powershell

```
depth=   0 deferred=   0 backlog=   0 -> 积压正常
depth=  25 deferred=   0 backlog=  25 -> 积压 ≥20：留意趋势，可能是下游变慢
depth= 120 deferred=   0 backlog= 120 -> 积压 ≥100：加 worker（先确认单个任务耗时没有变长）
depth=   1 deferred= 300 backlog= 301 -> ⚠️ 有死信超过 24 小时无人处理：先走人工兜底流程，再谈扩容
```

三条刻意的口径：

* **延迟任务不算积压**：`depth()` 只数「立刻可取的」（`zcard`），
  `deferred()` 单独数「还没到点的」（`zcount(now, +inf)`）。
  把定时报表算进扩容信号，会让 worker 每天上午 8 点定时被加一批。
* **`scale_hint()` 的判据刻意粗**：它是给人看的**一句话**，不是自动扩缩容的输入。
  自动扩缩容要的是延迟分位数（第 11 步的指标），不是队列长度
  （一个「每任务 5 分钟」的队列，积压 10 也完全正常）。
* **最老死信优先于积压**：`scale_hint()` 先看 `oldest_dead_letter_seconds > 86400`，
  命中就直接说「先走人工兜底流程，再谈扩容」—— 因为积压的根因可能是「没人处理死信」。

> ⚠️ **两个查询接口都不在限流映射里**（`api/scope.SCOPE_BY_ROUTE` 只登记了 `("POST", "/api/tasks")`
> → `"tasks"`；其余路径走未登记分支 → 退回 `DEFAULT_RULE` 60 次/分钟）。
> 两个查询接口都要 `require_principal`（要令牌），各自读的又是 Redis 的一个 `zcard`/`zcount`，
> 在当前拓扑下够用；**但这是一处值得 review 的口径，不是「已经想清楚了」的结论**。
> `tasks` 的限流额度是 **10 次/分钟**（`ratelimit.DEFAULT_RULES`），比 `chat` 的 30 更严 ——
> 理由写在 `scope.py` 的注释里：一次提交换来一个后台长任务，
> 被滥用的代价落在**队列**上（积压会让所有人的任务一起变慢），而 chat 只影响调用者自己。

### 8.5 `agent` 任务的返回值契约（`task = graph 的一次执行`）

`run_agent_turn` 的返回值里有三个字段是**给队列看的**，不是给人看的：

| 字段 | 队列据此做什么 |
|---|---|
| `exhausted` | **决定这次任务算不算成功**：`True` → 抛 `RetryableToolError`（交给内核按策略重试 → 用尽 → 进死信） |
| `pending_approval` | 挂起等人工批准**不是失败**：任务成功结束（否则「等人批准」的噪音会把死信灌满） |
| `visited` / `replayed` | 第 11 步的埋点要它们（这一轮走了哪条路、重放了哪几步） |

```powershell
uv run python -c @"
from app.queue.agent_runs import REQUIRED_PAYLOAD_KEYS, check_payload
print('必填入参 =', REQUIRED_PAYLOAD_KEYS)
for kind, payload in (('report', {}), ('agent', {'thread_id': 'u2:s1'}), ('kb_rebuild', {})):
    try:
        check_payload(kind, payload)
        print(kind, 'OK')
    except ValueError as exc:
        print(kind, '拒绝:', exc)
"@
```

```
report       {}                         -> 拒绝：report 任务缺少必填参数：user_id
agent        {'message': '你好'}          -> 拒绝：agent 任务缺少必填参数：thread_id, user_id
kb_rebuild   {}                         -> OK
report       {'user_id': 2}             -> OK
```

> 读法：`agent` 那条的报错**一次列全**缺的两个参数（`thread_id` / `user_id`），
> 而不是「先报一个、改完再报下一个」—— 入参自检的价值就在这里：
> 调用方一轮就能把请求修对，而不是靠试。

> ⚠️ **这条翻译（`exhausted` → `RetryableToolError`）是本模块最要紧的一处**：
> `run_turn` 的语义是「永远给你一个 `Turn`」（它把失败兜底成一句实话，用户不会看到 500），
> 但对**队列**来说「兜底话术」不等于「任务成功」。少了这层翻译，
> 「重放修不好的失败」会静默地变成「成功的任务」，而死信队列永远是空的。
> 它把第 8 步 §5.4 那条「`RetryableToolError` 刻意不被 `run_turn` 吞掉」的接缝真正接上了。

> ⚠️ **队列这一层不做鉴权**：`enqueue_agent_run` 的 `thread_id` 必须由调用方
> （`app/api/deps.thread_id_for`）从鉴权结果派生。API 若允许客户端自己指定 `thread_id`，
> 这条路径就成了「推进别人的会话」的旁路（与 `8.graph-runbook.md` §4.4 是同一件事）。

### 10.1 实现期间撞到的坑（实测，含修法）

**坑 1 是本轮最贵的一个**（它让整条「零任务丢失」的验收静默失效）；
**坑 2、3 是「离线全绿、真库一跑就炸」**；**坑 4、5 是并发与幂等的边界**；
**坑 6、7 是路由与退避**；**坑 8、9 是「看起来能用但口径不对」的隐患**；
**坑 10、11 是最后跑真 Redis 与 gauge 时才暴露的**；
**坑 12 是安全相关的一处静默失效**；**坑 13 是「加一张表」的爆炸半径**（靠全量回归才发现）；
**坑 14 只在边界值上出现**；**坑 15、16 是「分层错了就报错类型也错」**。

#### 坑 1：arq 的 `max_tries` 会让「额度用尽」那一次**不进函数**（死信永远不会被写）

这是本步最贵的一个坑，也是本文档反复强调它的原因。读 arq 0.28 的
`Worker.run_job`（`.venv/Lib/site-packages/arq/worker.py`）源码，实测的行为是：

```python
# 取到任务先做三件事（一个事务里的 pipeline）
pipe.get(job_key_prefix + job_id)
pipe.incr(retry_key_prefix + job_id)      # ← job_try 每次取到就 +1，从 1 开始
pipe.expire(retry_key_prefix + job_id, 88400)
...
max_tries = self.max_tries if function.max_tries is None else function.max_tries
if job_try > max_tries:
    logger.warning('%6.2fs ! %s max retries %d exceeded', t, ref, max_tries)
    ...
    return await asyncio.shield(self.finish_failed_job(job_id, result_data))   # ← 函数**一次都没跑**
```

也就是说：**如果让 arq 的 `max_tries` 来判定「重试额度用尽」，那么「用尽」那一刻
我们的函数一次都不会被调用** —— 于是「进死信」这件事永远没有机会发生，
任务从 Redis 消失、死信表里也没有。

* ❌ 症状极具误导性：**一切正常**（任务确实重试了、也确实失败了、日志里也有
  `max retries exceeded`），**只有死信队列永远是空的**。
* ✅ 修法：`MAX_ATTEMPTS = max(policy.attempts) + 1`，即 `WorkerSettings.max_tries = 6`
  （最大额度是 `kb_rebuild` 的 5）。于是「额度用尽」的那一次**会**进函数，
  由 `core.execute_job` 写完死信再收场；arq 那一档只做**最后一道保险**
  （防我们自己的计数出问题）。
* ✅ 再加一条**启动期检查**：`selfcheck()` 把「`max_tries` 必须大于最大额度」变成一条
  自检项 —— 因为**这个数字改错了不会有任何报错**，只会让死信队列静默地永远是空的。
* ✅ 再加一条**可复现**：`tests/queue/fake_queue.py` 的 `drain()` 刻意保留
  `if attempt > enabled: status = JOB_DEAD; continue` 这个分支
  （注释里写着「与 arq 的 `run_job` 同一条判据」），于是这个坑可以被一条用例复现。
* 教训：**框架的「已经帮你做了」可能恰好拿走了你唯一需要的那个钩子**。
  引入一个队列时，第一件该读的不是它的文档，而是它的 `run_job` ——
  「函数在什么条件下**不会**被调用」比「它怎么被调用」重要得多。

#### 坑 2：`sqlalchemy.insert` 没有 `on_conflict_do_update()`（离线用例永远跑不到）

第一版 `store.record()` 写了：

```python
from sqlalchemy import insert          # ← 通用 Insert
statement = insert(QueueDeadLetter).values(**values)
statement = statement.on_conflict_do_update(...)   # AttributeError
```

`on_conflict_do_update()` 是 **PostgreSQL 方言**的 API，通用 `insert` 上没有它。
而这段代码在**离线用例里根本不会被执行**（内存 store 不走 SQL），
所以「离线全绿」没有任何意义。

* ✅ 修法：`from sqlalchemy.dialects.postgresql import insert as pg_insert`。
* 教训：**「落库」这件事必须有真库用例**（`@pytest.mark.db`），否则你验的是内存实现。
  这正是 `test_queue_dead_letter.py` 分两层（离线 / 真库）的理由，
  而它 docstring 的第一句就是「真库层的第一条用例就抓过一个真实的坑」。

#### 坑 3：`select(ORM 实体)` 的 `.mappings()` 里没有列键（`KeyError: 'job_id'`）

读语句第一版写的是 `select(QueueDeadLetter)`，然后 `.mappings().first()` 拿去喂 `to_record()`：
`session.execute(select(Entity))` 返回的是 `Row`，`.mappings()` 拿到的是以**实体**为键的形状，
里面**没有** `job_id` 这个键。

* ✅ 修法：一律 `select(QueueDeadLetter.__table__)`（**Table**），
  于是拿到的就是标准列映射，`to_record()` 能统一吃「真库的行」与「内存 store 的对象」。
* 教训：同一个 `to_record` 要吃两种来源的行时，**先统一行的形状**，而不是让两种来源各改一次。

#### 坑 4：`redis.asyncio` 的连接绑定在事件循环上（跨循环复用 = `Event loop is closed`）

「一行入队」要求有个默认队列，而三个选项各有代价：

| 方案 | 代价 |
|---|---|
| 每次入队新建连接池 | 每个请求一次 TCP + AUTH，而且池不会被关（连接泄漏） |
| 模块级全局单例 | **跨事件循环复用**：`redis.asyncio` 的连接绑在循环上，于是「测试里第二个 `asyncio.run()` 用第一个循环的池」会得到 `RuntimeError: Event loop is closed` —— 最难查的一类（单跑绿、全量红） |
| **按事件循环缓存（本实现）** | 缓存字典里会留下已关闭循环的条目 → 用 `close_default_queues()` 补上 |

* ✅ 修法：`_QUEUES: dict[int, RedisJobQueue]`（键是 `id(asyncio.get_running_loop())`）+
  `close_default_queues()`，后者由 FastAPI 的 `lifespan` 退出时与 worker 的 `on_shutdown` 调用。
* ⚠️ 还有一个**只有测试会踩到**的细节：`main.py` 里那句「注入队列的 app 不关默认队列」
  （`if queue is None: await close_default_queues()`）—— 注入内存队列时那个池压根没建，
  关它没有意义；而关掉别人循环里的池才是真正的 bug。
* ✅ `enqueue_*` 的 `_queue_scope` 也守同一条：**注入的队列原样用且不关，默认的用完不关**
  （池必须活到本事件循环结束；在入队函数里关掉它，下一个请求会拿到一个已关闭的池）。
* 教训：**「谁的循环、谁负责关」这条所有权规则要在代码里写出来**，
  否则它一定会在某个测试文件里被违反。

#### 坑 5：状态查询会把「已完成」也放过去（幂等边界，非 bug 但是必须写清）

`RedisJobQueue.enqueue` 的预检查只挡
`not_found` / `complete` 之外的四种状态（`queued` / `deferred` / `in_progress` / `unknown`）。
也就是说「**已完成**」的任务会被再次入队 —— 这正是人工重放的工作方式
（重放就是要再投一次），但它同时意味着「幂等键 ≠ 永不再跑」。

* ✅ 处置：不修（那是刻意的），而是**把这个边界写成一条用例与一节文档**：
  `test_idempotent_enqueue_does_not_run_twice` 的第三条断言（`created=True`、`count_calls == 2`）
  与 §5.6。
* 教训：**一个「安全默认值」式的幂等承诺，必须连边界一起写出来**。
  只写「同一个键只执行一次」会让下一个人在重放功能上线后困惑整整一天。

#### 坑 6：`/tasks/queue` 被 `/tasks/{job_id}` 吃掉（FastAPI 按声明顺序匹配）

两个路由同时存在时，反了的话 `queue` 会被当成一个 `job_id`：

```
GET /api/tasks/queue  →  404 {"error":{"code":"not_found_or_forbidden","message":"未找到该任务，或你没有访问它的权限"}}
```

**路由其实是对的，只是匹配顺序反了** —— 而这条 404 会把排查方向引向「鉴权」或「数据」。

* ✅ 修法：`tasks.py` 里 `queue_status` 声明在 `task_status` 之前（文件里有一行注释钉住它）。
  **用例已落地**：`tests/api/test_tasks.py::test_queue_status_endpoint_is_reachable` ——
  它断言的是**响应形状**（有 `depth` / `scale_hint`、没有 `status`），而不是「HTTP 200」：
  顺序反了的那个 404 恰好也带 200 的兄弟形态（`status="not_found"`），只断言状态码是抓不住的。
* 教训：**路由的声明顺序是语义的一部分**，静态路径必须排在参数路径之前 ——
  这是「加上就能跑」的框架里少数必须靠纪律维持的约定。

#### 坑 7：桥里的延迟必须来自内核（否则退避策略静默失效）

桥第一版按「有重试就 `raise Retry(defer=1)`」写。测试全绿（因为只断言「抛了 `Retry`」），
而生产里的表现是**退避策略配置了但不生效**。

* ✅ 修法：桥只做翻译（`Retry(defer=planned.defer)`），
  并让用例断言**延迟的数值**（`Retry.defer_score` 毫秒）。
* 教训：**「抛出了正确的异常类型」是很弱的断言**。凡是有数值的地方，断言数值。

#### 坑 8：幂等键用「业务字段 + 非规范 JSON」派生 → 键序不同就是两个键

第一版 `derive_key` 直接 `json.dumps(params)`，而 Python 的 `json.dumps`
**保持插入顺序** —— 于是 `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 派生两个键，
「客户端重发一次」变成「跑两个任务」，而调用方完全看不出区别。

* ✅ 修法：`json.dumps(..., sort_keys=True, separators=(",", ":"))`，并加一条用例专门钉它
  （`test_derive_key_is_a_pure_function_of_the_business_request` 的第一条断言）。
* 教训：**幂等键的派生必须是纯函数** —— 对「同一份业务请求」的每一种书写方式都得到同一个结果。
  这类 bug 的共同特征：测试全绿、账单变贵、副作用重复，而**没有任何日志说它发生了**。

#### 坑 9：`scripts/worker.py` 没落地（`12.queue.md` §6 第 4 步）—— 有意为之

文档写「写 `scripts/worker.py` 启动入口（`arq worker`）」，落地时**没有**这个文件：
arq 的标准入口就是 `uv run arq app.queue.worker.WorkerSettings`（`WorkerSettings` 类本身就是入口），
再包一层脚本会多出「配置从哪读」的第二处真相。

* ✅ 处置：在 `worker.py` 的模块 docstring 里把两种启动方式都写清楚
  （`uv run arq app.queue.worker.WorkerSettings` / 前台），并在本文 §1.2 记下这次差异。
* 教训：**文档里的「开发步骤」是意图，不是必须逐字落地的文件清单** ——
  差异要在 runbook 里显式记下来（否则下一个人会去找一个不存在的文件）。

#### 坑 10：`arq:retry:<job_id>` 在任务收场时会被删掉（实测，不是推断）

「重试计数在 Redis 里（`INCR arq:retry:<id>`）」这句话本身没错，但**收场时它会被删**
（`finish_job` 的 `delete_keys += [retry_key_prefix + job_id, ...]`）。
第一版用例在任务跑完之后去 `GET arq:retry:<id>` 断言计数，于是**永远拿到 `None`** ——
看起来像「重试根本没发生」，而实际发生了两次。

* ✅ 修法：用**任务自己看到的序号**（`ctx["job_try"]` → 结果里的 `attempts`）与
  `Worker.jobs_retried` 作为证据；`arq:retry:*` 只在**任务还在跑或还没到重投点**时读得到。
* 教训：**「某个键代表某个事实」必须连生命周期一起确认** ——
  一个会被框架删掉的键，用它做「事后断言」时读到的是「不存在」，而那是**歧义**（从没写过 vs 已删除）。

#### 坑 11：`snapshot()` 分不出 gauge 与 counter（名字形状可以一模一样）

`Metrics.snapshot()` 第一版靠「名字后缀」判型，而 `shopsage_queue_depth`（gauge）
与一个 counter 的名字形状可以完全一样 —— 猜错的后果**不是报错**，
而是「当前积压」被读成「累计入队数」，两条曲线看起来都很正常。

* ✅ 修法：**问 collector 自己**（`metric.type`），`snapshot()` 返回三个键
  （`counters` / `histograms` / `gauges`），并加 `gauge_value()` 读口。
* 教训：`prometheus_client` 暴露出来的**样本名里没有类型信息** ——
  这件事只有在「同一个名字可能是两种类型」时才会暴露，而它一旦暴露就是静默的错误读法。

#### 坑 12：结果里没有 `user_id` → 越权判定**静默失效**

`GET /api/tasks/{job_id}` 的归属判定有两个来源：队列里的入队参数（`owner()`）
结果里的 `user_id`。第二版只从结果里读 → 「排队中/执行中」的任务**不判**，
于是拿到 `job_id` 就能一直读别人的任务状态，直到它跑完才被挡住（那时数据已经出去了）。

* ✅ 修法：`RedisJobQueue.owner()` 从 `arq:job:<id>` 的入队参数里读发起人；
  `worker._result_payload` 再**统一补一个 `user_id`**（任务自己不必返回它）——
  于是「任务跑完、`arq:job:*` 被删」之后仍然判得出来。
* 教训：**归属判定要在「任何状态」下都有效**，而不是「有数据可看时才有效」——
  后者留下的正是「谁都能看到别人正在跑什么」这个窗口。

#### 坑 13：加一张表就把**别的层**打红了（两处，都是全量回归抓出来的）

`queue_dead_letters` 是队列的表，但它会出现在两个「按 metadata / 按表清单遍历」的地方：

1. `tests/conftest.py` 的 `seeded` 装置按 `MIN_COUNTS[t]` 查 `snapshot().counts` ——
   `counts` 现在多了这张表 → `KeyError: 'queue_dead_letters'` → **50 个 error**
   （所有依赖 `seeded` 的工具层用例在 setup 阶段全红，症状看起来像「工具层坏了」）；
2. `app/agents/data.py::schema_text()` 按 `Base.metadata` 全量渲染 prompt 里的 schema ——
   新表**漏进了 Text-to-SQL 的 prompt**，`test_agents_data.py::test_schema_text_lists_all_allowed_tables` 红。

* ✅ 修法：① `seeded` 只按 `MIN_COUNTS` 的键判断；② `schema_text()` 只渲染 `BUSINESS_MODELS`。
  两处都补了注释说明「为什么是这两张表的区别」。
* 教训：**「加一张表」的爆炸半径只在全量回归里看得见** ——
  本步的全部队列用例（含真库、真 Redis）当时**全绿**。
  凡是有 `Base.metadata` / `snapshot().counts` 这类「遍历全部表」的地方，
  新增表都要顺手检查一遍；而唯一靠得住的检查就是**跑全量**。

#### 坑 14：`job_id = "q_" + 键` 会突破键的长度上限

`normalize_key` 的上限是 64 字符（**幂等键**的上限），而 `job_id_for` 第一版把
「加了 `q_` 前缀的结果」又喂回 `normalize_key` → 「刚好 64 字符的键」在最后一步抛
`ValueError: 幂等键过长（66 > 64）`。

* ✅ 修法：校验分两步（先按键的规则校验键，再按 `job_id` 的规则校验 `job_id`），
  并加一条边界用例（`MAX_KEY_CHARS` 长度的键必须成功）。
* 教训：**派生物的上限与源的上限不是同一个数**。用一个「校验源」的函数去校验「源+前缀」，
  错误只会在边界值上出现 —— 而边界值正是最容易漏测的地方。

#### 坑 15：把「授权判断」写进 pydantic 模型 → 403 变成 500

第一版把「`kb_rebuild` 只有内部角色能提交」写在 `schemas.TaskRequest.enqueue_kwargs` 里，
并在那里 `raise PermissionError`。结果是一次权限拒绝变成了 **500**：

```
PermissionError: kb_rebuild 是内部操作：知识库重建会影响所有人的检索结果
  → 没有被任何 exception handler 接住 → 500 internal error
```

* ✅ 修法：模型只描述「请求长什么样」，授权判断搬到路由（`api/tasks.py` 的 `INTERNAL_KINDS`
  + `ApiError(403, "forbidden", ...)`）。顺带修了同一处的一个隐患：
  `enqueue_kwargs()` 现在**放在 `try` 里**调用，于是它自己抛的 `ValueError`（agent 缺 `message`）
  会被翻成 **422** 而不是 500。
* 教训：**「谁能做这件事」和「这件事的请求长什么样」是两层**。
  把它们写在一起时，异常类型就会跟着分层一起错位 ——
  而 403 → 500 这种错位会让值班人第一眼去查代码，而不是查权限。

#### 坑 16：`app.routes` 在新版 FastAPI 上遍历不到已挂载的路由

自查命令第一版写的是 `for r in app.routes: print(r.path)`，在 FastAPI 0.143 上输出里
**只有 `/` 与 `/docs`**（内层是 `_IncludedRouter` 包装对象，`app.routes` 不再直接给 `APIRoute`）：

```
Route /openapi.json …
Route /docs …
_IncludedRouter None None      # ← 三条都在这一层里，遍历时看不到 path
APIRoute / {'GET'}
```

* ✅ 修法：要看路由顺序就直接读挂载源 `app.api.tasks.router.routes`
  （或 `app.openapi()["paths"]`，但它会丢掉顺序）。
* 教训：**「自查命令」也是代码**，它坏掉时的表现是「输出少了东西」——
  而那看起来像「路由没挂上」。写自查命令时优先挑**不依赖框架内部结构**的入口。

> ⚠️ 本步最后**已把「本机未验证」全部补完**（真 Redis 跑了、全量回归跑了），
