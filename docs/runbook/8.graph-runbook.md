三条铁律：

1. **图只做编排，不实现节点**。`app/graph/` 里出现业务判断（SQL、prompt、脱敏规则）就是越界；
   它只做四件事：**绑定注入点、归一状态、装配图、管 checkpointer**（§12 ② 用 AST 检查钉住）。
2. **失败要能重放，用户不该看到 500**。这两件事互相拉扯 —— 节点里 `except` 会吃掉断点，

3. **`thread_id` 只由鉴权结果产生**。它等于会话 id，是 checkpoint 的隔离键；
   本步只提供 `thread_config()` / `graph_config()`，**绝不**从请求体里取一个任意字符串（§4.4）。

另一条：**每个状态键都必须声明 reducer**。裸注解的键不进图的 `output_channels`，
`ainvoke` 的返回值里就没有它 —— 而图跑起来、checkpoint 落库都完全正常（§10.1 坑 5 是本步最贵的坑）。

```
   │                │                                                  （短路，D2）│

   │                       ├─ route=rag ──────► ④ rag ───┼──────────────────┤   │
   │                       ├─ route=analysis ─► ③ data ──┘  ⑤ analysis ◄───┘   │
   │                       └─ route=ticket/final ──────────────────────────┐   │

   │                                                    ⑥ synthesis ◄─────────┘ │
   │                                                         │                  │
   │                                                         ▼                  │

   │                                        │             （被拦的一轮不进历史）  │
```

**每个环节「拦得住什么 / 拦不住什么」**（与 [`7.agents-runbook.md`](7.agents-runbook.md) §1.0 同口径）：

| 环节 | 拦得住 | 拦不住 / 需要别的环节 |
|---|---|---|
| `guardrail_input` | 注入关键词（零 token、微秒级） | 换个说法的注入（那是输出侧 LLM 判定的事） |
| `router` 的条件边 | 把「意图 → 分支」收成**一处路由表** | 意图判错本身（那是 prompt 与第 16 步评测的事） |
| `data / rag` 汇合 | 保证 `synthesis` 只有一个入口 | 「材料里有别人的数据」→ 由第 6/7 步的行级过滤 + 输出侧护栏兜 |
| `after_data` 分叉 | 「对内分析要等数据到位」这条依赖 | 数据质量差（那是第 16 步评测的事） |
| `guardrail_output` | 内部口径词、明文 PII、编造/越界 | 它不是唯一防线：硬边界仍是 SQL 守卫与只读角色 |
| `run_turn` 的重放 | 进程挂掉/上游抖动这类**可重放**失败 | 「代码有 bug」的重放是白跑（这时该修代码，见 §5.4） |
| `gate`（可选） | 敏感分支在**花任何代价之前**停住 | 它不判断「该不该批」，只负责停 |

### 1.3 状态键与 reducer（谁写哪个键、怎么合并）

| 键 | 谁写 | reducer | 语义 |
|---|---|---|---|
| `messages` | 入口 + `guardrail_output`（通过时追加） | `add_messages` | **追加**（对话历史累积） |
| `user_id` / `role` | 入口（router 原样回写） | `LastValue` | 本轮覆盖 |
| `permissions` / `is_customer` | **只有 router** | `LastValue` | 本轮覆盖 |
| `route` / `route_confidence` / `route_reason` | router | `LastValue` | 本轮覆盖（条件边读它） |
| `sql` / `sql_attempts` / `rows` / `row_meta` | data | `LastValue` | 本轮覆盖 |
| `docs` / `citations` | rag（synthesis 也写 `citations`） | `LastValue` | 本轮覆盖 |
| `analysis` / `chart_spec` | analysis | `LastValue` | 本轮覆盖 |
| `answer` | synthesis（护栏/兜底会替换） | `LastValue` | 本轮覆盖 |
| `refusals` | data / rag / analysis / gate / 回合兜底 | `LastValue` | 本轮覆盖（**每轮重新算**） |
| `blocked` / `guardrail_stage` / `guardrail_rules` / `guardrail_message` | guardrail 两侧 + 回合兜底 | `LastValue` | 本轮覆盖 |

**为什么只有 `messages` 是「追加」**：其余字段的语义都是**本轮覆盖** —— 第二轮问了别的问题，
`route` 就该是新的那个值；留着上一轮的 `route=data` 会让条件边按旧意图分支（那是脏读，不是历史保留）。
只有对话历史的语义是累积。这条分工由 §12 ④ 与 `test_graph_state.py` 钉住。

## 2. 图怎么装配（builder + config）

### 2.1 装配代码的形状（读 `builder.py` 只看这一段就够）

```python
builder = StateGraph(GraphStateDoc)                       # ① 状态 schema（带 reducer）
for name, factory in node_specs(runtime).items():          # ② 节点（工厂造，注入点显式）
    if name == NODE_GATE and not runtime.interrupts.enabled:
        continue                                           #    闸门按策略条件注册
    builder.add_node(name, factory(runtime))

builder.add_edge(START, NODE_GUARDRAIL_INPUT)              # ③ 边（拓扑）
builder.add_conditional_edges(NODE_GUARDRAIL_INPUT, after_guardrail_input, {...})
builder.add_conditional_edges(NODE_ROUTER, route_by_intent, _route_map())
builder.add_edge(NODE_RAG, NODE_SYNTHESIS)
builder.add_edge(NODE_ANALYSIS, NODE_SYNTHESIS)
builder.add_conditional_edges(NODE_DATA, after_data, {...})   # data 是岔路口
builder.add_edge(NODE_SYNTHESIS, NODE_GUARDRAIL_OUTPUT)
builder.add_conditional_edges(NODE_GUARDRAIL_OUTPUT, after_guardrail_output, {END: END})

return builder.compile(checkpointer=..., name="shopsage")
```

**为什么节点用工厂造，而不是 `add_node("router", router_node)`**：六个节点的签名是
`node(state, *, llm=None)`，而 `add_node` 传的是位置参数 —— 直接注册看上去能跑，
但**注入点就消失了**：测试只能靠 monkeypatch 掏内部实现，「六个 Agent 可独立调用、独立测试」
这条第 7 步的验收会在第 8 步被悄悄破坏。工厂让注入点在**构建期**显式存在（`GraphRuntime`）。

### 2.2 `GraphRuntime`：一次跑图的全部外部依赖与预算

```powershell
uv run python -c "from app.graph import GraphRuntime; import dataclasses; [print(f'{f.name:16s} = {f.default!r}') for f in dataclasses.fields(GraphRuntime)]"
```

| 字段 | 默认 | 说明 |
|---|---|---|
| `llm` | `None` | 模型出口（`JsonLLM` 协议）；`None` = 走生产实现 |
| `search` | `None` | 检索注入点；`None` = 走生产实现 |
| `row_limit` | `50`（= `data.DEFAULT_ROW_LIMIT`） | 向工具要多少行 |
| `max_attempts` | `3`（= `data.MAX_SQL_ATTEMPTS`） | NL→SQL 尝试次数 |
| `top_k` / `min_score` | `5` / `None` | 检索参数（`min_score=None` = 不设阈值，`rag.DEFAULT_MIN_SCORE` 的取值） |
| `chart_type` | `"bar"` | analysis 出图类型 |
| `max_analysis_rows` | `200`（= `analysis.MAX_ANALYSIS_ROWS`） | 分析输入上限 |
| `interrupts` | `InterruptPolicy(enabled=False)` | 人工审批策略 |

> ⚠️ 这些默认值**从节点侧 import**（而不是在 graph 里再写一遍数字）：
> 「重试几次」「最多几行」只有一处真相，否则图与节点会各自漂移。

### 2.3 `ensure_compatible_event_loop()`：为什么图相关代码要显式调一次

Windows 上 psycopg 的**异步模式不能在默认的 `ProactorEventLoop` 上跑**：

```
psycopg.InterfaceError: Psycopg cannot use the 'ProactorEventLoop' to run in async mode.
```

这不是本仓的缺陷，是 psycopg 的既定限制；而事件循环策略是「新建循环时读一次」的全局量，
**循环已经建好再改就对它无效**。所以本步在「图相关的异步入口」显式调一次：

```powershell
uv run python -c "from app.graph import ensure_compatible_event_loop as f; print('policy =', f())"
# 实测（Windows）：policy = WindowsSelectorEventLoopPolicy
# 生产（Linux）：空操作，返回当前策略名（PlatformSelector 系列）
```

调用点有三处：`tests/graph/conftest.py`（import 期）、`tests/graph_helpers.py`（import 期）、
`scripts/graph_replay_demo.py` 的 `main`。**第 9 步的 FastAPI 入口也要调一次**（在 `lifespan` 启动早期）——
忘了它的症状是「内存后端全绿、一换成 postgres 就 InterfaceError」（§10.1 坑 1）。

### 2.4 `durability="sync"`：那个容易漏掉的参数

LangGraph 1.x 默认**异步**持久化（`durability="async"`）：节点结果先返回，checkpoint 后台写。
它更快，但「重放」的前提是**落盘已经发生** —— 默认值下进程在写完之前挂掉，
你会得到一个「节点跑过了、checkpoint 没有」的状态，而重放恰恰要用它。

所以 `graph_config()` 把它钉进**每一次调用**：

```powershell
uv run python -c "from app.graph import graph_config, TURN_DURABILITY; print('durability =', TURN_DURABILITY); print(graph_config('会话id'))"
# 实测：durability = sync
#       {'configurable': {'thread_id': '会话id'}, 'durability': 'sync'}
```

代价是每步多一次写库往返（实测单轮 4~6 个节点、本地库 < 10ms/次）。
这笔钱买的就是 §5 那一整套重放能力 —— 换成异步持久化，就只剩「大部分时候不丢」。

## 5. 断点重放（本步最核心的机制）

### 5.1 一次重放的完整时序（实测）

```powershell
uv run python -m scripts.graph_replay_demo --scenario crash
```

实测输出：

```
==============================================================================
场景 3：data 节点失败 → 断点重放（不重头跑）
==============================================================================
  thread=demo-crash 路径=guardrail_input→router→data→data→synthesis→guardrail_output 结论=正常 | 重放：['data']
  route='data' blocked=False rows=2
  answer='您最近 2 笔订单：1 笔已发货、1 笔待付款。'
  replayed=['data']
  checkpoint 条数 = 7
```

读法（这三行就是重放的全部证据）：

* `路径` 里 `data` 出现**两次**：第一次失败、第二次（重放）成功；
* `guardrail_input` / `router` **各只出现一次**：它们已完成，没有被重头跑；
* `checkpoint 条数 = 7`：每一步一个检查点，包括失败那一步之前的全部状态。

逐步展开（`run_turn` 的驱动循环）：

```
① 首次执行：guardrail_input ✔  router ✔  data ✘（抛异常）
   → LangGraph 不写 data 这一步的 checkpoint，也不推进 next：next == ('data',)
   → 异常穿透到 run_turn（这就是「断点还在」）
② run_turn 看到 next=('data',)：还有重放预算 → payload=None → 再 astream 一次
   → 图从 checkpoint 的 next 继续：只跑 data（以及它之后没跑过的）
③ data 成功 → synthesis → guardrail_output → END
```

### 5.2 为什么「兜底」必须在回合边界，不能在节点里（本步最贵的一课）

两件事要同时成立：

| 要求 | 做法 | 反面 |
|---|---|---|
| 失败能**从断点重放** | 异常**穿透**节点 | 节点里 `except` 并返回兜底 → LangGraph 认为这步**成功完成**、`next` 变空 → **断点消失** |
| 用户**看不到 500** | 在 `run_turn` 里接住异常 → 重放 → 重放不成再写一句实话 | 让异常一路冒到 API → 对客路径上一次 500 |

第一版（用 `error_handler=` + 节点内兜底）满足了第二条、**毁掉了第一条**。
修正后的分工：

```
节点（nodes.safe_node）  ：只归一状态，异常穿透        ← 保住断点
回合（run.run_turn）     ：接异常 → 重放 → 兜底写状态   ← 保住用户体验
```

验证（两条互补的用例）：

```powershell
# ① 异常必须穿透，断点必须停在失败节点上
uv run pytest -q -p no:cacheprovider tests/graph/test_graph_replay.py -k breakpoint -v
# ② 重放预算用尽时，这一轮仍然答得出来（少一份材料 ≠ 答不了）
uv run pytest -q -p no:cacheprovider tests/graph/test_graph_replay.py -k exhaustion -v
```

### 5.3 幂等：重放不会重复建工单（§7 第三条用例）

```powershell
uv run python -m scripts.graph_replay_demo --scenario idempotent
```

实测：

```
  节点执行次数 = 2（失败一次 + 重放一次）
  工单表行数 = 1（期望 1）| ticket_id = 1001
```

**为什么必须专门验这一条**：`8.graph.md` §5 第三条 —— *图能重放，但节点内部若不幂等，
重放就会重复执行*。这是重放机制自带的代价，不是它的保证。写路径的幂等键口径见
[`6.tools-runbook.md`](6.tools-runbook.md)（`app/tools/write_path.py` 的
`(user_id, idempotency_key)` 复合唯一键 + `ON CONFLICT DO NOTHING`）。

**图这一层要提供的两样东西**（本步已交付）：

1. `graph_config()` 里带 `durability="sync"`：失败之前的每一步都确实落盘了；
2. `Turn.replayed` 记录「这次重放了哪几步」—— 第 11 步的指标与排障都要它。

**第 9 步落地 ticket 节点时要做的事**：把幂等键从「图的执行 id」派生
（例如 `chat:<thread_id>:<轮次>`），**不要**用时间戳或随机数 —— 那会让重放每次都建一张新单。

### 5.4 重放修不了什么（先想清楚再重放）

| 失败类型 | 重放有用吗 | 为什么 |
|---|---|---|
| 进程挂了 / 上游抖了一下 | ✅ 有用 | 状态还在，继续跑就行 |
| 模型这一轮返回了空 | ✅ 通常有用 | 第二次大概率能拿到内容 |
| 代码有 bug（例如 `KeyError`） | ❌ 没用 | 同一个输入必然同样失败 —— 这时该修代码，`turn.exhausted=True` 是给你的信号 |
| 可重试错误（`RetryableToolError` / `RetryableLLMError`） | ❌ 本步**刻意不兜** | 那是第 12 步队列的重投语义；在这里打转会掩盖「该退避」的事实 |
| 数据库不可达 | ❌ 不该兜成「查不到」 | 那是可用性问题，要报警而不是答一句「我没查到」 |

```powershell
# 「可重试错误原样上抛」的证据
```


### 6.3 输出侧护栏**自己**失败时：不允许 fail-open

情形：`synthesis` 返回了空回答 → 输出护栏拿不到待审文本 → 它抛错。
处置遵循「收口型节点的兜底」：这一轮直接以固定话术收场（`guardrail_stage="fallback"`），
**不放行**。理由：审查崩了就放行，等于「审计坏掉时最该审的那次反而没审」，
而且它的坏法是**静默的**（用户看到一个正常回答）。


### 6.4 图级兜底的两条分支（网络型 vs 收口型）

| 节点类别 | 失败后果 | 处置 | 用户看到 |
|---|---|---|---|
| 网络型（`data` / `rag` / `analysis`） | 少一份材料 | 写 `refusals`，**继续**跑到 synthesis | 一句「这次没查到那部分」 |
| 收口型（`synthesis` / `guardrail_output`） | 没有回答 / 没有审查 | 写 `blocked=True` + 固定话术，**结束本轮** | 一句安全的兜底话术 |

`guardrail_stage="fallback"` 是刻意的新取值：埋点要能区分「护栏拦下的」（查攻击）
与「系统没做到的」（查故障）—— 这两件事的运营动作完全不同。

### 6.5 human-in-the-loop：闸门现在能做什么、第 9 步要接什么

**已验证的框架能力**（`test_graph_interrupt.py`，用一张最小图）：

* `interrupt({"question": ...})` 能让图在带 checkpointer 时**真正挂起**，
  `ainvoke` 返回 `__interrupt__`，`next` 停在那一刻；
* `ainvoke(Command(resume=True/False), cfg)` 能恢复，**节点函数从头重跑**
  （所以 `interrupt()` 之前的副作用必须幂等 —— 这就是主图把「写 refusal」放在挂起之前的理由）。

**本步交付的策略与挂点**（默认关闭）：


2. 把 `app/graph/nodes.py::make_gate` 里那句 `return {...}` 换成

> ⚠️ 现在的「开着闸门」语义是 **fail-closed**：没有批准通道时**不放行**。
> 这是刻意的 —— 「没人批就默认放行」等于把人工审批变成装饰。

## 9. 与后续步骤的接线点（本步留好的接缝）

| 后续步骤 | 直接用本步的什么 | 本步**不做**的 |
|---|---|---|
| 第 9 步 `api/` | `run_turn(graph, state, thread_id=...)` → `Turn`（`answer` / `blocked` / `visited` / `exhausted`）；`open_checkpointer()` 的生命周期 | 不做路由、不做 JWT、不做限流；不产生 `thread_id` |
| 第 9 步的错误映射 | `MissingIdentityError` → 500 级接线错误；`PermissionDenied` → 403；`SQLSecurityError` → 400；`Turn.exhausted` → 503/降级 | 不做 HTTP 状态码决策（那是 API 层的语义） |
| 第 9 步的 SSE | `run_turn(..., on_event=...)`：每个节点的增量都能被转发出去 | 不做流式协议、不做背压 |
| 第 9 步的写节点 | `InterruptPolicy` + `make_gate` 的挂点；写操作必须带幂等键（§5.3） | 不做 ticket/refund 节点（属第 9 步） |
| 第 10 步 `rag/` | `GraphRuntime.search` 注入点（落地后默认后端自动生效） | 不做检索算法、不做 rerank |
| 第 11 步 `observability/` | `Turn.summary()` / `Turn.replayed` / `Turn.exhausted`；`guardrail_stage="fallback"` 与 `node_failure:<节点>` 规则名 | 不做埋点、不做 Grafana |
| 第 12 步 `queue/` | `RetryableToolError` / `RetryableLLMError` **不被 `run_turn` 吞掉**（原样上抛） | 不做 Arq、不做死信表 |
| 第 13 步 `cache/` | 图是纯函数式的一轮一状态（对缓存友好） | 不做语义缓存 |
| 第 16 步 `web/` / `eval/` | `Turn.visited` 是「这一轮走了哪条路」的稳定信号 | 不做 golden set、不做 CI 接线 |

## 10. 故障速查

| 症状 | 最可能的原因 | 怎么确认 | 修法 |
|---|---|---|---|
| `psycopg.InterfaceError: Psycopg cannot use the 'ProactorEventLoop'` | 没调 `ensure_compatible_event_loop()`（或其调用晚于事件循环创建） | 看 traceback 是不是在 `open_checkpointer` | 在**创建任何循环之前**调它（§2.3、§10.1 坑 1） |
| `ainvoke` 只返回 `{'messages': [...]}` | 有键没写 reducer 注解（裸注解的键不进 `output_channels`） | `graph.output_channels` 是不是只有 `messages` | 给每个键加 `Annotated[..., LastValue]`（§10.1 坑 5） |
| 第二轮 `AttributeError: 'HumanMessage' object has no attribute 'get'` | 节点入口没过 `normalize_input`（对象形态的消息） | traceback 指向 `messages_of` / `last_user_message` | 用 `safe_node` 包装节点；别绕过它（§10.1 坑 2） |
| `TypeError: '<' not supported ... NoneType and str`（在 `get_graph()` / `draw_mermaid()`） | 用了 `error_handler=` 或把**节点**当条件边目的地 | 报错栈里有 `_draw.py` | 兜底写进节点内部 / 回合边界；条件边只指向 `END`（§10.1 坑 3） |
| `KeyError: 'synthesis'`（走 `final` 分支时） | 条件边的 `path_map` 少了 `synthesis` | | `_route_map()` 必须含 `ROUTE_NODES` 的全部目的地 + `synthesis`（§10.1 坑 4） |
| analysis 报「没有可分析的数据行」 | `ROUTE_NODES["analysis"]` 直接指向了 `analysis` 节点（跳过了 data） | `ROUTE_NODES` 的取值 | 指向 `data`，由 `after_data` 决定是否接着分析（§3.2、§10.1 坑 7） |
| 失败之后 `next` 是空的（重放不了） | 有人把兜底写进了节点内部（吞掉了异常） | `aget_state().next == ()` 而 `blocked` 为真 | 让异常穿透；兜底放 `run_turn`（§5.2、§10.1 坑 8） |
| 重放**无限循环**（同一个节点反复跑） | `aupdate_state` 没传 `as_node=`（默认记成「上一个写状态的节点」干的） | 日志里同一个节点反复出现 | `aupdate_state(config, update, as_node=失败节点)`（§10.1 坑 9） |
| 兜底话术被覆盖成正常回答 | 兜底之后图又跑了一两步，`guardrail_output` 顺手写了 `blocked=False` | `turn.answer` 是兜底话术但 `turn.blocked` 是 False | 兜底增量压在最后合并（`Turn.fallback`，§10.1 坑 10） |
| `NameError: name 'Annotated' is not defined`（构造 `StateGraph` 时） | `TypedDict` 定义在**函数里** | 报错在 `get_type_hints` | 状态类定义在**模块级**（§10.1 坑 11） |
| 迁移一致性用例要「删掉 checkpoints 表」 | LangGraph 把 checkpointer 的表注册进了 `Base.metadata` | diff 里有 `remove_table` / `remove_index` | `alembic/env.py` 与本仓用例都排除 `CHECKPOINT_TABLES`（§10.1 坑 12） |
| Redis checkpointer 起不来（`unknown command 'FT.INFO'` / `'FT._LIST'` / `'JSON.SET'`） | 镜像里没有 RediSearch / RedisJSON | `uv run python -m scripts.redis_checkpointer_probe` | 换 `redis/redis-stack-server`（§4.3，两条修法） |
| `thread_config(None)` 不报错 | `str(None)` == `'None'`（非空！） | `thread_config(None)` 的返回 | 已经修好：先拦非字符串再 strip（§4.4） |
| `ModuleNotFoundError: No module named 'langgraph'` | 环境没同步（本步新增的依赖） | `uv run python -c "import langgraph"` | `uv sync`（或 `uv add` 之后确认 `pyproject.toml` 里有它） |
| `ModuleNotFoundError: No module named 'app'` | 不在仓库根执行 | `Get-Location` | `cd` 回仓库根（`uv run` 不改工作目录） |
| `uv ... Failed to initialize cache ... os error 5` | uv 全局缓存目录不可写 | 看报错路径 | `$env:UV_CACHE_DIR = "$PWD\.uv-cache"` |
| 真库用例成批 skip | PostgreSQL 不可达 / 业务表不存在 | skip 原因里写了 | 见 [`3.db-runbook.md`](3.db-runbook.md) §1；或跑 `uv run alembic upgrade head` |
| Redis 真库用例 skip | 缺 RediSearch/RedisJSON 模块 | `scripts.redis_checkpointer_probe` 的第 ② 步 | §4.3（换镜像 + `SHOPSAGE_TEST_REDIS_CHECKPOINTER=1`） |

### 10.1 实现期间撞到的十二个坑（实测，含修法）

**坑 3、5、8 是本轮最贵的三个**（分别破坏了「图可检查」「返回值完整」「可重放」）；
**坑 1、2、4、6、7 是第一跑就崩的**；**坑 9–12 是「看起来能用但会出事」的隐患**。

#### 坑 1：psycopg 的异步模式不能在 Windows 默认事件循环上跑

第一版直接 `AsyncPostgresSaver.from_conn_string(url)`：

```
psycopg.InterfaceError: Psycopg cannot use the 'ProactorEventLoop' to run in async mode.
Please use a compatible event loop, for instance by running
'asyncio.run(..., loop_factory=asyncio.SelectorEventLoop(selectors.SelectSelector()))'
```

* ✅ 修法：`checkpointer.ensure_compatible_event_loop()` 在**建循环之前**把策略换成
  `WindowsSelectorEventLoopPolicy`；`tests/graph/conftest.py` 在 **import 期**调它
  （放在 fixture 里就晚了 —— pytest-asyncio 可能已经建好循环）。
* 教训：**平台限制要在入口收敛成一个显式调用**，而不是散落在每个 `asyncio.run` 旁边。
  放到 conftest 的 import 期还有个额外好处：它只影响 `tests/graph/`，不动其余 600+ 条既有用例的循环。

#### 坑 2：`add_messages` 不在 `langchain_core.messages` 里

```python
from langchain_core.messages import add_messages   # ImportError: cannot import name 'add_messages'
```

报错还给了个建议 `Did you mean: 'trim_messages'?` —— 那会把你带向完全无关的方向。

* ✅ 修法：`from langgraph.graph.message import add_messages`（它是 **LangGraph** 的 reducer，
  langchain-core 1.6 已移除）。
* 教训：**报错里的「建议」不是文档**。`grep` 一下包的实际导出比跟着建议猜快得多。

#### 坑 3：`error_handler=` 会让 `get_graph()` 抛错（图能跑，但结构不可检查）

第一版用 LangGraph 的 `add_node(..., error_handler=graph_fallback, destinations=(...))` 做图级兜底。
图跑得完全正常，但：

```
TypeError: '<' not supported between instances of 'NoneType' and 'str'
  at langgraph/pregel/_draw.py:203  → for src, cond, label in sorted(trigger_to_sources[trigger])
```

`error_handler` 生成的**内部节点**在边遍历里带 `label=None`，排序时与字符串标签混在一起。

* ❌ 不是「图坏了」——**而是「图结构不再可验证」**：`draw_mermaid()` 与「边表断言」
  这两条最有价值的验收手段同时失效。
* ✅ 修法：兜底挪出节点（写进 `run_turn`），条件边只指向 `END`，不用 `error_handler`。
* 教训：**框架的便利 API 可能破坏你的验收手段**。判断标准不是「能不能跑」，
  而是「出了问题我还看得见吗」。

#### 坑 4：条件边的 `path_map` 漏一个目的地 → 运行时 `KeyError`

`ROUTE_NODES` 里 `ticket` / `final` 的目标是 `synthesis`，但 `path_map` 只列了
`{data, rag, analysis}` —— 于是「你好」这种**最无害的问题**直接崩：

```
KeyError: 'synthesis'
```

* ✅ 修法：`_route_map()` 返回 `{**ROUTE_NODES, NODE_SYNTHESIS: NODE_SYNTHESIS}`，
  并加一条用例断言「分支函数可能返回的每个值都在映射里」。
* 教训：LangGraph **编译期不检查**条件边的返回值域，这属于「跑到才炸」的一类；
  唯一可靠的防线是「映射 = 取值域的闭包」这个不成文约定，把它写进注释与用例。

#### 坑 5：**裸注解的状态键不会出现在 `ainvoke` 的返回值里**（本步最贵的坑）

第一版只给 `messages` 加 `add_messages`，其余键保持裸注解：

```
$ graph.ainvoke(state, cfg)        → {'messages': [...]}            # 只剩一个键
$ graph.aget_state(cfg).values     → 18 个键（全是全的！）            # checkpoint 里都对
$ graph.get_output_jsonschema()    → 只有 messages 一个属性
$ graph.stream_channels_asis       → 22 个键                        # 内部通道是全的
```

根因：LangGraph 把「带注解的键」当作**显式通道**来推 `output_channels`，
而 `ainvoke` 的返回值取自 `output_channels`。

* ✅ 修法：每个键声明 reducer —— `messages` 用 `add_messages`（追加），
  其余用 `LastValue`（= 本轮覆盖，正是我们要的语义）。
* 教训：**这个 bug 的症状极具误导性** —— 测试全绿、checkpoint 正确、只有返回值不对。
  真正抓住它的是「`aget_state()` 里有 18 个键，`ainvoke` 只回 1 个」这个对比。
  排查这类问题要问的不是「代码对不对」，而是「框架的哪个契约我没满足」。

#### 坑 6：`synthesis` 不给 `generate_json` 传 `agent=`，假 LLM 认不出调用者

按 `agent=` 分派的假 LLM 在 `synthesis` 这一步拿到的是 `'unknown'`（`app/agents/synthesis.py`
调 `generate_json` 时没写 `agent=`）。

* ✅ 修法：测试辅助 `resolve_agent()` 先看 `agent=`，取不到就按 **system prompt 的角色说明**
  猜（"客服助手" / "内部业务助手" / "财务口径助手" → synthesis）。这与模型的认法一致。
* 教训：这不算「第 7 步的缺陷」（`agent` 只用于日志归并），但如果第 9 步要做**按节点的成本核算**，
  就得给它补上。已记进 §9 的接线点。

#### 坑 7：`route=analysis` 直连 `analysis` 节点 → 它永远说「没有可分析的数据行」

第一版 `ROUTE_NODES["analysis"] = NODE_ANALYSIS`。图照跑、日志有话说，**但没有任何地方报错**：

```
WARNING app.agents.analysis: analysis 无数据可分析：没有可分析的数据行：analysis 需要先由 data 节点查出数据
```

* ✅ 修法：`analysis` 这条 route 的第一个节点是 `data`，再由 `routing.after_data` 决定是否接着分析。
* 教训：**「节点的输入从哪来」是图的职责**。节点自己声明依赖（`analysis` 要 `rows`），
  图必须负责把它排在生产者之后 —— 而这条依赖在文档的示意图里看不出来（图里三条分支是并列的）。

#### 坑 8：节点内兜底会**吃掉断点**（重放因此不可能）

第一版 `safe_node` 里 `try/except` 把永久失败翻成兜底增量并返回。结果：

```
run1: {'a': 'A', 'c': 'C', 'blocked': True}   # c 照样跑了（图认为 b 成功完成）
run1 next: ()                                  # ← 断点没了
run2（换新模型、不注入故障）: calls 里**没有** prod_b   # 重放无从谈起
```

* ✅ 修法：`safe_node` 只归一状态、**异常穿透**；兜底交给回合驱动 `run_turn`。
  于是 `next == ('data',)` 保住，`run_turn` 用 `astream(None, cfg)` 从断点继续。
* 教训：**「不让用户看到 500」与「保住断点」是不能在同一层解决的问题** ——
  它们一个有副作用（改状态）、一个要求无副作用（别推进），放一起必然牺牲一个。

#### 坑 9：`aupdate_state` 不传 `as_node` → 重放无限循环

兜底写状态时用了默认的 `as_node`（= 「上一个写状态的节点」），于是 `next` 按**那个节点**的出边重算，
失败节点又被排进 `next`：

```
兜底后 next = ('data',)  → 再驱动一次 → 又失败 → 又兜底 → …
```

* ✅ 修法：`await graph.aupdate_state(config, update, as_node=target)` ——
  语义是「这一步我们替它收尾」，图从**它的下游**继续。实测后端到端跑通（`next` 变空、`answer` 正常）。
* 教训：`aupdate_state` 的默认参数不是「我更新的那个节点」，而是「**谁**更新的」。
  这类「参数存在但含义与直觉不同」的 API，必须在调用处写清注释。

#### 坑 10：兜底结论被下游节点覆盖（`blocked` 被冲回 False）

收口型节点失败后写了 `blocked=True` + 固定话术，但图还会走完剩下的一两步，
而 `guardrail_output` **通过时会顺手写 `blocked=False`**：

```
turn.answer  = '抱歉，这次没能查到需要的信息…'   # 还好
turn.blocked = False                            # ← 调用方据此返回 200，而这一轮什么都没做成
```

* ✅ 修法：`Turn.fallback` 记住兜底增量，在最后**再合并一次**（兜底的语义是「本轮最终结论」）。
* 教训：**「谁写的最终值」要有明确的优先级**。多个节点写同一个键时，
  「最后写的赢」（`LastValue`）是默认规则，而兜底需要**例外**——那就得显式实现这个例外。

#### 坑 11：`TypedDict` 定义在函数里 → `NameError: name 'Annotated' is not defined`

`StateGraph(WriteState)` 会调用 `get_type_hints`，而函数内定义的类型在**函数作用域**里解析注解。

* ✅ 修法：状态类一律定义在**模块级**（`app/graph/state.py`、测试与演示脚本同理）。
* 教训：`from __future__ import annotations` + 局部 TypedDict 是**必然**踩的组合。

#### 坑 12：LangGraph 的 checkpointer 表被注册进 `Base.metadata` → 迁移一致性用例要求删表

跑过真库 checkpointer 用例之后，`test_no_pending_migration_against_models` 开始红，
diff 是「删掉 `checkpoints` / `checkpoint_blobs` / `checkpoint_writes` / `checkpoint_migrations`」。
一个**自动生成的迁移就会删掉全部会话状态**，而它在评审里长得像一次正常清理。

* ✅ 修法：把表名单写成 `checkpointer.CHECKPOINT_TABLES` 常量，
  **两处**排除：`alembic/env.py` 的 `include_object`（人工迁移）与 `tests/test_db_migrations.py`（自动化）。
  索引也要一起排除（否则「表排除了、它的索引还在比」，报出一堆 `remove_index`）。
* 教训：**引入一个会用 ORM 元数据的依赖时，要检查它往全局元数据里放了什么**。
