三条必须知道的取值规则（都已在 `tests/test_config.py` 里钉住，别再自己发明）：

1. **`llm_primary` 不许为空**。`Settings` 的 `_validate_llm_routing` 会在构造期抛

### 1.2.1 降级模型为什么必须用**单独**的密钥

**规则**：主模型用 `LLM_API_KEY`，降级模型用 `LLM_FALLBACK_API_KEY`，两者**不许互相顶替**。
这条不是洁癖，四个理由按重要性排：

1. **降级链天生是「跨厂商」的**（A3 的全部意义就在这）：主模型是 DeepSeek、备模型是 OpenAI/Claude
   时，拿 A 家的 key 去打 B 家的端点**必然 401**。如果密钥只有一把，
   「自动降级」会在最需要它的那一刻失败——而且失败原因（鉴权）被 `errors.py` 正确判为
   **不可恢复**，所以既不会重试也不会再降级，用户看到的就是**直接报错**，可用性目标反而更差。
2. **故障隔离与最小权限**：主模型 key 泄漏/被限流/超额时，降级 key 还能用；
   反之备模型的预算与速率限制也是独立的。共用一个 key 时，**一次限流会同时打掉主备两条路**，
   降级链形同虚设。
3. **可独立轮换与计费归属**：轮换一把钥匙不需要动另一条路径；账单按 key 归属自然就能分出
   「主模型花了多少、降级兜底花了多少」（第 11/13 步的成本面板直接吃这个）。
4. **审计上「谁在用谁的凭据」是可回答的**：出问题时你能明确说「这次调用走的是降级凭据」，
   而不是去猜 effective key 是哪一把。

**实现口径**（第 13 步接降级链时按这个写，本步只需把字段与配置写好）：

```python
# app/llm/client.py（第 13 步：按「实际要打的模型」解析凭据）
def _resolve_credentials(model: str, settings) -> tuple[str, str | None]:
    """返回 (api_key, api_base)；**按模型解析**，不按调用顺序解析。

    为什么强调「按模型」：降级链里 `used_model` 会在运行期从主模型切成备模型，
    若密钥是在**入口**解析一次（拿 `llm_api_key` 就往下传），降级那一刻用的还是主模型的 key ——
    这正是「跨厂商降级必然 401」的成因。所以解析必须发生在「最终 used_model 定了之后」。
    """
    if model == settings.llm_fallback and settings.llm_fallback_api_key.get_secret_value():
        return settings.llm_fallback_api_key.get_secret_value(), (settings.llm_fallback_api_base or None)
    return settings.llm_api_key.get_secret_value(), None
```

配套两条**校验规则**（已实现在 `Settings` 的 `_validate_llm_routing` / `_validate_prod_requirements`）：

- `llm_fallback` 非空、但 `llm_fallback_api_key` 为空 → `ENV=prod` 时**启动即失败**
  （宁可开不了机，也不要在故障时才暴露「降级键没配」）；dev 只告警。
- `llm_fallback_api_key` 与 `llm_api_key` **相同**时告警：这不是错误（同一个厂商的两个模型确实可能共用一把钥匙），
  但它意味着**没有故障隔离**，值得在启动日志里说一句。

`client.py` 侧已按这个口径实现并测过（`tests/test_llm_client_retry.py`）：
`model == llm_fallback` → 用 `llm_fallback_api_key` + `llm_fallback_api_base`；
缺这把钥匙时**明确报错**（`PermanentLLMError`，且**一次下游都不打**），而不是静默回落到主密钥 ——
静默回落正是要防的那条 401 路径。

> ⚠️ **本步只做到「按模型取凭据」，还没有自动降级链**：`llm_call` 不会在主模型失败时自动切到备模型
> （那是第 13 步）。显式传 `model=<llm_fallback>` 时现在就能用对凭据 —— 这样第 13 步接线时只需要改
> 「何时切模型」，不必再碰密钥。

> ⚠️ **不要在进程里额外 `setx OPENAI_API_KEY` / `DEEPSEEK_API_KEY`**。
> litellm 确实会自己去读厂商专属环境变量，但那会造成**第二处真相**：
> 出问题时你无法判断生效的是 `Settings` 注入的那把、还是环境变量里的那把。
> 一律显式传 `api_key=`（`client.py` 里那两处调用就是唯一出口），并把 key 只留在 `.env` 里。
>
> ⚠️ **不要试图用「前缀/别名」复用一把钥匙**（例如同一个 key 填三遍）。
> 三处填同一个值不是节省，而是把「将来要拆开」这件事推迟到故障现场——
> 那时你正在排查可用性事故，没有余力做配置重构。

### 1.2.2 `.env` 里长什么样

```ini
# 主模型
LLM_PRIMARY=deepseek/deepseek-flash
LLM_API_KEY=sk-主模型-xxx

# 降级模型：**独立密钥 + 可选独立端点**
# 留空 = 本步不启用降级（第 13 步才真正使用）；一旦填了模型名，就把对应 key 一起填上
LLM_FALLBACK=
LLM_FALLBACK_API_KEY=
# LLM_FALLBACK_API_BASE=https://api.openai.com/v1   # 仅当备模型走 OpenAI 兼容网关时用

# 向量化（两种后端选一种，见 §7）
EMBEDDING_BACKEND=litellm
EMBEDDING_MODEL=openai/text-embedding-3-small
EMBEDDING_API_KEY=            # 留空 = 复用 LLM_API_KEY；**厂商不同就必须单独填**
EMBEDDING_DIM=0               # >0 = 强校验维度，建议填真值（见 §7.6）
```

三条必须知道的取值规则（都已在 `tests/test_config.py` 里钉住，别再自己发明）：

1. **`llm_primary` 不许为空**。`Settings` 的 `_validate_llm_routing` 会在构造期抛
   `ValueError: llm_primary 不能为空（LLM_PRIMARY 被显式设为空/空白）`。留空**不会**回退到任何默认模型。
2. **`llm_fallback` 非空时必须 ≠ `llm_primary`**，否则抛错：降级会变成「再打一次同一个模型」，
   既没有可用性收益，还让故障时的重试量翻倍。本步留空最省事。
3. **`llm_primary` 只做形状校验，不校验「厂商认不认识这个模型名」**（`settings.py` 里有明确注释：
   那等于替 litellm 维护它自己的模型表）。所以**模型名写错要到第 1 次真实调用才暴露** ——
   这就是 §2 那次探活存在的唯一理由。

> ⚠️ **`get_settings()` 是进程内单例（`lru_cache`）**：改了 `.env` 必须**重启进程**才生效；
> 临时改一次用 `$env:LLM_PRIMARY="..."`（优先级：环境变量 > `.env`，见 [`1.config-guide.md`](1.config-guide.md) §1.1）。
> 若看到 `配置冲突：进程环境变量 LLM_API_KEY 正在覆盖 .env 中的同名值` —— 那是**正常告警**，说明你机器上有同名用户级环境变量。

### 1.3 `.env.example` 要补的键

`.env.example` 里原有 `LLM_PRIMARY` / `LLM_FALLBACK` / `LLM_API_KEY` 三项；本次要补的是：

| 键 | 为什么补 |
|---|---|
| `LLM_FALLBACK_API_KEY` | 降级模型**独立密钥**（§1.2.1）——不补的话，跨厂商降级必然 401 |
| `LLM_FALLBACK_API_BASE` | 可选：备模型走 OpenAI 兼容网关/自建代理时才填（留空即用默认端点） |
| `EMBEDDING_BACKEND` | 选 `litellm`（调 API）或 `local`（本地 sentence-transformers，§7.4） |
| `EMBEDDING_MODEL` | API 后端填 litellm 模型名；本地后端填 HF 仓库名 |
| `EMBEDDING_API_KEY` | 可选：embedding 与主模型**厂商不同**时单独给一把（留空 = 复用 `LLM_API_KEY`） |
| `EMBEDDING_DIM` | 建议填真值：换模型导致维度变化时**直接报错**，而不是静默写废向量库（§7.6） |
| `EMBEDDING_LOCAL_PATH` / `EMBEDDING_DEVICE` | 本地后端的可选项：离线模型目录 / `cpu`⬝`cuda` |

> ⚠️ **这些字段必须显式声明进 `Settings`**，不能靠 `extra="allow"` 兜：
> pydantic 的 extra 只保留「看起来像本模型字段」的键，`getattr(settings, "embedding_dim", 0)`
> 这种写法**键名打错不会报错**，只会静默用默认值。
> 加完字段记得跑 `uv run pytest -q tests/test_config.py`：那批用例对「字段 ↔ 环境变量映射」很敏感，
> 它们绿了才说明新字段被正确装配（别只看 `python -c` 通过）。

## 2. 探活：先证明「key + 模型名」能用（1 次调用，最省钱）

**做这一步的唯一目的**是把两类错误分开：**配置错**（模型名/key/额度）与**代码错**（重试/门面写错）。
跳过它，你会拿着一个「模型名拼错」的 `BadRequestError` 去调试 tenacity，白烧一小时。


> **为什么这里显式写 `num_retries=0`**：litellm 自己**默认就会重试**。探活要的是「第一次到底成不成」，

> `litellm.completion(model="gpt-4o-mini", mock_response="在的", api_key="sk-fake")` 就能离线拿到一个

> 所以「key 能用」这条验收仍然只认上面那次真实调用（§10 证据 4）。

> 🔍 **API 事实核对（本节与 §3、§4、§7 关于 litellm 的说法都据此写）**
>

> | `litellm.exceptions.PermissionDeniedError` | `response` 是**必填**（httpx.Response）；`APIError` 还要 `status_code` |
> | `litellm.exceptions.Timeout` 的继承 | `Timeout → openai.APITimeoutError → openai.APIConnectionError`，**不是** litellm 自己的 `APIConnectionError`（两个不同的类） |

## 3. 写 `app/llm/`（门面 + 错误分类）

### 3.1 目录与文件分工

```
app/llm/
├─ __init__.py    # 唯一对外出口：llm_call / embed / LLMResponse / 异常类
├─ client.py      # LiteLLM 门面 + tenacity 退避重试（本模块**唯一**允许 import litellm 的地方）
└─ errors.py      # 错误分类：可恢复（可重试/可降级） vs 不可恢复（立刻抛）
```

`errors.py` 单独成文件不是洁癖：`5.llm.md` §5 第 2 条把「**只有限流/超时/5xx 才降级**」列为关键技术点，
分类逻辑必须能被**单独单测**（§4.1 的 `test_llm_errors.py` 就是纯逻辑、不起网络）。
第 13 步的熔断器与降级链会复用同一个分类函数 —— 分类一旦有两份，熔断与降级就会打架。

### 3.2 `errors.py`：错误分类表（**这张表就是本模块的核心规则**）

| 异常 | 性质 | 允许重试 | 允许降级（第 13 步） | 理由 |
|---|---|---|---|---|
| `litellm.exceptions.RateLimitError`（429） | 可恢复 | ✅ | ✅ | 限流是「等一会儿就好了」，退避正对它（A1） |
| `litellm.exceptions.Timeout` | 可恢复 | ✅ | ✅ | 超时是网络/负载抖动，重试有效（实测它继承 **openai.APITimeoutError**，**不是** litellm 的同名类） |
| `litellm.exceptions.APIConnectionError` | 可恢复 | ✅ | ✅ | 连不上是瞬时故障（DNS/握手/连接被断） |
| `openai.APITimeoutError` / `openai.APIConnectionError`（**裸 SDK 异常**） | 可恢复 | ✅ | ✅ | 实测必须登记：litellm 的 Timeout 就走这族，漏登记会让瞬时故障被判成永久错误（§10.1 坑 1） |
| `TimeoutError`（内建 / asyncio） | 可恢复 | ✅ | ✅ | 3.12 下 `asyncio.TimeoutError is TimeoutError`；非 litellm 路径的超时靠它兜 |
| `litellm.exceptions.InternalServerError`、`ServiceUnavailableError`（5xx） | 可恢复 | ✅ | ✅ | 厂商侧故障，等一等/换模型有效 |
| `litellm.exceptions.BadRequestError`（400，参数错） | **不可恢复** | ❌ | ❌ | 重试与降级都改不了「请求本身写错了」，只会掩盖 bug |
| `litellm.exceptions.AuthenticationError`（401）/ `PermissionDeniedError`（403） | **不可恢复** | ❌ | ❌ | key 错/无权限：换模型也白搭，**且会放大故障**（把每个副本都打上去） |
| `litellm.exceptions.NotFoundError`（404，模型名错） | **不可恢复** | ❌ | ❌ | 模型名/端点写错，属配置错误，必须立刻炸出来 |
| `litellm.exceptions.ContentPolicyViolationError` | **不可恢复** | ❌ | ❌ | 内容违规：换模型是「绕过风控」，不能做 |
| `litellm.exceptions.ContextWindowExceededError` | **不可恢复** | ❌ | ⚠️ 例外：可考虑换长上下文模型 | 本步不处理；第 13 步若要降级，需显式列入白名单并写清理由 |
| 其它未识别异常（含 `litellm.exceptions.APIError` 这类通用基类） | **保守当成不可恢复** | ❌ | ❌ | 未知错误重试 = 用真实流量赌运气；宁可立刻暴露（实测 litellm 1.103.0 共 30 个异常类，本步只对核心 11 个负责） |

```python
# app/llm/errors.py（骨架；表就是它，别把规则散在 client.py 里）
"""LLM 错误分类：决定「重试」「降级（第 13 步）」还是「立刻抛」。"""

import asyncio

import litellm
import openai  # ⚠️ 实测发现：litellm 的 Timeout 继承的是 **openai 的** APIConnectionError，
              #    不是 litellm 自己的同名类 → **两族都要登记**（§10.1 坑 1）。
              #    直接 import 就必须自己声明依赖：openai 也要进 pyproject.toml。

# 可恢复：限流 / 超时 / 连接失败 / 5xx —— 等一会儿或换个模型真的能好
#
# ⚠️ 别以为「列 litellm 的 APIConnectionError 就覆盖了 Timeout」——实测（1.103.0）为假：
#     issubclass(litellm.exceptions.Timeout, litellm.exceptions.APIConnectionError) → False
#     issubclass(litellm.exceptions.Timeout, openai.APIConnectionError)            → True
# 两族是两个不同的类对象，漏登记 openai 族会让「裸 SDK 异常」被判成永久错误、一次都不重试。
RETRYABLE: tuple[type[BaseException], ...] = (
    litellm.exceptions.RateLimitError,
    litellm.exceptions.Timeout,
    litellm.exceptions.APIConnectionError,
    litellm.exceptions.InternalServerError,
    litellm.exceptions.ServiceUnavailableError,
    openai.APITimeoutError,      # ← 裸 openai 传输异常
    openai.APIConnectionError,   # ← 同上
    asyncio.TimeoutError,        # ← 3.12 下与内建 TimeoutError 是**同一个对象**
)

# 不可恢复：参数错 / 鉴权 / 模型名错 / 内容违规 —— 重试与降级都无意义
NON_RETRYABLE: tuple[type[BaseException], ...] = (
    litellm.exceptions.BadRequestError,
    litellm.exceptions.AuthenticationError,
    litellm.exceptions.PermissionDeniedError,
    litellm.exceptions.NotFoundError,
    litellm.exceptions.ContentPolicyViolationError,
    litellm.exceptions.ContextWindowExceededError,
)


class LLMError(RuntimeError):
    """本模块对外统一的错误类型（调用方只需要 catch 这一个）。"""


class RetryableLLMError(LLMError):
    """可恢复错误：重试若干次后仍失败才抛这个。"""


class PermanentLLMError(LLMError):
    """不可恢复错误：**第一次就抛**，不做任何重试。"""


def is_retryable(exc: BaseException) -> bool:
    """保守判定：只有明确列在 RETRYABLE 里的才算可恢复。

    ⚠️ 返回 False 的两种情形要分清：
      ① 明确列在 NON_RETRYABLE 里（400/401/403/404/内容违规）；
      ② **没见过的异常**（如 KeyError/TypeError）—— 同样不重试。
    用「白名单」而不是「黑名单」，是因为漏判一个可恢复错误只损失一次重试机会，
    而误判一个不可恢复错误会变成「拿真实流量反复撞墙」，后者更贵。
    """
    if isinstance(exc, NON_RETRYABLE):
        return False
    return isinstance(exc, RETRYABLE)


def is_permanent(exc: BaseException) -> bool:
    return isinstance(exc, NON_RETRYABLE)
```

### 3.3 `client.py`：门面 + 退避重试（**唯一允许 import litellm 的文件**）

```python
# app/llm/client.py（骨架；关键是「唯一的 litellm 出口 + 显式 num_retries=0 + 退避 jitter」）
"""LLM 统一门面：所有 Agent 调模型都必须走这里（5.llm.md 第 1 节的硬约束）。"""

import logging
import random
import time
from dataclasses import dataclass
from typing import Any

import litellm
from tenacity import (
    AsyncRetrying,
    RetryCallState,
    retry_if_exception,
    stop_after_attempt,
)

from app.config import get_settings
from app.llm.errors import PermanentLLMError, RetryableLLMError, is_retryable

logger = logging.getLogger(__name__)

# 退避上限：单次等待最多 20s（避免第 5、6 次重试把请求拖到分钟级）
MAX_BACKOFF_SECONDS = 20.0
# 单次调用超时：交给 litellm 的 per-request timeout（不用全局 socket 超时）
DEFAULT_TIMEOUT = 30.0
# 默认重试次数（**总尝试次数 = 1 + max_retries**）
DEFAULT_MAX_RETRIES = 3


def _wait(state: RetryCallState) -> float:
    """指数退避 + jitter：`min(2^n, cap)` 秒再乘一个随机系数。

    为什么必须带 jitter（5.llm.md 第 5 节）：无抖动时所有失败请求会在**同一时刻**重试，
    多副本/多 Agent 一起撞上去形成「惊群」，把刚缓过来的模型再打趴一次。
    乘 `random.uniform(0.5, 1.0)` 保留退避量级又错开时刻；别用 `random()`（可能退避到 0，等于没退避）。
    """
    attempt = state.attempt_number
    return min(2.0**attempt, MAX_BACKOFF_SECONDS) * random.uniform(0.5, 1.0)


def make_retry_logger(max_retries: int):
    """造一个 `before_sleep` 回调：把「第几次 / 共几次 / 什么错」打成一条日志。

    为什么用闭包而不是在回调里问 tenacity：`RetryCallState` 只有
    `attempt_number` / `outcome` / `seconds_since_start` 这类很少的字段，
    **没有**「最多几次」（别凭记忆写 `state.retry_state_max_attempts(...)`，那不存在）；
    总次数在构造策略时就知道，闭包捕获最省事。
    """
    max_attempts = max_retries + 1

    def _log_retry(state: RetryCallState) -> None:
        exc = state.outcome.exception() if state.outcome else None
        logger.warning(
            "LLM 调用失败，准备退避重试：attempt=%d/%d error=%s: %s",
            state.attempt_number,
            max_attempts,
            type(exc).__name__,
            exc,
        )

    return _log_retry


class _RetryPolicy(AsyncRetrying):
    """一份退避策略，llm_call / embed 共用（两处各写一份必然漂移）。"""

    def __init__(self, max_retries: int) -> None:
        super().__init__(
            stop=stop_after_attempt(max_retries + 1),      # 1 次首发 + max_retries 次重试
            wait=_wait,
            retry=retry_if_exception(is_retryable),        # 不可恢复错误**不进**退避
            before_sleep=make_retry_logger(max_retries),
            reraise=True,                                  # 重试用尽后抛**原始**异常（不被 RetryError 包住）
        )


@dataclass(frozen=True)
class LLMResponse:
    """结构化结果：第 11/13 步的 token/成本计量直接吃这些字段，调用方不必再解 litellm 对象。"""

    content: str
    model: str
    prompt_tokens: int
    completion_tokens: int
    total_tokens: int
    cost_usd: float | None
    latency_ms: int


def _settings():
    return get_settings()


async def llm_call(
    messages: list[dict[str, Any]],
    model: str | None = None,
    *,
    max_retries: int = DEFAULT_MAX_RETRIES,
    timeout: float = DEFAULT_TIMEOUT,
    **kwargs: Any,
) -> LLMResponse:
    """调一次 LLM，带指数退避重试。

    参数（与 5.llm.md 第 2 节的接口一致）：
      messages     OpenAI 格式的消息列表
      model        主模型；None = 用 config 的 llm_primary
      max_retries  重试次数（总尝试 = 1 + max_retries）
      timeout      单次请求超时（秒）；**超时错误本身也是可重试的**
      **kwargs     透传给 litellm（temperature / max_tokens / …）

    注意：**fallback_models 参数属于第 13 步**，本次刻意不接受 —— 传进来会被静默忽略，
    那是比「没有这个功能」更糟的行为（调用方以为有降级，其实没有）。
    """
    settings = _settings()
    used_model = model or settings.llm_primary

    # ⚠️ `num_retries` 不在 acompletion 的**具名参数**里（它是 **kwargs 透传）；
    #    litellm 会自己消费它。所以「写错名字」不会有任何报错 —— 只会静默地不生效。
    #    这也是为什么 §4.2 必须有那条 `calls["n"] == 3` 的断言：参数名写错时它是唯一的哨兵。
    try:
        async for attempt in _RetryPolicy(max_retries):
            with attempt:
                t0 = time.perf_counter()
                response = await litellm.acompletion(
                    model=used_model,
                    messages=messages,
                    api_key=settings.llm_api_key.get_secret_value(),   # 唯一密钥入口（§1.2）
                    timeout=timeout,
                    num_retries=0,      # ⚠️ 必须显式关掉 litellm 自带重试，见 §5.1
                    **kwargs,
                )
                latency_ms = int((time.perf_counter() - t0) * 1000)
                return _to_response(response, latency_ms)
    except asyncio.CancelledError:
        raise                       # 取消不该被翻译成 LLM 错误（上层要能区分「被取消」与「模型不可用」）
    except LLMError:
        # ⚠️ 已经是我们自己的对外异常（例如 embed 抛的「条数不一致」）→ **原样抛出**。
        #    漏掉这一条会把它二次包装成 RetryableLLMError，于是「不可恢复」被误报成「稍后可重试」，
        #    第 12 步的队列会一直重排它（实测踩过，见 §10.1 坑 5）。
        raise
    except Exception as exc:
        # ⚠️ 这段翻译是**必须**的：策略里的 reraise=True 会把 litellm 原始异常直接抛出来，
        #    而调用方（第 7/12 步）需要能区分「可以稍后重试」与「别重试了」——
        #    见 §5.4 的对照表。少了这一段，retryable/permanent 的区分就形同虚设。
        raise _translate(exc) from exc


def _translate(exc: Exception) -> LLMError:
    """把 litellm 异常翻译成本模块的两种对外错误（判据就是 errors.py 的分类表）。"""
    if is_permanent(exc):
        return PermanentLLMError(f"LLM 不可恢复错误：{type(exc).__name__}: {exc}")
    return RetryableLLMError(f"LLM 重试 {DEFAULT_MAX_RETRIES} 次后仍失败：{type(exc).__name__}: {exc}")
```

> ⚠️ **`before_sleep` 回调里别凭记忆写 tenacity 的 API**：`RetryCallState` 只有
> `attempt_number` / `outcome` / `seconds_since_start` 等很少的字段，**没有**「最多几次」。
> 上面用 `make_retry_logger(max_retries)` 闭包捕获总次数，就是为了避开这个坑 ——
> 写错的代价是「第一次失败时」才炸，而那时候你正忙着排查真正的故障。

`_to_response` 把 litellm 响应翻译成我们自己的结构（第 13 步接 Langfuse 时只改这一处）：

```python
def _to_response(response: Any, latency_ms: int) -> LLMResponse:
    usage = getattr(response, "usage", None)
    try:
        # litellm 内置成本表；算不出来（如本地模型）时返回 0.0/抛错都见过 → 用 None 表示「未知」
        cost = float(litellm.completion_cost(completion_response=response))
    except Exception:  # noqa: BLE001 - 计费失败绝不能影响业务调用
        cost = None
    return LLMResponse(
        content=response.choices[0].message.content or "",
        model=getattr(response, "model", "") or "",
        prompt_tokens=int(getattr(usage, "prompt_tokens", 0) or 0),
        completion_tokens=int(getattr(usage, "completion_tokens", 0) or 0),
        total_tokens=int(getattr(usage, "total_tokens", 0) or 0),
        cost_usd=cost,
        latency_ms=latency_ms,
    )
```

### 3.4 为什么返回 `LLMResponse` 而不是原样的 litellm 对象

| 做法 | 后果 |
|---|---|
| 直接返回 `ModelResponse` | 调用方要自己 `response.usage.prompt_tokens`、自己算 cost → **每个 Agent 各写一份**，第 11/13 步的「统一计费」无处落脚 |
| 返回自定义 `LLMResponse` | 计费口径只有一处；换 provider / 升级 litellm 时只改 `_to_response`；测试里断言也简单（不用构造 litellm 内部对象） |

代价：**丢掉了 litellm 的部分透传信息**（如 `response.id`、原始 `raw_response`）。
第 13 步接 Langfuse 若需要 trace id，就在 `LLMResponse` 上加字段 —— 依然只改 `_to_response` 一处。

### 4.2 造 429/超时：**假异常注入 + litellm mock 响应**（不引入任何测试依赖）

两种手段配合用，各有不可替代的地方：

| 手段 | 用来做什么 | 为什么不能只用另一种 |
|---|---|---|
| `monkeypatch.setattr(llm_client.litellm, "acompletion", 假函数)` + **手工 `raise` 一个真实异常类** | 制造**确定次数**的失败序列（「前两次 429、第三次成功」） | litellm 的 `mock_response` **没有**「第 N 次才失败」的能力 |
| `litellm.completion(..., mock_response="文本")` | 造一个**形状真实**的成功响应（`choices`/`usage`/`model` 都是真的） | 手搓 `SimpleNamespace(choices=[...])` 会在 litellm 改内部结构时**静默变假** |
| `mock_response=<异常实例>`（实测可用） | 走**真实 litellm 调用路径**抛指定异常（含真解析） | 它进不了「次数序列」 |

> 三者都**不发网络请求**。所以「拔网线也全绿」这条 CI 判据照旧成立。
> 本步**不引入** `respx` / `pytest-httpserver`（少一个依赖少一处漂移）；
> 真要验 TLS/代理/真实超时，见 §4.4。

> ⚠️ **单测里关退避要替换策略类，不要 monkeypatch `_wait`**：`_RetryPolicy.__init__` 里写的是
> `wait=_wait`（捕获的是**函数对象**），替换模块属性改不到它 —— 你以为关掉了，用例却在真等 2/4/8 秒
> （症状：整个测试套件莫名其妙变慢）。下面的 `FastRetryPolicy` 就是为此写的。

```python
# tests/test_llm_client_retry.py（骨架）
"""重试行为测试：不联网、不需要真 key。"""
import asyncio

import litellm
import pytest
from tenacity import AsyncRetrying, retry_if_exception, stop_after_attempt

from app.llm import client as llm_client
from app.llm.errors import PermanentLLMError, RetryableLLMError, is_retryable

# ⚠️ 让退避在单测里**不等**的真实做法：替换掉 client.py 里的**策略类**，不是替换 _wait。
#    为什么不能 monkeypatch `llm_client._wait`：`_RetryPolicy.__init__` 里写的是
#    `wait=_wait`（模块级函数对象），属性替换改不到已经捕获的那个引用 ——
#    于是你以为退避被关掉了，其实用例真的在等 2/4/8 秒（表现为「测试莫名其妙很慢」）。
#    换成策略类还有一个好处：`make_retry_logger`（证据用）与 `_wait`（真实退避）
#    在单测里一起被绕过，语义清楚：**这条用例测的是次数，不是时长**。
class FastRetryPolicy(AsyncRetrying):
    def __init__(self, max_retries: int) -> None:
        super().__init__(
            stop=stop_after_attempt(max_retries + 1),
            wait=lambda state: 0,
            retry=retry_if_exception(is_retryable),
            reraise=True,
        )


@pytest.fixture
def fake_settings(monkeypatch):
    """钉住配置：模型名与 key 都用假值，绝不读你本机 .env。"""
    monkeypatch.setenv("LLM_PRIMARY", "gpt-4o-mini")
    monkeypatch.setenv("LLM_API_KEY", "sk-fake-for-test")
    monkeypatch.setenv("LLM_FALLBACK", "")
    from app.config import get_settings
    get_settings.cache_clear()
    yield
    get_settings.cache_clear()


def test_retry_on_429_then_success(monkeypatch, fake_settings):
    """前两次 429、第三次成功 → 最终成功，且**恰好**重试了 2 次（5.llm.md §7 第 1 条）。"""
    calls = {"n": 0}

    async def fake_acompletion(**kwargs):
        calls["n"] += 1
        if calls["n"] <= 2:
            raise litellm.exceptions.RateLimitError(
                message="rate limited", llm_provider="openai", model=kwargs.get("model")
            )
        # 用 litellm 自己的 mock 造一个**形状真实**的响应（比手搓 SimpleNamespace 稳）
        return litellm.completion(
            model="gpt-4o-mini", messages=[{"role": "user", "content": "hi"}],
            mock_response="好的", api_key="sk-fake",

    assert calls["n"] == 3, f"期望 3 次尝试（1 首发 + 2 重试），实际 {calls['n']}"


def test_retry_exhausted_raises_retryable(monkeypatch, fake_settings):
    """**一直** 429 → 重试用尽后抛 `RetryableLLMError`（调用方据此「稍后再试」，见 §5.4）。"""
    calls = {"n": 0}

    async def always_429(**kwargs):
        calls["n"] += 1
        raise litellm.exceptions.RateLimitError(
```

```python
def test_backoff_is_exponential_and_jittered(monkeypatch):
    """退避量级：第 n 次约 2^n 秒，且带抖动（两次取值不应完全相同）。

    ⚠️ 断言量级与单调性，**不要断言精确秒数** —— jitter 的存在就是为了让它不是一个定值。
    """
    waits = []
    for n in range(1, 5):
        class S:                       # 只喂 _wait 需要的字段
            attempt_number = n
        samples = [llm_client._wait(S()) for _ in range(20)]
        assert min(samples) >= min(2.0**n, llm_client.MAX_BACKOFF_SECONDS) * 0.5 - 1e-6
        assert max(samples) <= min(2.0**n, llm_client.MAX_BACKOFF_SECONDS) + 1e-6
        assert len(set(samples)) > 1, "没有抖动 → 多副本会同时重试（惊群）"
        waits.append(min(samples))
    assert waits == sorted(waits), "退避应随尝试次数单调不减"
```

```python
def test_max_backoff_is_capped():
    """第 10 次重试不应等 1024 秒 —— 上限 MAX_BACKOFF_SECONDS 必须生效。"""
    class S:
        attempt_number = 10
    assert llm_client._wait(S()) <= llm_client.MAX_BACKOFF_SECONDS
```

> ℹ️ 这两条 `_wait` 用例**不 monkeypatch 任何东西** —— 它们测的就是真实的退避函数本身
> （量级、抖动、上限）。线上真正的等待时刻由 `_RetryPolicy` 消费这个函数的返回值，
> 所以「值对了」等价于「等对了」；真正掐表反而更不可靠（见 §4.3）。
>
> ⚠️ 上面 `class S:` 这种「只有一个属性的假对象」是刻意的：`_wait()` 只读 `attempt_number`，
> 给它真 `RetryCallState` 得先造 outcome/异常，纯属自找麻烦。**但也因此要注意**：
> 将来 `_wait` 若改用别的字段，这些用例不会报错，只会静默地测一个假对象 ——
> 所以 `_wait` 的字段用法要保持在「只读 attempt_number」这一条上。

### 4.3 退避「真的等了吗」——看日志与回调，别掐表

| 做法 | 靠不靠谱 |
|---|---|
| 用 `time.perf_counter()` 掐表断言「等了 ≥2 秒」 | ❌ 脆：CI 机器负载、`min(2^n, cap)` 与 jitter 叠加，容易假红；而且慢 |
| **断言 `_wait()` 的返回值 + `before_sleep` 被调用次数** | ✅ 推荐：快、稳、语义清晰（§4.2 用的就是它） |
| 跑一次真 429 观察日志 | ✅ 作为**验收证据**（§10 证据 2/3），不做断言 |

真实的「退避生效」证据长这样（**这是我们要在 §10 回填的东西**）：

```powershell
# 跑那条 429 用例，**保留真实退避与真实 before_sleep 日志**（不要替换成 FastRetryPolicy）
uv run pytest -q tests/test_llm_client_retry.py -k "429" -s -o log_cli=true --log-cli-level=WARNING
# 期望（证据 2）：
#   ① 日志出现 `LLM 调用失败，准备退避重试：attempt=1/3 ... RateLimitError` 与 `attempt=2/3 ...`
#   ② 这条用例的耗时明显高于同文件其它用例（它真的等了约 1+3 秒）—— 「等过」这件事的旁证
#
# ⚠️ 两种「看不到日志」的原因要分清：
#   ① 你把 `_RetryPolicy` 换成了 `FastRetryPolicy`（wait=0）→ 次数对、日志对，但没有真实等待；
#      这是**单测**该有的样子；要拿「真的等了」的证据，就得跑一条不替换策略的用例；
#   ② `--log-cli-level=WARNING` 没生效（logger 被别处配置过）→ 用 `-s` + 看 stderr，
#      或临时在 `make_retry_logger` 里加一行 `print(...)`（别提交）。
```

### 4.4 可选：想连「真 HTTP」怎么办（本步不做，留个门）

`mock_response` 覆盖不了的东西有：**TLS/代理/真实超时**（`timeout=` 真的到点抛 `Timeout`）。
要验这一层，有两个不引新依赖的办法：

1. **指到本地假端点**：`litellm.acompletion(model="openai/任意名", api_base="http://127.0.0.1:8009/v1", ...)`，
   再用 `uv run python -m http.server` 级别的假服务返回固定 JSON 或 429 —— 能验「HTTP 层错误映射」；
2. **指到真实厂商但只发 1 次**（§2 的探活），超时用 `timeout=0.001` 人为触发（⚠️ 会真实产生一次请求记录）。

> 这两条都**不进 CI**（一个要起服务、一个要 key）。第 6 步（tools）/第 14 步（eval）如果要更系统的
> HTTP 级 mock，那时再统一引 `respx`，别在本步先引一个只用一次的依赖。

## 5. 重试设计：四条必须理解的规则

### 5.1 `num_retries=0`：**不要两层重试**

litellm 自带 `num_retries`（默认非 0）。如果门面不显式关掉它，一次业务调用会变成：

```
业务层 max_retries=3  ×  litellm 内部重试 N  →  实际请求数 = 4 × (1+N)
```

后果：① 退避时间完全失控（你以为最多等 7 秒，实际等了一分钟）；② 429 时**主动加倍**限流压力，
正好制造出 `5.llm.md` §5 说的「惊群」；③ 你在日志里数到的重试次数对不上代码里的参数，
排查时先怀疑自己写错了。

**结论**：`num_retries=0` 是**必须**的，且要有测试钉住 —— 见 §4.2 的断言第 3 条（`calls["n"] == 3`）。
一旦有人删掉这个参数，`calls["n"]` 会变成 6/12 之类，测试立刻红。

> ⚠️ **实测（litellm 1.103.0）**：`num_retries` / `mock_response` / `max_retries` / `fallbacks`
> 都**不是** `litellm.acompletion()` 的具名参数，它们走 `**kwargs` 透传（实测 `acompletion(..., num_retries=0)`
> 正常接受并生效）。这是本手册里最阴的一个坑：**参数名写错（如 `max_retries=`）不会报错**，
> litellm 只会当成「你不想要重试控制」，于是两层重试照旧发生，而你在代码里明明写着「已关闭」。
> 唯一的哨兵就是 §4.2 那条计数断言 —— 所以它看起来只是「数了几次」，实际守的是这条。

### 5.2 只有「可恢复错误」才重试（§3.2 的表就是全部规则）

直觉上「多试几次总没坏处」，实际上：

- 对 400 重试：**只是把同一个错误犯 4 次**，用户多等 3 个退避周期才拿到同一个报错；
- 对 401 重试：key 错了重试 100 次也还是错，**且每个副本都在打厂商的鉴权接口**；
- 对内容违规重试：等于在「换个姿势绕过风控」，是安全红线（`4.security.md` 的 guardrail 是同一条线）。

`is_retryable()` 用**白名单**（只认列出来的可恢复异常）而不是黑名单，
理由写在 `errors.py` 的 docstring 里：漏判只损失一次重试机会，误判要拿真实流量撞墙。

### 5.3 退避 = `min(2^n, cap)` × jitter

- `2^n`：失败往往意味着对端过载，**立刻重试只会加重过载**；指数增长给对端恢复时间（A1）。
- `cap`（本手册取 20s）：不设上限时第 10 次要等 17 分钟，「重试」就变成了「挂死」。
- `jitter`：**没有它，所有副本会在同一毫秒一起重试**。这就是「惊群」的成因，
  也是 `5.llm.md` §5 第 1 条要你「懂为什么」的那一点。
- 用 `uniform(0.5, 1.0)` 而不是 `random()`：后者可能退避到接近 0，等于退避没生效。

### 5.4 重试到底该抛什么

`reraise=True`：重试用尽后抛**原始异常**（而不是 tenacity 的 `RetryError` 包一层）。
但我们又做了一层翻译：对外抛 `LLMError` 的两个子类，让调用方只需要 `except LLMError`。
两种错误必须能被**区分**，因为调用方的处置不同：

| 对外异常 | 调用方该做什么 | 典型场景 |
|---|---|---|
| `PermanentLLMError` | **不要重试**、不要重排队列；报错给用户（或走人工兜底） | 参数错、key 错、模型名错 |
| `RetryableLLMError` | 可以放进队列稍后重试（第 12 步 queue）、可以回答「稍后再试」 | 厂商持续 429/5xx/超时 |

> ⚠️ **不要把 `RetryableLLMError` 当成「任务失败」直接丢进死信队列**：它更像「暂时不可用」，
> 第 12 步的队列要按 `RetryableLLMError` 做带延迟的重排，否则 429 一多就批量进死信。
> 这条现在写下来，是为了那时不用回头改门面的异常类型。

## 7. `embed()`：embedding 也走同一个门面（API 或**本地**两种后端）

### 7.1 为什么 embedding 也必须在门面里

因为 embedding **可能花钱**（API 后端按 token 计费）、**一定是延迟的一部分**：
第 10 步 rag 要检索、第 13 步 cache 要判相似，两处都会高频调它。
如果它们各自 `openai.embeddings.create(...)`，就会出现：改不了超时、加不了重试、
计不了费、也没有「切换 embedding 模型/后端」的单一开关。RAG 效果差时你会找不到是哪个环节。

### 7.2 两种后端：`litellm`（默认）与 `local`

由 `EMBEDDING_BACKEND` 选择。**接口完全一样**（`await embed(texts) -> list[list[float]]`），
所以调用方（rag / cache）不需要知道用的是哪种 —— 这正是把它放进同一个门面的价值。

| | `EMBEDDING_BACKEND=litellm`（默认） | `EMBEDDING_BACKEND=local` |
|---|---|---|
| 实现 | `litellm.aembedding` | `sentence_transformers.SentenceTransformer` |
| 模型名 | litellm 模型名，**建议带前缀**（如 `openai/text-embedding-3-small`） | HuggingFace 仓库名或本地目录（如 `BAAI/bge-m3`、`./models/bge-m3`） |
| 密钥 | `EMBEDDING_API_KEY`，留空则复用 `LLM_API_KEY` | **不需要**（没有密钥、没有配额） |
| 成本 | 按 token 计费 | 0（电费/机器） |
| 延迟 | 网络往返（几十~几百 ms） | 本机推理（CPU 上小模型约几 ms/条；首次加载慢） |
| 隐私 | 文本**出网**到第三方 | 文本**不出网**（合规/离线场景的正解） |
| 依赖 | 已有（litellm） | **可选依赖**：`sentence-transformers` + `torch`（约 2 GB，见 §7.4） |
| 首次运行 | 无额外准备 | **要下模型权重**（几百 MB~2 GB）→ 离线环境要预置（§7.5） |
| 失败模式 | 429/超时/鉴权（可重试/可降级） | 权重下载失败、显存/内存不足、维度不符（**多为不可恢复**，别指望重试） |

**怎么选**（判据写清楚，别凭感觉）：

- 生产/演示默认用 **API 后端**：不用在机器上装 torch、向量质量由厂商保证、扩容简单；
- 选 **本地后端** 的正当理由有三个：① 文本不允许出网（合规）；② 完全离线环境；
  ③ 成本敏感且调用量极大（省掉按 token 计费）；④ 开发机上不想为每次调试付费。
- **不要**因为「本地免费」就默认切本地：它会带来权重下载、维度变化、设备/内存这些**运维面**的新问题，
  而这些问题在 API 后端根本不存在。收益要能覆盖这些成本再切。

### 7.3 接口

```python
# app/llm/client.py（追加；两种后端共用一个签名）
async def embed(
    texts: Sequence[str],
    model: str | None = None,          # None = 读 config 的 embedding_model
    *,
    max_retries: int = DEFAULT_MAX_RETRIES,
    timeout: float = DEFAULT_TIMEOUT,  # local 后端不用它，保留是为了签名一致

      - "litellm"：litellm.aembedding（§7.3.1）
      - "local"  ：sentence-transformers，**同步推理必须丢进线程**（§7.3.2）

    ⚠️ **必须保序**：rag 的「检索结果 ↔ 向量」对齐全靠顺序。
    litellm 的响应里 `data` 带 `index` 字段，**要按 index 排序**而不是假定返回顺序
    （批量并发时顺序不保证 —— 这是最隐蔽的一类 bug，症状是「偶尔答非所问」）。
    本地后端天然保序（按输入顺序返回 ndarray），**但仍然要校验条数**，理由见 §7.6。
    """
    ...
```

`embed()` 与 `llm_call()` 的差别（容易写错的地方）：

| 维度 | `llm_call` | `embed`（litellm 后端） | `embed`（local 后端） |
|---|---|---|---|
| 调用 | `litellm.acompletion` | `litellm.aembedding` | `SentenceTransformer.encode`（**同步**） |
| 响应结构 | `choices[0].message.content` | `response.data[i]["embedding"]`（**按 `data[i]["index"]` 排序**） | `ndarray` (n, dim)，行序 = 入参序 |
| 用量 | `usage.prompt/completion/total_tokens` | 通常只有 `usage.prompt_tokens`/`total_tokens`（**没有 completion**） | 无（不产生 token 计费） |
| 超时/重试 | 同一套策略 | 同一套（`api_base`/`timeout` 同样走 `**kwargs` 透传） | 同一套策略外壳；但「权重下载失败」这类错误重试也没用 |

#### 7.3.1 litellm 后端的两个实测坑

1. `input=['a','b']` + `mock_response=['x','y']` **只返回 1 个 data 项**（§10.1 坑 4）；
2. 配 `model="bge-m3"` 这类非 litellm 认识的模型名**会直接抛错**（mock 不生效，litellm 去解析 provider）。
   → 所以 API 后端的模型名要么能被 litellm 识别，要么显式带前缀/`api_base`。

#### 7.3.2 local 后端：**同步推理必须丢进线程**（本选项的头号坑）

`SentenceTransformer.encode()` 是**同步、CPU 密集**的。在 async 门面里直接调用它会
**阻塞整个事件循环** —— 第 9 步的 FastAPI 会因此整站卡住（不只这一个请求），
而且症状是「并发一上来所有接口都变慢」，很容易误判成数据库或队列问题。

```python
# app/llm/client.py（local 后端要点）
import asyncio
import threading

from app.llm.errors import PermanentLLMError

_local_model = None
_local_model_name: str | None = None
_local_lock = threading.Lock()   # encode 不是线程安全的，同一实例要串行


def _load_local_model(model_name: str, device: str | None = None):
    """懒加载 + 进程内单例。加载很慢（几百 MB~2 GB），绝不能每个请求加载一次。"""
    global _local_model, _local_model_name
    from sentence_transformers import SentenceTransformer  # ⚠️ 可选依赖：别在模块顶层 import

    with _local_lock:
        if _local_model is None or _local_model_name != model_name:
            _local_model = SentenceTransformer(model_name, device=device or None)
            _local_model_name = model_name
        return _local_model


async def _embed_local(items: list[str], model_name: str) -> list[list[float]]:
    def _run() -> list[list[float]]:
        model = _load_local_model(model_name)
        with _local_lock:   # 同一实例串行 encode（并发调用会互相踩）
            vectors = model.encode(items, normalize_embeddings=True, convert_to_numpy=True)
        return [list(map(float, row)) for row in vectors]

    # ⚠️ 关键：to_thread 才不会阻塞事件循环（这是本后端最容易被漏掉的一行）
    return await asyncio.to_thread(_run)
```

四条必须遵守的细节：

1. **`sentence_transformers` 要在函数内 import**：它是可选依赖，顶层 import 会让
   「没装 torch 的环境」连 `import app.llm` 都失败 —— 那时连 API 后端都用不了了。
   同理，`EMBEDDING_BACKEND=local` 而依赖没装时，要给一条**能照着修**的报错
   （`PermanentLLMError("本地 embedding 需要 sentence-transformers：uv sync --extra local")`），
   而不是把 `ModuleNotFoundError` 原样抛给用户。
2. **`normalize_embeddings=True` 要跟着检索方式走**：归一化后用**余弦相似度**
   （pgvector 的 `<=>` 距离）与不归一化时的点积/欧氏距离**不等价**。
   `13.cache.md` 的相似度阈值和 `10.rag.md` 的检索算子必须与此一致，否则「阈值调不出来」。
3. **encode 要串行**：`SentenceTransformer` 实例不是线程安全的；`to_thread` 允许多个线程同时进来，
   所以需要那把锁（或者按模型实例建连接池式的队列）。锁会让并发退化成串行 ——
   吞吐不够时正确做法是**多进程**（uvicorn worker 各自一份模型）或换 GPU，而不是拆掉锁。
4. **`EMBEDDING_DEVICE`**：默认让 sentence-transformers 自己挑；显式写 `cpu` 最稳
   （避免在没装 CUDA 的机器上尝试 GPU 而报一堆 warning）。

### 7.5 本地后端的运维面（离线、缓存、许可）

| 事项 | 怎么做 |
|---|---|
| 首次运行会下权重 | 从 HuggingFace 拉取（几百 MB~2 GB）。**这是第一次调用时才发生**，会让首个请求超时 → 建议在启动预热阶段先 encode 一条短文本 |
| 缓存位置 | 默认 `~/.cache/huggingface`（Windows：`%USERPROFILE%\.cache\huggingface`）；用 `HF_HOME` 改到磁盘宽裕的位置 |
| **完全离线** | ① 先在能上网的机器下好 → 拷过来，`EMBEDDING_LOCAL_PATH=/path/to/model`；② 或设 `HF_HUB_OFFLINE=1` 强制离线（下不到就明确报错，而不是静默吊死在下载上） |
| 许可 | 模型各自有许可证（bge 系多为 MIT/Apache-2.0，**逐模型确认**）；商用前把模型卡里的 license 看清楚 |
| 资源 | CPU 上 `bge-m3` 这类大模型很慢；生产建议小模型或 GPU。**别在 worker 里加载多个大模型实例**（内存会按 worker 数翻倍） |
| 与 API 后端的等价性 | 换后端**必然换向量空间**：旧向量全部作废（见 §7.6），不存在「先 API 后本地」混着用的中间态 |

### 7.6 维度守卫：换模型/换后端必须**报错**，不能静默

这是本选项**最容易造成不可逆事故**的一点。`embedding_model` 一换，向量维度就变
（`text-embedding-3-small` = 1536、`bge-m3` = 1024、`bge-large-zh` = 1024 ……），
而后端一换（API ↔ 本地）**向量空间完全不相容**。后果分两种，都很糟：

- **维度不一致**：写库直接失败（pgvector 的 `vector(n)` 列类型固定）——还算好的，至少响；
- **维度恰好相同但空间不同**：**静默错**。检索结果看似正常，实际全是乱序的「不相干文档」，
  评测分数掉下来你会先去怀疑 prompt，几天后才想到是 embedding 换了。

所以 `embed()` 出口加一道守卫（`EMBEDDING_DIM=0` 表示不校验，但**生产建议填真值**）：

```python
# app/llm/client.py（embed 返回前）
dim = len(vectors[0]) if vectors else 0
if settings.embedding_dim and dim != settings.embedding_dim:
    raise PermanentLLMError(
        f"embedding 维度不符：期望 {settings.embedding_dim}，实际 {dim}"
        f"（model={used_model}）。换模型/换后端必须同步："
        "① 改 EMBEDDING_DIM；② 改 10.rag.md 的 vector(n) 列并重建索引；③ 重灌全部向量。"
    )
```

维度真值怎么拿（**别凭记忆写**）：

```powershell
# API 后端：真调一次，看真实维度
uv run python -c "import asyncio; from app.llm import embed; print('dim =', len(asyncio.run(embed(['退货政策是什么']))[0]))"
# 本地后端（离线也算得出来）：直接问模型对象
uv run python -c "from sentence_transformers import SentenceTransformer; m=SentenceTransformer('BAAI/bge-m3'); print('dim =', m.get_sentence_embedding_dimension())"
```

> ⚠️ 第 10 步 rag 建表时的顺序必须是：**先定 backend + model + dim**，再写迁移里的 `vector(n)`。
> 反过来的话，你会在「表已建好、维度变了」的处境里做数据迁移（还要重建 IVFFlat/HNSW 索引）。
> 交接给第 10 步的清单：`backend / model / dim / 是否归一化 / 是否需要 query·passage 前缀`。

### 7.7 `BAAI/bge-*` 系模型要区分「query 前缀」与「passage 前缀」

中文检索常用 bge 系，它们**要求**给查询加指令前缀，否则召回明显变差（属于「模型约定」，不是可选项）：

```python
QUERY_PREFIX = "为这个句子生成表示以用于检索相关文章："   # bge-large-zh 系
# 入库的 chunk 不加前缀；查询要加
```

⚠️ **前缀属于调用方语义，不属于 `embed()`**：门面只负责「把给它的文本向量化」，
不该猜哪条是查询、哪条是文档。所以：

- `10.rag.md` 的 ingest 路径：直接 `await embed(chunks)`；
- 查询路径：`await embed([QUERY_PREFIX + question])`；

| 第 13 步要做的事 | 本步已经留好的接缝 | 不要提前做的理由 |
|---|---|---|
| fallback 链（主→备→小） | ① `llm_call` 的签名里**刻意没有** `fallback_models`；② **降级模型的独立密钥字段已就位**（`llm_fallback_api_key` / `llm_fallback_api_base`，§1.2.1）；③ 凭据解析函数 `_resolve_credentials(model, settings)` 的写法与理由已写好 | 有了降级，「重试是否生效」会被降级掩盖（看起来成功了，其实是换了模型） |

### 8.1 降级接线时最容易错的一步：**凭据必须在「模型定了之后」解析**

第 13 步加 fallback 时，`used_model` 会从主模型切成备模型。如果密钥是在**函数入口**解析一次
（拿 `settings.llm_api_key` 就往下传），降级那一刻用的仍是主模型的钥匙 ——

```
主模型 deepseek/*  +  备模型 gpt-4o  +  只配了 LLM_API_KEY（DeepSeek 的）
        ↓ 主模型 429，触发降级
gpt-4o 拿 DeepSeek 的 key 去认证 → 401 AuthenticationError
        ↓ errors.py 把 401 判为**不可恢复** → 不重试、也不再降级
用户看到：直接报错（可用性比不降级还差，因为多花了一次调用与一次退避）
```

所以接线时**必须**用 §1.2.1 那个 `_resolve_credentials(model, settings)`，
把「取哪把钥匙」绑定到「最终要打哪个模型」，并补一条单测：
**给 fallback 模型传入了 fallback 的 key**（断言 `kwargs["api_key"]` 与 `kwargs["api_base"]`）。
这条断言是第 13 步「自动降级」能真正工作的**前提**，不是可选项。

`5.llm.md` 第 8 节的四条验收里，**本步只认前两条**（自动降级那条属第 13 步，
「token/成本汇入 Langfuse」也属第 13 步）—— 回填证据时**别把没做的勾上**。

## 10.1 实现期间撞到的十个新坑（实测，含修法）

这些是「照着手册做」时真正卡住过的地方（有的已修在仓库里，有的是认知修正）。
新环境复现时可以直接跳过；**其中第 3 条不是本模块的锅，但值得全项目知道**。

### 坑 1：litellm 的 `Timeout` 继承的是 **openai 的** `APIConnectionError`，不是 litellm 的同名类

```python
issubclass(litellm.exceptions.Timeout, litellm.exceptions.APIConnectionError)   # 实测 False
issubclass(litellm.exceptions.Timeout, openai.APIConnectionError)              # 实测 True
```

两族是**两个不同的类对象**（名字一样，模块不同）。所以 `errors.RETRYABLE` 里
**必须同时登记 litellm 族与 openai 族**：只登记 litellm 族时，一个从 SDK 直接冒出来的
连接/超时错误会被判成「永久错误」、**一次都不重试** —— 传输层瞬时抖动被当成配置错误，最难查。
修法：把 `openai.APITimeoutError` / `openai.APIConnectionError` 也列入 `RETRYABLE`，
并用 `test_raw_openai_transport_errors_are_retryable` 钉住（防「整理表」时被删）。

### 坑 2：`PermissionDeniedError` 的 `response` 是**必填**，`APIError` 必须给 `status_code`

```text
TypeError: PermissionDeniedError.__init__() missing 1 required positional argument: 'response'
TypeError: APIError.__init__() missing 2 required positional arguments: 'llm_provider' and 'model'
```

构造假异常做单测时最容易踩。有效写法：

```python
request = httpx.Request("POST", "https://api.example.com/v1/chat/completions")
litellm.exceptions.PermissionDeniedError(
    message="forbidden", llm_provider="openai", model="gpt-4o-mini",
    response=httpx.Response(403, request=request),
)
litellm.exceptions.APIError(status_code=500, message="generic", llm_provider="openai", model="m")
```

（`RateLimitError` / `BadRequestError` / `Timeout` 只要 `message` + `llm_provider` + `model`，已实测。）

### 坑 3（**最阴的一个**）：`alembic/env.py` 的 `fileConfig()` 会**全局关停 logger**，让 `caplog` 失效

这条不在 LLM 模块里，但它是本轮最费时间的故障，症状极具迷惑性：

```text
tests/test_llm_client_retry.py::test_retry_really_waits ... FAILED
    AssertionError: assert ('attempt=1/4' in '')      ← caplog.text 竟然是空的
```

- **单独跑该文件：绿；全量跑：红**（看起来像「测试互相干扰」，其实是全局日志被改）。
- 根因：`logging.config.fileConfig()` 默认 `disable_existing_loggers=True`，
  它会把**此刻已存在的所有 logger** 强制 `disabled=True`，并替换 root logger 的 handler。
  `tests/test_db_migrations.py` 在 import 期触发了 `alembic/env.py`，于是**它之后**的用例全部失去日志捕获。
- 实测取证手法（值得记住）：临时替换 `logging.Logger.__setattr__` 打印 `disabled=True` 的调用栈，
  一眼看到 `alembic/env.py:61 → logging/config.py:201 in _handle_existing_loggers`。
- **修法（已落地）**：`alembic/env.py` 里显式传 `disable_existing_loggers=False`，
  并加注释说明为什么（见该文件 `config.config_file_name` 那一段）；
  `tests/conftest.py` 再加一道防御性 autouse 装置，把任何被库代码关停的 logger 重新打开。
- 教训：**断言日志的用例必须能在全量套件里通过**；「单独跑绿」不是证据。

### 坑 4：`litellm.Embedding` 在运行期取不到；多元素 embedding 也别用 `mock_response`

- `litellm.Embedding` → `AttributeError`（模块级 `__getattr__` 不导出它）；
  正确引用是 **`litellm.types.utils.Embedding`**（`litellm.utils.Embedding` 是同一个对象）。
- `mock_response` 造 embedding 有两个坑：① `input=['a','b']` + `mock_response=['x','y']`
  只返回**一个** data 项；② 配 `model="bge-m3"` 这类非 litellm 认识的模型名会**直接抛异常**
  （mock 未生效，litellm 试图解析 provider）。
- 修法：embedding 的离线用例改成 monkeypatch `litellm.aembedding`，自造「故意逆序」的响应
  （另用一个 pydantic 守卫用例钉住「真实 `Embedding` 支持 `item["index"]` 下标访问」这个假设）。

### 坑 5：`_run_with_retry` 会把**自己抛的** `PermanentLLMError` 二次包装成 `RetryableLLMError`

`embed()` 在「返回条数与入参不一致」时主动抛 `PermanentLLMError`，
但它是在重试回调**内部**抛的 → 冒泡到 `except Exception` → 被 `_translate()` 按
「未识别异常」翻成 `RetryableLLMError`。后果：**「不可恢复」被误报成「稍后可重试」**，
第 12 步的队列会一直重排它。修法：在翻译前先 `except LLMError: raise`（已落地）。

### 坑 6：`pytest-asyncio` 不是自带依赖，且 `asyncio.TimeoutError is TimeoutError`

- 异步用例（如「取消语义」那条）需要 `pytest-asyncio`，本仓已 `uv add --dev pytest-asyncio`
  并在 `[tool.pytest.ini_options]` 里设 `asyncio_mode = "auto"`（省掉逐条 `@pytest.mark.asyncio`）。
- 另一个认知修正：**`asyncio.TimeoutError is TimeoutError` 在 3.12 下是 `True`**（同一个对象）。
  所以「两者是不同的类，都要登记」的说法要改成：内建/asyncio 族与 litellm 族是两族，
  前者由 `TimeoutError` 一条覆盖即可。
- 顺带：`litellm` 启动时会尝试从 GitHub 拉取 `model_prices_and_context_window.json`，
  **无外网环境会重试 3 次并打印 WARNING 后回退到内置表**（实测）。这不是错误，
  但会让首次 import 变慢；离线跑测试时看到这几行 WARNING 属正常。

### 坑 7：假 key 骗过了「占位符检测」→ 真实探活变成真打网络

`tests/test_llm_live.py` 原本只把「等于 `sk-your-key` 等几个字面量」判为占位符。
实测把 `.env` 的 `LLM_API_KEY` 填成 `sk-from_env` 之后，探测没认出来 → 用例**真的请求了
`api.deepseek.com`** 并拿到 `401 Authentication Fails`。两个后果：

1. **验收信号被污染**：那一刻这条用例测的不再是「key 能用」，而是「本机网络能不能到厂商」；
2. 白跑一次真实网络与配额（还可能被厂商计进风控次数）。

修法（已落地）：改成按**片段**判断（`your-key` / `from_env` / `fake` / `placeholder` / `changeme` / `xxx`），
并给判定函数补**两侧守卫用例** —— 假 key 必 skip、真 key 必放行
（只加一侧的话，把规则写宽了会变成「永远 skip」，验收就成了空转）。

> 教训：**「跳过」这件事本身也要有测试。** 凡按条件 skip 的用例，都要有反向用例证明条件成立时
> 它真的会跑 —— 否则你无法区分「环境没配好所以 skip」与「判定写错了所以永远 skip」。

### 坑 8：推理模型的空 `content` —— 不是失败，是被 `max_tokens` 掐掉了

实测（`deepseek/deepseek-flash`，本仓当前主模型）：`max_tokens=16` 时返回

```
content=''   finish_reason='length'   tokens=36/16/52
```

**`content` 是空串，但调用本身是「成功」的** —— 它是**推理模型**，会先把 token 花在
`reasoning_content` 上（实测该字段里是完整的思考过程），16 个 token 全被推理吃掉，
留给正文的额度就是 0。`usage.completion_tokens_details.reasoning_tokens = 50` 是直接证据。

两个后果：

1. **验收被误判**：`assert result.content.strip()` 直接红，看起来像「模型不可用/网络问题」，
   实际只是**参数给小了**（第 5 步那次真实探活就卡在这里）；
2. **空 content ≠ 失败**：调用方若只看「有没有抛异常」，会把一个被截断的半成品当正常结果
   返回给用户（第 7/9 步的合成 Agent 尤其危险）。

修法（已落地）：

- `LLMResponse` 增加 **`finish_reason`** 字段（`_to_response` 透出）——它是唯一的区分线索：
  `length` = 被截断（调大 `max_tokens`），`stop` = 模型真的没说话（那才是异常）；
- `_to_response` 在「空 content + `length`」时打一条**指着修**的 WARNING；
- 真实探活用例给足额度（`max_tokens=256`），并**先断言 `finish_reason != "length"`** 再断言非空，
  这样失败信息能直接指出是「被截断」还是「模型没说话」。

> 选模型时要有这个意识：**推理模型的输出预算要按「推理 + 正文」一起算**，
> `max_tokens` 是两者的总量。成本同理：那次 16 个 completion token 里，真正答应用户的只有最后几个。

### 坑 9：`.env` 的 `EMBEDDING_BACKEND` 会**改变测试走哪条路径**

实测踩到（一次报 12 条失败）：把 `.env` 的 `EMBEDDING_BACKEND` 从 `litellm` 改成 `local` 之后，
`tests/test_llm_embed.py` 里那些「monkeypatch `litellm.aembedding`」的用例**全部失败**，
错误却是 `RepositoryNotFoundError: 401 Client Error`（HuggingFace 的报错）——
用例名与失败原因完全对不上，极难排查。

原因：那些用例的 fixture 只设了 `EMBEDDING_MODEL`，没设 `EMBEDDING_BACKEND`，
于是后端由**本机 `.env`** 决定 → 走到了真实的本地模型 → 真的去 HuggingFace 下权重。

修法（已落地）：凡是会调 `get_settings()` 的 fixture，**把所有被测字段都显式设成环境变量**
（`EMBEDDING_BACKEND` / `EMBEDDING_MODEL` / `EMBEDDING_API_KEY` / `EMBEDDING_DIM` / `LLM_FALLBACK_API_KEY` …）。
判据很简单：**用例的失败原因必须与它的名字对得上**；对不上就说明它不 hermetic。

> ⚠️ **`_env_file=None` 不等于「干净环境」**（这一条是同一个坑更隐蔽的一面，实测算错过）：
> 它只关掉**文件来源**，而 `Settings` 的优先级是「初始化入参 > 环境变量 > `.env` > 字段默认值」——
> 所以本机若设了 `$env:EMBEDDING_DIM=1024`，`Settings(_env_file=None, llm_primary="x")` **仍然**拿到 1024。
> 断言**默认值**的用例必须 `monkeypatch.delenv("EMBEDDING_DIM", raising=False)`；
> 断言**字段定义里的默认值**更稳的写法是直接读 `Settings.model_fields["embedding_dim"].default`
> （不依赖任何外部来源）。要验证自己的用例是否 hermetic，用这个探针跑一遍最省事：
>
> ```powershell
> # 用环境变量模拟一份「和本机不一样」的配置，看有没有用例跟着变红
> $env:EMBEDDING_DIM="1024"; $env:EMBEDDING_BACKEND="local"; $env:EMBEDDING_MODEL="BAAI/bge-m3"
> $env:LLM_PRIMARY="probe/model"; $env:LLM_FALLBACK="probe/other"; $env:LLM_FALLBACK_API_KEY="sk-probe"
> uv run pytest -q tests/test_config.py tests/test_llm_embed.py tests/test_llm_embed_local.py -p no:cacheprovider
> # 期望：与不设这些变量时**同样的结果**（实测：103 passed / 6 errors，两种口径一致）
> ```

> 附带教训：新增「配置驱动的分支」时，一定要回头检查**已有用例的 fixture 是否把新开关钉住**。

### 坑 10：`.env.example` 里给「取值行」加行内注释 = 复制粘贴陷阱

我原先在模板里写成：

```ini
EMBEDDING_MODEL=openai/text-embedding-3-small   # litellm 后端填模型名（建议带 provider 前缀）
```

整行抄进 `.env` 时只要**粘连**（注释被换行切断、或手工编辑时把说明并进值里），
模型名就会变成 `BAAI/bge-m3    # litellm 后端填模型名…` —— 本地后端于是拿着一个**不存在的仓库名**
去 HuggingFace，报 401/404，错误信息离根因十万八千里。

修法（已落地，两处一起做）：

- **模板里取值行只写「键=值」，说明文字单独成行**（`.env.example` 已改，并加了显式警告）；
- `client._validate_local_backend()` 增加**前置检查**：模型名为空 / 首尾带空白 / 含 `#`·`（` 时
  直接抛 `PermanentLLMError` 并提示「取值行只写键=值」，错误出现在**第一次尝试之前**。
  （这也顺带落实了「配置错不该重试」：这类错误一次都不该重试，否则只是把同一个错误犯 4 次。）

> 通用教训：**示例文件是会被整段复制的**。凡是「值 + 行内说明」混在一行的模板，
> 迟早有人把说明抄进值里；把说明挪到上一行是零成本的防御。
