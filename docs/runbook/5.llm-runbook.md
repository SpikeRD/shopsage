- 开发机实测环境：**Python 3.12.9**（`requires-python = ">=3.12"`）、uv 0.11.33、pytest 9.1.1。

```powershell
# 确认它进了 pyproject.toml 的 [project] dependencies（uv add 会自动改，手写会漂移）
uv run python -c "import tomllib,pathlib; d=tomllib.loads(pathlib.Path('pyproject.toml').read_text('utf-8'))['project']['dependencies']; print([x for x in d if 'litellm' in x or 'tenacity' in x])"
```

不要为了让 `uv tree` 好看去 `--no-deps`，那会把 litellm 打瘸。

### 1.2 配置：`LLM_PRIMARY` / `LLM_API_KEY` 怎么被读到

字段与取值规则**已经在第 1 步就位**（`app/config/settings.py`），本步**不需要**新增字段，
只需要把 `.env` 填对。字段 ↔ 环境变量同名大写（`case_sensitive=False`、无前缀）：

| 字段 | 环境变量 | 默认值 | 本步是否必填 | 说明 |
|---|---|---|---|---|
| `llm_primary` | `LLM_PRIMARY` | `""` | **必填**（空则 `Settings` 构造直接 `ValidationError`） | 主模型名，**透传给 litellm** |
| `llm_fallback` | `LLM_FALLBACK` | `""` | 本步**可留空** | 降级链，第 13 步才用；非空时必须 ≠ `llm_primary` |
| `llm_api_key` | `LLM_API_KEY` | `""` | 必填（`ENV=prod` 时缺失 fail-fast） | `SecretStr`，**门面唯一密钥入口** |

```powershell
# ① 确认配置被读到（输出已掩码，可安全贴出来）
uv run python -c @"
from app.config import get_settings
s = get_settings()
d = s.dump_for_logging()
print('llm_primary  :', d['llm_primary'])
print('llm_fallback :', repr(d['llm_fallback']))
print('llm_api_key  :', d['llm_api_key'])      # 永远 **********
print('key 长度(仅自检) :', len(s.llm_api_key.get_secret_value()))
"@
# 期望：
#   llm_primary  : <你在 .env 里填的模型名>
#   llm_fallback : ''            ← 本步留空是允许的
#   llm_api_key  : **********
#   key 长度(仅自检) : 数字 > 0    ← 只打印长度，**永远不要打印 key 原文**
```

三条必须知道的取值规则（都已在 `tests/test_config.py` 里钉住，别再自己发明）：

1. **`llm_primary` 不许为空**。`Settings` 的 `_validate_llm_routing` 会在构造期抛
   `ValueError: llm_primary 不能为空（LLM_PRIMARY 被显式设为空/空白）`。留空**不会**回退到任何默认模型。
2. **`llm_fallback` 非空时必须 ≠ `llm_primary`**，否则抛错：降级会变成「再打一次同一个模型」，
   既没有可用性收益，还让故障时的重试量翻倍。本步留空最省事。
3. **`llm_primary` 只做形状校验，不校验「厂商认不认识这个模型名」**（`settings.py` 里有明确注释：
   那等于替 litellm 维护它自己的模型表）。所以**模型名写错要到第 1 次真实调用才暴露** ——
   这就是 §2 那次探活存在的唯一理由。

> ⚠️ **`get_settings()` 是进程内单例（`lru_cache`）**：改了 `.env` 必须**重启进程**才生效；
> 临时改一次用 `$env:LLM_PRIMARY="..."`（优先级：环境变量 > `.env`，见 [`1.config-guide.md`](1.config-guide.md) §1.1）。
> 若看到 `配置冲突：进程环境变量 LLM_API_KEY 正在覆盖 .env 中的同名值` —— 那是**正常告警**，说明你机器上有同名用户级环境变量。

> ⚠️ **密钥只走 `Settings` 这一条路**：不要另外 `setenv OPENAI_API_KEY` / `DEEPSEEK_API_KEY`。
> LiteLLM 的 `api_key=` 参数由 `client.py` 从 `settings.llm_api_key` 注入（§3.3），
> 这样「密钥从哪来」只有一个答案，dump/日志/repr 的掩码机制也才守得住。
> （厂商专属环境变量确实也能被 litellm 自己读到，但那等于**第二条真相**：出问题时你不知道生效的是哪个 key。）

## 2. 探活：先证明「key + 模型名」能用（1 次调用，最省钱）

**做这一步的唯一目的**是把两类错误分开：**配置错**（模型名/key/额度）与**代码错**（重试/门面写错）。
跳过它，你会拿着一个「模型名拼错」的 `BadRequestError` 去调试 tenacity，白烧一小时。

```powershell
# ── 执行位置：Windows 开发机，仓库根 ──
# 直接调 litellm（**这一步故意绕开 app/llm 门面**：它要单独证明「厂商侧配置没问题」）
uv run python -c @"
from app.config import get_settings
import litellm, time
s = get_settings()
t0 = time.perf_counter()
r = litellm.completion(
    model=s.llm_primary,
    api_key=s.llm_api_key.get_secret_value(),
    messages=[{'role': 'user', 'content': '只回复两个字：在的'}],
    max_tokens=16,
    timeout=30,
    num_retries=0,
)
print('content :', r.choices[0].message.content)
print('model   :', r.model)
print('usage   :', r.usage.prompt_tokens, r.usage.completion_tokens, r.usage.total_tokens)
print('latency : %.2fs' % (time.perf_counter() - t0))
print('cost    :', litellm.completion_cost(completion_response=r))
"@
# 期望：打印一行中文回复 + model/usage/latency/cost 四项都有数
#   ⚠️ 不要照抄具体 token 数/金额 —— 以你这次真实输出为准（回填证据时要贴真实值）
# 报错分诊：
#   AuthenticationError        → key 不对（§9 第 1、2 条）
#   BadRequestError/NotFoundError → **模型名不对**（llm_primary 的形状校验不查厂商表，见 §1.2 第 3 条）
#   RateLimitError(429)        → 额度/频率问题：**注意这本身不是 bug**，本步的退避重试就是为它写的
```

> **为什么这里显式写 `num_retries=0`**：litellm 自己**默认就会重试**。探活要的是「第一次到底成不成」，
> 让 litellm 偷偷重试会把「配置错」伪装成「慢但成功」。这个参数在 §3.3 的门面里也是**必须**显式设的，
> 理由见 §5.1（否则一次调用会被重试两层，退避时间完全失控）。

> 💡 **不想花真钱也有办法**：litellm 内置 mock，把 `completion(...)` 换成
> `litellm.completion(model="gpt-4o-mini", mock_response="在的", api_key="sk-fake")` 就能离线拿到一个
> 形状完全正确的响应（含 `usage`）。它证明的是**代码路径通**，**不**证明 key 能用 ——
> 所以「key 能用」这条验收仍然只认上面那次真实调用（§10 证据 4）。

> 🔍 **API 事实核对（本节与 §3、§4、§7 关于 litellm 的说法都据此写）**
>
> 核对环境：临时干净环境（`uv venv` + `uv pip install litellm`），实测版本 **litellm 1.103.0**；
> 只核对**接口形状**，**没有**调用任何真实模型。以下事实可以省掉你自己试错的时间：
>
> | 事实 | 实测结果 |
> |---|---|
> | `litellm.__version__` | **不存在**（`AttributeError`）→ 用 `importlib.metadata.version("litellm")` |
> | `litellm.exceptions.*` 的 11 个异常类 | 全部存在（`RateLimitError` / `Timeout` / `APIConnectionError` / `InternalServerError` / `ServiceUnavailableError` / `BadRequestError` / `AuthenticationError` / `PermissionDeniedError` / `NotFoundError` / `ContentPolicyViolationError` / `ContextWindowExceededError`） |
> | `RateLimitError(message=…, llm_provider=…, model=…)` | 可直接构造（§4.2 的假异常就是这么造的） |
> | `litellm.exceptions.Timeout` | **不是** 内建 `TimeoutError`；继承链 `Timeout → APITimeoutError → APIConnectionError` |
> | `num_retries` / `mock_response` / `max_retries` / `fallbacks` | **不在** `acompletion` 具名参数里，走 `**kwargs` 透传（写错名字不报错，见 §5.1） |
> | `completion_cost(completion_response=…)` | 参数名正确、可算（mock 响应实测返回 `1.35e-05`） |
> | `completion_cost(..., call_type="aembedding")` | **支持**，可算 embedding 成本 |
> | `mock_response` 传**异常对象** | 会真的把该异常抛出来（`litellm.exceptions.Timeout` 实测） |
> | `mock_response` 传**字符串** | 返回正常响应，`usage` 为 `10/20/30`（**是 mock 造的假数**） |
> | `aembedding` / `embedding` 返回 | `EmbeddingResponse`（字段 `model`/`data`/`object`/`usage`）；`data[i]["embedding"]`、`data[i]["index"]` |
> | embedding 的 `mock_response=["x","y"]` | ⚠️ **只返回 1 个 data 项**，`data[0]["embedding"] == ["x","y"]` → 测顺序别用它（§7.3） |
>
> 换 litellm 版本时**先复跑这张表**：接口形状一变，本文的骨架与判据就得跟着改。

## 3. 写 `app/llm/`（门面 + 错误分类）

### 3.1 目录与文件分工

```
app/llm/
├─ __init__.py    # 唯一对外出口：llm_call / embed / LLMResponse / 异常类
├─ client.py      # LiteLLM 门面 + tenacity 退避重试（本模块**唯一**允许 import litellm 的地方）
└─ errors.py      # 错误分类：可恢复（可重试/可降级） vs 不可恢复（立刻抛）
```

`errors.py` 单独成文件不是洁癖：`5.llm.md` §5 第 2 条把「**只有限流/超时/5xx 才降级**」列为关键技术点，
分类逻辑必须能被**单独单测**（§4.1 的 `test_llm_errors.py` 就是纯逻辑、不起网络）。
第 13 步的熔断器与降级链会复用同一个分类函数 —— 分类一旦有两份，熔断与降级就会打架。

### 3.2 `errors.py`：错误分类表（**这张表就是本模块的核心规则**）

| 异常（litellm 的异常类，继承自 openai 的） | 性质 | 允许重试 | 允许降级（第 13 步） | 理由 |
|---|---|---|---|---|
| `litellm.exceptions.RateLimitError`（429） | 可恢复 | ✅ | ✅ | 限流是「等一会儿就好了」，退避正对它（A1） |
| `litellm.exceptions.Timeout`（= `APITimeoutError`） | 可恢复 | ✅ | ✅ | 超时是网络/负载抖动，重试有效 |
| `litellm.exceptions.APIConnectionError` | 可恢复 | ✅ | ✅ | 连不上是瞬时故障（DNS/握手/连接被断） |
| `litellm.exceptions.InternalServerError`、`ServiceUnavailableError`（5xx） | 可恢复 | ✅ | ✅ | 厂商侧故障，等一等/换模型有效 |
| `litellm.exceptions.BadRequestError`（400，参数错） | **不可恢复** | ❌ | ❌ | 重试与降级都改不了「请求本身写错了」，只会掩盖 bug |
| `litellm.exceptions.AuthenticationError`（401）/ `PermissionDeniedError`（403） | **不可恢复** | ❌ | ❌ | key 错/无权限：换模型也白搭，**且会放大故障**（把每个副本都打上去） |
| `litellm.exceptions.NotFoundError`（404，模型名错） | **不可恢复** | ❌ | ❌ | 模型名/端点写错，属配置错误，必须立刻炸出来 |
| `litellm.exceptions.ContentPolicyViolationError` | **不可恢复** | ❌ | ❌ | 内容违规：换模型是「绕过风控」，不能做 |
| `litellm.exceptions.ContextWindowExceededError` | **不可恢复** | ❌ | ⚠️ 例外：可考虑换长上下文模型 | 本步不处理；第 13 步若要降级，需显式列入白名单并写清理由 |
| 其它未识别异常 | **保守当成不可恢复** | ❌ | ❌ | 未知错误重试 = 用真实流量赌运气；宁可立刻暴露 |

```python
# app/llm/errors.py（骨架；表就是它，别把规则散在 client.py 里）
"""LLM 错误分类：决定「重试」「降级（第 13 步）」还是「立刻抛」。"""

import asyncio

import litellm

# 可恢复：限流 / 超时 / 连接失败 / 5xx —— 等一会儿或换个模型真的能好
#
# 继承关系（实测 litellm 1.103.0）：Timeout → APITimeoutError → APIConnectionError → APIError。
# 也就是说列一个 APIConnectionError 就覆盖了「超时 + 连不上」两族；这里仍然把 Timeout 显式写出，
# 因为它是最常被单独讨论的一条，显式列出来别人查表时不用去翻继承链。
# 另注：`litellm.exceptions.Timeout` **不是** 内建 TimeoutError（实测 `Timeout is TimeoutError` → False），
# 所以内建/asyncio 的超时（非 litellm 路径，如自建 httpx 调用）要自己补一行。
RETRYABLE: tuple[type[BaseException], ...] = (
    litellm.exceptions.RateLimitError,
    litellm.exceptions.Timeout,
    litellm.exceptions.APIConnectionError,
    litellm.exceptions.InternalServerError,
    litellm.exceptions.ServiceUnavailableError,
    asyncio.TimeoutError,
)

# 不可恢复：参数错 / 鉴权 / 模型名错 / 内容违规 —— 重试与降级都无意义
NON_RETRYABLE: tuple[type[BaseException], ...] = (
    litellm.exceptions.BadRequestError,
    litellm.exceptions.AuthenticationError,
    litellm.exceptions.PermissionDeniedError,
    litellm.exceptions.NotFoundError,
    litellm.exceptions.ContentPolicyViolationError,
    litellm.exceptions.ContextWindowExceededError,
)


class LLMError(RuntimeError):
    """本模块对外统一的错误类型（调用方只需要 catch 这一个）。"""


class RetryableLLMError(LLMError):
    """可恢复错误：重试若干次后仍失败才抛这个。"""


class PermanentLLMError(LLMError):
    """不可恢复错误：**第一次就抛**，不做任何重试。"""


def is_retryable(exc: BaseException) -> bool:
    """保守判定：只有明确列在 RETRYABLE 里的才算可恢复。

    ⚠️ 返回 False 的两种情形要分清：
      ① 明确列在 NON_RETRYABLE 里（400/401/403/404/内容违规）；
      ② **没见过的异常**（如 KeyError/TypeError）—— 同样不重试。
    用「白名单」而不是「黑名单」，是因为漏判一个可恢复错误只损失一次重试机会，
    而误判一个不可恢复错误会变成「拿真实流量反复撞墙」，后者更贵。
    """
    if isinstance(exc, NON_RETRYABLE):
        return False
    return isinstance(exc, RETRYABLE)


def is_permanent(exc: BaseException) -> bool:
    return isinstance(exc, NON_RETRYABLE)
```

### 3.3 `client.py`：门面 + 退避重试（**唯一允许 import litellm 的文件**）

```python
# app/llm/client.py（骨架；关键是「唯一的 litellm 出口 + 显式 num_retries=0 + 退避 jitter」）
"""LLM 统一门面：所有 Agent 调模型都必须走这里（5.llm.md 第 1 节的硬约束）。"""

import logging
import random
import time
from dataclasses import dataclass
from typing import Any

import litellm
from tenacity import (
    AsyncRetrying,
    RetryCallState,
    retry_if_exception,
    stop_after_attempt,
)

from app.config import get_settings
from app.llm.errors import PermanentLLMError, RetryableLLMError, is_retryable

logger = logging.getLogger(__name__)

# 退避上限：单次等待最多 20s（避免第 5、6 次重试把请求拖到分钟级）
MAX_BACKOFF_SECONDS = 20.0
# 单次调用超时：交给 litellm 的 per-request timeout（不用全局 socket 超时）
DEFAULT_TIMEOUT = 30.0
# 默认重试次数（**总尝试次数 = 1 + max_retries**）
DEFAULT_MAX_RETRIES = 3


def _wait(state: RetryCallState) -> float:
    """指数退避 + jitter：`min(2^n, cap)` 秒再乘一个随机系数。

    为什么必须带 jitter（5.llm.md 第 5 节）：无抖动时所有失败请求会在**同一时刻**重试，
    多副本/多 Agent 一起撞上去形成「惊群」，把刚缓过来的模型再打趴一次。
    乘 `random.uniform(0.5, 1.0)` 保留退避量级又错开时刻；别用 `random()`（可能退避到 0，等于没退避）。
    """
    attempt = state.attempt_number
    return min(2.0**attempt, MAX_BACKOFF_SECONDS) * random.uniform(0.5, 1.0)


def make_retry_logger(max_retries: int):
    """造一个 `before_sleep` 回调：把「第几次 / 共几次 / 什么错」打成一条日志。

    为什么用闭包而不是在回调里问 tenacity：`RetryCallState` 只有
    `attempt_number` / `outcome` / `seconds_since_start` 这类很少的字段，
    **没有**「最多几次」（别凭记忆写 `state.retry_state_max_attempts(...)`，那不存在）；
    总次数在构造策略时就知道，闭包捕获最省事。
    """
    max_attempts = max_retries + 1

    def _log_retry(state: RetryCallState) -> None:
        exc = state.outcome.exception() if state.outcome else None
        logger.warning(
            "LLM 调用失败，准备退避重试：attempt=%d/%d error=%s: %s",
            state.attempt_number,
            max_attempts,
            type(exc).__name__,
            exc,
        )

    return _log_retry


class _RetryPolicy(AsyncRetrying):
    """一份退避策略，llm_call / embed 共用（两处各写一份必然漂移）。"""

    def __init__(self, max_retries: int) -> None:
        super().__init__(
            stop=stop_after_attempt(max_retries + 1),      # 1 次首发 + max_retries 次重试
            wait=_wait,
            retry=retry_if_exception(is_retryable),        # 不可恢复错误**不进**退避
            before_sleep=make_retry_logger(max_retries),
            reraise=True,                                  # 重试用尽后抛**原始**异常（不被 RetryError 包住）
        )


@dataclass(frozen=True)
class LLMResponse:
    """结构化结果：第 11/13 步的 token/成本计量直接吃这些字段，调用方不必再解 litellm 对象。"""

    content: str
    model: str
    prompt_tokens: int
    completion_tokens: int
    total_tokens: int
    cost_usd: float | None
    latency_ms: int


def _settings():
    return get_settings()


async def llm_call(
    messages: list[dict[str, Any]],
    model: str | None = None,
    *,
    max_retries: int = DEFAULT_MAX_RETRIES,
    timeout: float = DEFAULT_TIMEOUT,
    **kwargs: Any,
) -> LLMResponse:
    """调一次 LLM，带指数退避重试。

    参数（与 5.llm.md 第 2 节的接口一致）：
      messages     OpenAI 格式的消息列表
      model        主模型；None = 用 config 的 llm_primary
      max_retries  重试次数（总尝试 = 1 + max_retries）
      timeout      单次请求超时（秒）；**超时错误本身也是可重试的**
      **kwargs     透传给 litellm（temperature / max_tokens / …）

    注意：**fallback_models 参数属于第 13 步**，本次刻意不接受 —— 传进来会被静默忽略，
    那是比「没有这个功能」更糟的行为（调用方以为有降级，其实没有）。
    """
    settings = _settings()
    used_model = model or settings.llm_primary

    # ⚠️ `num_retries` 不在 acompletion 的**具名参数**里（它是 **kwargs 透传）；
    #    litellm 会自己消费它。所以「写错名字」不会有任何报错 —— 只会静默地不生效。
    #    这也是为什么 §4.2 必须有那条 `calls["n"] == 3` 的断言：参数名写错时它是唯一的哨兵。
    try:
        async for attempt in _RetryPolicy(max_retries):
            with attempt:
                t0 = time.perf_counter()
                response = await litellm.acompletion(
                    model=used_model,
                    messages=messages,
                    api_key=settings.llm_api_key.get_secret_value(),   # 唯一密钥入口（§1.2）
                    timeout=timeout,
                    num_retries=0,      # ⚠️ 必须显式关掉 litellm 自带重试，见 §5.1
                    **kwargs,
                )
                latency_ms = int((time.perf_counter() - t0) * 1000)
                return _to_response(response, latency_ms)
    except Exception as exc:
        # ⚠️ 这段翻译是**必须**的：策略里的 reraise=True 会把 litellm 原始异常直接抛出来，
        #    而调用方（第 7/12 步）需要能区分「可以稍后重试」与「别重试了」——
        #    见 §5.4 的对照表。少了这一段，retryable/permanent 的区分就形同虚设。
        raise _translate(exc) from exc


def _translate(exc: Exception) -> LLMError:
    """把 litellm 异常翻译成本模块的两种对外错误（判据就是 errors.py 的分类表）。"""
    if is_permanent(exc):
        return PermanentLLMError(f"LLM 不可恢复错误：{type(exc).__name__}: {exc}")
    return RetryableLLMError(f"LLM 重试 {DEFAULT_MAX_RETRIES} 次后仍失败：{type(exc).__name__}: {exc}")
```

> ⚠️ **`before_sleep` 回调里别凭记忆写 tenacity 的 API**：`RetryCallState` 只有
> `attempt_number` / `outcome` / `seconds_since_start` 等很少的字段，**没有**「最多几次」。
> 上面用 `make_retry_logger(max_retries)` 闭包捕获总次数，就是为了避开这个坑 ——
> 写错的代价是「第一次失败时」才炸，而那时候你正忙着排查真正的故障。

`_to_response` 把 litellm 响应翻译成我们自己的结构（第 13 步接 Langfuse 时只改这一处）：

```python
def _to_response(response: Any, latency_ms: int) -> LLMResponse:
    usage = getattr(response, "usage", None)
    try:
        # litellm 内置成本表；算不出来（如本地模型）时返回 0.0/抛错都见过 → 用 None 表示「未知」
        cost = float(litellm.completion_cost(completion_response=response))
    except Exception:  # noqa: BLE001 - 计费失败绝不能影响业务调用
        cost = None
    return LLMResponse(
        content=response.choices[0].message.content or "",
        model=getattr(response, "model", "") or "",
        prompt_tokens=int(getattr(usage, "prompt_tokens", 0) or 0),
        completion_tokens=int(getattr(usage, "completion_tokens", 0) or 0),
        total_tokens=int(getattr(usage, "total_tokens", 0) or 0),
        cost_usd=cost,
        latency_ms=latency_ms,
    )
```

### 3.4 为什么返回 `LLMResponse` 而不是原样的 litellm 对象

| 做法 | 后果 |
|---|---|
| 直接返回 `ModelResponse` | 调用方要自己 `response.usage.prompt_tokens`、自己算 cost → **每个 Agent 各写一份**，第 11/13 步的「统一计费」无处落脚 |
| 返回自定义 `LLMResponse` | 计费口径只有一处；换 provider / 升级 litellm 时只改 `_to_response`；测试里断言也简单（不用构造 litellm 内部对象） |

代价：**丢掉了 litellm 的部分透传信息**（如 `response.id`、原始 `raw_response`）。
第 13 步接 Langfuse 若需要 trace id，就在 `LLMResponse` 上加字段 —— 依然只改 `_to_response` 一处。

### 4.2 造 429/超时：**假异常注入 + litellm mock 响应**（不引入任何测试依赖）

两种手段配合用，各有不可替代的地方：

| 手段 | 用来做什么 | 为什么不能只用另一种 |
|---|---|---|
| `monkeypatch.setattr(llm_client.litellm, "acompletion", 假函数)` + **手工 `raise` 一个真实异常类** | 制造**确定次数**的失败序列（「前两次 429、第三次成功」） | litellm 的 `mock_response` **没有**「第 N 次才失败」的能力 |
| `litellm.completion(..., mock_response="文本")` | 造一个**形状真实**的成功响应（`choices`/`usage`/`model` 都是真的） | 手搓 `SimpleNamespace(choices=[...])` 会在 litellm 改内部结构时**静默变假** |
| `mock_response=<异常实例>`（实测可用） | 走**真实 litellm 调用路径**抛指定异常（含真解析） | 它进不了「次数序列」 |

> 三者都**不发网络请求**。所以「拔网线也全绿」这条 CI 判据照旧成立。
> 本步**不引入** `respx` / `pytest-httpserver`（少一个依赖少一处漂移）；
> 真要验 TLS/代理/真实超时，见 §4.4。

> ⚠️ **单测里关退避要替换策略类，不要 monkeypatch `_wait`**：`_RetryPolicy.__init__` 里写的是
> `wait=_wait`（捕获的是**函数对象**），替换模块属性改不到它 —— 你以为关掉了，用例却在真等 2/4/8 秒
> （症状：整个测试套件莫名其妙变慢）。下面的 `FastRetryPolicy` 就是为此写的。

```python
#    `wait=_wait`（模块级函数对象），属性替换改不到已经捕获的那个引用 ——

#    在单测里一起被绕过，语义清楚：**这条用例测的是次数，不是时长**。
```

```python
def test_backoff_is_exponential_and_jittered(monkeypatch):
    """退避量级：第 n 次约 2^n 秒，且带抖动（两次取值不应完全相同）。

    ⚠️ 断言量级与单调性，**不要断言精确秒数** —— jitter 的存在就是为了让它不是一个定值。
    """
    waits = []
    for n in range(1, 5):
        class S:                       # 只喂 _wait 需要的字段
            attempt_number = n
        samples = [llm_client._wait(S()) for _ in range(20)]
        assert min(samples) >= min(2.0**n, llm_client.MAX_BACKOFF_SECONDS) * 0.5 - 1e-6
        assert max(samples) <= min(2.0**n, llm_client.MAX_BACKOFF_SECONDS) + 1e-6
        assert len(set(samples)) > 1, "没有抖动 → 多副本会同时重试（惊群）"
        waits.append(min(samples))
    assert waits == sorted(waits), "退避应随尝试次数单调不减"
```

```python
def test_max_backoff_is_capped():
    """第 10 次重试不应等 1024 秒 —— 上限 MAX_BACKOFF_SECONDS 必须生效。"""
    class S:
        attempt_number = 10
    assert llm_client._wait(S()) <= llm_client.MAX_BACKOFF_SECONDS
```

> ℹ️ 这两条 `_wait` 用例**不 monkeypatch 任何东西** —— 它们测的就是真实的退避函数本身
> （量级、抖动、上限）。线上真正的等待时刻由 `_RetryPolicy` 消费这个函数的返回值，
> 所以「值对了」等价于「等对了」；真正掐表反而更不可靠（见 §4.3）。
>
> ⚠️ 上面 `class S:` 这种「只有一个属性的假对象」是刻意的：`_wait()` 只读 `attempt_number`，
> 给它真 `RetryCallState` 得先造 outcome/异常，纯属自找麻烦。**但也因此要注意**：
> 将来 `_wait` 若改用别的字段，这些用例不会报错，只会静默地测一个假对象 ——
> 所以 `_wait` 的字段用法要保持在「只读 attempt_number」这一条上。

### 4.3 退避「真的等了吗」——看日志与回调，别掐表

| 做法 | 靠不靠谱 |
|---|---|
| 用 `time.perf_counter()` 掐表断言「等了 ≥2 秒」 | ❌ 脆：CI 机器负载、`min(2^n, cap)` 与 jitter 叠加，容易假红；而且慢 |
| **断言 `_wait()` 的返回值 + `before_sleep` 被调用次数** | ✅ 推荐：快、稳、语义清晰（§4.2 用的就是它） |
| 跑一次真 429 观察日志 | ✅ 作为**验收证据**（§10 证据 2/3），不做断言 |

真实的「退避生效」证据长这样（**这是我们要在 §10 回填的东西**）：

## 5. 重试设计：四条必须理解的规则

### 5.1 `num_retries=0`：**不要两层重试**

litellm 自带 `num_retries`（默认非 0）。如果门面不显式关掉它，一次业务调用会变成：

```
业务层 max_retries=3  ×  litellm 内部重试 N  →  实际请求数 = 4 × (1+N)
```

后果：① 退避时间完全失控（你以为最多等 7 秒，实际等了一分钟）；② 429 时**主动加倍**限流压力，
正好制造出 `5.llm.md` §5 说的「惊群」；③ 你在日志里数到的重试次数对不上代码里的参数，
排查时先怀疑自己写错了。

**结论**：`num_retries=0` 是**必须**的，且要有测试钉住 —— 见 §4.2 的断言第 3 条（`calls["n"] == 3`）。
一旦有人删掉这个参数，`calls["n"]` 会变成 6/12 之类，测试立刻红。

> ⚠️ **实测（litellm 1.103.0）**：`num_retries` / `mock_response` / `max_retries` / `fallbacks`
> 都**不是** `litellm.acompletion()` 的具名参数，它们走 `**kwargs` 透传（实测 `acompletion(..., num_retries=0)`
> 正常接受并生效）。这是本手册里最阴的一个坑：**参数名写错（如 `max_retries=`）不会报错**，
> litellm 只会当成「你不想要重试控制」，于是两层重试照旧发生，而你在代码里明明写着「已关闭」。
> 唯一的哨兵就是 §4.2 那条计数断言 —— 所以它看起来只是「数了几次」，实际守的是这条。

### 5.2 只有「可恢复错误」才重试（§3.2 的表就是全部规则）

直觉上「多试几次总没坏处」，实际上：

- 对 400 重试：**只是把同一个错误犯 4 次**，用户多等 3 个退避周期才拿到同一个报错；
- 对 401 重试：key 错了重试 100 次也还是错，**且每个副本都在打厂商的鉴权接口**；
- 对内容违规重试：等于在「换个姿势绕过风控」，是安全红线（`4.security.md` 的 guardrail 是同一条线）。

`is_retryable()` 用**白名单**（只认列出来的可恢复异常）而不是黑名单，
理由写在 `errors.py` 的 docstring 里：漏判只损失一次重试机会，误判要拿真实流量撞墙。

### 5.3 退避 = `min(2^n, cap)` × jitter

- `2^n`：失败往往意味着对端过载，**立刻重试只会加重过载**；指数增长给对端恢复时间（A1）。
- `cap`（本手册取 20s）：不设上限时第 10 次要等 17 分钟，「重试」就变成了「挂死」。
- `jitter`：**没有它，所有副本会在同一毫秒一起重试**。这就是「惊群」的成因，
  也是 `5.llm.md` §5 第 1 条要你「懂为什么」的那一点。
- 用 `uniform(0.5, 1.0)` 而不是 `random()`：后者可能退避到接近 0，等于退避没生效。

### 5.4 重试到底该抛什么

`reraise=True`：重试用尽后抛**原始异常**（而不是 tenacity 的 `RetryError` 包一层）。
但我们又做了一层翻译：对外抛 `LLMError` 的两个子类，让调用方只需要 `except LLMError`。
两种错误必须能被**区分**，因为调用方的处置不同：

| 对外异常 | 调用方该做什么 | 典型场景 |
|---|---|---|
| `PermanentLLMError` | **不要重试**、不要重排队列；报错给用户（或走人工兜底） | 参数错、key 错、模型名错 |
| `RetryableLLMError` | 可以放进队列稍后重试（第 12 步 queue）、可以回答「稍后再试」 | 厂商持续 429/5xx/超时 |

> ⚠️ **不要把 `RetryableLLMError` 当成「任务失败」直接丢进死信队列**：它更像「暂时不可用」，
> 第 12 步的队列要按 `RetryableLLMError` 做带延迟的重排，否则 429 一多就批量进死信。
> 这条现在写下来，是为了那时不用回头改门面的异常类型。

## 7. `embed()`：embedding 也走同一个门面

### 7.1 为什么 embedding 也必须在门面里

因为 embedding **是花钱的调用**（按 token 计费），而且**是延迟的一部分**：
第 10 步 rag 要检索、第 13 步 cache 要判相似，两处都会高频调它。
如果它们各自 `openai.embeddings.create(...)`，就会出现：改不了超时、加不了重试、
计不了费、也没有「切换 embedding 模型」的单一开关。RAG 效果差时你会找不到是哪个环节。

### 7.2 接口


`embed()` 与 `llm_call()` 的**三个差别**（容易写错的地方）：

| 维度 | `llm_call` | `embed` |
|---|---|---|
| litellm API | `acompletion` | `aembedding` |

| `ReadTimeout` / 代理相关报错 | 企业代理 / 本机代理没配到进程环境 | `$env:HTTPS_PROXY` 是否有值 | 给进程配代理；⚠️ 别把代理凭据写进 `.env` 提交 |
| 日志里出现密钥明文 | 有人 `print(settings.llm_api_key)` 或 `print(response)` 时带出了请求头 | grep 一下日志来源 | 一律用 `settings.llm_api_key.get_secret_value()` 后**只传给 litellm**，不打印；要自查就打印 `len()`（§1.2） |
| 换了 `.env` 但模型没变 | `get_settings()` 是 `lru_cache` 单例 | 重启进程再试 | 重启进程；或临时 `$env:LLM_PRIMARY="..."`（优先级更高） |
| 看到 `配置冲突：进程环境变量 LLM_API_KEY 正在覆盖 .env` | 本机有同名用户级环境变量 | [`1.config-guide.md`](1.config-guide.md) §1.5 只列变量名 | **正常告警**；要么删掉该环境变量，要么承认它以环境变量为准 |
