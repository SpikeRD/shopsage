三条铁律：

1. **判分只有一处口径**。阈值只在 `RagEvalSettings.thresholds()` 里定义，指标名只有一套
   （`recall` / `faithfulness` / `answer_relevancy`）；「不合格」的判定只有 `metrics.passed_overall()`
   一个函数。两个地方判「通过」= 两条不同的合格线，而它们的差别只在边界样本上显形 ——
   那种 bug 会活很久（本仓实测第一版就有一处，见 §10.1 坑 2）。
2. **报告里必须写出「分数是在什么条件下量的」**：数据集版本、判官、合成方式、语料指纹。
   少了任何一项，两份报告放在一起就会得出错误结论 —— 而它们看起来完全可比。
3. **评测自己也要能被测**。`tests/eval/` 全部用假检索 + 假判官 + 假 LLM 跑完整链路，
   零依赖、零成本、可复现；真依赖那三条单独用 `--rag-live` 开门。
   一个「只能靠真依赖才能跑」的评测模块，在依赖坏掉的那天会连「评测坏了」还是「系统坏了」都分不清。

另一条（本步最贵的认知）：**评测最容易骗过的是写它的人**。
`14.eval.md` §5 第二条说「纯 LLM 打分不稳定」——我们实测到的是更深一层的问题：
**规则判分也会不稳定，如果判据写错了的话**（拒答识别、数字判据、挑句启发式三处都踩过）。
所以每加一条判据，都要能回答两个问题：*它在惩罚什么？* 与 *那个东西该被惩罚吗？*
（§10.1 的 11 个坑里有 5 个是这一条的实例。）

## 1. 环境与前提

### 1.0 本步的链路（两条：一条量检索，一条量整张图）

```
【A】RAG 三指标（量检索层）
   eval/datasets/rag_golden_v1.json（15 条：问题 + 标准答案 + 事实点 + 期望来源）
        │
        ▼  app/eval/rag_eval.py::evaluate_rag
   ┌─ 每条用例 ────────────────────────────────────────────────────────────┐
   │ ① 检索：search(query, top_k, with_rerank)  ← 注入（生产实现 = Retriever.search）
   │        └─► metrics.retrieval_quality  → Recall（命中哪几份 / 漏哪几份）
   │ ② 合成：answerer(question, hits)           ← 注入（context / extract / llm）
   │ ③ 材料：pipeline.context_block(hits)      → Faithfulness 的判据来源
   │ ④ 规则判据：metrics.answer_quality         → 事实点覆盖 / 数值支持 / 拒答 / 篇幅
   │ ⑤ 判官：judge(question, reference, context, answer, key_facts)  ← 注入
   │ ⑥ 合并：rag_eval._combine（规则是否决项，分数取更保守的那个）
   └───────────────────────────────┬───────────────────────────────────────┘
                                   ▼
                     app/eval/report.py::Report（JSON + Markdown 同源）

【B】Agent 成功率（量整张图）
   eval/datasets/agent_golden_v1.json（10 条：含期望 route / 角色 / user_id）
        │
        ▼  app/eval/agent_eval.py::evaluate_agent
   ┌─ 每条用例（thread_id 每轮都换）───────────────────────────────────────┐
   │ app/graph/run.py::run_turn(graph, {messages,user_id,role}, thread_id)  │
   │        └─► 生产同款的图：guardrail → router → data/rag/analysis → synthesis → guardrail
   │ ⑥ 判分：agent_eval.score_agent_row（**纯函数**：给定 state 就能复算，不必重跑图）
   │        · route 判对？ · Recall 达阈？ · Faithfulness 达阈？ · Relevance 达阈？
   │        · 答完了？（有答案 + 未被拦 + 无 refusal）→ 四条全过才算「成功」
   └───────────────────────────────┬───────────────────────────────────────┘
                                   ▼
                       报告里的「成功率 X/N」+ 关键事实命中率
```

**每个指标「拦得住什么 / 拦不住什么」**（与 [`13.cache-runbook.md`](13.cache-runbook.md) §1.0 同口径）：

| 指标 | 拦得住 | 拦不住 / 需要别的指标 |
|---|---|---|
| **Recall@K** | 「该检索到的文档一份都没进 top-k」；分块/embedding/rerank 的退化 | 「检索到了但排在第 5 条」与「排在第 1 条」在它眼里一样（看 `top_score` 与分组明细） |
| **Faithfulness** | 编造数字、把条款记错、材料里没有的东西被答出来 | 「检索没给材料所以如实说不知道」——它也会掉分（拒答折半，见 §4.3） |
| **Answer Relevance** | 答非所问、空话、只答一半、拒答 | 「答案很切题但事实是错的」——那是 Faithfulness 的活 |
| **关键事实命中率** | 「答得流畅但一个要点都没说到」（Agent 层最值钱的一列） | 同义改写的说法（规则判据只认字面，见 §4.3） |
| **成功率** | 路由错 / 被护栏拦 / 空回答 —— 三类「没答完」 | 「答完了但答错了」（那由三个指标拦） |
| **单 vs 多 Agent 增益** | 「拆了 Agent 却没有任何收益」 | 「收益来自机制还是来自运气」——靠「两条路只差一个自变量」保证（§6.1） |

### 1.4 配置面（阈值全在代码里，**不进 `.env`**）

```powershell
uv run python -c @"
from app.eval.settings import RagEvalSettings
s = RagEvalSettings()

print('自检             :', s.validate() or '通过')
"@
```

| 阈值 | 默认 | 作用 | 配错的后果 |
|---|---|---|---|
| `recall_threshold` | **0.70** | Recall 合格线 | 太高 → 换个 chunk 策略就红（渐成噪音）；太低 → 检索退化没人发现 |
| `faithfulness_threshold` | **0.70** | Faithfulness 合格线 | 太高 → 正常的同义改写被判失败；太低 → 编造数字也不拦 |
| `relevance_threshold` | **0.60** | Answer Relevance 合格线 | 比前两条低是刻意的：它是最主观的一维，当哨兵用、不当闸门 |
| `min_multi_agent_gain` | **0.15** | 多 Agent 相对单 Agent 的最低增益 | 定太高会让「机制有效但幅度小」被误判为无效；**负数**被 `validate()` 拦下（那等于把对照题的意义抹掉） |
| `top_k` | 5 | 检索条数 = Recall@K 的 K | 改它会让**历史报告不可比**（K 变了分母就变了） |
| `judge` | `rules` | 判分后端（rules/strict/llm） | 写成 `llm` 会让 CI 每次跑都花真金白银且不可复现 |
| `rerank` | `True` | 是否精排 | 关掉后 Recall 通常不变、但 top-1 命中率会降（第 10 步的 E2 结论） |

> ⚠️ 本步的配置项**全部走 `RagEvalSettings` 的默认值**，`app/config/settings.py` 里
> **没有加任何字段**。理由与第 13 步的缓存阈值完全一样（见 `13.cache-runbook.md` §1.4）：
> 它们是**语义选择**而不是环境差异 —— 「这套语料 + 这个 LLM + 这个判据」绑死，
> 换环境要重新校准。做成环境变量只会让「两份环境跑出两种判决」而没人知道谁对。
>
> **但阈值必须能被命令行覆盖**（`--recall-threshold 0.62` 等）：评测阈值的用途是
> 「卡住 CI」与「校准该定在哪」，这两件事都要求「不改仓库任何文件先试试」。
> 覆盖的落点是 `settings_from_args()`（CLI → 设置的**唯一映射处**，见 `run.py`）。

## 3. golden dataset：怎么标、怎么加、怎么防漂移

### 3.1 一条用例长什么样

```json
{
  "id": "return-shipping",
  "question": "无理由退货的运费谁承担？",
  "reference": "无理由退货的运费由买家承担；因商品质量问题发起的退货，往返运费由本店承担。",
  "key_facts": ["由买家承担", "质量问题"],
  "expected_sources": ["docs/kb/退货政策.md"],
  "expected_route": "rag",
  "role": "customer",
  "tags": ["退货", "运费"],
  "note": "答案里有两个方向相反的条件，是「答一半」最容易发生的样本"
}
```

| 字段 | 必填 | 作用 | 不带会怎样 |
|---|---|---|---|
| `question` | ✅ | 送进链路的**用户原话** | —— |
| `reference` | ✅ | 标准答案（Ragas 的 ground truth） | 只能做规则判分，没法量化「答得全不全」 |
| `key_facts` | 建议 | **必须命中**的事实点（归一后的子串） | 判分退回纯主观打分，离线不可复现 |
| `expected_sources` | ✅* | 该问题**应该**检索到的文档 | Recall 没有分母（`*` 除非显式声明 `expect_empty`） |
| `expect_empty` | —— | 「知识库里确实没有答案 / 走的是 data 分支」 | 这类用例会被当成「Recall 0 分」（本仓实测踩到，见 §7.3） |
| `expected_route` | agent 用 | 期望的路由分支 | agent 套件的路由准确率没得判 |
| `role` / `user_id` | agent 用 | 身份（影响 synthesis 模板与 data 分支行级过滤） | 对客/对内口径会走错 |
| `time_sensitive` | —— | 该问题应被判成强时效（不进缓存） | 第 13 步的 bypass 口径没得回归 |

### 3.3 判据的三层（golden set 怎么变成分数）

```
key_facts（必须命中的事实点）
    ├─► 规则层：归一后子串匹配 → fact_coverage（离线、可复现、可逐条追责）
    └─► 判官层：LLM/严格判官判「忠于材料 + 切题」（能判同义改写）

expected_sources（应该检索到的文档）
    └─► Recall@K：命中几份 / 漏哪几份（归一掉目录与扩展名）

reference（标准答案）
    └─► 判官的对照物（不参与规则判分）——「同义改写」这件事只能靠它
```

> ⚠️ `14.eval.md` §5 第二条的原话是「标注必须命中的事实后可用规则 + LLM 双重判分，更可靠」。
> 本仓把它落成**两条路各自有明确边界**（`metrics.py` 的 docstring 有完整表格）：
> 规则强在可复现、弱在同义；判官强在同义、弱在随机与成本。**没有一条判据同时强在两头** ——
> 所以「两条都过才算过」（`rag_eval._combine`），而不是「取平均」（平均会把「规则 0 判官 1」
> 变成 0.5，看起来像答了一半，而真相是事实点一个都没命中）。

### 3.4 加一条用例 / 改一条标准答案（三条硬约束）

```powershell
# 加完立刻验一次（**不要等到跑评测时才发现**）：
uv run python -c @"
from app.eval.dataset import load_dataset
ds = load_dataset('rag')
print(ds.summary())
print('最后一条:', ds.cases[-1].id, '| 事实点:', ds.cases[-1].key_facts)
"@
```

三条硬约束（不满足就**加载即抛**，`DatasetError`）：

| 约束 | 报错信息里会说什么 | 为什么必须有 |
|---|---|---|
| 必填字段齐全 | `缺少必填字段 'reference'` | 缺字段会让算分在半路崩，而那时已经花掉检索与生成的钱 |
| 有 `expected_sources` 或 `expect_empty=True` | `既没有 expected_sources 也没有 expect_empty=True` | Recall 的分母不存在；而「忘记写」与「本来就没有」必须区分 |
| `key_facts` 每一条都能在 `reference` 里找到 | `key_facts 里有 1 条不在 reference 里：['48 小时']` | **最值钱的一条**：它拦的是「标准答案与事实点来自不同用例」的复制粘贴事故 —— 那种错误不会让任何测试变红，只会让 Faithfulness 永久偏低，而人会先去怀疑检索 |

```powershell
# 亲眼看见这三条报错（用一段内联 JSON，不碰仓库文件）
uv run python -c @"

    {'id':'x','question':'q'},                                                        # 缺字段

    {'id':'x','question':'q','reference':'7 天内可退','key_facts':['48 小时'],
     'expected_sources':['s']},                                                       # 事实点对不上
```

```powershell
# 数据集的改动必须与代码改动分开提交：这样 review 时能一眼看出「改的是题还是算法」
```

### 3.6 为什么没有装 `ragas`（**本步最重要的一个决定**）

`14.eval.md` §3 把 `ragas` 列成依赖。本仓**没有**把它装进默认依赖，三条实测理由：

```powershell
# ① 它会换掉我们锁定的包（这是实测，不是推测）
uv add --optional eval "ragas>=0.2" --dry-run 2>&1 | Select-String -Pattern "uninstall|"
# 实测（uv pip install ragas 的解析结果）：Resolved 95 packages；Would install 22 packages；
#   Would uninstall 3 packages —— jiter 0.17.0→0.14.0、fsspec 2026.9.0→2026.7.0、rich 15.0.0→14.3.4
#   新增：langchain / langchain-openai / langchain-community / datasets / pandas / pyarrow /
#        instructor / scikit-network / diskcache / multiprocess / nest-asyncio / appdirs / …
```

② **它的判分内核是 LLM 打分**：`faithfulness` 要拆 claim 再逐条问模型「这条有依据吗」，
`answer_relevancy` 要反向生成问题再算相似度 —— 15 条 × 多次调用是真实开销，
而且**离线没法复现**（LLM 有随机性）。而本步的验收要求「低于阈值即阻断合并」——
一个「同一次提交今天 0.71、明天 0.68」的闸门会立刻被人关掉。

③ **它的口径本身是一段可读的定义**（Ragas 论文的贡献是「把 RAG 评测拆成可测量的几维」，
而不是某个不可替代的实现）。本仓把这几个维度**逐条实现成显式判据**，
判据名进报告（`key_facts` / `numbers_supported` / `answered` / `not_hedged` / `faithful` / `relevant`）——
掉分时能一眼看出是哪一条掉的，这不是黑箱分数能给的信息。

**本仓的做法（接口对齐、实现自持、可选对照）**：

| Ragas 指标 | 本仓的落点 | 一致性 |
|---|---|---|
| `context_recall` | `metrics.retrieval_quality` 的 `recall` | 同名同义（命中期望文档 / 期望文档总数） |
| `faithfulness` | `metrics.answer_quality` 的 `faithfulness` | 同名同义（是否忠于检索材料），判据是「事实点覆盖 + 数值支持率」 |
| `answer_relevancy` | `metrics.answer_quality` 的 `relevance` | 同名同义（是否切题），判据是「问题词项覆盖 + 事实点 + 不跑题」 |
| `AnswerCorrectness` | **不做** | 需要与标准答案做语义比对（一次额外 LLM 调用/条），而本步的闸门要能离线跑 |
| 真 ragas 作为对照 | 未接入 | 要接的话走 `uv sync --extra eval`（可选依赖组），**不要进默认依赖** |

> ⚠️ 想接真 ragas 做对照时，**必须**在报告里把 `judge` 写成 `ragas:<版本>`：
> 同一份答案在不同判官下分数不同，而报告里没有这一列时，两份报告放在一起会得出错误结论。

### 4.2 三指标各测什么（报告与 runbook 的唯一解释）

| 指标 | 回答的问题 | 涨了说明 | 掉了说明 |
|---|---|---|---|
| **Recall@K** | 该检索到的有没有检索到 | 分块/embedding/rerank 在变好 | 召回漏了 —— 后面两步再强也没用 |
| **Faithfulness** | 答案是否忠于检索材料（不编造） | prompt 的材料边界更严 | 模型在编，或检索没给它材料 |
| **Answer Relevance** | 答案是否切题 | 措辞更贴问题 | 答非所问 / 空话 / 拒答 |

⚠️ 三者**必须一起看**，因为它们的失败模式互相伪装（本仓实测）：

| 组合 | 真相 | 该去改哪里 |
|---|---|---|
| Faithfulness ↓ + Recall ↑ | **模型的锅**（材料给到了它没用） | synthesis 的 prompt / 材料渲染 |
| Faithfulness ↓ + Recall ↓ | **检索的锅**（材料没给到，模型只能编） | 分块 / embedding / rerank |
| Relevance ↑ + Faithfulness ↑ + **Recall ↓** | **最危险的一格**：答案流畅、切题、且「忠于它拿到的那点材料」，但那点材料根本不是答案 | 检索（只看后两个指标会以为一切正常） |
| 三个都 ↑ 但 `hits=0` | 答案来自模型自己的记忆，材料是空的 | 看 `context_block` 是不是空了（`expect_empty` 用例除外） |

### 4.3 打分公式（**权重写在代码里，不在配置里**）

`app/eval/metrics.py` 的模块 docstring 是唯一来源，这里抄一遍便于查：

```
Recall@K         = 命中的期望文档数 / 期望文档总数                     ∈ [0, 1]
faithfulness     = (0.6·事实点覆盖 + 0.4·数值支持率) × 不拒答系数
answer_relevancy = (0.5·问题词项覆盖 + 0.3·事实点覆盖 + 0.2·不跑题) × 篇幅系数
```

| 量 | 怎么算 | 为什么这么算 |
|---|---|---|
| 事实点覆盖 | 归一后子串命中数 / 事实点总数 | 主判据：可复现、可逐条追责（报告里列出缺哪几条） |
| 数值支持率 | 答案里的数字串（**≥2 位**）里有材料支撑的比例 | 编造政策条款最典型的形态就是改数字（「7 天」→「15 天」） |
| 不拒答系数 | 拒答时 **×0.5**（不清零） | 拒答不是幻觉，但它也没答问题；清零会惩罚「如实说不知道」这个正确行为 |
| 问题词项覆盖 | 问题去掉疑问词后的 **2-gram** 命中率 | 中文不做分词，2-gram 召回高、精度低 —— 正好适合当「切题」的粗判据 |
| 篇幅系数 | < 30 个归一字符时线性折扣（下限 0.3） | 一句话回答一个需要条件的政策问题，通常意味着没答完 |
| 数值支持率**单独不判失败** | 有数字不在材料里，但**至少命中了一个事实点** → 不算失败；一个事实点都没命中却给了数字 → 判失败 | 前者的典型是「以结算页金额为准」这类来自别处的数字（合规且正确）；后者才是「没材料还硬答」的签名 |

> ⚠️ 权重（0.6/0.4、0.5/0.3/0.2）**刻意不放进配置**：改它们等于改指标定义 ——
> 那不是运行时该调的东西（要改就改 `metrics.py` 并重跑基线）。阈值可以覆盖（§4.5），定义不行。

### 4.6 报告里的 `answerer` 三态（**别拿它们互相比较**）

| `--answer` | 答案来自 | Faithfulness 的含义 | 什么时候用 |
|---|---|---|---|
| `context`（默认） | 检索命中的**片段原文** | 定义上的 1.0（答案就是材料）→ 它退化成完整性检查；真正的信号在 Recall 与 Relevance | 量检索层（本步的验收口径） |
| `extract` | 从命中里挑最相关的几句 | 一半是「挑句启发式准不准」 | 「挑句值多少分」这个反向问题 |
| `llm` | 经 `llm_call` 门面打真模型 | 真正在量模型（但引入了随机性） | 端到端质量、prompt 改动的前后对比 |

> ⚠️ 本仓实测（§10.1 坑 3）：`extract` 模式的 Faithfulness **不是 1.0** ——
> 而它抽的每一句都逐字来自材料。也就是说那个分数量的**不是**「答案忠不忠于材料」，
> 而是「我的挑句启发式准不准」。这正是同义反复的一半：把评分器自己的缺陷算进了被测系统的分数里。
> 默认改用 `context` 就是为了避开这一格。

### 5.2 对照一次（挑句 vs 片段原文 —— 本步最重要的一个实验）

```powershell
uv run python -m eval.run --suite rag --answer extract --out-dir eval-reports
uv run python -m scripts.eval_report --diff <挑句.json> <片段原文.json>
```

三次实测（同一份 golden set、同一份检索、同一个判官）：

| 合成方式 | Recall | Faithfulness | Relevance | 结论 |
|---|---|---|---|---|
| 挑句（4~5 句，4-gram 排序，**第一版**） | 1.000 | **0.771** | 0.674 | 抽出来的答案常常是一串**小标题** |
| 挑句 + 长度破平局（5 句，每命中最多 2 句） | 1.000 | 0.918 | 0.760 | 标题被压下去了，但仍会漏句 |
| **片段原文（`context`，现在的默认）** | 1.000 | **1.000** | 0.824 | 语义唯一：答案就是材料 |

**这张表怎么读**（它决定了很多人的第一个疑问：「Faithfulness 1.0 是不是自证？」）：

* 挑句模式的 0.771 **不是**「答案不忠于材料」（抽的每句都逐字来自材料），
  而是「挑句启发式没挑中该挑的那句」。把评分器自己的缺陷算进分数里，是同义反复的一半。
* 片段原文模式的 1.0 是**定义上**的结果 —— 它不是「好消息」，而是「这一维退化了」。
  所以本步的验收看的是 **Recall（检索到了没有）与 Relevance（材料覆盖了问的东西没有）**。
* 想要「Faithfulness 真的在量模型」就必须用 `--answer llm`（真生成），
  代价是引入随机性（那时请把 `judge` 也换成 `llm`，并接受「两次运行差 0.1 是正常的」）。

### 5.3 本步落地时的实测基线（回填 `14.eval.md` §8 第 1 条用）

| 项 | 值 | 命令 |
|---|---|---|
| Recall@5 | **1.000** | `uv run python -m eval.run --suite rag` |
| Faithfulness | **1.000**（片段原文合成） | 同上 |
| Answer Relevance | **0.824** | 同上 |
| 逐维通过条数 | Recall 15/15 · Faithfulness 15/15 · Relevance 11/15 | 报告 §1 |
| 漏检的文档 | **0 份**（15 条用例的期望文档全部进 top-5） | 报告 §4 逐条一览 |
| 语料指纹 | `chunks=61 rev=1 hash=d3690c9b` | `--corpus-fingerprint` |

> ⚠️ **这不是「Recall 从 X% 提到 Y%」** —— 那句验收要的是**改动前后**两个数。
> 请用 §8.3 的 `--diff` 生成你自己的 X/Y：改一次分块策略或 embedding 模型，
> 各跑一次 `--out-dir`，然后 `--diff 旧.json 新.json`。可照做的步骤在 §8.3。

## 6. 单 Agent vs 多 Agent：量化收益怎么来的

### 6.1 两条路只差**一个自变量**（这是全部含量）

| | 多 Agent（本仓的图） | 单 Agent（对照） |
|---|---|---|
| 路由 | `router` 节点先判意图，再进对应分支 | **没有路由**：一个大 prompt「判断并回答」 |
| 材料 | `rag` 节点**先检索**，命中片段作为唯一材料喂给合成 | **不给材料**：模型凭参数记忆直接答 |
| 权限 | `router` 注入权限点，`synthesis` 按角色选模板 | 没有身份概念 |
| 护栏 / 缓存 | 输入输出两侧横切 / 语义缓存闸在检索之前 | 都没有 |

⚠️ **「单 Agent 不给材料」是刻意的，也是最容易被质疑的一处**，所以理由写在这里：
一个「单 Agent」如果也能自己调检索工具，那它就不是「一个大 prompt 全干」了 ——
它已经拥有多 Agent 的**核心机制**（工具调用本身就是一种分工）。
`7.agents_module.md` §5 第一条描述的正是这种「意图模糊、出问题分不清哪一环坏了」的形态。

于是对照实验测的是**「把检索材料交给模型」这件事值多少钱**：

* 单 Agent 的答案来自**参数记忆** → 政策里的天数、比例、条款号会漂移或编造
  （本仓语料是自建的政策文档，模型从未见过它，所以它的 Faithfulness 会很低 ——
  这不是「我们选了一个笨模型」，而是**任何**模型对未见过的内部语料都只能编）；
* 多 Agent 的答案来自**检索片段** → 事实点在材料里，逐字可核对。

### 6.2 跑一次对照（两种口径：真模型 / 离线可复现）

### 7.2 四条判据合成一个「成功」

```
成功 = ① route 判对 + ② Recall 达阈（不适用则跳过） + ③ Faithfulness 达阈
       + ④ Relevance 达阈  +  ⑤ 答完了（有答案 + 未被拦 + 无 refusal）
```

⚠️ **为什么路由也算进成功率**：路由错的轮次不可能成功（该查知识库却生成了 SQL），
而只看答案分数时，一次「碰巧答对」会掩盖路由已经坏了 —— 那是第 7 步最贵的 bug。

⚠️ **为什么 `cache=None`**（`build_default_graph` 里刻意不注入缓存）：
命中缓存时答案来自缓存而不是模型，于是「改了 prompt 之后评分变了吗」这个问题失去意义。
评测要的是**被测对象**，而缓存会把被测对象换掉。

### 7.3 两类用例「不适用 Recall」（本仓实测修正过的一处）

agent 数据集里有 6 条 `expect_empty`（`data` / `analysis` / `final` 分支与「知识库里没有答案」）。
它们**没有期望来源**，所以 Recall 的分母不存在 —— 把它们的 0 分算进平均，
会把「一次全绿的运行」显示成「Recall 0.36、成功率 20%」。

处置（`metrics.recall_for` + `aggregate`）：

```
Recall 的取值域 = [0, 1] ∪ {RECALL_NA}
    RECALL_NA（float('nan')）的含义是「这条不适用于 Recall」
    聚合时被跳过，并在报告的 extra 里留下 recall_applicable=<条数>
```

```powershell
# 亲眼看见这条区分：报告 1 的「逐维通过条数」与 recall_applicable
uv run python -c @"
import json, glob
path = sorted(glob.glob('eval-reports/eval-agent-*.json'))[-1]
payload = json.load(open(path, encoding='utf-8'))
overall = [g for g in payload['groups'] if g['name'] == '全部'][0]
print('条数:', overall['count'], '| Recall 适用条数:', overall['extra']['recall_applicable'])
print('Recall 平均:', overall['recall'], '| 逐维通过:', overall['passed'])
"@
```

> ⚠️ 这条区分的通用形态是：**「没测到」与「测出来是 0」必须能分开**。
> 混在一起的后果本仓实测过：6 条不适用用例把 Recall 从 0.90 拉到 0.36，
> 而报告看起来像「检索坏了」（见 §10.1 坑 6）。

### 7.4 判分材料是**五类来源**，不只是检索命中的片段

`agent_eval.material_for_judging()` 拼的是合成节点**真正看到的全部材料**：

| 来源 | 谁写 | 出现在哪条分支 |
|---|---|---|
| `docs`（知识库片段，带出处） | `rag_node` | rag |
| `rows`（SQL 查询结果） | `data_node` | data / analysis |
| `analysis`（对内解读的结论与要点） | `analysis_node` | analysis |
| `refusals`（没拿到的材料） | 各节点 / 图级兜底 | 全部 |
| `sql`（内部参考） | `data_node` | data / analysis |

> ⚠️ 第一版只把 `docs` 当材料，于是**所有 `data` 分支的用例 Faithfulness 恒为 0.6** ——
> 因为答案里的订单数、退款额来自 SQL 结果，而它们不在 `docs` 里（`data` 分支不检索知识库）。
> 症状极具误导性：报告说「模型编造了数字」，而实际上模型逐字引用了查询结果（见 §10.1 坑 9）。

## 10. 故障速查

### 10.1 本步实测撞到的 11 个坑

> 这些坑按「症状的误导性」排序 —— 越靠前的越容易让人去查错地方。

#### 坑 1：好答案里的一句「我这边看不到」被判成**拒答**

* **症状**：`kb-warranty` / `kb-shipping-fee` / `kb-enterprise` 三条**质量最好的回答**
  成了失败样本（Faithfulness 0.43~0.50），而它们逐字引用了材料。
* **根因**：`text.is_hedged` 第一版是「命中任一 `HEDGE_PHRASES` 就算拒答」。
  而合规的对客回答**会带免责说明**：「具体金额以结算页显示为准，我这边看不到您当前是什么等级」。
* **处置**：判据收紧成两条**结构性**条件（任一成立才算拒答）：
  ① 短回答（<40 归一字符）且含拒答措辞；② 开头 24 字符内出现拒答措辞**且**总长 <90。
  两条都带「短」这个条件，因为**长回答里的免责说明不改变「它已经答了问题」这个事实**。
* **通用教训**：判据在惩罚**正确的行为**时，症状看起来永远像「模型的问题」。

```powershell
uv run pytest -q -p no:cacheprovider tests/eval/test_eval_metrics.py -k "免责说明 or refuses_at_the_beginning" -v
```

#### 坑 2：`KeyError: 'answer_relevancy'`（阈值字典的键与指标名不一致）

* **症状**：第一次跑 `--suite rag` 直接崩，栈里只有一行 `KeyError: 'answer_relevancy'`。
* **根因**：`RagEvalSettings.thresholds()` 返回的键是 `relevance`（配置字段名），
  而 `rag_eval._score_row` 按**指标名** `answer_relevancy` 去查。
  两套名字并存 = 一次必然发生的 `KeyError`，而且它发生在**跑完所有用例之后**（钱已经花了）。
* **处置**：`thresholds()` 统一返**指标名**；配置字段名只保留在 `RagEvalSettings` 里
  （并留一个 `relevance_threshold_ceiling` 属性解释这层映射）。
  有一条用例钉住这件事（`test_settings_thresholds_use_metric_names`）。
* **通用教训**：**同一个量有两套名字**是最廉价的 bug 温床（另一个例子见坑 3 的 `relevance`/`answer_relevancy`）。

#### 坑 3：挑句合成抽出一串**小标题**（Faithfulness 0.771）

* **症状**：`extract` 模式下 15 条里有 4 条的答案是**纯标题**
  （`### 发票丢了可以补开吗。`、`2. 运费标准。`），事实点覆盖 0.00。
* **根因**：排序用「问题 4-gram 覆盖率」，而文档里的**小标题**几乎总是问题词的超集
  （`### 如何修改收货地址？` 命中「地址/收货/修改」），于是它与正文答案句**完全并列**；
  并列时排序退化成「谁在文档里更靠前」——而标题永远靠前。
* **处置（两步，都留在代码里）**：
  ① 破平局项用**长度**（`0.1 × min(句长/40, 1)`）——长度是与语料格式无关的性质，
  换成 `.txt` 语料时它对同一件事仍然成立（而「是不是标题」要靠 Markdown 记号判断，那会在别的格式上失效）；
  ② **每个命中最多贡献 2 句**（`PER_HIT_SENTENCES`）—— 否则排第一的文档把名额吃光，
  而答案需要的第二个条件常常在第二份文档里。
  实测：0.771 → 0.918（长度破平局）→ 1.000（改用片段原文，见 §5.2）。
* **通用教训**：**启发式的失败会伪装成被测系统的失败**。判别方法是问一句：
  「把这一步换成完美的实现，分数会变吗？」会变 → 那个分数量的不是被测系统。

#### 坑 4：`'coroutine' object is not iterable`（同步/异步接线不匹配）

* **症状**：`--suite agent` 的每条用例都记一条拒答
  `知识库检索这一步没做成（TypeError）：'coroutine' object is not iterable`，
  图跑完了、答案也生成了（模型看到「检索不可用」就如实说拿不到材料），
  **Recall / Faithfulness 双双为 0** —— 看起来像「检索质量崩了」。
* **根因**：`app/tools/retriever.retrieve_docs` 是**同步**函数（它做 `list(searcher(...))`），
  而 `Retriever.search` 是 async。第一版把 async 那一个直接塞进 `GraphRuntime.search`。
* **处置**：评测侧提供两个检索器，契约写清：
  `build_default_searcher`（async，给 `rag_eval`/`compare` 用）与
  `build_sync_searcher`（内部 `ThreadPoolExecutor + asyncio.run`，给图的同步工具层用）。
* **通用教训**：**注入点的契约包含同步/异步**，而类型标注（`Searcher = Callable[..., Any]`）
  不会替你检查这件事。形状不对时优先怀疑接线，而不是怀疑算法。

#### 坑 5：一位数字被当成「编造信号」（干净的寒暄被判不通过）

* **症状**：`final-greeting`（「你好」）的答案是「你好！我是电商平台的客服助手，很高兴为你服务」，
  报告却写着 `材料里没有的数字：['1']（**编造信号**）`，Faithfulness 0.600 → 失败。
* **根因**：`unsupported_numbers` 第一版抽 `[0-9]+`，而答案里的 `[1]`（引用编号）也算数字。
* **处置**：数字串改成**至少两位**（`[0-9]{2,}`）—— 一位数字在中文回答里遍地都是
  （引用编号、`第 1 条`、`1 元`），假阳性远高于信息量。
  另外「有数字不在材料里」**单独不让分数失败**：只有「一个事实点都没命中却给出了数字」
  才是「没材料还硬答」的签名（§4.3 的表格）。
* **通用教训**：判据的**假阳性**要把「它拦住了什么」一起看。一条爱误报的判据，
  最终会被人整体关掉 —— 那时它连真阳性也拦不住了。

#### 坑 6：`compare` 报告的汇总表全是 0.000（同一份报告自相矛盾）

* **症状**：对照报告的第 1 节写着「用例条数 0 / Recall 0.000 / ✗ 未通过」，
  而第 3 节的对照表里明明是一串 1.000。读的人第一反应是「评测坏了」。
* **根因**：`compare` 套件**只有对照表、没有逐条 `rows`**，而 `Report.overall()` 只从 `groups` 里找。
* **处置**：`overall()` 在 `groups` 为空时退回「第一个方案那一行」（`comparison.variants[0]`）。
* **通用教训**：报告的**每一节都必须由同一份事实渲染**。一处读不到就退回 0 的写法，
  会让报告自我矛盾 —— 而自我矛盾的报告比没有报告更危险（它会被信）。

#### 坑 7：中文数字归一顺序错，`二十四` → `十4`

* **症状**：`normalize_text('二十四小时')` 得到 `十4小时`，于是「24 小时」这条事实点永远判不命中。
* **根因**：`十` 被放进了「单个汉字数字」的替换表里（`十`→`10`），
  于是 `四` 先把 `二十四` 变成 `二十4`，而正则 `([0-9])?十([0-9])?` 只匹配到 `十4` 那一截。
* **处置**：把 `十` **从单字表里拿出来**，只由一个专门的规则处理；
  并固定处理顺序为「全角→小写→单个汉字数字→`十` 复合数→去标点空白」。
  三条用例钉住（`十五天`→`15天`、`二十个月`→`20个月`、`二十四小时`→`24小时`）。
* **通用教训**：**归一化是有顺序的**，而顺序错了不会抛异常，只会让某些写法永远对不上。
  凡是有「多步替换」的地方，都要用例把中间形态钉住。

#### 坑 8：`RagEvalSettings(suite=...)` 写错**不报错**，只是分数偏低

* **症状**：`scripts/eval_demo --scenario agent` 的 Faithfulness 只有 0.540、成功率 10%，
  而同一个数据集用 `eval/run --suite agent` 跑是 0.910 / 70%。两者差得很远却都不报错。
* **根因**：`run_suite` 里 agent 套件要靠 `settings.suite == "agent"` 才会走
  `build_default_graph` 与 agent 专属阈值；`eval_demo` 第一版对所有场景都传了
  `suite="rag"`（只有 compare 例外），于是 agent 场景用了 rag 的口径。
* **处置**：`eval_demo.run()` 显式按场景给 suite，并在注释里写明「suite 写错不报错」这件事。
* **通用教训**：**枚举型配置写错时最该做的事是「立刻报错」**。
  这里没做到（`RagEvalSettings.suite` 是普通 str），所以至少要用例把一个「套件 → 口径」的映射钉住
  （见 `test_suite_names_map_to_dataset_files`）。

#### 坑 9：只把 `docs` 当判分材料 → 所有 `data` 分支假性掉分

* **症状**：`data` 分支的三条用例 Faithfulness 恒为 0.6，报告说「模型编造了数字」。
* **根因**：`agent_eval.score_agent_row` 第一版只拼 `state['docs']` 当材料，
  而 `data` 分支的答案来自 `state['rows']`（SQL 结果）—— 它不在 `docs` 里（那条分支不检索知识库）。
* **处置**：抽出 `material_for_judging(state)`，把**五类来源**（docs / rows / analysis / refusals / sql）
  一起拼成材料，并且**判官与规则判分用同一个函数算材料**
  （否则判官与规则分会在「材料是什么」这个前提上分叉，而 `_combine` 只能合并结论）。
* **通用教训**：Faithfulness 的分母是「**这一轮真正看到了什么**」。
  在多分支系统里，这个问题的答案随分支而变 —— 用一句「拼 docs」代替它，必然在某个分支上错。

#### 坑 10：全量回归会把**向量库清空**（评测突然全 0）

* **症状**：`--suite rag` 突然全部 `Recall 0.000`，报告里 15 条用例的
  `retrieved_sources` 全是空列表；而 `rag_chunks where is_active` 数出来是 **0**。
* **根因**：`tests/test_db_migrations.py::test_migration_round_trip_is_repeatable` 会
  `alembic downgrade base` → **`DROP TABLE rag_*`** → `upgrade head` 建回来的是**空表**。
  也就是说「跑一次全量测试」= 「清空知识库」。
  这条代价在 `test_db_migrations.py` 的 docstring 里**早就写明了**（第 10 步的坑），
  并明确要求「跑完本用例后再执行一次 `load_knowledge_base`」。
  本步实测用探针确认了肇事者就是它：
  ```
  start=61
  61 -> 0 于 tests/test_db_migrations.py::test_migration_round_trip_is_repeatable
  ```
* **处置（顺序纪律）**：**先跑完全量回归 → 再灌语料 → 再跑评测**。
  写进本文开头（🖥 执行位置那一块）与 §1.1。
* **通用教训**：**「清库」与「评测」是全仓最容易撞上的两条路径**。
  凡是「分数突然全 0」的现场，第一件事是数一下语料还在不在（一条 SQL，两秒），
  而不是去怀疑 embedding 或 rerank。

```powershell

from app.db.session import get_read_engine
from sqlalchemy import text
with get_read_engine().connect() as c:
    print('活跃片段:', c.execute(text('select count(*) from rag_chunks where is_active')).scalar())
"@
# 0 → `uv run python -m scripts.load_knowledge_base`（约 45s）后再跑评测
```

#### 坑 11：沙箱里 `tmp_path` 不可写（6 个 error 的来源）

* **症状**：报告落盘的用例 `PermissionError: [WinError 5]`，而它们单独跑又可能过。
* **根因**：本机沙箱不允许写系统临时目录（与 `tests/test_config.py` 那 6 个 error 同一个环境限制）。
* **处置**：本步的落盘用例**不用 `tmp_path`**，改用仓库内可写的
  `.pytest-tmp/eval-tests/<uuid>/`（`tmp_dir` 装置，用例结束即删）。
* **通用教训**：新增用例时先看**已知的环境限制清单**（`11.observability-runbook.md` 的状态表里
  一直记着那 6 个 error），不要给基线额外加 error —— 那会让「多了几个 error 是不是我改坏的」变得无法判断。

### 10.2 症状 → 去哪查

| 症状 | 先查 | 命令 |
|---|---|---|
| 全部 `Recall 0.000` | 语料还在吗 | §10.1 坑 10 的那条 SQL |
| `Recall` 正常但 `Faithfulness` 偏低 | 是模型编还是判据误报 | `--show --case <id>` 看 `findings` 与 `unsupported_numbers` |
| `answerer` 一列不同 | **分数不可比** | `--diff` 会先警告口径不同（§8.3） |
| 一条用例永远失败 | 它的 `expected_sources` 对不对 | 先手工 `hybrid_search` 看一眼 |
| `--suite agent` 全部失败 | 检索器是同步的那个吗 | §10.1 坑 4（看拒答原因） |
| 判分看起来「松」 | 判官是哪个 | 报告的 `judge` 列（`rules` / `strict` / `llm:*`） |
| 退出码 2 | 环境还是配置 | 报错里那句 `[评测无法启动] ...` |
| 报告读不了 | schema 对不对 | `load_report` 会说是哪个 schema |

### 10.3 三个反直觉的读数（别当成 bug）

1. **`Faithfulness = 1.000` 在 `context` 模式下是正常的**：答案就是材料（§5.2）。
2. **`Recall = 0.000` 对单 Agent 是定义上的**：它没有检索环节（§6.3）。
3. **`recall_applicable < count`**：有 `expect_empty` 的用例不参与 Recall（§7.3）。
