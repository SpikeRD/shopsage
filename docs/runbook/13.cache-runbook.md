三条铁律：

1. **判「命中」只有一个地方**（`core.judge`），阈值只在那里被读。
   两个地方读阈值 = 两条不同的命中线，而它们的差别只在边界样本上显形 —— 那种 bug 会活很久。
2. **写进缓存的键必须由「读那一步」决定**。本步有三处非对称会直接导致「写完读不到」：
   指纹里的参数、拼问题用的消息串、时间戳的时钟域（§10.1 坑 1/2/3）。
   它们的共同症状都是「命中率恒为 0」，而**代码看起来完全正确**。
3. **强时效数据（订单/库存/物流）不进缓存**，判据只看**问法**不看 route
   （`data` 分支里既有「本月退货几单」也有「我的订单到哪了」）。

另一条（本步最贵的认知）：**「相似」的分布里没有天然的大缝**。
实测（bge-m3）「怎么样才能退货」= 0.9865，而语义上完全等价的「退货流程是什么」只有 **0.8835**。
所以阈值不是「调到能分开两个峰」，而是**在漏报与误报之间选一个取舍**，
而那个取舍必须由第 14 步的 golden set 定 —— 本文只给分布与默认值（§3.3）。

## 1. 环境与前提

### 1.0 本步的链路（两段式：查 → 生成 → 写，且三处成本递增）

```
  一次问答（route=rag）
        │
        ▼
┌─ app/agents/rag.py::rag_node ───────────────────────────────────────────────┐
│  ① 策略判定（intent 正则，**2µs**）                                          │
│        │ 强时效（订单/库存/物流）──► bypassed：不查也不写，直接去检索           │
│        ▼                                                                     │
│  ② Redis 精确匹配（`question_hash`，**0.2ms**）                               │
│        │ 命中 ──► 返回答案 + 出处（**不检索、不生成**）                         │
│        ▼ miss                                                                │
│  ③ 版本查询（`cache_corpus_versions`，**0.5ms**，一次主键 select）             │
│        ▼                                                                     │
│  ④ 问题 embedding（**先查 Redis 的向量缓存**；miss 才算：本地 30ms / API 计费）  │
│        ▼                                                                     │
│  ⑤ pgvector 相似度查询（HNSW，**1~2ms**）                                     │
│        │                                                                     │
│        ▼                                                                     │
│  ⑥ core.judge：完全匹配不走阈值 / 相似度 ≥ 0.93 命中 / 灰区保守不命中            │
│        │ 命中 ──► 返回答案 + 出处 + 年龄                                       │
│        ▼ miss                                                                │
│  ⑦ 正常检索（hybrid_search + rerank，第 10 步）                                │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │  state["cache_context"]（**可序列化的字段**）
                                ▼
┌─ app/agents/synthesis.py ────────────────────────────────────────────────────┐
│  `cached_answer` 非空 → **直接返回它，不打模型**（E1 的落点）                    │
│  否则 → 打模型生成 → 写缓存（`Cache.record(**cache_context)`）                 │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                ▼
                       cache_semantic_entries（Postgres）
                       + Redis 的精确匹配快路径与向量缓存
```

**每个环节「拦得住什么 / 拦不住什么」**（与 [`8.graph-runbook.md`](8.graph-runbook.md) §1.0 同口径）：

| 环节 | 拦得住 | 拦不住 / 需要别的环节 |
|---|---|---|
| 策略闸（`decide`） | 订单/库存/物流这类**问法**明确的强时效问题 | 「本月退货几单」也随时间变，但它被判成普通类（可缓存 24h）—— 那是**有意**的取舍 |
| scope（`user_id + role`） | 用户 A 的答案给用户 B、内部查询的答案给客户 | 「同一个人的两次不同意图」—— 靠问题串本身区分 |
| 版本指纹 | 知识库/prompt/embedding 模型/检索参数变了之后的旧答案 | 「同一版知识库里某份文档被改」（全局失效，不是按文档失效，见 §5.2） |
| 阈值（0.93） | 完全不相关的问题（实测 0.49~0.58） | 「相关但答案不同」（0.80~0.90）—— 靠保守阈值 + 灰区账目 |
| TTL | 时间本身带来的陈旧 | 「数据变了但时间没到」—— 那是版本失效与主动失效的活 |
| Redis 快路径 | 「完全同一句话」的重算（刷新、反复点开同一 FAQ） | 同义改写 —— 那要走到 ⑤ 向量查询 |
| 降级回落 | 缓存整体不可用（Redis 挂了照跑） | **多副本命中率被副本数除** —— 只能靠指标与 `/health` 看见 |

> 因为「怎么退货」不含政策类关键词（`policy_doc` 的正则是

> 症状是「脚本随机变慢/偶发失败」。

### 2.3 Redis 快路径与 embedding 缓存的分工（为什么顺序不能换）

```powershell
uv run python -c @"
from app.cache.backend import CacheKeySpace
from app.cache.stores import ScopeContext
keys = CacheKeySpace(namespace='cache', instance='dev')
print('条目 key :', keys.entry(ScopeContext('customer:2', 'fc97596cf243a1b2'), '怎么退货'))
print('scope pattern:', keys.scope_pattern('customer:2'))
print('向量 key :', keys.embedding(model='BAAI/bge-m3', text='怎么退货'))
print('向量 key 里没有原文吗:', '怎么退货' not in keys.embedding(model='BAAI/bge-m3', text='怎么退货'))
"@
```

```
条目 key : cache:dev:entry:customer:2|fc97596cf243a1b2|82fdffdb7da0c42cc31d42b8d4867bd2
scope pattern: cache:dev:entry:customer:2|*
向量 key : cache:dev:embed:BAAI/bge-m3:82fdffdb7da0c42cc31d42b8d4867bd2
向量 key 里没有原文吗: True
```

三条读法：

* **`scope` 在第一段、`fingerprint` 在第二段**：`|` 是分隔符而 `scope` 里含冒号 ——
  所以「分隔符不能有歧义」这件事是靠「`|` 不出现于 scope」保证的（`scope_for()` 的职责，
  有用例钉住）。少一段就会跨用户命中。
* **向量 key 里没有原文**：问题可能含 PII（手机号、订单号），而 key 会进日志、指标、`redis-cli` 输出。
  代价是「同一个问题」必须靠 hash 对上 —— 这没问题，因为 hash 的输入就是那个问题本身。
* **`scope_pattern` 带着 `entry:` 这一段**：第一版漏了它，于是「按 scope 清缓存」的通配
  什么都匹配不到（静默返回 0）。见 §10.1 坑 5。

## 3. 命中判定：阈值、灰区与强时效（本步的核心）

### 3.1 一次查询要过五道闸（顺序即语义）

| # | 闸 | 判据 | 结果 |
|---|---|---|---|
| ① | **策略闸** | `decide(问法)` → `bypass`？ | `bypassed`（**连存储都不碰**） |
| ② | **完全匹配** | `scope + fingerprint + question_hash` 命中？ | `hit`（**阈值完全不参与**） |
| ③ | **相似度闸** | 最近邻 ≥ `semantic_threshold`？ | `< floor` → `miss`；`floor ≤ sim < threshold` → `miss`（灰区，带出候选） |
| ④ | **时效闸** | `CacheEntry.is_expired()`？ | `stale`（与 `miss` **分开报**） |
| ⑤ | **版本闸** | `entry.revision == 当前 revision`？ | `stale` |

```powershell
uv run python -c @"
from app.cache.settings import CacheSettings
from app.cache.core import decide, classify_cache_intent, is_time_sensitive
for text in ('怎么退货', '退货流程是什么', '我的订单 1024 到哪了', '还有货吗', '现在这个卖多少钱', '你们几点上班'):
    d = decide(text)
    print(f'{text:22s} tier={d.tier:15s} {d.summary()}')
"@
```

```
怎么退货                   tier=normal          可缓存 86400s（normal）
退货流程是什么              tier=policy          可缓存 604800s（policy：policy_doc）
我的订单 1024 到哪了        tier=time_sensitive  不缓存（time_sensitive：强时效数据必须实时查库）
还有货吗                   tier=time_sensitive  不缓存（time_sensitive：强时效数据必须实时查库）
现在这个卖多少钱            tier=time_sensitive  不缓存（time_sensitive：强时效数据必须实时查库）
你们几点上班                tier=normal          可缓存 86400s（normal）
```

> ⚠️ 「完全匹配不走阈值」（②）是刻意的：同一句话就是同一个问题，
> 让它再跟自己的向量比一次，只会在「维度/浮点变化」时造出
> 「自己跟自己的相似度不到阈值」这种无法解释的怪事。
>
> ⚠️ `stale` 与 `miss` 必须分开（④⑤）：两者的**运维动作完全不同** ——
> 「未命中」是正常的（命中率就是它算出来的），而「失效」意味着**发生了某件事**
> （时间到了 / 知识库变了）。混成一个 `None`，「知识库更新之后缓存有没有被清掉」
> 这条验收就永远答不出来。

### 3.2 灰区：为什么 `floor` 与 `threshold` 是两个数

```powershell
uv run python -c @"
import time
from app.cache.core import LookupRequest, judge, CacheDecision
from app.cache.stores import CacheEntry, CacheMatch
from app.cache.settings import CacheSettings

s = CacheSettings()
def entry(q='怎么退货', revision=1):
    # ⚠️ revision 必须与 request 里的那一个一致，否则第 ⑤ 道闸（版本）会先判 stale
    return CacheEntry(scope='customer:2', fingerprint='fp', question=q, raw_question=q,
                      embedding=(1.0,), answer='答案', ttl_seconds=3600,
                      revision=revision, created_at=time.time())
def req(**kw):
    base = dict(question='退货流程是什么', raw_question='退货流程是什么', scope='customer:2',
                fingerprint='fp', revision=1,
                decision=CacheDecision(action='cache', tier='normal', ttl_seconds=3600))
    base.update(kw); return LookupRequest(**base)

for sim in (0.99, 0.93, 0.929, 0.85, 0.80, 0.79, 0.30):
    log = judge(req(candidates=(CacheMatch(similarity=sim, entry=entry()),)), settings=s)
    print(f'sim={sim:.3f}  outcome={log.outcome:9s} nearest={"yes" if log.nearest else "no":3s}  {log.detail[:52]}')
"@
```

```

第 14 步的 golden set 校准就是拿这两个数加上人工标注的样本做的。

> 所以「等一分钟答案会不会变」这件事只能从**问法**里读。

## 4. 存储：三套实现、一场降级棋、一个时钟问题

### 4.1 降级矩阵（四格，**每一格都可用**）

| Redis | 缓存表（Postgres） | 条目存储 | 相似度查询 | 结果缓存 |
|---|---|---|---|---|
| 可用 | 可用 | Postgres | HNSW 索引（1~2ms） | Redis |
| 可用 | 不可用 | Redis | **客户端全量算**（慢但正确） | Redis |
| 不可用 | 可用 | Postgres | HNSW 索引 | 进程内存 |
| 不可用 | 不可用 | 进程内存 | 暴力相似度 | 进程内存 |

**第一列的四种组合全部可用是刻意的**：缓存的价值是「让主路径更快」，

### 4.3 跨机器时钟：为什么时间戳要「对齐到数据库那一边」

本机实测的时钟差（Windows 开发机 ↔ VMware-Linux 上的 PostgreSQL）：

```powershell
uv run python -c @"
import time
from sqlalchemy import text
from app.db.session import get_read_engine
for _ in range(3):
    t0 = time.time()
    with get_read_engine().connect() as conn:
        db_now = float(conn.execute(text('select extract(epoch from now())')).scalar_one())
    t1 = time.time()
    print(f'db_now - client_mid = {db_now - (t0 + t1) / 2:+.3f}s （rtt={(t1 - t0) * 1000:.1f}ms）')
"@
```

```
db_now - client_mid = -1.879s （rtt=33.6ms）
db_now - client_mid = -1.892s （rtt=3.5ms）
db_now - client_mid = -1.892s （rtt=2.1ms）
```

**差了将近 1.9 秒**（VM 的时钟比 Windows 快）。这件事的直接后果（本仓实测踩到）：

* 应用写入 `expires_at = 应用时钟的 now + 1 秒`，数据库看它是**未来 2.9 秒**；
* 于是那条 `ttl_seconds=1` 的条目在库里继续「新鲜」将近 3 秒；
* `count()` / `purge()`（它们问的是数据库的 `now()`）慢半拍 ——
  症状是「明明配了 1 秒 TTL，计数还是 2 条 / 回收删了 0 条」。

**处置**：写库时把应用侧的时间戳**平移到数据库的时钟域**（`epoch + skew`），读回来再平移回去 ——
于是**存储里的 `created_at` / `expires_at` 与数据库的 `now()` 是同一个口径**，
SQL 里的 `expires_at >= now()` 与 Python 里的 `CacheEntry.is_expired()` 得到同一个答案。

```powershell
uv run python -c @"
from app.cache.stores import PostgresEntryStore
from app.cache.schema import VECTOR_DIM
store = PostgresEntryStore(dimension=VECTOR_DIM)
print(f'测量到的时钟偏差 = {store.clock_skew():+.3f}s（db_now - app_now）')
"@
# 实测：测量到的时钟偏差 = -1.892s（db_now - app_now）
```

> ⚠️ 为什么不干脆「统一用应用时钟」：`purge()` 是一条 `DELETE ... WHERE`，
> 它天生要在数据库里过滤（否则要先 `SELECT` 全表回内存）。让存储侧的时间戳
> **服从数据库时钟**，代价只是一次 `select now()`（每个 store 实例缓存一次），
> 换的是「一条不会因为 NTP 漂移而失准的 TTL」。
>
> ⚠️ **生产上两台机器的时钟一般是对齐的（NTP），所以这个坑在开发机上更常见** ——
> 但它的另一面是：**一旦生产上出现时钟漂移，症状就是「TTL 不准」，而没有任何报错**。
> 所以这条处置是「防御性的」，不是「只为了开发机」。

### 4.4 跨节点只能传可序列化的东西（三处非对称，本步最贵的坑）

写缓存需要的东西（问题串 / scope / 指纹 / 版本 / 分档 / TTL）**全部来自「读那一刻」**，
而它们在 `rag_node` 里产生、在 `synthesis` 里使用。中间隔着 LangGraph 的 state：

```powershell
uv run python -c @"
import app.agents.state as s, app.graph.state as g
fields = ('cached_answer', 'cache_info', 'cache_params', 'cache_context')
print('agents/state :', {f: f in s.GraphState.__annotations__ for f in fields})
print('graph/state  :', {f: f in g.GraphStateDoc.__annotations__ for f in fields})
"@
```

```
agents/state : {'cached_answer': True, 'cache_info': True, 'cache_params': True, 'cache_context': True}
graph/state  : {'cached_answer': True, 'cache_info': True, 'cache_params': True, 'cache_context': True}
```

⚠️ **四个字段全是 `dict` / `str` —— 这不是风格，是硬约束**。实测：

| 想传的东西 | 结果 |
|---|---|
| `state["cache_prepared"] = prepared`（dataclass） | **被 LangGraph 静默丢掉**（checkpointer 的 msgpack 序列化不接受它）→ 症状：写了但永远不命中 |
| `state["cache_write"] = closure`（闭包） | `TypeError: Type is not msgpack serializable: function`（直接抛） |
| `state["cache_context"] = {...}`（字符串/整数/dict） | ✅ 正常穿过 |

所以最终的设计是：`rag_node` 只放**重建一次写操作所需的全部字段**，
`synthesis` 把它们喂回 `Cache.record(**context)`。三处非对称（指纹参数、消息串、时钟域）
合起来就是 §10.1 的前三条坑 —— 它们的症状完全一样（**命中率恒为 0**），
**代码各自看起来都对**。

## 5. 三级失效：TTL / 主动失效 / 版本失效

### 5.1 TTL（第一级）——时间到期

```powershell
uv run python -m scripts.cache_demo --scenario ttl
```

```
  ✅ TTL 之内命中
      age=0.0s / ttl=3600s
  ✅ TTL 之后**判 stale**（不是 miss —— 两者的运维动作不同）
      TTL 已过（3601s > 3600s）
  ✅ 过期条目仍在存储里（**没被删**）—— 版本失效靠的就是「旧行留着」
      is_expired=True，只能靠 TTL/回收清掉
```

> ⚠️ 它是**时间旅行**（`prepare(now=...)`）而不是 `sleep(3601)` ——
> 后者会让用例/演示慢一小时，且与「TTL 判定」这件事毫无关系。
>
> ⚠️ Redis 侧也有 TTL（`SET ... EX`），但它比应用层 TTL **长 60 秒**
> （`backend.KEY_VALUE_TTL_GRACE_SECONDS`，口径在 `backend.key_value_ttl()` 这一个函数里）。
> 顺序反了的话「条目消失了」与「条目过期了」在排障时无法区分 ——
> 前者连一条账目都没有（`judge` 看不到它），后者可以说出「躺了 3601s / TTL 3600s」。

### 5.2 版本失效（第三级）——知识库/配置变了

      版本 2 → 3；新指纹 51b651a37ad1（与旧的 fc7ff4c3869e 不同）→ 对新指纹来说根本没有候选
  ✅ 旧条目**仍在存储里**（2 条）—— 失效 ≠ 删除（可解释、可回滚）
      真正回收靠 `scripts/cache_report.py --purge`（只删已过期的）
      ⚠️ 本场景**真的推进了知识库版本**（只增不减）——它会让所有旧缓存失效，这正是「版本失效」的定义。
```

**入库路径怎么触发它**（`app/rag/ingest.py` 的 `on_change`）：

```powershell

```

> ⚠️ **「重复入库不 bump」这条很值钱**：入库是幂等的（`ingest_document` 指纹没变就短路），
> 而「每跑一次同步就白清一次缓存」会让命中率掉一个坑，看起来只是「偶尔抖一下」。
> `ingest_document` 只在 `report.doc_changed` 为真时调回调。
>
> ⚠️ 全局失效（而不是「只失效引用了被改文档的那些问题」）是**刻意的保守口径**：
> 「哪条缓存引用了哪份文档」需要缓存里存文档清单并在每次查询时逐个比对，
> 而它的收益（少清几条）远小于它的风险（漏清一条就是旧答案出网）。
> 将来要按文档失效，接口不需要变（把 `fingerprint_for` 的 `corpus_revision` 换成按 source 取版本即可）。

### 5.3 主动失效（第二级）——按问题 / 按 scope / 回收

```powershell
# 先造几条（演示脚本会写），然后：
uv run python -m scripts.cache_report --invalidate-scope customer:2
# 实测：已让 scope=customer:2 的 N 条缓存失效（行保留，仅标记失效）
# 想看四态的健康读数：uv run python -m scripts.cache_report --health
```

| 函数 | 粒度 | 谁调 | 落点 |
|---|---|---|---|
| `invalidate_document(store, scope=…, question=…)` | 一条 | 人工（答案错了）、内容运营 | **`fingerprint=""` 通配**：调用方不必知道指纹 |
| `invalidate_scope(store, user_id=…, role=…)` | 一个身份 | 数据主体删除请求、越权修复 | 整批 `is_active=false` |
| `purge_expired(store)` | 过期行 | cron / `--purge` | 行了留着的旧行才需要它 |

> ⚠️ `fingerprint=""` 是**通配**（不是「匹配空指纹」）：`invalidate_document` 的语义是
> 「不再需要它了」，而调用方（人工、注销流程）**不该**需要知道指纹是什么 ——
> 那是缓存内部的版本细节。要求调用方提供指纹，等于让「删一条缓存」变成一件
> 要先去查 `fingerprint` 的事。三个实现（内存 / Postgres / Redis）都有这条语义，有用例钉住。

> ⚠️ 这三条路径**都不返回 `None`**：它们返回「删了几条」。理由是运维时最先问的问题就是
> 「到底删掉了没有」—— 一个返回 `None` 的失效函数在「缓存还是旧的」这一刻无法回答自己是否生效，
> 而它最可能的失败原因是**没生效**（scope 拼错了、问题串不一致）。

### 5.4 结果缓存（`result_cache_get/set`）——与语义缓存完全不同的一档

```powershell
uv run python -c @"

print('读:', result_cache_get(kind='report', key='u2:2026-09'))
print('未命中:', result_cache_get(kind='report', key='u2:2026-10'))
try:
    result_cache_set(kind='report', key='u2:2026-09', value={1, 2}, ttl_seconds=600)
except Exception as exc:
    print('不可序列化的值:', type(exc).__name__, exc)
try:
    result_cache_set(kind='report', key='u2:2026-09', value=1, ttl_seconds=0)
except Exception as exc:
    print('TTL=0:', type(exc).__name__, str(exc)[:44])
"@
```

```
写: 137 字节
读: {'rows': [{'order_id': 1024, 'amount': '129.00'}], 'total': 1}
未命中: None
不可序列化的值: ResultCacheError 结果缓存的值无法 JSON 序列化：类型 set 不可 JSON 序列化。请先转成基础类型（`model_dump()` / `asdict()` / `int()`），缓存层不做隐式转换。

**两者为什么都要有**（`13.cache.md` §2 列了四组接口）：

| | 语义缓存 | 结果缓存 |
|---|---|---|
| 键 | 问题的**向量**（相似即命中） | 调用方给的**字符串**（完全匹配才命中） |
| 值 | 答案 + 出处 + 时间戳（要溯源） | 任意 JSON |
| 正确性来源 | **阈值 + 溯源** | **键本身足够精确** |
| 判错的后果 | **答错问题**（最严重） | 拿到旧结果（调用方自己知道键意味着什么） |
| 谁用 | RAG 问答链路 | 报表、聚合、外部只读查询 |

> ⚠️ 把结果缓存做成语义的，等于让「本月报表」与「上月报表」有可能互相命中 ——
> 而那是一个没人能解释的错误。

|---|---|

> ⚠️ 「命中的那一条没过期就重写」被明确拒绝，是因为它会**掩盖缓存的年龄**：
> 每次用户问都重新生成、重新写一遍，缓存里那条的 `created_at` 永远是刚才 ——
> 于是「这条答案到底多久没被真正校验过」永远查不出来（而它恰恰是排障第一问）。
>
> ⚠️ 「指纹对不上就拒绝写入」那道闸是**锁**，不是选项：它由
> `app/agents/rag.remember_answer` 从「读那一步的 `cache_context`」算出来并显式传入。
> 它是本步实测踩到坑之后补上的 —— 详见 §10.1 坑 1。

### 7.2 指标的分工（6 条，名字只在 observability 定义）

| 指标 | 类型 | 谁写 | 回答的问题 |
|---|---|---|---|
| `shopsage_cache_results_total` | counter | `semantic.prepare` | 命中 / 未命中 / 失效 / 跳过 / 错误各多少（标签 `outcome` / `policy`） |
| `shopsage_cache_lookup_seconds` | histogram | 同上 | **缓存有没有反而拖慢主路径** |
| `shopsage_cache_saved_calls_total` | counter | 命中时 | **省下的是哪一层**（E1 的分母） |
| `shopsage_cache_degraded` | **gauge** | 每次查询 | 存储是否处于降级形态（0/1） |
| `shopsage_cache_entries` | **gauge** | 写入时 | 缓存里现在有多少条 |
| `shopsage_cache_near_miss_total` | counter | 灰区时 | **阈值该往哪调**（唯一在线信号） |

> ⚠️ **`miss` 才是要注意的那个**：命中率是「省钱了多少」的代理指标（E1），
> 而「miss 突然变多」有两类完全不同的原因 ——
> ① 阈值调高了 / 知识库版本变了（**缓存被正确地失效了**，是好事）；
> ② Redis 挂了、回落成了每个副本一份的内存缓存（**故障**，命中率被副本数除）。
> 两者看同一条曲线（都在掉），所以本指标必须与 `CACHE_DEGRADED` 一起看。

> ⚠️ **`CACHE_SAVED_CALLS` 为什么不能从 `hit` 里推**：命中**不等于**省下一次 LLM 调用 ——
> 命中的可能是「检索结果」这类中间产物（那省的是检索而不是生成）。
> E1（成本下降）要的是后者，所以让「省下的是哪一层」由**写入方显式声明**，
> 而不是让看板去猜。

  未装配（app 建好后摘掉）           status=skipped
      语义缓存未装配（业务不受影响，只是每次问答都要走完整链路）
```

> ⚠️ **第一态为什么是 `degraded` 而不是 `ok`**：`--health` 里没给 `redis_url`
> （它是脚本，不该假定 `.env` 的地址永远可达），于是键值层回落内存 → 那就是降级。
> 想看到 `ok` 就把 `.env` 里的 `REDIS_URL` 传进去（或者直接用真 app 跑 `/health`）。
> 这一条也是「降级会被看见」的直接证据 —— 它**不会**被伪装成 `ok`。
>
> ⚠️ **`skipped` 那一态是怎么造出来的**：`create_app(cache=None)` 的含义是
> 「**自己去建一个**」而不是「不装缓存」，所以「摘掉缓存」只能在 app 建好之后做
> （`app.state.cache = None`）。也就是说 `cache_component` 的 `skipped` 分支
> 在生产路径上几乎不可达（只要走了 lifespan 就一定装配过）—— 它为「lifespan 没跑完」准备。
> 第一版按「传 None = 不装」写，打印出来是 `ok`，看起来像「skipped 分支坏了」。

| 状态 | 含义 | 该不该处理 |
|---|---|---|
| `ok` | 条目存储与预期一致（表在 / Redis 通） | 不用 |
| `skipped` | 缓存没装配（没走 `create_app` 的 lifespan） | 不用（业务不受影响） |
| `degraded` | **存储降级了**（回落内存 / 缓存表不存在） | 要查：命中率会悄悄掉 |
| `down` | 配置本身不合法（阈值/策略写错） | 要查：会让缓存**要么永不命中、要么答错问题** |

> ⚠️ 「配置不合法」为什么算 `down` 而不是 `degraded`：阈值写反会让缓存**永远不命中**
> （成本白花），而 `time_sensitive_policy` 写成别的值可能让强时效数据被缓存（**答错**）。
> 这两件事都比「慢一点」严重，所以它必须比 `degraded` 更醒目。

| 接缝 | 落点 | 第 14/15/16 步会用它做什么 |
|---|---|---|
| **阈值校准** | `CacheSettings.semantic_threshold` + `CACHE_NEAR_MISS` + `--scenario threshold` | 第 14 步（eval）拿 golden set 找「漏报/误报」的取舍点，回填成默认值 |
| **缓存命中率的成本口径** | `CACHE_SAVED_CALLS{policy}` + `LLM_COST` | 第 14 步算「缓存让成本降了多少」（E1 的分母与分子都是现成的） |
| **首 token 延迟（B2）** | `CACHE_RESULTS{outcome="hit"}` 与 `api_stream_first_frame_seconds` 的对照 | 第 9/16 步的流式看板：命中时首帧应当**在一个数量级以内** |
| **结果缓存的消费者** | `result_cache_get/set` | 第 15 步（MCP）的外部只读查询、第 16 步（Web）的报表页 |
| **按文档失效** | `fingerprint_for(corpus_revision=…)` | 把「全局版本」换成「按 source 取版本」，**接口不变**（§5.2 的说明） |
| **L1 进程内缓存** | `ResultStore` 的 `KeyValue` 契约 | 第 16 步若要在 API 进程里加一层 L1，实现一个 `MemoryKeyValue` 变体即可 |
| **缓存击穿防护** | 目前**不做**（见下面的说明） | 第 16 步若有热点问题，需要「同一问题只重建一次」的单飞机制 |

> ⚠️ **为什么本步不做「缓存击穿/雪崩」的防护**：
> 击穿（同一个热点问题并发重建）与雪崩（大量 key 同时到期）都真实存在，
> 但它们的处置会引入「锁 / 单飞 / TTL 抖动」这些**新的失败模式**，
> 而本步的验收（`13.cache.md` §8）一条都没要求它们。
> 现在的取舍是：TTL 有分档（普通 24h / 政策 7d / 强时效 60s），
> 已经天然把「同时到期」打散了一部分；剩下的等有真实流量画像再说。
> **这是一处「已知未做」，不是「忘了」** —— 回填验收时不要把它算成已完成。

## 10. 故障速查

### 10.1 实现期间撞到的坑（实测，含修法）

#### 坑 1（本步最贵）：「写了但永远不命中」——读写两侧的**指纹**不同

**症状**：第一次问答成功、答案也写进了缓存，但**第二次问同一个问题仍然未命中**。
两边代码各自看起来都对（读路径传了 `top_k`/`min_score`/`embedder_key`，
写路径传了 `top_k`/`llm_calls_saved`），日志里没有任何错误。

**根因**：版本指纹把**写路径的记账标志**（`llm_calls_saved`）也算了进去 ——
它只是一个「省了调用」的标记，**不改变答案**，但它改变了指纹。
于是读路径算 `40020354`、写路径算 `cb1de87b`，两条记录互相看不见。

**怎么发现的**：`tests/cache/test_cache_graph.py::test_second_turn_hits_and_skips_retrieval_and_model`
（它的失败信息是「命中时不该再检索」）。调试方式是给 `SemanticCache.prepare` 打一层 trace，
把每次调用的 `retrieval` 参数与算出的指纹打出来 —— 一眼就看到两个不同的指纹。

**修法**（三层，缺一层都会复发）：

1. **判据**：`params` 里只允许放「这个参数变了，答案会变吗」为**是**的量；
2. **构造**：唯一的构造处是 `app/cache/params.retrieval_params()`（白名单，多传一个直接抛错），
   读路径与写路径都调它；
3. **锁**：`respond(..., fingerprint=...)` 在指纹与读路径不一致时**拒绝写入**并打 WARNING ——
   写一条「之后永远读不到」的记录毫无价值，而它的症状（命中率莫名其妙地低）极难查。

> ⚠️ 这条的教训是通用的：**任何「两边各算一次」的值都可能不一致**，
> 而缓存键上的不一致**不会报错**，只会让命中率变低。

#### 坑 2：「写了但永远不命中」之二——**消息串**在写的时候已经变了

**症状**：同坑 1（命中率恒为 0），但指纹一致。

**根因**：写缓存发生在 `synthesis` 里，而**图会在 `synthesis` 之后把这一轮的问答
追加进 `messages`**（`add_messages`）。于是「写缓存时手里的 `messages`」
比「读缓存时的那一份」多了一条 assistant 消息 → 拼出来的问题串不同 → 缓存键不同。

**修法**：`rag_node` 把「读那一刻的问题串 / scope / 指纹 / 版本 / 分档 / TTL」
作为一个**可序列化的 dict**（`state["cache_context"]`）交给 `synthesis`，
`Cache.record(**context)` 直接用它构造条目 —— **写路径不看 `state["messages"]`**。

#### 坑 3：「写了但永远不命中」之三——**跨节点传不了非序列化的东西**

**症状**：想把 `Prepared`（含读那一刻的上下文）从 `rag_node` 传到 `synthesis`：

| 试法 | 结果 |
|---|---|
| `state["cache_prepared"] = prepared`（dataclass） | **被 LangGraph 静默丢掉** → 命中率恒为 0 |
| `state["cache_write"] = closure`（闭包） | `TypeError: Type is not msgpack serializable: function` |
| `state["cache_context"] = {...}`（字符串/整数/dict） | ✅ |

**根因**：checkpointer 会对 state 值做 msgpack 序列化。dataclass 被丢弃时**没有任何告警**
（`cache_params` 是 dict 能过、`cache_prepared` 是 dataclass 被丢），
所以「一半的字段到了、另一半没到」这种状态最难查。

**修法**：跨节点只传**可序列化的值**（坑 2 的修法同时解决了这条）。
判据：**一个值要进 state，它就必须能过 msgpack**（dict / str / int / float / list / bool）。

#### 坑 4：`is_expired(now=...)` 的括号——三元表达式的优先级

**症状**：所有传了 `now=` 的判定**全部**返回过期，日志说「TTL 已过（0s > 3600s）」。
`judge()` 里每一处都是 `is_expired(now=moment)`，于是**缓存永远不命中**。

**根因**：条件表达式的优先级**低于**比较运算符，所以

```python
return float(now) if now is not None else time.time() >= self.expires_at
```

被解析成 `float(now) if cond else (time.time() >= expires_at)` —— 传了 `now` 时它返回一个**浮点数**
（恒为真）。`tests/cache/test_cache_core.py::test_fresh_entry_is_not_expired` 抓到的。

**修法**：拆成两句（`moment = ... ; return moment >= self.expires_at`）。**别省那个括号**。

#### 坑 5：`scope_pattern` 少了 `entry:` 那一段——「按 scope 清缓存」静默地什么都不做

**症状**：`deactivate_scope("customer:2")` 返回 0，而那个 scope 明明有 3 条。
`count(scope=…)` 也是 0。

**根因**：通配写成 `cache:dev:customer:2*`，而真实的 key 是
`cache:dev:entry:customer:2|…` —— **`entry:` 在 scope 之前**，所以什么都匹配不到。

**修法**：key 的构造收敛到 `CacheKeySpace`（`entry()` / `scope_pattern()` / `entry_pattern()`
三个方法一处实现），有用例逐字钉住 key 的形态。

#### 坑 6：`ResilientEntryStore` 漏转发一个方法——报告里「有 1 条」与「抽样为空」同时出现

**症状**：`scripts/cache_report.py` 打印「未过期条目 1」，紧接着的抽样是空的。

**根因**：门面拿到的是 `ResilientEntryStore`，而它只转发 `EntryStore` 协议里的方法；
`list_entries()`（运维工具用的）没在里面 → `getattr(store, "list_entries")` 拿到 `None` →
工具静默跳过抽样。

**修法**：把 `list_entries()` 加进协议 + `ResilientEntryStore` 转发 + Postgres 实现。
**判据**：往 `EntryStore` 协议里加方法时，`ResilientEntryStore` 必须同步加一个转发 ——
漏掉的表现是「某个功能静默变成空操作」。

#### 坑 7：Redis 的 TTL 被加了两次宽限——`ttl=0` 的条目活了 61 秒

**症状**：真 Redis 用例 `test_ttl_really_expires` 里，`grace_seconds=1` 的 store
写进去的条目在 Redis 里的 TTL 是 **61**（`ttl=0` + 1 + 60），等 1.3 秒不会消失。
生产上的表现是「`ttl_seconds` 配置改了但缓存还是活很久」。

**根因**：`RedisKeyValue.set` 无条件做 `ttl + 60`，而 `RedisEntryStore.put`
又调了一次 `key_value_ttl(...)` —— **两次变换**。（第一版没有 `grace_seconds` 参数，
宽限只在 `set` 里加；中途重构时把它挪到了 `put`，忘了删 `set` 里的那一份。）

**修法**：宽限只走一个显式参数（`set(..., grace_seconds=...)`，默认 0 = 不加宽限），
调用方自己决定加不加 —— 于是「加了几次」在代码里**数得出来**。

#### 坑 8：假 embedding 的「未知文本」方向撞上了第一个基准方向

**症状**：`--backend memory` 下的多轮用例里，**任何**未登记的问题都与「怎么退货」
相似度约 1.0（命中），于是「同一句话在不同上下文里不命中」这条断言失败。
更坏的是它在**测试辅助装置**里，所以看起来像「生产代码判定错了」。

**根因**：`tests/cache/conftest.py` 的 `vector_of()` 用 `(_bases + 7) % dim` 算未知文本的方向 ——
在 `_bases=1`、`dim=8` 时结果是 **0**，正好等于第一个基准的方向。

**修法**：未知文本固定用 `dim - 1` 那个下标（基准从 0 开始递增，用例不可能登记那么多基准），
并把「为什么不能用取模」写在注释里。

> ⚠️ 这条的教训：**测试装置里的"随机/派生"方向必须与"剧本里登记的方向"严格不相交**，
> 否则断言失败会指向被测代码，而真相在装置里。第 10 步的假 embedding 是纯噪声
> （所以没有这个问题），而本步的假 embedding 必须是**可控**的（阈值才是被测对象）。

#### 坑 9：`make_ingest_callback()` 在 `revisions=None` 时另造了一份版本表

**症状**：演示脚本里「推了版本但缓存没失效」—— 回调返回 `revision: 2`（它自己那份内存表），
而读路径读的是 Postgres 的版本表（还是 1）。

**根因**：`make_ingest_callback(revisions=None)` 把 `None` 透传给了 `bump_after_ingest`，
而那条路径会**懒建一个进程默认版本表**；如果调用方在此之前没有显式设置过默认，
两人拿到的就是**不同的对象**。

**修法**：`corpus.default_revision_store()` 作为「默认」的**唯一出口**，
`make_ingest_callback` 在 `revisions=None` 时显式解析成它 ——
于是「读用哪个、写用哪个」在代码里是同一个表达式。

### 10.2 三条「不是坑，但会被误读」的说明

1. **真 embedding 命中时 `embed()` 会被调用 0 次，这是对的**：
   命中路径根本不需要问题向量（完全同问走 hash）。
   演示脚本场景 1 的 `embed 调用 0 次` 是**真后端**下的读数 ——
   而假后端下第一次查询会算 1 次（第二次 0 次），因为假后端没有「Redis 向量缓存」那一层。
   **别把两个后端下的期望值写成同一个数**。
2. **`--backend auto` 会真的写缓存表**：跑完之后命中率变高、知识库版本也推进过一次。
   要干净重跑先 `--purge-all --yes`。演示脚本末尾会打印当前条目数。
3. **`/health` 的 `cache` 组件在注入内存缓存时是 `degraded`**：
   因为「Redis 没配」这件事本身就是降级（键值层落到了进程内存）。
   它不是故障，但**必须看得见** —— 见 §7.3 的四态表。
