| 改维度（换 embedding 模型） | Windows | §7（三处一起改 + 重建索引 + 重灌） |
| 「检索不到 / 排序不对 / 权限报错」 | Windows | §10 故障速查 |
| 回填验收证据 | Windows | §11 → `docs/modules/10.rag.md` §8 |

三条铁律：

1. **入库与查询必须用同一套切词与同一个 embedding 空间**。切词不一致的症状是
   「库里明明有的词就是搜不到」；embedding 空间不一致的症状更糟 ——
   检索**看起来正常、结果全是乱的**（见 §7）。所以两者都只有一处实现：
   `textkit.index_text()/query_terms()` 与 `app.llm.embed()`。
2. **旧片段只失效、不删除**（`is_active=false`）。会话历史与审计日志里存的是 `chunk_id`，
   删掉之后那条引用就永久断了（前端点「查看原文」404）。保留 + 失效让
   「引用可查、检索不可见」两件事同时成立。
3. **送进 LLM 的只能是精排后的 top-k**。初召回宁可多（召回优先），
   但上下文必须收窄 —— 实测候选池 12255 token → top-5 3282 token（-73%，E2）。
   把候选池直接塞进 prompt 是这类系统最常见的隐性成本泄漏。

另一条：**rerank 不是「锦上添花」而是必需品**。向量相似度 ≠ 相关度：
双塔模型把 query 与 passage 各自编码，两者的交互只发生在最后一次点积；
交叉编码器把 `(query, passage)` 拼在一起送进模型，判别力高一个档次 ——
代价是不能预计算，所以只能用在「已缩小到几十条」的候选集上（§6）。

## 1. 环境与前提

### 1.0 本步的链路（一条入库链 + 一条检索链）

```
                                    ┌──────── 第 10 步 rag/ ────────────────────────────┐
  docs/kb/*.md|html|txt|pdf         │                                                    │
        │                           │  ① parse：按后缀选解析器 → 纯文本（PDF 带分页符）    │
        ▼                           │  ② chunk：按文档类型定粒度（政策按条款/手册按章节/    │
   parse_text()                     │           FAQ 一条一块）+ 章节路径 + 页码 metadata    │
        │                           │  ③ embed：app.llm.embed()（API 或本地，**同一门面**） │
        ▼                           │  ④ upsert：只写**变化**的片段；旧片段 is_active=false │
   chunk_document()                 └────────────────────────────┬───────────────────────┘
        │                                                        │
        ▼                                                  rag_chunks（pgvector）
   embed()（第 5 步门面）                                        │  HNSW 索引（向量）
        │                                                        │  GIN 索引（n-gram 词表）
        ▼                                                        │
   upsert_document() ─────────────────────────────────────────────┘
                                                                 │
  query ──┬─→ embed(带 bge 查询前缀) ──→ 向量腿（余弦 ANN）        │
          │                                                      │
          └─→ 切词 → 覆盖率门槛 → BM25（SQL 内手算）→ 关键词腿 ─────┘
                                                                 │
                        RRF 融合（1/(k+rank)，只看名次）────────────┤
                                                                 │
                        rerank（交叉编码器逐对打分，只打前 2×top-k）──┤
                                                                 │
                        带溯源的 top-k（text/source/chunk_id/section/page）──► app/agents/rag.py（第 11 步）
```

**每个环节「拦得住什么 / 拦不住什么」**：

| 环节 | 拦得住 | 拦不住 / 需要别的环节 |
|---|---|---|
| 解析 | 排版垃圾进索引（`<script>`、`##` 标记） | 扫描件/加密 PDF → 抽不出文字（本步不做 OCR，只 WARNING） |
| 分块 | 语义被稀释（大块）、embedding 变噪声（碎块） | 跨条款的推理问题（「退货要不要付运费」需要合并第 2 条与第 9 条） |
| embedding | 「换个说法」找不到（向量腿的专长） | 精确编号（裸 `第 9 条` 没有语义）→ 交给关键词腿 |
| 关键词腿 | 精确词/编号/条款号；库里没有的词零召回 | 错别字（未登录词被剔出分母，但不做纠错） |
| RRF | 两路量纲不同（余弦 ∈[-1,1]、BM25 无界） | 丢掉分差信息 → 由 rerank 补回来 |
| rerank | 「主题相近但不回答问题」的片段 | 候选池里根本没有正确片段时无能为力（初召回的锅） |
| `is_active` | 旧片段被检索到 | 历史版本行本身会占空间（保留 1 个失效版本，更老的清掉） |

### 1.3 数据契约一览（谁给谁什么）

三个必须问「为什么这么建」的地方：

| 决定 | 为什么 |
|---|---|
| **HNSW 而不是 IVFFlat** | IVFFlat 要先有**数据**才能训练聚类中心，「先建索引后灌数据」会让它退化；HNSW 空表建索引也正确，增量插入自动维护。代价：建索引慢、索引更占内存 |

| **触发器同步 `ngram_tsv`/`ngram_doc`** | 用生成列更"现代"，但生成列要求表达式 **immutable**，而 `to_tsvector('simple', x)` 是 **stable**（依赖 `default_text_search_config`）—— 硬塞进去会得到一个「有时对、有时错」的索引，那比慢更糟 |

### 2.2 为什么是三张表（而不是文档里的一张 `chunks`）

| 表 | 生命周期 | 存什么 |
|---|---|---|
| `rag_documents` | 一份文档一行（`source` 唯一），增量更新时**原地更新**版本与指纹 | `doc_hash`（内容指纹）、`chunk_strategy`、`version`、`chunk_count`、`chunk_hashes`、`is_active` |
| `rag_chunks` | 每个片段内容一行，内容变了**插新行 + 旧行失效** | 文档里的六列 + 我们加的 n-gram 四列 |
| `rag_corpus_stats` | **单行**，每次入库 upsert | BM25 的全局量：`docs` / `chunks` / `total_tokens`（= `N` 与 `avgdl` 的来源） |

合成一张表会逼出「同一文档的元数据在 N 行里各存一份」的冗余，而冗余一定漂移
（第 3 行与第 7 行的 `updated_at` 不一致时，谁是对的？）。
`rag_corpus_stats` 单独一张的理由：BM25 的 `N` 与 `avgdl` **每条查询都要用**，
现算要扫全表（`avg(ngram_doc)`），而维护成本只是每次入库一次 upsert。

## 3. 中文检索的三块地基（切词 / 关键词腿 / 分块）

### 3.1 坑：`to_tsvector('simple', 中文)` 会把汉字全部丢掉

这是本步最先要验证的一件事，也是「为什么不能直接用 PostgreSQL 的全文检索」的全部理由：

```powershell
uv run python -c @"

with psycopg.connect('postgresql://shopuser:shoppass@192.168.167.130:5432/shopsage') as c, c.cursor() as cur:
    cur.execute(\"select to_tsvector('simple', '第 3 条：自签收之日起 7 天内，商品完好可申请无理由退货。')::text\")
    print('simple :', cur.fetchone()[0])
    cur.execute(\"select to_tsvector('english', '第 3 条：自签收之日起 7 天内')::text\")
    print('english:', cur.fetchone()[0])
"@
```

实测输出：

```
simple : '3':2 '7':3
english: '3':2 '7':3
```

**整段中文变成了零个词元**，只剩两个数字。也就是说：不切词的话，
「退货政策」这种查询在关键词腿上会**永远是零召回** —— 而且它**不报错**。

三种方案的实测取舍（选第 3 种）：

| 方案 | 结论 |
|---|---|
| `zhparser` / `pg_jieba` 扩展 | 最正统，但要在开发镜像里装扩展（`pgvector/pgvector:pg16` 里没有），换机器即失效 |
| `pg_trgm`（trigram） | 只能做 LIKE/相似度，**没有词频与长度归一化**，做不了 BM25 |
| ✅ **CJK n-gram 词表 + tsvector + SQL 内手算 BM25** | 零扩展依赖，GIN 索引照常生效，tf 与长度归一化都在 tsvector 里 |

实现（`app/rag/textkit.py`）：入库时把文本切成「单字 + 相邻二字（bigram）+ ASCII 词」拼成
空格分隔的词表，交给 `to_tsvector('simple', ...)` —— 此时 `simple` 的「按空白切分」
正好就是我们想要的 tokenizer。

```python
from app.rag.textkit import index_text, terms, query_terms

terms("自签收之日起 7 天内，商品完好可申请无理由退货。")[:8]
# ['自', '自签', '签', '签收', '收', '收之', '之', '之日']
index_text("七天无理由退货")            # 空格分隔的词表（直接喂 tsvector）
# '七 七天 天 天无 无 无理 理 理由 由 由退 退 退货 货'
query_terms("7天无理由退货")            # (候选词, 兜底词)
# (['7', '天无', '无理', '理由', '由退', '退货'],
#  ['7', '天', '天无', '无', '无理', '理', '理由', '由', '由退', '退', '退货', '货'])
```

**为什么是 1-gram + 2-gram 而不是 jieba 那样的分词**：

- 分词要词典，**词典之外的新词**（型号、编号、政策名）都切不出来，而 RAG 的查询
  恰恰大量是长尾专名；
- n-gram 没有未登录词问题，且「2-gram 命中率」天然是一个**短语近似匹配**信号：
  查询里相连的两个字同时出现在同一段相邻文本上，等价于「这句话里真的出现过这个词」；
- 1-gram 保召回（单字查询、错别字场景），2-gram 保精度（做候选门），
  两者的分工写在 `query_terms()` 的返回里（候选词 vs 兜底词）。

### 3.2 关键词腿：覆盖率门槛 + SQL 内手算 BM25

**为什么不直接用 `ts_rank_cd`**：它算的是 cover density（覆盖密度），
没有 IDF 与标准形式的长度归一化 —— 在中文 1-gram 参与评分时，
「的/是/不」这类满篇都有的字与「条款号」这类稀有词权重相同，排序直接失效。
所以自己算 BM25（`k1=1.2, b=0.75`）：

```
tf'   = tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl))
idf   = ln(1 + (N - df + 0.5) / (df + 0.5))
score = Σ idf * tf'
```

三个量的来源（这也是为什么它必须写在 SQL 里）：

| 量 | 来源 | 代价 |
|---|---|---|
| `tf` | `ts_stat()` 从该行的 `tsvector` 取 `nentry` | 每行一次函数调用（候选集已缩小到几十条，可接受） |
| `df` | 逐词 `ngram_tsv @@ to_tsquery(...) count(*)` | **每个词一次 GIN 索引扫描**（实测 2~6ms） |
| `N` / `avgdl` | `rag_corpus_stats` 单行表 | 每次入库一次 upsert |

**候选门：bigram 覆盖率阈值**（默认 0.6）。为什么不是 `AND`、也不是 `OR`：

| 语义 | 后果 |
|---|---|
| `AND` 全部 bigram | 太脆：用户少打一个字 → 零召回（实测：「7天无理由退货」的 AND 候选是 0 条） |
| `OR` 任一 bigram | 太松：一个「退」字就召回一切（低精度，污染融合） |
| ✅ 覆盖率 `matched / known >= 0.6` | 两者之间唯一可调的旋钮；**分母只算「库里真实存在的词」** |

⚠️ 分母必须剔除未登录词，否则「打错一个字」会把覆盖率打到 0 —— 也就是
「本来能召回的文档被门槛挡掉」。这一条有专门的用例
（`test_keyword_search_handles_unknown_tokens_gracefully`）。


  **一个**词元 —— 因为 `9` 在这个查询的候选词里是 ASCII 词、而 `第`/`条` 是单字（不进候选门），
  bigram 只有 `第9`（`9 ` 与 `第` 不构成 bigram，见 §3.1 的切词规则）。
  这正是「裸编号查询」在词法上的真实形态：**信息量全在那一个数字上**。
* `顺丰速运` 的 `matched=3`（`顺丰`/`丰速`/`速运` 三个 bigram 全中）→ 它是最"干净"的一类查询。
* `1.1` 同时命中《会员积分》与《物流政策》—— 因为两份文档里都有「1.1」这个小节号。
  **关键词腿不负责消歧**，它只保证「含这个词的片段都会被召回」；
  消歧由 rerank（结合 query 的其它部分）与融合完成。这也是「**不要**用关键词腿单独排序」的原因。
* 「零召回」那一条是本步的一条**硬约束**：库里没有的词必须给出空结果，
  而不是「随便给几条」—— 一个只有 OR 语义的实现会在这里返回一堆无关片段，
  然后让 rerank 去清理（而 rerank 只能排序，不能从「全都不相关」里变出正确答案）。

### 3.3 分块：按文档类型定粒度

```powershell
uv run python -m scripts.load_knowledge_base --dry-run
# 每个文件的「自动判」那一列就是策略判定的结果（policy / manual / faq 三选一）
```

| 策略 | 适用 | 边界判据 | 实测效果 |
|---|---|---|---|
| `policy` | 政策/条款/规章 | 条款号（`第 3 条`、`7.1`、`（二）`、`Rule 4`）+ Markdown 标题 | 《退货政策》12 个片段，**一条一款一块** |
| `manual` | 手册/说明书/长文 | 只按标题层级 | 《会员积分》4 个片段（按 `## 1. 等级划分` 切） |
| `faq` | FAQ / 问答对 | 「问…答…」成对；`### 如何…？` 这种问句标题 | 《常见问题》10 个片段，**一问一答一块** |
| `auto`（默认） | —— | 先看「标题是不是问句」（>= 2 个且占标题 1/3），再看 Q/A 前缀行，再看条款号 | 8 份文档全部判对（见 §2.4 的 `--dry-run`） |

三条硬约束（都是「不这么做就出事故」级别）：

1. **每个 chunk 都带 metadata**（`source / section / page / updated_at`）——
   溯源（§4.2）、增量比对、前端「跳到原文」全靠它。
2. **`chunk_id` 是内容指纹**（`"c" + sha256(text)[:16]`），不是位置型 ID：
   位置型 ID 在文档中间插一句话时会让后面所有片段「全变了」（增量更新退化成全量重嵌）。
3. **超长段落用重叠窗口切**（默认 80 字），不能硬断 —— 答案被切在缝上是最难查的一类问题。
   代价是同一段文字出现在两个片段里，而检索时这是**好事**（命中概率更高）。

⚠️ **陷阱**：`overlap >= max_chars` 会让「按段落累加到 max_chars」的循环**永远不前进**。
配置层就夹住它并告警（`RagSettings.from_settings`），这条有专门的用例。
（`RAG_CHUNK_OVERLAP` 与 `RAG_CHUNK_MAX_CHARS` 的正常取值是 80 / 600。）

### 4.2 溯源三件套

+ 可选 `page`（PDF 页码），`citation()` 直接拼出人可读的出处：

也不给一条查不到出处的 —— 后者会把幻觉洗白成「有出处」。

### 4.3 RRF：为什么是它，而不是加权求和

```
score(d) = Σ_lists 1 / (k + rank(d))        # rank 从 1 开始，k = 60
```

两路的分数**量纲不同**（余弦相似度 ∈ [-1,1]，BM25 是无界正数）。加权求和必须先归一化，
而归一化会让「绝对分差」消失 —— 一条 BM25=12 与一条 BM25=1.5 被压到 0.98 / 0.12，
再乘权重，**权重就变成了尺度的函数**。RRF 只用名次，天然免疫量纲，且不需要调参。

代价是丢掉分差信息（第一名 0.99 与第二名 0.20 的差距不再体现）——
这个代价由 **rerank** 补回来：精排是在候选集内部逐对打分，本来就不依赖初召回的分差。

```python
from app.rag.retriever import reciprocal_rank_fusion
reciprocal_rank_fusion([[7, 9], [9, 11]], k=60)
# {7: 1/61, 9: 1/62 + 1/61, 11: 1/62}   ← 9 被两路都命中 → 排第一
```

## 5. 增量更新（F1：更新 < 1min 可见）

### 5.1 三种同步方式

| 方式 | 命令 | 适用 |
|---|---|---|
| 一次性灌库 | `uv run python -m scripts.load_knowledge_base` | 上线前 / 定时任务（cron、K8s CronJob） |
| 轮询同步 | `uv run python -m app.rag.sync --interval 30`（或 `RagSyncWorker(...).run_forever()`） | 开发期、小知识库、无 CDC 的环境 |
| 单轮同步 | `RagSyncWorker(...).sync_once(prune=True)` | CI 里跑一次，或手工触发 |

**为什么不做文件系统事件（watchdog/inotify）**：事件在容器/网络盘/编辑器「原子写」
（临时文件 + rename）下的行为差异很大，容易漏事件 —— 而漏事件的症状是「检索到旧内容」，
正是 F1 要解决的问题。轮询的代价是「一次目录遍历 + 一次 SELECT」，
在知识库这个量级（几十~几千份文档）完全可接受，且**行为确定**。

**已删除的文件默认不动**（保守）：一份文件消失可能是「误删」「挂载没同步过来」「临时移走」，
直接下线文档会让一次误操作变成一次检索事故。清理要显式 `--prune`
（让「删除」成为一个明确的动作）。

**怎么读这张表**（避免把它误读成「rerank 能省 73% token」）：

| 数字 | 含义 |

| **-73%** | 「初召回池 → 精排 top-5」的压缩率。**这才是 E2 的落点**：先生成池、只把精华送进 LLM |
| 粗排 rank → 精排 rank | 期望来源在 top-5 里的名次（`2→1`、`3→2` 各一条） |
| MRR / top-1 | `0.861 → 0.917` / `9/12 → 10/12`：**质量不降**（实测是升） |

> ⚠️ **不要**把「粗排 top-5 的 token vs 精排 top-5 的 token」当成收益 ——
> 两组都只取 5 条，差异只来自「选中的片段不同」，它是**有正有负**的
> （实测第一版 demo 就是这么写的，得到 `+6%`，看起来像「rerank 增加了成本」）。
> 真正的收益是「30 条 → 5 条」，而这一步的压缩率是 73%。

`rerank` 三个后端的取舍：

| `RAG_RERANK` | 后端 | 什么时候用 |
|---|---|---|
| `local`（默认） | 本地 `sentence-transformers` CrossEncoder（bge-reranker-base） | 正常开发/生产：零边际成本、文本不出网 |
| `api` | 兼容 `/rerank` 协议的 HTTP 端点（Jina/Cohere/vLLM/TEI） | 本地没有 GPU、或想用更强的商用 reranker |
| `off` | 关掉（用 RRF 融合分排序） | **对照实验**与离线单测 —— 证明「rerank 有增益」必须有个不带它的对照组 |

**降级是显式的**：`local` 后端加载失败（没装依赖 / 权重不在本地 / 离线）时，
记一条 WARNING 并**退回 RRF 排序**，而不是抛错让整条检索路径不可用 ——
「检索没有精排」远好于「检索完全不可用」。但降级必须留下日志：

```
WARNING app.rag.retriever: rerank 不可用，已退回 RRF 融合排序：本地 rerank 模型加载失败（...）
```

否则「rerank 坏了三周没人发现」会成为评测掉分时最难查的一类问题
（`test_rerank_failure_degrades_to_fusion_order_with_a_warning` 钉住这条）。

## 7. 换模型 / 改维度（最容易做错的一件事）

**必须先定死三个字段，再写迁移的 `vector(n)`**（`10.rag.md` 第 3 节）：
`backend` / `model` / `dim`，外加「是否归一化」「是否需要 query·passage 前缀」。
反过来做，你会在「表已建好、维度变了」的处境里做数据迁移 + 重建索引。

```powershell
# ① 改之前先看现状（表维度 vs 配置维度）
uv run python -c @"
from app.rag.settings import RagSettings
from app.rag.store import RagStore
s = RagSettings.from_settings(); print('配置:', s.vector_dim, s.rerank_model)
print('库  :', RagStore(dimension=s.vector_dim).health())
"@
# 实测：配置: 1024 BAAI/bge-reranker-base
#       库  : {'table': 'rag_chunks', 'exists': True, 'dim': 1024, 'expected_dim': 1024, 'dim_ok': True}
```

改维度的**完整动作清单**（三处 + 两步）：

| # | 改什么 | 在哪 |
|---|---|---|
| ① | `EMBEDDING_DIM` + `RAG_VECTOR_DIM` | 仓库根 `.env`（与 `.env.example`） |
| ② | `VECTOR_DIM` | `app/rag/schema.py` **与** 迁移文件里的 `VECTOR_DIM`（两处，有测试对账） |
| ③ | `vector(n)` 列 | 这一步靠**一次新迁移**（`op.execute` 改列类型 + 重建 HNSW 索引） |
| ④ | 重建索引 + 重灌全部向量 | `uv run python -m scripts.load_knowledge_base --force`（或先 `delete_document(hard=True)`） |

⚠️ **最坏的情况不是「维度不一致」**（写库会直接响），而是
**维度恰好相同但向量空间不相容** —— API 后端与本地后端之间**必然**属于后者：
检索看起来完全正常，结果全是乱的，掉分时你会先去怀疑 prompt。
所以 `scripts/load_knowledge_base.py` 开头会做一次维度自检并在不一致时**拒绝执行**：

```
⚠️ 维度不一致：表上是 vector(1024)，配置要 1536。先统一 RAG_VECTOR_DIM / EMBEDDING_DIM / 迁移三处，再灌库。
```

⚠️ **bge 系必须加查询前缀，且只在查询侧加**（`5.llm-runbook.md` §7.7）：
`app/rag/retriever.py::QUERY_PREFIXES` 按模型名匹配，命中就加
「为这个句子生成表示以用于检索相关文章：」。**文档侧不加**（入库直接用 `embed(chunk.text)`）——
两边都加等于把指令当成文档内容的一部分，实测会掉分，而且掉得很隐蔽（检索还能用，只是变差）。

### 10.1 实测坑（本步踩到的，全部有回归用例）

#### 坑 1：`to_tsvector('simple', 中文)` 不切词 → 中文关键词腿是「永不命中的死代码」

`select to_tsvector('simple', '第 3 条：自签收之日起 7 天内')` 的实测结果是 `'3':2 '7':3` ——
**汉字一个都不剩**。而它不会报错，只会让关键词腿永远返回 0 条；
如果检索还有向量腿在工作，你根本不会发现关键词腿其实没生效（这正是它危险的地方）。

* ✅ 修法：入库时另存一份切好的 n-gram 词表（`ngrams`），由触发器同步成 `ngram_tsv`；
  查询侧用同一套切词（`textkit`）。
* 教训：**「不报错」不等于「在工作」**。关键词腿的覆盖必须有独立信号 ——
  本步把 `vector_hits` / `keyword_hits` 都放进 `RetrievalResult`，
  演示脚本每条查询都会打印（§4.1 的「向量腿 30 / 关键词腿 3」）。

#### 坑 2：`ts_rank_cd` 在中文 1-gram 上会毁掉排序

第一版直接用 `ts_rank_cd(ngram_tsv, to_tsquery(...))` 排序，实测「第7条」与「第 3 条」
得分**完全相同**（0.3），因为 cover density 只看覆盖密度，**没有 IDF** ——
「第」「条」这种到处都有的字与稀有词权重一样。

* ✅ 修法：在 SQL 里手算 BM25（`idf = ln(1 + (N - df + 0.5)/(df + 0.5))`），
  三个量分别来自 `ts_stat`（tf）、逐词 `@@` 计数（df）、`rag_corpus_stats`（N/avgdl）。
* 教训：**「有排序函数」不等于「排序正确」**。判断标准是「稀有词能不能压过常见字」，
  而这需要 IDF —— 没有它，任何基于词频的排序都只是「谁出现次数多谁靠前」。

#### 坑 3：`bigram AND` 太脆，`OR` 太松 → 必须用覆盖率阈值

- 第一版候选门是 `AND` 全部 bigram：查询「7天无理由退货」的 bigram 里有 `天无`、`无理`…
  而文档里是「7 天内…可申请无理由退货」—— `天无` 这个跨词边界的 bigram **不存在**，
  于是 AND 的候选是 **0 条**（连续子串假设在真实中文里不成立）。
- 第二版换成 `OR`：一个「退」字就召回一切，关键词腿从「有用」变成「污染」。

* ✅ 修法：**覆盖率阈值**（命中 bigram / 已登录 bigram ≥ 0.6），
  且分母**只算库里真实存在的词** —— 否则用户打错一个字就会把覆盖率为 0、
  把本来能召回的文档挡在门外（这条单独有测试）。
* 教训：**召回与精度之间没有免费的开关**，只有一个可调的旋钮；
  而旋钮的分母必须先"洗干净"（未登录词剔除），否则你会发现「错字让检索失效」这种诡异现象。

#### 坑 4：多行单元让所有标题判据失效

FAQ 策略会把「问句 + 答句」合并成一个**多行**单元，而我的标题正则没开 `re.MULTILINE` ——
`$` 在默认模式下只匹配**字符串末尾**，于是 `### 如何修改收货地址？\n在订单详情页…`
一条标题判据都命中不了，章节全部退化成父级（「常见问题」），
「一条 FAQ 一块」跟着失效 —— 而且**没有任何报错**（分块还是一种"结果"）。

* ✅ 修法：所有标题判据加 `re.MULTILINE`；并且对「多行单元」用**首行**做标题判定。
* 教训：**正则的 `$` 不是「行尾」**。处理多行文本时，`re.MULTILINE` 与
  「按行取首行」这两件事必须显式写出来 —— 否则你会得到一个"看起来在工作"的东西。

#### 坑 5：给 pure-DDL 表加进库之后，`alembic --autogenerate` 想删掉它

`rag_*` 三张表是**纯 DDL** 建的（`vector(n)` / `tsvector` / HNSW / PL/pgSQL 触发器），
刻意没有等价的 SQLAlchemy 模型。但 `alembic revision --autogenerate` 与
`tests/test_db_migrations.py::test_no_pending_migration_against_models` 会认为
「库里有、模型里没有」→ 生成一串 `op.drop_table('rag_chunks')` ——
它长得完全像一次正常的清理，跑下去**把整个知识库删掉**。

* ✅ 修法：把「不是本仓模型」的表抽成一份清单（`app/db/excluded.py`），
  `alembic/env.py` 的 `_include_object` 与结构比对用例**都用它**。
* 教训：**迁移工具的"自动"是以「库与模型的差集」为判据的**。
  任何「只存在于数据库、不存在于模型」的对象，都必须显式排除 ——
  且清单只有一处（抄一份到测试里，两者会漂移，然后测试开始报「库里多了三张表」，
  而人手工生成的迁移仍然是删表）。

#### 坑 6：迁移不能 import 应用代码（`alembic history` 会因此变重，历史迁移会被改写）

第一版迁移文件写 `from app.rag.schema import create_statements` —— 结果是：
① `alembic` 的**任何**命令（含 `history`）都会 import 整个应用（连带 embedding/DB 链路）；
② 将来有人改了 `rag/schema.py`，**历史上已经执行过的迁移也会跟着变**。
实测第一个后果直接把 `alembic upgrade head` 打崩了（`ModuleNotFoundError: app.rag.ingest`，
因为门面 `app/rag/__init__.py` 会 import 还没写完的模块）。

* ✅ 修法：迁移自己写一份 DDL，并由 `tests/rag/test_rag_migrations.py` **读文件对账**
  （维度/表名/索引种类/函数名漂移会红），而不是靠 import 保持一致。
* 教训：**迁移是历史，不是代码**。它可以被"对账"（测试读文件比对事实），
  但不该被"引用"（import 应用模块）。

#### 坑 7：`alembic upgrade --sql`（离线模式）里 `op.get_bind()` 没有 `exec_driver_sql`

离线模式（`--sql`）下 `op.get_bind()` 返回的是 `MockConnection` —— 它**没有**
`exec_driver_sql`（那是真实 DBAPI 连接的方法）。症状：

```
AttributeError: 'MockConnection' object has no attribute 'exec_driver_sql'
```

而 `tests/test_db_migrations.py::test_offline_sql_generation_does_not_need_database`
与 `3.db-runbook` 的「不连库也能出 DDL」都依赖这条路径。

* ✅ 修法：按 `op.get_context().as_sql` 分流 —— 离线走 `op.execute()`（本迁移的语句没有绑定参数，
  所以离线可执行），在线走 `exec_driver_sql`。
* 教训：**同一个 API 在不同模式下能力不同**。写迁移时，「离线可用」是一条独立要求，
  不是「在线能跑就自动能跑」。

#### 坑 8：`.env` 取值行末尾的说明文字被当成值

`.env` 里原来是：

```
EMBEDDING_MODEL=BAAI/bge-m3    # litellm 后端填模型名（建议带 provider 前缀）
```

`dotenv` 会把整段算进值里，于是本地后端的模型名变成
`BAAI/bge-m3    # litellm 后端填模型名（建议带 provider 前缀）` ——
拿着一个不存在的仓库名去 HuggingFace（401/404）。第 5 步为「配置里混进说明文字」
专门写过前置检查，这次是同一个坑的另一个入口。

* ✅ 修法：取值行只写「键=值」，说明单独成行（`.env.example` 里就是这么示范的）。
* 教训：**配置文件的解析规则要当成接口来看**。dotenv 的注释规则与 shell 不同
  （shell 里 `#` 前的空格是分隔符，dotenv 里不一定是）。

#### 坑 9：演示脚本自己的前置条件（与第 9 步同一个教训）

`--scenario incremental` 第一版直接改文档，但**没先清理**上一次留下的同名文档 ——
于是第二次跑时「首次入库」实际上返回 `unchanged`（文档指纹没变），
打印出来的账目看起来像「增量没生效」。

* ✅ 修法：场景开始时 `delete_document(source, hard=True)`，并在注释里写明为什么
  （「场景自己要声明前置条件」）。
* 教训：**演示脚本也是代码**。它会在某个执行顺序下骗人，而这个顺序往往正是"第二次跑"。

#### 坑 10：`--rag-live` 开关写在子目录 conftest 里 → 全量跑时「参数不认识」

第一版把 `pytest_addoption("--rag-live")` 写在 `tests/rag/conftest.py` 里。结果：

```
uv run pytest -q tests/rag --rag-live                    # ✅ 能跑
uv run pytest -q -m "not llm_live" --rag-live            # ❌ error: unrecognized arguments: --rag-live
```

根因：pytest 的**参数解析发生在根 conftest 加载期间**，而子目录 conftest 要到
「收集该目录的用例」时才加载 —— 全量收集时参数已经解析完了，于是这个开关「时好时坏」。

* ✅ 修法：`--rag-live` 注册在根 `tests/conftest.py` 里（子目录只负责用它来 skip）。
* 教训：**pytest 插件的注册点是有层次顺序的**。凡是「命令行开关」都要放在根 conftest；
  子目录 conftest 适合放装置（fixture）与「读取开关后怎么处理」。
  症状是最难查的一类：**同一条命令换个路径就报参数错误**。

#### 坑 11：`TRUNCATE ... CASCADE` 顺着外键把向量库删了（seed 脚本）

`scripts/seed.py` 用 `TRUNCATE TABLE 8 张业务表 ... CASCADE` 清空演示库。
第 10 步加了向量表之后，`rag_chunks.doc_id → rag_documents.doc_id ON DELETE CASCADE`
这条外键让 **CASCADE 顺着删掉了整个知识库**。后果是：

* `tests/conftest.py` 的 `seeded` 装置（需要种子数据的用例声明它）会让
  **跑一次全量测试 = 清空知识库**；
* 随后 `tests/rag/test_rag_live.py` 的 6 条用例**静默 skip**（「向量库是空的」）——
  现象看起来完全像「真模型用例没跑」，而真相是种子脚本。

* ✅ 修法：`_truncate_business_tables()` 显式只清业务表 ——
  向量库的内容来自 `docs/kb`，与种子数据**没有任何依赖关系**（业务表里没有
  `chunk_id` 的外键，反过来也一样）。
  `tests/rag/test_rag_seed_isolation.py` 三条用例钉住它（行为 + 结构 + 源码 AST）。
* 教训：**`CASCADE` 是一个跨模块的隐式契约**。加了新表之后要问一句
  「有没有别的 `TRUNCATE`/`DELETE` 会顺到我？」—— 而这一问最容易在
  「新表与旧表看起来毫无关系」时被跳过。真正兜住它的是**在外键上加约束**这个动作本身
  （`ON DELETE CASCADE` 的语义就是"跟着删"），所以更稳的做法是：
  新增的独立域**不要**用 `TRUNCATE ... CASCADE` 覆盖到，而是显式列出要清的表
  （本仓现在就是显式列 8 张业务表）。

#### 坑 12：迁移回环（`downgrade base` → `upgrade head`）同样会清空向量库

`tests/test_db_migrations.py::test_migration_round_trip_is_repeatable` 会
`alembic downgrade base`（连 `rag_*` 三张表一起删）再 `upgrade head`（建成空表）。
实测确认：

```
uv run pytest -q tests/rag --rag-live        → 143 passed，语料 8 份 / 59 片段（没被动）
uv run pytest -q tests/test_db_migrations.py → 10 passed
之后语料                                      → {docs: 0, chunks: 0, total_tokens: 0}
```

* ✅ 修法（两处一起）：
  ① `tests/rag/test_rag_live.py::live_retriever` 在**空库时自动补灌**一次
  （复现 `scripts/load_knowledge_base.py` 的默认行为）——
  这样「跑全量测试」是自洽的：要么语料在，要么这次把它灌好；
  ② 迁移用例的 docstring 写明这个副作用（不在这里自动灌库：
  那会把「跑一次全量测试」变成「每次重算 59 个向量」）。
* 教训：**「迁移可重复」与「派生数据还在」是两件事**。向量库是**派生数据**
  （可由 `docs/kb` 重建），所以它的丢失不该被当成数据事故 ——
  但**必须有一个明确的补灌入口**，否则「静默 skip」会长期伪装成「测试没问题」。
