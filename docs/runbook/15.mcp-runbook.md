三条铁律：

1. **MCP 是「薄壳」，不是「重写」**。`app/mcp/tools.py` 的四个函数只做三件事：
   下线程、翻译异常、盖章审计。任何 SQL / 业务规则 / 重试逻辑出现在 `app/mcp/` 下就是越界 ——
   契约测试用 AST 扫描 `SessionLocal` / `get_write_engine` / `write_session` / `insert_once`
   来钉住这一条（§7.1）。
2. **身份只能来自服务端配置**。`MCP_POLICY` + `MCP_ACTOR_USER_ID` 决定「这次调用以谁的身份执行」，
   它们**不是工具参数**。让客户端申报身份 = 把 D1 的第二半交给不可信输入，
   与第 9 步「请求体里没有 `user_id`」是同一条纪律（§4.1）。
3. **错误消息带规则名，但不带内部细节**。客户端（一个模型）靠 `[not_read_only]`
   这类标记自我纠正；而它不许从错误里读到库结构、连接串、堆栈（§5.5）。

另一条（本步最值钱的认知）：**「共用同一套安全层」这句话需要逐段证明，不能靠声明**。
`15.mcp.md` §4 第 2 条写的是「MCP 与内部调用共用同一安全层」——
但**行级过滤那半条只能由入口驱动**，工具层根本没有「你是谁」这个概念。
所以本步真正的设计工作不是「把工具包一层 MCP」，而是回答：
**入口声明的身份，怎么变成工具层能执行的形状**（§4.2 的三种形态 + §4.3 的风险清单）。

## 1. 环境与前提

### 1.0 本步的链路（一条入口 + 两道边界 + 四个工具）

```
   外部 MCP 客户端（Claude 桌面端 / Cursor / 任何实现了 MCP 的 Agent）
        │  ① stdio（子进程，本机）  或  ② streamable-http / sse（共享服务）
        ▼
   ┌──────────────────────────────────────────────────────────────────────────┐
   │  app/mcp/server.py  build_server(settings)      ← 装配（4 个工具 + 注解）  │
   │  ┌────────────────────────────────────────────────────────────────────┐  │
   │  │ app/mcp/tools.py   async 薄壳：下线程 + 翻译异常 + 盖审计章           │  │
   │  │   ▲ 唯一属于本层的两件事，没有第三件                                  │  │
   │  └──────────────────────────────┬─────────────────────────────────────┘  │
   │                                 ▼                                        │
   │  ┌────────────────────────────────────────────────────────────────────┐  │
   │  │ app/mcp/sync_calls.py  **身份边界 + 结果形状**（唯一真相）            │  │
   │  │   ① 参数上限只许变严（capped）                                       │  │
   │  │   ② validate_sql（静态守卫，先）                                     │  │
   │  │   ③ 行级过滤（后）：必须有 `user_id = :user_id` 且值 == 服务端身份     │  │
   │  │   ④ 调 app/tools 的既有函数（caller=None + caller_override 盖章）     │  │
   │  │   ⑤ Decimal → 字符串（精度不过这条边界）                             │  │
   │  └──────────────────────────────┬─────────────────────────────────────┘  │
   └─────────────────────────────────┼────────────────────────────────────────┘
                                     ▼
   app/tools/（第 6 步，一行没重写）：只读引擎 + 行数截断 + 幂等 + 审计 + 埋点
                                     ▼
      PostgreSQL（读走 shopsage_readonly；写走 shopuser）/ pgvector 知识库
```

**每个工具「MCP 这一层拦什么 / 拦不住什么」**（与 [`6.tools-runbook.md`](6.tools-runbook.md) §1.0 同口径）：

| 工具 | MCP 这一层负责 | 拦不住 / 靠上一层 |
|---|---|---|
| `sql_query` | 上限收敛；**强制行级过滤**（缺过滤 / 字面量 / 值指向别人三种形态）；先过静态守卫 | 守卫本身（写语句、白名单、危险函数）是第 4 步的；「合法但业务上不该给」是 RBAC 的事 |
| `retrieve_knowledge` | 上限收敛；结果只含带溯源片段 | **知识库没有行级归属**（8 份政策文档对所有客户同一份）—— 不是「已做行级过滤」，见 §4.2 |
| `create_ticket` | 对客只能建自己的工单；`idempotency_key` 必须由客户端给；角色取服务端配置 | 幂等本身是 DB 唯一约束；「该不该批」是第 9 步的审批通道 |
| `build_chart` | 点数上限；**载荷最小化**（只带声明列的复用） | 行数据从哪来是调用方的事（`build_chart` 不查库） |

> 2. **多了一个 `sync_calls.py`**：文档的接口清单里只有「初始化 server + 注册 4 个工具」。
>    但没有它，「脚本想调同一个工具」就只能复制一遍身份校验（§3.4 有实测的失败形态）。
> 3. **`sql_query` 多了一条文档没写的硬要求**：只读策略下 SQL **必须**带
>    `WHERE user_id = :user_id`。文档 §4 第 2 条只说「共用同一安全层」，
>    而工具层做不了行级过滤 —— 这条要求就是「共用」在本入口的**具体形态**（§4.2）。

### 1.3 数据契约一览（谁给谁什么）

| 契约 | 位置 | 关键点 |

### 1.4 配置面（三个新环境变量，全在 `app/mcp/settings.py` 里读）

| 配置项 | 默认 | 作用 | 配错的后果 |
|---|---|---|---|
| `MCP_POLICY` | **`customer`** | `customer` = 强制行级过滤；`internal` = 不强制（放宽） | 拼错会被 `validate()` 拒绝（**不取默认值** —— 拼错退化成更宽那档是最坏的结果） |

| `MCP_MAX_CHART_POINTS` | 50 | 图表点数上限 | 图不是数据导出通道（第 6 步的口径） |


> `Settings` 里放的是**全进程都要知道**的东西；MCP 的身份只对 MCP 这一个入口有意义，

> 靠的是 `settings.py::_env_value` 那一小段（为什么抄一份而不 import，见 §10.1 坑 2）。

### 2.3 为什么有两个 `-m` 入口（以及它们的关系）

| 入口 | 是什么 | 允许加逻辑吗 |
|---|---|---|
| `python -m app.mcp` | `app/mcp/__main__.py`（3 行） | ❌ 只许 `import` + `sys.exit(main())` |
| `python -m app.mcp.server` | 实现所在位置（`server.py::main`） | ✅ 全部逻辑在这 |

```powershell
# 两条命令必须**行为完全一致**（它们是同一个 main）：
$env:MCP_ACTOR_USER_ID="1"
$ a = uv run python -m app.mcp --check --json
$ b = uv run python -m app.mcp.server --check --json
# 实测：两段输出逐字节一致（60 行），且 stderr 里都没有 RuntimeWarning
```

> ⚠️ 薄壳里**不允许**任何逻辑：一旦有人「顺手处理一下」，两个入口就会出现两种行为。
> 判断标准很简单：`__main__.py` 应该永远只有 import 与 `sys.exit(main())`。
>
> ⚠️ 但「等价」这件事**不是自动成立的**，它需要两处配合（本步实测各踩一次，见 §10.1 坑 10）：
>
> 1. `server.py` 末尾必须有 `if __name__ == "__main__": raise SystemExit(main())` ——
>    `python -m <模块>` 是把该模块当 `__main__` 执行，没有这个 guard 就**什么都不做、静默退出 0**；
> 2. `app/mcp/__init__.py` 必须是**惰性门面**（PEP 562）：若它在 import 期就把 `app.mcp.server`
>    拉进来，`-m app.mcp.server` 会先 import 包（`__init__`）再执行 `server`，
>    Python 报 `RuntimeWarning: 'app.mcp.server' found in sys.modules after import of package …`。
>
> 两条都由 `tests/mcp/test_mcp_server.py::test_both_cli_entry_points_behave_identically` 钉住
> （它在**子进程**里跑两条命令并逐字节比对输出 —— CLI 的坑几乎全在进程边界上）。

## 3. 实现：薄壳怎么搭（含 FastMCP 改名这个坎）

### 3.1 `FastMCP` → `MCPServer`：三种处置与取舍

`15.mcp.md` 第 3 节把依赖写成 `mcp`（Python SDK，`FastMCP`）。实测装到的是 **2.3.0**，
而 2.x 把 `mcp.server.fastmcp.FastMCP` **改名**成 `mcp.server.mcpserver.MCPServer`
（见 [What's new in v2](https://py.sdk.modelcontextprotocol.io/whats-new/)）：

```
>>> from mcp.server.fastmcp import FastMCP
ModuleNotFoundError: No module named 'mcp.server.fastmcp'; This is mcp 2.x,
where FastMCP was renamed to MCPServer (from mcp.server.mcpserver import MCPServer)
```

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| ① 钉 `mcp<2` | 与文档字面一致，代码照抄现成教程 | 钉在上一代 SDK；2.x 的新特性（缓存提示、请求状态隔离等）全拿不到 | ❌ |
| ② 装独立的 `fastmcp` 包 | 名字与文档一致，功能也全 | **引入第三方框架**：一个薄壳不需要框架；而且它与官方 SDK 是两套演进节奏 | ❌ |
| ③ **用 2.x 的 `MCPServer`**（本仓） | 能力与协议完全一致：`@server.tool` 装饰器、docstring 自动成为描述、stdio/sse/streamable-http 三种传输都在；**且多一个测试用的进程内 `Client`** | 与文档的类名不一致 | ✅ |

③ 的关键收益是**测试**：`mcp.Client` 支持直接传一个 `MCPServer` 实例，在**同一进程内**完成
`initialize` → `tools/list` → `call_tool`。整条协议链路因此可以进默认回归（零子进程、零端口，13 条 skip 的情况下 12s 跑完 85 条）；
真子进程 stdio 单独留一个场景（§6.5）作为传输层的证据。


### 3.2 装配（`build_server`）：三个刻意的做法

```python
# app/mcp/server.py（节选，实际代码见文件）
def build_server(settings: McpSettings | None = None) -> MCPServer:
    resolved = settings if settings is not None else get_settings()
    problems = resolved.validate()
    if problems:                     # 启动期 fail-fast：身份不明就不该起来
        raise ValueError("MCP 配置不可用：" + "；".join(problems))
    server = MCPServer(name=SERVER_NAME, title=SERVER_TITLE, version=SERVER_VERSION,
                       instructions=SERVER_INSTRUCTIONS)
    ...
    server.add_tool(_sql_query, name=EXPOSED_TOOLS[0],
                    description=TOOL_DESCRIPTIONS[EXPOSED_TOOLS[0]],
                    annotations=ToolAnnotations(read_only_hint=True))
```

| 做法 | 为什么 |
|---|---|
| **每个工具一个闭包**，把 `settings` 捕获进去（不是模块级全局） | 同一个进程里造两个不同身份的 server（对客 + 内部）互不干扰；多租户部署与测试都靠它。实测见 §7.2 |
| **工具名与描述显式传入**（`name=` / `description=`） | 名字是**对外契约**，函数名是可以被重命名重构的；描述取自常量表，契约测试才能逐个断言 |
| **docstring 仍然写全**（含 `Args:`） | 给人看的详细说明留在函数上；`description=` 覆盖的是「给客户端模型看的那一句」 |

| `retrieve_knowledge` | `query`（必填）、`top_k` | `{results[{text,source,citation,chunk_id,page,score}], meta{returned,top_k,backend}}` | `retrieve_docs` |

### 3.4 本步对第 6 步的唯一改动：`caller` 的可选性与一处 contextvar

「薄壳」不等于「一行不改」。本步实测撞到一个**必须动第 6 步**的问题，值得完整记录：

**症状**：MCP 侧想让审计里的 `caller` 记成 `mcp:sql_query`（入口可归属），
但工具函数的 `caller` 是**必填关键字参数**，且只有**一个位置**。

```python
# 第一版（错的）做法：工具层传入口的 caller
rows, meta = execute_readonly_query(sql, bound, max_rows=cap, caller=settings.caller("sql_query"))
```

这么写有两个问题：

1. **看起来对，实际也不对**：`settings.caller("sql_query")` 是常量 `mcp:sql_query`，
   它**能**工作 —— 但这只是因为我们恰好只有一个身份。同一个 MCP 进程并发服务多个客户端时，
   调用点自己拼 caller 迟早会拼错或漏掉。
2. **更坏的形态是「在 MCP 层再包一层审计」**：那样同一次查询会被记**两条**
   （`rows` 与耗时各两遍，「被拒的调用」还会因为内层先抛而看起来像两次失败）。

**修法**：让**入口声明、内层复用**（`app/tools/audit.py`）：

```python
# 入口（app/mcp/tools.py::_in_thread）：设一次 contextvar，工具内部读它
token = caller_override.set(settings.caller(tool))
try:
    return await to_thread.run_sync(fn)   # anyio 会把当前 context **复制**进工作线程
finally:
    caller_override.reset(token)

# 工具内部（app/tools/audit.py::audit_tool_call）：显式 caller > override > 拒绝
resolved = caller if isinstance(caller, str) and caller.strip() else caller_override.get()
if not resolved:
    raise ToolContractError("工具调用必须显式传 caller…或由入口设置 caller_override")
```

三个好处，每个都能验证：

* 审计里是 `mcp:sql_query`（§5.4 实测）；**恰好一条**记录（§7.5 实测）；
* **并发不串**：`ContextVar` 是 per-task 的，两个入口并发时各自的 caller 不互相污染
  （`tests/mcp/test_mcp_audit_db.py::test_concurrent_calls_do_not_mix_up_their_callers`）；
* 「审计不可绕过」**没有被放宽**：两条来源都没有时直接 `ToolContractError`
  （`tests/test_tools_contracts.py` 的契约改成了「可归属」，同时新增了这条运行期断言）。

> ⚠️ 这次改动的**契约影响**要认下来：`app/tools/*.py` 里 7 个公开工具的 `caller` 从
> 「必填（无默认值）」变成「可空，但**没有来源就拒绝**」。第 6 步那条契约测试
> （`test_every_public_tool_requires_caller_keyword`）因此改了判据，并在同一处补了
> 「两条来源都没有 → 拒绝执行」的运行期证明。这是**有意的语义收窄**，不是「放宽」：
> 之前是「函数签名强制」，现在是「执行路径强制」。

## 4. 身份与授权：MCP 入口的 D1 边界

### 4.1 一条纪律：身份不是工具参数

| 反例（**不要**这么做） | 后果 |
|---|---|
| `sql_query(sql, user_id=...)` 让客户端传身份 | 客户端说是谁就是谁 —— 行级过滤变成装饰 |
| `create_ticket(..., role="customer_service")` | 客户端一句话把自己提权成客服（还能退款的路径） |
| 用 `X-User-Id` 之类的头当身份 | 与上一条等价，只是换了个地方传 |

```powershell
# 契约测试逐个工具证明这一点（本仓的做法：遍历真实签名，而不是抄一份清单）
uv run pytest -q -p no:cacheprovider tests/mcp/test_mcp_contracts.py -k identity -v
# 期望：4 passed（四个工具各一条：`role` 与 `requester_user_id` 都不许出现在签名里）
```

> 💡 与第 9 步「请求体里没有 `user_id`」完全同源：**身份的来源必须是服务端已知的事实**
> （JWT 的 claim / 服务端配置），而不是请求内容。MCP 没有 HTTP 会话，
> 所以这一层的事实就是 `McpSettings`。

### 4.2 三种工具形态：身份怎么变成「工具层能执行的形状」

| 工具 | 有没有行归属 | 本层的动作 | 拦得住 | 拦不住 / 要靠别人 |
|---|---|---|---|---|
| `sql_query` | **有**（订单/退款/工单都按 `user_id`） | 强制 SQL 带 `WHERE user_id = :user_id`，且绑定值 == 身份 | 全表查询、跨用户查询、字面量过滤、换参数名绕过 | 守卫本身（写语句/白名单/危险函数）是第 4 步的 |
| `create_ticket` | **有** | 对客策略下 `user_id` 强制等于身份（客户端传别人 → 拒绝） | 给别人建工单 | 幂等由 DB 唯一约束保证；「该不该批」不在本步 |
| `retrieve_knowledge` | **没有** | 只做上限收敛 | 无（知识库对所有客户是同一份政策文档） | ⚠️ 见下面的警告 |
| `build_chart` | **没有** | 只做点数上限 + 载荷最小化 | 图里带出未声明的列 | 行数据的来源（`build_chart` 不查库） |

> ⚠️ **`retrieve_knowledge` 不是「已经做了行级过滤」**：ShopSage 的知识库是 8 份公开政策文档
> （退货/物流/保修/积分/账户安全/企业采购…），对所有客户是**同一份内容**，
> 所以它天然没有「这行属于谁」的问题。但这个结论**依赖语料形态**：
> 哪天知识库里放进「这单的物流面单」这类客户私有文档，`retrieve_knowledge`
> **必须**补上按 `user_id` 的元数据过滤 —— 而那一天的正确做法是让检索层
> （第 10 步的 `hybrid_search` + `rag_documents`）带上作用域，
> 而不是在 MCP 这层做结果后过滤（后过滤会让召回率看着正常、实际漏掉本该有的片段）。
> 这条边界写在这里，是为了避免下一个人误以为「MCP 已经统一做了行级过滤」。

### 4.3 两种策略与风险清单（`MCP_POLICY`）

| 策略 | 身份 | 本层的额外强制 | 谁负责鉴权 |
|---|---|---|---|
| `customer`（**默认**） | 必填 `MCP_ACTOR_USER_ID` | `sql_query` 强制行级过滤；`create_ticket` 强制本人 | 部署方保证「这个进程只服务这一个用户」 |
| `internal` | 可空 | 无（守卫 / RBAC / 只读引擎照旧生效） | 部署方全责：本机受信进程，或前置网关已鉴权 |

```powershell
# 看一眼两种策略下同一条 SQL 的命运（零依赖，静态校验）
uv run python -c @"
from app.mcp.settings import McpSettings
from app.mcp.sync_calls import sql_query_sync
from mcp.server.mcpserver.exceptions import ToolError

sql = 'SELECT status, count(*) AS n FROM orders GROUP BY status LIMIT 10'   # 无行级过滤
for policy in ('customer', 'internal'):
    s = McpSettings(policy=policy, actor_user_id=1, actor_role='internal_employee' if policy=='internal' else 'customer')
    try:
        sql_query_sync(sql, None, None, settings=s)
        print(f'{policy:<9} 放行（会真去查库）')
    except ToolError as exc:
        print(f'{policy:<9} BLOCK {str(exc).split(chr(93))[0] + chr(93)}')
"@
# 实测：
#   customer  BLOCK [mcp_missing_row_filter]
#   internal  放行（本机没有真执行：会抛数据库错误，属预期）
```

> ⚠️ **选 `internal` 是在认一笔风险**，请把下面三条写进部署文档：
>
> 1. **这个进程能看全站数据**：任何能连上它的客户端（本机任何用户、任何能访问该端口的进程）
>    都能读到全部订单/退款/工单。`streamable-http` 传输下这意味着**必须**放在受信网络里，
>    或者由前置网关完成鉴权。
> 2. **`MCP_ACTOR_ROLE` 决定能做什么**：写成 `admin` 就等于给了全站读写；
>    对内部用途应当给最小角色（例如 `internal_employee`：有 `read:all_orders`，没有 `read:finance`）。
> 3. **审计仍在，但归属变粗**：`caller` 只会是 `mcp:<工具名>`，分不出「是哪个客户端调的」。
>    要可归属就得给每个 MCP 进程一份配置（一台一个账户），或接入 MCP 的 auth 能力（本步不做）。

### 4.4 配置不可用 = 起不来（fail-fast 的实测）

```powershell
$env:MCP_ACTOR_USER_ID=""; uv run python -m app.mcp --check; echo "退出码=$LASTEXITCODE"
# 实测：打印一行「[MCP 无法启动] …」后退出码 2（不是 1，也不是 0）
```

> ⚠️ 这条与第 14 步的口径一致：**「配置写错」是退出码 2（没跑起来），不是 1（不达标）**。

> 而那看起来像工具坏了。

## 5. 安全与审计：D1 在这条入口上的具体形态

### 5.1 三道门（缺一不可，且**顺序有讲究**）

```
客户端 SQL
   │
   ├─① security.sql_guard.validate_sql   ← 静态：写语句/多语句/白名单/危险函数/无 WHERE/超上限
   │      └─ 规则名：not_read_only / multiple_statements / table_not_allowed / column_not_allowed /
   │                missing_where / trivial_where / forbidden_function / limit_too_large …
   ├─② app/mcp/sync_calls 的行级过滤      ← 本步新增：缺过滤 / 字面量 / 值指向别人
   │      └─ 规则名：mcp_missing_row_filter / mcp_row_filter_needs_binding / mcp_row_filter_mismatch
   └─③ 只读数据库角色（第 4 步）          ← 运行时兜底：即使前两道被绕过，写操作在库层报权限错误
```

**顺序**：① → ② → ③，**先守卫再行级过滤**。理由是「报错必须指向真正的问题」（§10.1 坑 1）。

> ⚠️ ② 这一道**不能省**，也不能靠「工具层已经过守卫」替代：守卫拦的是「SQL 长什么样」，
> 它完全允许一条合规的 `SELECT ... FROM orders WHERE status = 'paid'`（带 WHERE，合法，但看全站）。
> 行级过滤是**另一件正交的事**（第 4 步 `4.security-runbook.md` §3 有对照表）。

### 5.2 一张矩阵：越权形态 → 拦在哪一层（全部实测）

```powershell
uv run python -m scripts.mcp_demo --scenario guard
```

```
==============================================================================
场景 2：越权与写语句会被拦吗（零依赖，纯静态校验）
==============================================================================
  ✅ 写语句：BLOCK[not_read_only]（静态守卫）
  ✅ 多语句：BLOCK[multiple_statements]（静态守卫）
  ✅ 无 WHERE 全表：BLOCK[missing_where]（静态守卫）
  ✅ 白名单外的表：BLOCK[table_not_allowed]（静态守卫）
  ✅ 缺行级过滤：BLOCK[mcp_missing_row_filter]（MCP 入口的边界校验）
  ✅ 字面量过滤：BLOCK[mcp_row_filter_needs_binding]（MCP 入口的边界校验）
  ✅ 正例：带 `WHERE user_id = :user_id` 的查询通过静态校验（未执行）
```

把矩阵补全（含需要库的那几条，来自 §7.5 的用例与 `--mcp-live` 实测）：

| 客户端输入 | 拦截层 | 规则名（客户端据此纠正） | 退出形态 |
|---|---|---|---|
| `DELETE FROM orders` | ① 守卫 | `not_read_only` | `is_error=True` |
| `SELECT 1; DROP TABLE orders` | ① 守卫 | `multiple_statements` | `is_error=True` |
| `SELECT order_id FROM orders` | ① 守卫 | `missing_where` | `is_error=True` |
| `SELECT order_id FROM orders WHERE 1=1` | ① 守卫 | `trivial_where` | `is_error=True` |
| `SELECT email FROM users WHERE user_id = :user_id` | ① 守卫 | `column_not_allowed`（受保护列） | `is_error=True` |
| `SELECT order_id FROM secret_table WHERE user_id = :user_id` | ① 守卫 | `table_not_allowed` | `is_error=True` |
| `SELECT pg_read_file(...) …` | ① 守卫 | `forbidden_function` | `is_error=True` |
| 带 WHERE 但**没有** `user_id` 过滤 | ② 行级过滤 | `mcp_missing_row_filter` | `is_error=True` |
| `WHERE user_id = 1`（字面量） | ② 行级过滤 | `mcp_row_filter_needs_binding` | `is_error=True` |
| `WHERE user_id = :user_id` 但绑定 `2`（身份是 1） | ② 行级过滤 | `mcp_row_filter_mismatch` | `is_error=True` |
| `WHERE user_id = :user_id` 但参数表里没有它 | ② 行级过滤 | `mcp_missing_row_filter` | `is_error=True` |
| `params={"user_id": "1"}`（字符串） | ② 行级过滤 | `mcp_invalid_row_filter` | `is_error=True` |
| `max_rows=10000` | ② 上限收敛 | 不报错，夹到 100 | `rows_cap=100` |
| `top_k=500` | ② 上限收敛 | 不报错，夹到 10 | `meta.top_k=10` |
| `create_ticket(..., user_id=2)`（身份是 1） | ② 行级过滤 | `mcp_row_filter_mismatch` | `is_error=True` |
| `create_ticket(...)` 不给 `idempotency_key` | ② 契约 | `tool_contract` | `is_error=True` |
| `create_refund_request(...)`（未暴露） | 协议/分发层 | `unknown_tool` | `is_error=True` |

> 💡 「夹住」与「拒绝」的区分是有意的：**参数超配额**（想要更多行）该夹住并继续，
> 因为请求本身是合理的；**参数形态错**（`user_id="1"`）该拒绝，因为那是调用方的错。
> 两类混在一起会让模型因为一个无关紧要的数字彻底失败，或者反过来把类型错误当成配额问题重试。

### 5.3 写路径：对客只能建自己的工单 + 幂等必须由客户端给

```powershell
# 幂等的运行期证据（真库；需要 --mcp-live）
uv run pytest -q -p no:cacheprovider tests/mcp/test_mcp_live.py -k idempotent --mcp-live -v
```

两条设计口径（都来自第 6 步，本层只是**不做例外**）：

| 口径 | 为什么 |
|---|---|
| 返回值里**没有** `created` | 幂等的语义是「同一个键的多次调用返回**同一个**结果」；带一个每次都变的标志位，`k1 == k2` 就不成立。「本次是新建还是命中」在**审计字段** `details.created` 里 |
| `idempotency_key` **必须由客户端给** | 服务端生成 = 每次调用都是新键 = 每次都是一张新工单（幂等形同虚设）。报错消息里直接写了这条理由，客户端模型下次就会带上 |

```powershell
# 亲眼看到「谁在调用」与「是不是新建」（真库，逐行可核对）
uv run python -c @"

logging.basicConfig(level=logging.INFO, format='%(message)s')
from app.mcp.settings import McpSettings
from app.mcp.sync_calls import create_ticket_sync

s = McpSettings(policy='customer', actor_user_id=1)
key = 'mcp-demo-' + uuid.uuid4().hex[:8]
print('第一次:', create_ticket_sync('logistics', key, None, None, settings=s))
print('第二次:', create_ticket_sync('logistics', key, None, None, settings=s))
from app.db.session import SessionLocal
from app.db.models import Ticket
with SessionLocal() as db:
    n = db.query(Ticket).filter(Ticket.idempotency_key == key).count()
    print('库里行数:', n)
    db.query(Ticket).filter(Ticket.idempotency_key.like('mcp-demo-%')).delete()
    db.commit()
print('（演示数据已清理）')
"@
```

### 5.4 审计：`caller` 怎么归因到 MCP

一条审计记录长这样（真库实测，`caplog` 抓的 `extra={"tool_audit": …}`）：

```json
{"audit_id": "tc-e7f5cf6be4e2", "tool": "retrieve_knowledge", "caller": "mcp:retrieve_knowledge",
 "started_at": "2026-10-12T15:24:40.835+00:00", "duration_ms": 28955, "outcome": "ok", "rows": 3,
 "error_type": null,
 "args": {"query": "无理由退货的运费谁承担", "top_k": 3, "min_score": null},
 "details": {"hits_raw": 3, "hits_returned": 3, "dropped": {}, "top_k": 3, "backend": "app.rag.retriever"},
 "redacted_args": []}
```

四个读法：

| 字段 | 回答什么问题 |
|---|---|
| `caller: "mcp:retrieve_knowledge"` | **这次调用来自 MCP 还是内部 Agent**（`6.tools-runbook.md` §3.3 的约定取值） |
| `audit_id` | 与协议结果里的 `meta.audit_id` **是同一个** —— 用户报的那次查询能一键串到日志 |
| `details.dropped` | 检索「返回 0 条」的成因（`no_source` / `below_min_score`）/ 工单是否本次新建（`created`） |
| `redacted_args` | 「为什么日志里看不到这个字段」（打码路径清单） |

### 5.5 错误口径：带规则名，不带内部细节

| 异常 | 谁抛 | 客户端看到什么 | 为什么这么处理 |
|---|---|---|---|
| `SQLSecurityError`（带 `rule`） | `security.sql_guard` | `Error executing tool sql_query: [not_read_only] 拒绝非查询语句…` | 规则名让模型**能改**；原始 SQL 不进消息（可能含业务数据） |
| `PermissionDenied`（带 `role`/`missing`） | `security.rbac` | `[permission_denied] …（角色 customer；缺权限 write:refund）` | 与第 9 步的 403 语义对齐 |
| `ToolContractError` | `app/tools/errors.py` | `[tool_contract] top_k 必须是正整数，收到 …` | 调用方写错了，改调用而不是重试 |
| `ToolNotAvailableError` | `app/tools/errors.py` | `[not_available] 知识库检索后端尚未就绪…` | 与「知识库里没有这条」区分开 |
| **其它任何异常**（崩溃） | 任意 | `Error executing tool <name>`（**原始报文只留在服务端**） | 客户端是不可信输入源，不该从错误里读到堆栈/连接串 |

```powershell
# 白名单的实际形态：只有这四类会被翻译成可读消息，其余冒泡成通用错误
uv run python -c @"
from app.mcp.tools import as_tool_error, _CLIENT_FIXABLE
print('可翻译的异常类型:', [c.__name__ for c in _CLIENT_FIXABLE])
from app.security.sql_guard import SQLSecurityError
print(as_tool_error(SQLSecurityError('拒绝写语句', rule='not_read_only', sql='DELETE FROM orders')))
"@
```

### 5.6 注解（`ToolAnnotations`）为什么必须是诚实的

| 工具 | `read_only_hint` | `idempotent_hint` | `destructive_hint` | 依据 |
|---|---|---|---|---|
| `sql_query` | ✅ | — | 不设 | 只读角色 + 静态守卫 |
| `retrieve_knowledge` | ✅ | — | 不设 | 纯读 |
| `build_chart` | ✅ | — | 不设 | 纯函数（不碰库） |
| `create_ticket` | 不设 | **✅** | **不设**（刻意） | 会写库；幂等由 DB 唯一约束保证 |

> ⚠️ `create_ticket` **不标** `destructive`：它建的是新工单，不修改/删除既有数据。
> 把「新建」标成破坏性会让客户端对每一次正常建单都弹确认框，最后的结果是使用者习惯性点「允许」——
> 那比不标更危险（与 `4.security-runbook.md` 的告警疲劳同一条道理）。

| 症状 | 最可能的原因 | 怎么确认 | 修法 |

## 10. 坑与分诊

### 10.1 本步实测撞到的 10 个坑

**坑 1：`DELETE FROM orders` 报的规则名是错的（校验顺序）**

* 症状：越权矩阵里所有输入都返回 `[mcp_missing_row_filter]`，包括 `DELETE FROM orders`。
* 原因：第一版把「行级过滤校验」放在 `validate_sql` **之前**。写语句当然也没有 `user_id` 过滤，
  于是它先撞上行级过滤那条规则。
* 为什么危险：规则名是给**模型自我纠正**用的。它拿到 `mcp_missing_row_filter`，会去给
  `DELETE` 加一个 `WHERE user_id = :user_id` —— 改出一条「更合规的写语句」。
* 修法：`sync_calls.sql_query_sync` 先 `validate_sql` 再做行级过滤，并加一条**顺序用例**
  （`test_write_statement_is_reported_as_not_read_only_not_as_missing_filter`）把它钉住。

**坑 2：`import app.mcp` 把 FastAPI 拖了进来（薄壳的自我背叛）**

* 症状：契约测试报 `import app.mcp 之后拖进来了 web 层模块：[… 'fastapi', 'app.api.main', 'uvicorn' …]`。
* 原因：`app/mcp/settings.py` 第一版写了 `from app.api.config import _env_value` ——
  借了一行工具函数，代价是把 `app.api` 整条链（含 uvicorn）拉进 `sys.modules`。
* 为什么危险：MCP 服务是**短生命周期进程**（stdio 下每次连接都可能起一个新的），
  启动耗时直接体现为客户端「连上了但没反应」（§6.5 实测 import 占 2327ms 里的绝大部分）。
* 修法：在 `settings.py` 里写一份 10 行的 `_env_value`（**语义相同**：`os.environ` > `.env` > 默认），
  并把「为什么抄一份」写在 docstring 里。
* ⚠️ 顺带修掉一个**测试自己的坑**：判据不能是「`sys.modules` 里有没有 fastapi」——
  跑全量时它早被 `tests/api/` 拖进来了，那条断言**永远为真**。改成 AST 扫描 import 语句。

**坑 3：审计用例 monkeypatch 掉了被测对象（0 条记录）**

* 症状：`一次调用应当恰好一条审计，实际 0 条`。
* 原因：第一版审计用例为了「不连库」而 `monkeypatch.setattr(sync_calls, "execute_readonly_query", fake)` ——
  而**审计的唯一落点就在那个函数内部**（`audit_tool_call` 上下文管理器）。
  换掉它等于换掉了被测对象，用例变成「测我的假函数会不会写日志」。
* 修法：审计那组改成**真库用例**（`test_mcp_audit_db.py`，打 `db` + `mcp_live` 两个标记，默认 skip），
  其余用例继续用假执行器（它们量的是边界，不是审计）。
* 教训（写进 §7.3 第 2 条）：**红的原因必须与用例名对得上**。

**坑 4：MCP 想让审计记 `mcp:sql_query`，但工具层用的是自己的 caller**

* 症状：审计里 `caller` 是工具默认的调用者，看不出「这次来自 MCP」。
* 第一版修法（错的）：在 MCP 层再包一层 `audit_tool_call(caller=...)` → 同一次调用记**两条**。
* 正解：入口用 `caller_override`（contextvar）盖章、工具内部复用（§3.4）。
* 附带发现：**同步入口也要盖章**。`scripts/mcp_demo.py` 直接调 `sync_calls` 时，
  如果只有 async 薄壳盖章，脚本这条路会失败 —— 而失败信息看起来像「检索后端不可用」
  （`ToolContractError: 工具调用必须显式传 caller`被场景 5 的 `except Exception` 归到了
  「后端不可用」那一类，误导了一轮排查）。修法：`caller_stamp` 上下文管理器放在 `sync_calls` 层，
  两条路都盖。

**坑 5：`from __future__ import annotations` 也救不了嵌套引号**

* 症状：写 `settings.py` 时把中文引号写成了英文 `"`，`f"…{s}…"` 里嵌 `"` 直接 `SyntaxError`。
* 修法：中文文档里统一用「」，英文引号只出现在代码与 JSON 里。
* 这条之所以值得记：报错位置在**字符串中间**，看起来像内容问题而不是语法问题。

**坑 6：真依赖用例的顺序依赖（向量库被全量回归清空）**

* 症状：`--mcp-live` 的真检索用例返回 0 条 / 演示场景 5 打印「向量库是空的」。
* 原因：`tests/test_db_migrations.py::test_migration_round_trip_is_repeatable` 会
  `downgrade base` → `upgrade head`，`rag_*` 三张表连同数据一起没了（第 14 步 §1.0 记录过同一条）。
* 顺序：**先跑完全量回归 → 再 `load_knowledge_base` → 再跑 `--mcp-live` 与演示**。
* 顺带：演示脚本第一版在场景 4 里「随便挑一个订单的 `user_id`」，于是撞上
  `mcp_row_filter_mismatch`（身份是 1、挑到 8）—— 那条拦截**是对的**，但让演示看起来像坏了。
  修法：场景 4 用**本服务的身份**（`settings.actor_user_id`）。

**坑 7：演示脚本漏接了一种异常类型**

* 症状：`场景 guard 崩了：SQLSecurityError: 拒绝非查询语句…`。
* 原因：`sync_calls` 里的静态守卫是**同步**执行、异常原样抛出（不经 async 薄壳的翻译），
  所以脚本要同时接住 `SQLSecurityError`（守卫）与 `ToolError`（本层边界）。
* 修法：`except (SQLSecurityError, ToolError)` 分开打规则名（§6.2 的实测输出就是这么来的）。
* 顺带说明一件事：**「异常分三类」的纪律在 MCP 入口的表现就是这样** ——
  守卫的异常保持原类型（带 `rule` 字段），本层的拒绝用 `ToolError`（规则名写在消息里）。

**坑 8：沙箱里的 `uv` 全局缓存不可写**

* 症状：`uv run` 报 `error: Failed to initialize cache at C:\Users\…\AppData\Local\uv\cache … os error 5`。
* 修法：每条命令前设 `$env:UV_CACHE_DIR = "$PWD\.uv-cache"`（与第 5 步同一个坑）。

**坑 9：`PowerShell` 的 `-replace` + `Set-Content` 把源文件编码搞坏了**

* 症状：用 `(Get-Content x -Raw) -replace … | Set-Content x` 批量改一处 `strict=False` 之后，
  文件里的中文变成乱码（读回来是 `寤哄伐鍗?`）。
* 原因：`Get-Content` 用默认编码读、`Set-Content` 又写了一遍 —— 在 UTF-8 无 BOM 的中文源码上
  这一步就是有损的。
* 修法：**改源码一律用文件编辑工具**（按 UTF-8 精确替换），不要用 shell 做字符串替换；
  真要用 shell，也必须显式 `-Encoding utf8` 并用 `-Raw` 读。
* 这条值得单列：它是**唯一会静默毁掉一整个文件**的坑，而症状（乱码）出现在编辑器里、
  不在报错里。

**坑 10：`-m app.mcp.server` 静默退出 0（「两条入口等价」是一句需要验证的话）**

* 症状：`uv run python -m app.mcp.server --check` **什么都不打印、退出码 0**。
  只有当我在手册里写下「两条命令必须行为完全一致」并去实测时才发现。
* 原因：`python -m <模块>` 把该模块当 `__main__` 执行。`server.py` 里只有 `def main()`，
  没有 `if __name__ == "__main__"` 的 guard —— 于是导入、定义、退出，一步都没跑。
* 为什么危险：**静默成功的命令比报错的命令危险得多**（它会被写进运维脚本与容器配置，
  然后在某天以「服务起不来但没有任何日志」的形态爆炸）。
* 修法：`server.py` 末尾加 guard；同时把 `app/mcp/__init__.py` 改成惰性门面（PEP 562），
  否则第二条命令会因为在包 import 期就把 `app.mcp.server` 拉进 `sys.modules` 而报
  `RuntimeWarning: … this may result in unpredictable behaviour`。
* 加固：`test_both_cli_entry_points_behave_identically` 在**子进程**里跑两条命令、
  逐字节比对输出、并要求 stderr 里没有 `RuntimeWarning`。
  这条用例的教训与坑 3 同源：**CLI 的坑几乎全在进程边界上**，
  用 `inspect` 读函数签名一条都发现不了。

### 10.2 排障顺序（三条路，别乱）

1. **服务起不来 / 客户端连不上** → `uv run python -m app.mcp --check`（退出码 2 = 配置问题，§4.4）；
   再手工 `python -m app.mcp` 看 stdout 有没有非 JSON 行（§6.5）。
2. **调用被拒** → 先看**规则名**（`[not_read_only]` vs `[mcp_missing_row_filter]`）：
   前者改 SQL 形态，后者改过滤写法（§5.2 矩阵）。
3. **行为对但数据不对** → 找 `meta.audit_id`，去日志里 grep 那一条：
   `caller` 告诉你谁调的，`args` 告诉你传了什么，`details` 告诉你结果（§5.4）。
