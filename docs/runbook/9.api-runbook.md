三条铁律：

1. **API 层无业务逻辑**。`app/api/` 里出现 SQL、prompt 文本、脱敏规则、权限判断就是越界 ——
   只做四件事：**鉴权 → 校验 → 转交图 → 格式化返回**（§12 ② 用 AST 检查钉住）。
   ⚠️ 变更 001 给这条纪律开了**一处行级豁免**（`deps._session`，因为 WebSocket 握手与
   「非依赖式解析身份」拿不到 `Depends`）；它带标记、且有用例限制「最多 2 处、只许在本文件」。
2. **身份只来自令牌**。请求体里没有 `user_id` / `role`；`thread_id` 由服务端从
   「鉴权结果 + `session_id`」派生（**变更 001 起是 `c{user_id}:{session_id}` /
   `e{emp_id}:{session_id}`** —— 前缀分主体类别，否则员工 `emp_id=7` 与客户 `user_id=7`
   会落进同一个会话桶）—— 客户端能任选 `thread_id` 就等于能读写别人的会话状态，
   那比越权查一行数据更严重（§3.2）。
3. **错误只有一个形状**。所有 4xx/5xx 都是 `{"error": {code, message, detail}, request_id}`，
   前端只写一套解析；域异常带着的 `rule` / `missing` 字段在 `detail` 里保留（§7）。

另一条：**限流在最外层、鉴权在路由**。中间件按「用户 + 接口」扣配额（未鉴权的请求先被 429），
路由的依赖负责 401 语义 —— 两件事分开的理由是它们的失败语义完全不同（§5.2）。

## 1. 环境与前提

### 1.0 本步的链路（一个入口 + 三个出口 + 一条回环）

```
                        ┌──────────────── 第 9 步 api/ ────────────────┐
 客户端（Web/IM/内部系统）│                                            │
        │               │  ① 中间件：请求 id → 限流 → 访问日志 → 指标    │
        │  Authorization│  ② 依赖：JWT 校验 → Actor（身份 + 会话 + 隔离键）│
        │  : Bearer <JWT>│ ③ 路由：校验 → 写 state → 转交图               │
        └──────────────►│ ④ 格式化：Turn → 响应信封 / WS 帧             │
                        └───────────────┬────────────────────────────┘
                                        │  run_turn(graph, state, thread_id=u{uid}:{sid})
                                        ▼
                         第 8 步的图（guardrail → router → … → synthesis）
                                        │
                                        │  中断（敏感分支）
                                        ▼
                         第 9 步的审批通道：202 → POST /api/chat/approve → 200/409
```

**每个环节「拦得住什么 / 拦不住什么」**：

| 环节 | 拦得住 | 拦不住 / 需要别的环节 |
|---|---|---|
| 中间件限流 | 「一个人猛刷接口」——请求根本进不了图（零模型成本） | 分布式刷（多账号/多 IP）→ 网关/WAF 的活 |
| JWT 依赖 | 伪造/过期/类型混用的令牌 | 令牌**泄漏**后的冒用 → 短 `exp` + 刷新令牌轮换 |
| 请求体校验 | 请求体里塞 `user_id`/`role`（越权入口）、超长输入 | 「换个说法套数据」→ 行级过滤 + 输出护栏 |
| `thread_id` 派生 | 任选别人的会话（读历史/推进状态） | —— |
| 图（第 8 步） | 越权查询、注入、敏感操作 | 意图判错 → 第 16 步评测 |
| 输出裁剪 | 对客响应里的 SQL / 权限点 / `rows` | 模型自己把内部口径写进 `answer` → 输出护栏 |

### 2.2 一次请求的完整生命周期（读 `main.py` + `middleware.py` + `deps.py` 就够）

```
请求 → ApiMiddleware（纯 ASGI）
         ├─ 请求 id：客户端带 X-Request-Id 就用它（≤64 字符且可打印），否则生成 16 位 hex
         ├─ 限流：只对 LIMITED_SCOPES 里的路径；桶键 = {scope}:u:{user_id}:{role}（无令牌 → ip:<来源IP>）
         │       超限 → 429 + Retry-After（**不再往下走**，零成本）
         └─ 访问日志 + 指标（在 finally 里记，4xx/5xx 也留痕）
     → 路由
         ├─ 校验请求体（pydantic → 422）
         ├─ Depends(require_principal)：JWT → Principal（401 + WWW-Authenticate）
         ├─ resolve_session_id + thread_id_for → Actor（u{user_id}:{session_id}）
         ├─ entry_state(actor, message) → 四个键：messages / user_id / role / permissions
         └─ run_turn(graph, state, thread_id=…) → Turn
     → build_response(Turn, actor) → ChatResponse（或 202 / WS 帧）
     → 域异常在此刻被 handler 翻成统一错误信封（§7）
```

**无状态的两处状态**（多副本可水平扩容的前提）：

| 进程内状态 | 多副本下的影响 | 处置 |
|---|---|---|
| `MetricsRegistry`（计数/直方图） | 每个副本各报一份 | Prometheus 抓每个副本后 `sum()`（标准做法） |
| `MemoryRateLimitStore`（限流计数） | 额度被放大到「副本数 × limit」 | **生产必须 Redis**（`open_rate_limiter` 会告警，`/health` 会显示 `skipped` + 一句说明） |

会话状态（对话历史、断点、挂起）全在 checkpointer 里（Postgres/Redis），**不在**进程内。

## 3. 鉴权与身份

> 🔁 **变更 001 改了这一节的四处**（[变更单](../changes/001-account-login-and-admin-console.md)）：
> ① 令牌声明从「裸 `user_id`」改为「**主体 + 世代号**」（`sub=c7/e1`、`stype`、`sid`、`aid`、`ver`）；
> ② 鉴权依赖**每请求查一次账号**（停用/改密/改角色立即生效）；
> ③ `thread_id` 形状从 `u{user_id}:` 改为 `c{user_id}:` / `e{emp_id}:`；
> ④ 有了真登录接口（`POST /api/auth/login`），不再需要手工签令牌来登录。
> **升级影响**：旧令牌一律被拒、旧会话作废 ⇒ 需要重新登录。

### 3.0 现在怎么拿到令牌（变更 001 起）

```powershell
# ① 先灌演示账号（口令写在 scripts/seed.py 的 DEMO_ACCOUNTS，刻意不打印到终端）
uv run python -m scripts.seed

# ② 用账号 + 口令换令牌（这就是 Web 登录页做的事）
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/auth/login `
  -ContentType 'application/json' `
  -Body '{"identifier":"admin","password":"admin-demo-pass"}'

# ③ 排障时也可以签一个（**按账号**签，会带上 aid/ver；变更 001 之前是「不查账号直接签」）
uv run python -m scripts.dev_token --account admin
uv run python -m scripts.dev_token --role internal_employee   # 按角色取第一个启用账号
```

⚠️ **`dev_token` 现在必须能查到账号**：变更 001 之后鉴权会比对 `accounts`，
没有账号行的令牌一定被拒。所以「先 seed、再签」是硬顺序；
`--role internal_employee` 签出的主体是 **`e2`**（员工），不再是伪装成客户的 `c7`。

### 3.1 401 的四条路径（每条对应一种真实攻击面）

```powershell
uv run python -m scripts.api_demo --scenario auth
# 实测输出：
#   无令牌                -> 401 unauthorized           缺少 Authorization 头
#   过期令牌               -> 401 unauthorized           令牌已过期，请重新登录
#   篡改签名               -> 401 unauthorized           令牌无效：Invalid crypto padding
#   刷新令牌当访问令牌          -> 401 unauthorized           令牌类型不对：需要 access，收到 refresh
#   请求体里塞 user_id      -> 422 validation_error       请求参数不合规
#   X-Request-Id 透传 -> 'trace-from-gateway'
```

> ⚠️ 演示脚本里「刷新令牌」那条实际会先被限流拦住（429），因为脚本给的是小额度且前面几条共用同一份计数。
> 想单独看这一条：`uv run pytest -q tests/api/test_auth.py -k refresh`。

**变更 001 新增的第五类 401**（也是最容易误判的一类）：**令牌是好的、但账号已不能用了**。
`redirect` 到重新登录是对的动作，而它的原因有三种，文案会说明是哪一种：

| 场景 | 触发方式 | 响应 |
|---|---|---|
| 旧格式令牌 | 变更 001 之前签的令牌（没有 `aid`/`ver`） | 401「旧格式…请重新登录」 |
| 账号被停用 | 管理台点「停用」 | 401「账号已被停用…」 |
| 令牌被作废 | 改口令 / 改角色 | 401「令牌已被作废（口令或权限发生过变更）…」 |

```powershell
# 一次看全（也可以直接跑端到端脚本，见变更单 §7.7）
uv run pytest -q tests/api/test_auth_accounts.py -k "invalidates or refresh"
```

四条口径（都在 `app/security/auth.py` 里，本步只是**接线**，不重写）：

1. **算法固定 HS256**（`algorithms=["HS256"]`）——不写死是经典的算法混淆漏洞；
2. **`exp` / `iat` / `sub` 必填** ——不给「永不过期」留口子；
3. **密钥来源集中**（`JWT_SECRET` → `SecretStr`），`ENV=prod` 缺失时**启动即失败**；
4. **令牌类型区分** access / refresh ——刷新令牌不能直接访问业务接口。

> ⚠️ **不要写 `Depends(auth.get_current_user)`**：那个函数的 `authorization` 参数会被 FastAPI
> 当成**查询参数**，症状是「带 Authorization 头却拿不到身份」。本步用的是
> `deps.require_principal`（自己用 `request.headers` 取头再调 `parse_token`），
> 这条坑在 `4.security-runbook.md` §4.4 已经记过一次（§10.1 坑 1）。

> ⚠️ **变更 001 新增一条同族坑**：`db: Any = Depends(get_db)` 这种「把 `Depends` 当默认值」
> 的写法，会让**把该函数当普通函数调**的地方拿到 `Depends` 对象本身，报
> `'Depends' object has no attribute 'execute'`。而它**只在真有请求进来时才暴露**
> （收集期与纯逻辑用例全绿）。处置：`db: Any = None` + 缺省自己开会话（见 `deps._session`）。

### 3.2 身份与会话：`thread_id` 是**派生**的，不是客户端给的

```python
# 派生规则（只有一处实现：app/api/deps.py）
thread_id = f"u{user_id}:{session_id}"      # 例：u2:orders-1

# session_id 的字符集不允许 ':'（正则 ^[A-Za-z0-9_.\-]{1,64}$）
# 否则 session_id="1:foo" 会拼出 u2:1:foo —— 一个「看起来属于 user 1」的会话键
```

```powershell
uv run python -c @"
from app.api.deps import thread_id_for, resolve_session_id, restore_session_id
print('派生      :', thread_id_for(2, 'orders-1'))
print('还原      :', restore_session_id('u2:orders-1', user_id=2))
print('缺省生成  :', resolve_session_id(None))
for bad in ('1:foo', '', 'x' * 70):
    try:
        thread_id_for(2, bad)
        print('!! 未拦', repr(bad))
    except Exception as e:
        print(f'拒绝 {bad!r:12} -> {e}')
"@
# 实测：
# 派生      : u2:orders-1
# 还原      : orders-1
# 缺省生成  : s3f...（s + 16 位 hex）
# 拒绝 '1:foo'     -> session_id 非法：只允许字母/数字/下划线/连字符/点，长度 1~64
# 拒绝 ''          -> session_id 非法：…
# 拒绝 'xxxx…'     -> session_id 非法：…（70 字符超长）
```

**为什么必须派生**（三条收益，每条都对应一个真实风险）：

| 风险 | 派生如何消掉它 |
|---|---|
| 客户端任选 `thread_id` → 读写别人的会话状态 | 前缀 `u{user_id}:` 由**已验签的令牌**决定，客户端只能选后半段 |
| 客户端提交 `session_id="1:foo"` 造出「像别人」的键 | 字符集**不含** `:`，两道叠加（先验格式再拼） |
| 批准通道收到别人的 `thread_id` | `restore_session_id` 校验前缀，不属于当前用户 → 422 `invalid_thread` |

### 3.3 WebSocket 的令牌走**子协议**

浏览器**不能**给 WebSocket 自定义请求头，所以令牌只有三个去处：

| 去处 | 问题 | 本项目 |
|---|---|---|
| URL 查询串 `?token=...` | 会进 access log、浏览器历史、Referer | ❌ **刻意不支持**（有用例钉住这个缺口） |
| `Sec-WebSocket-Protocol` 子协议 | 唯一干净的通道 | ✅ 客户端带 `shopsage.v1, bearer.<token>` |
| cookie | 需要 CSRF 配套，且与 JWT 口径不一致 | ❌ |

```python
with client.websocket_connect(
    "/api/chat/stream",
    subprotocols=["shopsage.v1", f"bearer.{token}"],   # 两个都要：v1 是握手确认，bearer 是身份
) as ws:
    ...
```

**未鉴权 / 未带令牌时**：先 `accept` 再发一条 `error` 帧、最后用 **4401** 关闭。
为什么不是握手阶段直接拒：浏览器**读不到**握手失败的 HTTP 状态码，关闭码是它唯一能编程处理的信息。

### 3.4 `/health` 的两个刻意的决定

```powershell
uv run python -m scripts.api_demo --scenario health
# 实测输出：
# GET /health -> 200 status=ok env=dev
#   - rate_limit skipped  Nonems  限流后端 = memory（Redis 不可达时的降级：多副本下额度会被放大到「副本数 × limit」）
#   - postgres   ok       1.13ms  192.168.1.6:5432 可连接
#   - redis      ok       0.91ms  192.168.1.6:6379 可连接
# GET /metrics -> 200 text/plain; version=0.0.4; charset=utf-8
#   指标行数 = 13，前 5 行：
#     shopsage_api_request_duration_seconds_bucket{endpoint="GET /health",status_class="2xx",le="+Inf"} 1
#     ...
```

**① 恒返回 200，依赖故障写在 body 里。** `/health` 同时被存活探针与就绪探针使用，
而存活探针拿到非 2xx 会**重启进程** —— 依赖不通时进程本身完全健康，重启它只会把
「依赖故障」放大成「全站重启 + 连接风暴」。要「依赖不通就别切流量」，读 `components` 做决策。

**② 探活用 TCP，不引入数据库/Redis 客户端。** `app.db` 在 import 期就建连接池，
在探活路径上引入它 = 让「探活」变成「初始化一整套 ORM」。TCP 探活零依赖、零副作用、
耗时就是「通不通」的答案。⚠️ 它回答的是「依赖栈起来了吗」，**验收**靠
`scripts/db_check.py` / `scripts/redis_checkpointer_probe.py`。

**依赖挂了是什么样**（用例 `test_health_never_fails_even_when_dependencies_are_down` 的实测）：

```json
{"status": "down",
 "components": [{"name": "postgres", "status": "down",
                 "detail": "127.0.0.1:1 不可达（ConnectionRefusedError: …）。本机没有 Docker，依赖栈在 VMware-Linux 上 —— 先确认 .env 里的 host 是 Linux 虚拟机 IP（见 docs/runbook/2.infra-runbook.md）",
                 "latency_ms": 1.2}]}
```

`status` 的判定：**Postgres 挂了 = `down`**（业务数据一条都读不到）；
**Redis 挂了 = `degraded`**（它的用途全是优化：限流计数、未来的队列与语义缓存）。

## 4. WebSocket 流式（B2：先出骨架，再补细节）

### 4.1 帧的完整时序（实测原文）

```powershell
uv run python -m scripts.api_demo --scenario stream
# 实测输出：
#   握手子协议 = shopsage.v1
#   seq= 1 skeleton  收到，正在理解你的问题…
#   seq= 2 node      guardrail_input
#   seq= 3 node      router
#   seq= 4 skeleton  正在查询你的业务数据，结论马上给你…
#   seq= 5 node      data
#   seq= 6 node      synthesis
#   seq= 7 node      guardrail_output
#   seq= 8 answer    您最近 2 笔订单：1 笔已发货、1 笔待付款。
#   seq= 9 done      delivered
#
#   首帧实测 = 10.1ms（B2 要求 < 1000ms）
#   服务端自报 first_frame_ms = 0.13ms | latency_ms = 10.74ms
#   帧序列 = ['skeleton', 'node', 'node', 'skeleton', 'node', 'node', 'node', 'answer', 'done']
```

| `event` | 何时发 | `data` 里有什么 |
|---|---|---|
| `skeleton` | 收到一轮提问后**立刻**（`phase="accepted"`），以及 router 之后（`phase="routing"`） | `text`（给用户看的骨架话术）、`route`（第二帧才有） |
| `node` | 图每完成一个节点 | `node`、`progress`（中文进度文案）、`delta`（**白名单裁剪后**的增量） |
| `answer` | 合成出回答时 | `text`、`done`、`degraded`、`citations` |
| `done` | 一轮结束 | `flow_state`、`thread_id`、`latency_ms`、`first_frame_ms` |
| `error` | 任何失败（坏 JSON、空消息、超长、限流…） | `code`、`message` |

`seq` 从 1 单调递增（跨轮次继续递增）：前端据此发现丢帧。

> ⚠️ **服务端不会在握手后就主动推帧**：骨架帧是「收到一轮提问之后」才发的
> （accept → 限流 → 等消息 → 骨架 → 跑图）。只 accept 不发言的话，两边会一起等对方
> —— 调客户端时这是最常见的半小时（§10.1 坑 8）。

### 4.2 首帧延迟怎么来的（B2 的唯一依据）

```
t≈0ms   收到 message → 立刻发 skeleton（不含任何模型产物、不查库、不检索）
t≈?     run_turn(...) 跑图 —— 这一段是真正的耗时（模型 + SQL）
```

于是「首帧 < 1s」由**实现结构**保证，而不是靠模型快：

* 骨架话术是**固定文本**（`chat.SKELETONS`，按 route 各一句），不需要任何模型产出；
* 用例 `test_first_frame_latency_is_under_one_second` **实测**这个时间（不是只看自报值），
  并断言「自报值与实测值同量级」，防「自报值被写死成 0」这种自欺。

> ⚠️ **诚实的边界：`synthesis` 目前不是逐 token 产出的**。`generate_json` 要整体解析
> 结构化输出，所以 `answer` 帧里的 `text` 是**完整回答**（带 `"done": true` 让前端知道
> 不用等增量）。逐 token 的增量帧是第 11 步「带流式的合成」要补的活 ——
> 届时**只需在 `answer` 帧之前多发若干增量帧**，协议不用改（前端按 `event` 分支）。

### 4.3 `node` 帧的输出裁剪是**白名单**

```python
FRAME_SAFE_KEYS = ("route", "route_confidence", "answer", "citations",
                   "blocked", "guardrail_stage", "refusals", "chart_spec")
```

`stream_mode="updates"` 的增量里可能带 `rows`（原始查询结果，可能含他人数据/PII）、
`permissions`（权限点集合）、`messages`（完整对话历史）、`sql` —— **一律不出网**。

⚠️ 用「排除几个敏感键」的写法，新增状态键时会**默认泄漏**；白名单则默认安全
（新键要么被显式加进来，要么不出网）。这与 `4.security.md` 的表/列白名单是同一条纪律，
`test_node_frames_never_leak_rows_permissions_or_sql` 逐键钉住它。

## 5. 限流

### 5.1 额度表与桶键

```powershell
uv run python -c @"
from app.api import DEFAULT_RULES, SCOPE_BY_ROUTE
for scope, rule in DEFAULT_RULES.items():
    print(f'{scope:14s} {rule.limit:>3d} 次 / {int(rule.window_seconds):>3d}s（Redis 键 TTL={rule.ttl_seconds}s）')
"@
# 实测：
# chat            30 次 /  60s（Redis 键 TTL=120s）
# chat.stream     60 次 /  60s（Redis 键 TTL=120s）
# chat.approve    20 次 /  60s（Redis 键 TTL=120s）
# health         120 次 /  60s（Redis 键 TTL=120s）
# metrics        120 次 /  60s（Redis 键 TTL=120s）
```

**桶键**：`shopsage:rl:{scope}:{caller}`，其中 `caller` 是：

| 情况 | `caller` | 理由 |
|---|---|---|
| 带有效令牌 | `u:{user_id}:{role}` | 按人计；`role` 来自**已验签**的令牌（否则谁都能把自己标成 admin 去蹭别人的桶） |
| 无令牌/令牌无效 | `ip:{来源 IP}` | 匿名刷接口也要压住；**不能**共用一个 `anon` 桶（一个攻击者会把一片人限死） |
| 连 IP 都没有 | `anon` | 兜底 |

⚠️ **不信任 `X-Forwarded-For`**：客户端可随便写，用它分桶等于「每次换个假 IP 就换一个桶」。
生产在反向代理后面时，正确做法是在网关层限流（或把可信代理网段配进来）——那是第 19 步的事。

### 5.2 为什么用**滑动窗口**，以及它与「模型重试」的分工

| 层 | 拦的是什么 | 超限之后 |
|---|---|---|
| 本层（API） | **用户请求**（一个人刷接口） | 429，请求**根本不会进图** —— 零模型成本、零数据库代价 |
| `app/llm/`（第 5 步） | **模型调用**（一次请求里的某次调用 429/超时） | 指数退避重试，用户无感 |

两处都叫「限流」，但一个是「别让你进来」，一个是「进来了我重试」。混在一起的后果是：
把用户刷接口当成上游抖动去退避重试 —— 于是越刷越慢、还越刷越花钱。

**为什么是滑动窗口而不是令牌桶/固定窗口**：

* 语义一眼可解释：「最近 60 秒内你只能发 30 次」——用户、客服、评审都懂；
* 固定窗口（`INCR` + `EXPIRE`）在边界会放行 **2 倍**流量（59.9s 打满、60.1s 再打满）；
  滑动窗口不会。`test_sliding_window_does_not_allow_double_at_the_boundary` 用**可控时钟**
  把那个缺口钉住（不用真实 `sleep`，避免慢用例与 flaky）。

### 5.3 实操：429 长什么样、怎么改额度

```powershell
uv run python -m scripts.api_demo --scenario ratelimit
# 实测输出（演示脚本默认注入 3/60s 的小额度）：
#   第 1 次 -> 200 剩余=2
#   第 2 次 -> 200 剩余=1
#   第 3 次 -> 200 剩余=0
#   第 4 次 -> 429 剩余=0 Retry-After=61s code=rate_limited
#
#   结论：[200, 200, 200, 429]（前 3 次放行、第 4 次 429）
#   另一个用户（user_id=3）-> 200（自己那一份额度）
```

429 的完整响应（用例 `test_429_body_has_the_error_envelope_and_headers` 实测）：

```json

           "detail": {"limit": 3, "window_seconds": 60.0}},
 "request_id": "…"}
```

响应头：`Retry-After: 61` + `X-RateLimit-Limit/Remaining/Window`。

**改额度**（`.env`，生效即重启）：

| 键 | 默认 | 写法 |
|---|---|---|
| `RATE_LIMIT_CHAT` | `30/60` | `次数/窗口秒`（`30` = 30 次/60 秒） |
| `RATE_LIMIT_CHAT_STREAM` | `60/60` | 同上 |
| `RATE_LIMIT_CHAT_APPROVE` | `20/60` | 同上 |
| `API_PREFIX` | `/api` | 末尾斜杠会被自动去掉；非 `/` 开头直接**启动失败** |
| `API_DEBUG_PAYLOAD` | `false` | `1/true/yes/on` 时给内部角色带 `debug` |
| `API_PROBE_TIMEOUT` | `0.5` | `/health` 探活超时（秒） |
| `CHECKPOINT_BACKEND` | `memory` | `memory` / `postgres` / `redis`（生产用 `postgres`） |

```powershell
# 校验一份非法配置会被**启动即拒**（而不是静默退回默认值）
uv run python -c @"

        print(f'{value!r:8} -> {parse_rate_limit(value)}')

        print(f'{value!r:8} -> 拒绝：{e}')
"@
# 实测：
# '30/60'  -> (30, 60.0)
# '30'     -> (30, 60.0)
```

## 6. 人工审批（human-in-the-loop）

### 6.1 闸门按**角色**开关

```python
# app/graph/config.py（规则定义在图层，API 层只负责问它）
GATED_ROLES = frozenset({"customer"})          # 对客开、内部关
SENSITIVE_ROUTES = ("ticket",)                 # 需要审批的 route
```

**为什么内部角色不过闸门**：内部走的是标准作业流程（员工本来就是「被授权的人」），
每一步都停下来等批准会把「分析一下上月退款率」变成一次审批流程 —— 那是流程倒退。

⚠️ 闸门策略由 `chat.py::_runtime_with_policy` **按请求**算出来（`dataclasses.replace` 出新
`GraphRuntime`），**不就地改共享实例** —— 就地改会让「一个客户的请求」改变「另一个内部员工请求」
的行为，那是最难查的一类并发 bug。

### 6.2 挂起与拒绝是**两种状态**

| 状态 | `blocked` | `flow_state` | HTTP | 用户看到 |
|---|---|---|---|---|
| 挂起（还没人做决定） | **False** | `approval_required` | **202** | `approval.question` + `thread_id` |
| 拒绝（有人明确说不行） | **True** | `blocked` | 200 | `REJECTED_REASON` |
| 批准 | False | `delivered` | 200 | 正常回答 |

⚠️ 挂起时**不写** `blocked=True`：挂起不是拒绝。把它标成 blocked 会让
「等人工点头」与「已被拦下」在状态上无法区分，于是调用方没法决定该返回 202 还是 200。
挂起的事实由 `Turn.interrupt` 表达（它是从流的 `__interrupt__` 块里读出来的，§10.1 坑 5）。

### 6.3 实操：完整走一遍

```powershell
uv run python -m scripts.api_demo --scenario approve
# 实测输出：
#   第一次 -> 202 flow_state=approval_required
#     question = 该请求被判定为需要人工确认的敏感操作。请确认是否继续执行（批准后才会调用写路径）。
#     thread_id = u2:demo-approve | interrupt_id = e77f53353ce7…
#     resume_with = POST /api/chat/approve
#   批准后 -> flow_state=delivered answer=这项操作需要人工确认后再执行。
#   重复批准 -> 409 nothing_to_approve
#   拒绝后 -> flow_state=blocked answer=这项操作需要人工确认后再执行。
#     refusals = ['该敏感操作未获人工批准，已按未执行处理。如确需办理，请联系人工客服走标准流程。']
```

**批准通道的顺序不能换**（四步，每步防一件事）：

1. **校验 `thread_id` 属于当前用户** → 否则任何人都能批准别人的会话（422 `invalid_thread`）；
2. **确认这一轮确实在等批准**（`aget_state().next` 非空）→ 否则 LangGraph 会**从头重跑**
   整个图（用户拿到一句莫名其妙的新回答，而模型调用白花一遍）——所以是 409 而不是「照跑」；
3. **`Command(resume=...)`** 恢复：`resume` 的值就是闸门里 `interrupt()` 的返回值，
   本项目传 `{approved, reason, approver_user_id, approver_role}`（审计要这四个）；
4. **未批准时必须有一句如实的话术**（`REJECTED_REASON`），在这里补一道，
   不依赖闸门实现里那行 `refusals`。

### 6.4 本步对第 8 步的**唯一**一处改动（以及为什么必须改）

`app/graph/nodes.py::make_gate` 从「记录 refusal + 拒绝」改成**真的 `interrupt()`**。
理由：批准通道已经落地，闸门再走「一律拒绝」就是假的 human-in-the-loop。

改动带出一个真实的坑（§10.1 坑 9）：**闸门标死之后，图还会走完 synthesis 与输出护栏，
而输出护栏在通过时会写 `blocked=False`** —— 于是 `turn.blocked` 变回 False，
API 据此返回 `delivered`，用户看到「这一轮正常答完了」，而实际上敏感操作**没有执行**。

修法（`make_guardrail_output`）：

```python
already_blocked = bool(state.get("blocked"))            # 记住上游结论
outcome = await guardrail_node(state, stage=OUTPUT_STAGE, llm=runtime.llm)
if already_blocked and not outcome.get("blocked"):
    return {**outcome, "blocked": True}                 # 原样写回，并且**不进历史**
if outcome.get("blocked"):
    return outcome                                      # 输出侧自己拦下：也不进历史
return {**outcome, **_answer_message({**state, **outcome})}   # 通过：历史里存真正出网的文本
```

⚠️ 别用「blocked 为真时直接返回护栏输出」来「守住结论」——**没用**：通过时护栏返回的就是
`{"blocked": False}`，跳过的正是要守的那个值（§10.1 坑 9 有实测复现）。

## 7. 错误映射（域异常 → HTTP）

### 7.1 一张表

| 异常 | 码 | `error.code` | 为什么是这个码 |
|---|---|---|---|
| `AuthError` | 401 | `unauthorized` | 标准语义；带 `WWW-Authenticate: Bearer` |
| `PermissionDenied` | **404** | `not_found_or_forbidden` | 不告诉攻击者「资源存在」（见 §7.2） |
| `PromptInjectionError` | 400 | `prompt_rejected` | 是**用户的话**不合规，不是权限问题 |
| `SQLSecurityError` | 400 | `sql_rejected` | 模型生成的 SQL 不合规 → 这次请求做不成 |
| `AgentOutputError` | 502 | `model_output_unparsable` | **上游**（模型）坏了，不是调用方的错 |
| `ToolNotAvailableError` | 501 | `capability_not_available` | 「这个能力还没做」（rag 属第 10 步） |
| `ToolContractError` | 400 | `tool_contract` | 契约不满足 = 调用方写错了 |
| `PermanentToolError` | 500 | `tool_failure` | 库/工具永久失败（重试也没用） |
| `RetryableToolError` | 503 | `temporarily_unavailable` | 临时故障，**带 `Retry-After`** |
| `CheckpointUnavailable` | 503 | `checkpoint_unavailable` | 状态后端不可用 |
| `GraphTurnFailed` | 503 | `turn_failed` | 一轮的永久失败（重放预算用尽） |
| `MissingIdentityError` | 500 | `missing_identity` | **接线错误**：入口忘了写 `user_id`，必须显式暴露 |
| 未预期异常 | 500 | （**不走**我们的信封） | Starlette 默认 `text/plain` —— 刻意的边界（§7.3） |

⚠️ **注册顺序即优先级**：`ToolContractError` / `ToolNotAvailableError` 是
`PermanentToolError` 的子类，`RetryableToolError` 是 `ToolError` 的子类。
把父类排前面会把「契约错误」报成 500 —— 排障的人会去翻数据库日志，
而真实原因只是调用方少传了一个字段。用例 `test_contract_error_is_not_reported_as_500` 钉住它。

### 7.2 为什么越权是 **404** 而不是 403

D1 的场景是「用户 A 能不能查到用户 B 的订单」。两个层次的正确性：

1. **功能正确**：必须拦住（403 和 404 都拦住了）；
2. **信息正确**：**不该告诉 A「B 的订单存在」**。

403 的语义是「这东西存在，但你不够格看」——它确认了资源存在，攻击者据此可以枚举
「哪些订单号是真的」（用 403/404 的差异做存在性探测是经典的越权信息泄漏）。
404 的语义是「没有」——与「这个订单号根本不存在」不可区分。

代价是**排障时更难分辨**，所以处置是「**对外 404，对内留痕**」：日志里 WARNING（带 role 与
缺失权限），响应的 `detail` 里保留结构化字段（`role` / `missing`），但 `message` 统一是
`未找到该资源，或你没有访问它的权限`。

### 7.3 三条「形状」契约

```powershell
uv run pytest -q -p no:cacheprovider tests/api/test_errors_and_contracts.py
# 实测：23 passed
```

1. **所有 4xx/5xx 同一个信封**（含未知路径 404、方法不对 405）——前端只写一套解析；
2. **验证错误保留字段级原因**（`detail.fields[].loc/msg/type`）——那是调用方唯一能自救的信息；
   但**不回显整个 body**（少一分没必要的数据流转）；
3. **未预期异常不接管**：仍然走 Starlette 的 `text/plain` 500。
   把 `Exception` 也接管会得到一个「所有 500 都长得像业务错误」的 API —— 那会让真正的 bug
   消失在统一话术后面。用例用两条断言证明这件事：关掉 `raise_server_exceptions` 得到非 JSON 的 500；
   打开时原始异常**原样抛出**给调用方。

### 10.1 实现期间撞到的十个坑（实测，含修法）

**坑 1、4、8 是第一跑就崩的**；**坑 2、3、5、6 是「看起来能用但结论错了」的**；
**坑 7 是「把测试进程挂死」的**；**坑 9 是第 9 步最贵的一个**（它让安全结论反向）。

#### 坑 1：`Depends(get_current_user)` 会把令牌参数当查询参数

第 4 步就留了警告（`4.security-runbook.md` §4.4），真正接线时果然踩到：
`auth.get_current_user(authorization: str | None = None)` 的第一个参数**不是**
`Header(...)`，FastAPI 于是把它当成 query 参数 —— 「带了 Authorization 头却 401：缺少令牌」，
而 `/docs` 里那个参数的 `in` 是 `query`。

* ✅ 修法：`deps.require_principal(request)` 自己用 `request.headers.get("authorization")` 取头，
  再调 `bearer_token_from_header` + `parse_token`（**复用**第 4 步的解析，不重写）。
* 教训：**框架的依赖注入看的是签名，不是你脑子里的语义**。跨模块接线时先看一眼 `/docs`。

#### 坑 2：FastAPI 0.143 的 `include_router` 让 `app.routes` 看不到内层路径

第一版的契约用例这样收集 WebSocket 路由：

```python
for route in app.routes:
    if type(route).__name__ == "APIWebSocketRoute": ...
# 实测：一条都找不到 —— app.routes 里只有 5 个顶层 Route + 2 个 _IncludedRouter 包装对象
```

更坑的是第二版：`getattr(wrapper, "routes")` 返回的不是路由表而是**一个 str 描述**，
而 `wrapper.original_router.routes` 里的 `path` 是**内层的 `/chat/stream`（没带前缀）**。

* ✅ 修法：走 FastAPI 0.143 的 `effective_route_contexts()`（公开结构，带 `original_route`），
  内层路径 + `api_prefix()` 拼出真实路径再断言。
* 教训：**「路由挂上了吗」要用框架的公开结构去问**，别翻私有属性；翻出来的东西会骗你。

#### 坑 3：默认没有注入假模型 → 用例真的去打厂商 API

`create_app(runtime=GraphRuntime(llm=None, ...))` 里 `llm=None` 表示「走生产实现」，
于是一条断言 `answer.startswith("您最近 2 笔订单")` 的用例拿到了**真模型的回答**，
红得让人以为是流式协议坏了。它照样能过（拿到一段真回答），但每次回归都在花钱，
而且断言会随模型措辞漂移。

* ✅ 修法：`tests/api/conftest.py` 的 `app_factory` **默认**注入 `AgentFakeLLM(**DATA_REPLIES)`；
  要真模型必须显式传。
* 教训：**测试装置的默认值必须是安全的那一侧**（不花钱、不出网、不连库）。

#### 坑 4：`Settings` 的 `extra="allow"` **不保证**能读到 `API_*`

```python
os.environ["API_DEBUG_PAYLOAD"] = "1"
getattr(get_settings(), "api_debug_payload", "<missing>")   # 实测：'<missing>'
```

配置明明设置了，行为却是默认值，**而且没有任何报错**。

* ✅ 修法：`app/api/config.py::_env_value` 先读 `os.environ[<FIELD 大写>]`（进程环境变量优先级
  最高，与 `1.config.md` 的口径一致），再退回 `getattr(settings, field)`。
  pydantic-settings 会把 `.env` 的内容写进 `os.environ`，所以第 1 步就能读到它。
* 教训：**「配置读到了吗」要有办法单独验证**。`extra="allow"` 只承诺「不报错」，不承诺「读得到」。

#### 坑 5：`interrupt()` 的载荷**不在 state 里**

`aget_state().values` 里没有 `__interrupt__`（实测）；载荷只出现在流的增量块
与 `snapshot.tasks[*].interrupts` 里。于是「谁挂起了、挂起了什么」只有**驱动这一轮的人**
看得见 —— 而 `run_turn` 的第一版把 `__interrupt__` 当成一个普通节点名塞进了 `visited`。

* ✅ 修法：`run.py` 里识别 `INTERRUPT_KEY`，把载荷翻成 `Turn.interrupt`
  （`{question, interrupt_id, …}`），**不**污染 `visited`（挂起的那一步没有返回增量，
  它不是「跑完了一个节点」）。
* 教训：**「框架的状态」与「你的状态」是两回事**。要在边界处翻译，别让它漏进你的语义里。

#### 坑 6：`receive_json()` 的 `mode` 参数陷阱

```python
raw = await websocket.receive_json()          # 服务端：拿到消息后 KeyError('bytes')
ws.send_json({"message": ...})                # 客户端：TestClient 默认 mode="text"
```

Starlette 1.7 的 `receive_json(mode="text"|"binary")`：`mode="text"` 走 `message["text"]`，
`mode="binary"` 走 `message["bytes"]`。客户端发文本帧而服务端按二进制读 → `KeyError`。

* ✅ 修法：服务端**显式**写 `receive_json(mode="text")`（让「我们只收文本帧」这条约定
  出现在代码里），并把非文本帧翻成一条 `error` 帧而不是让异常穿透。
* 教训：**参数的默认值不等于参数的语义**。跨端对齐协议时，把 `mode` 这种东西写出来。

#### 坑 7：TestClient 的 WebSocket 会让「互等」变成**永久挂住**

一条用例写成了「`accept` 之后直接 `receive_json()`」（没先发消息），而服务端在等消息 ——
两边互等，`pytest` **永久挂住**：没有失败、没有输出、`-x` 也没用。
用 `| Select-Object -Last` 之类的管道时连日志都被缓冲住，看起来像「命令没反应」。

* ✅ 修法（两条一起才够）：
  1. **协议上**：测试先发消息再读帧（服务端不主动推帧，§4.1）；
  2. **装置上**：`tests/api/conftest.py` 给每条用例装了一个**看门狗**（30s 超时 →
     `faulthandler.dump_traceback(all_threads=True)` 打印所有线程栈）。
* 教训：**卡住比失败更贵**。任何「两边互等」的测试装置都该有一个超时兜底。

#### 坑 8：WS 限流用例把「一次连接」当成「已消耗额度」的证明

限流场景第一版直接用默认小额度连开三条连接，期望「前三条成功、第四条 4429」。
真实行为：额度是在**收到消息时**才计的（连接建立本身不占额度），而用例只 accept 没发言 ——
于是第一条连接就等在那儿，测试挂住（同坑 7）。

* ✅ 修法：把额度改成 `stream=1`，只开两条连接，并且**每条都先发消息**；
  断言第二条收到 `error` 帧 + 4429 关闭码。
* 教训：**用例要声明自己的前置条件**（额度=1），而不是依赖「前面几条的成功」这种顺序耦合。

#### 坑 9（本步最贵）：输出护栏把「审批拒绝」洗成了「正常答完」

修完闸门（改成真 `interrupt()`）之后，`flow_state` 仍然是 `delivered`，
只是 `refusals` 里多了一条 —— 也就是说：**用户被告知「答完了」，而敏感操作并没有执行**。

根因（`probe` 逐步打出来的调用序列）：

```
gate        -> {'blocked': True, 'refusals': [REJECTED_REASON]}
synthesis   -> {'answer': '…'}                      ← blocked 没被改，只是没提到
guardrail_output -> {'blocked': False, …}           ← 通过时**顺手**写了 False
```

第一版修法写成「`blocked` 为真时直接返回护栏输出」——**没用**：通过时护栏返回的
就是 `{"blocked": False}`，跳过的正是要守的那个值。实测输出：守卫生效了（日志有），
但出口仍是 `blocked=False`。

* ✅ 修法：**记住上游结论再原样写回**（`§6.4` 的代码），并且这一轮**不进历史**。
* 教训：**「不要覆盖某个值」不能靠「跳过某段代码」实现** —— 跳过的代码正是写那个值的代码。
  必须显式地把值写回去。这条也解释了为什么这类 bug 只会在「状态被多个节点写」的图里出现。

#### 坑 10：演示脚本自己踩了限流 —— 场景之间共享同一份额度

`--scenario all` 时，前面的场景（问答 / 流式）已经用掉了 3/60s 的额度，
于是限流场景看起来像「四次全 429」（结论仍正确，但看不到「前三次放行」的对比），
审批场景更是直接 `KeyError: 'approval'`（第 3 次请求被 429 了）。

* ✅ 修法：每个需要「干净额度」的场景在开始时 `store.reset()`（内存实现有这个方法），
  并在注释里写明为什么 —— 「场景自己要声明前置条件」（与坑 8 同一条教训）。
* 教训：**演示脚本也是代码**，它的前置条件同样要显式化；否则它会在某个执行顺序下骗人。
