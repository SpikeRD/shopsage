三条铁律：

1. **Agent 只编排，不碰数据库、不碰 `litellm`**。取数走 `app.tools`，模型调用走 `app.llm`。
   第 6 步已经把「唯一副作用出口」钉在 tools 上，第 5 步把模型出口钉在 `app.llm` 上；
   agent 是这两者之上的编排层。本步用 AST 检查把这条钉住（§12 ③）。
2. **节点返回「增量」，不返回整份 state**。`await router_node(state)` 只回 `{"route": …}` 那几个键，
   由第 8 步的图合并。这样「谁写了哪个键」在测试里可断言（§8.2）。
3. **LLM 一律可注入**（`llm=` / `search=`）。这是「独立测试」的全部代价，也是最划算的一笔：
   不注入就得 monkeypatch 内部实现，测试会随重构一起坏。

另一条：**对客身份只有一个来源，就是鉴权结果**。`user_id` 进 state、进绑定参数，
**绝不采信模型给的值**（模型可能给 `{"uid": 1}` 而当前用户是 2；形状合法、
守卫放行、行级过滤自检也通过，但查出来的是别人的数据 —— §3.5 专门处理这一条）。

### 1.0 本步的链路（六个节点 + 三处收口）

```
                    ┌─────────────────────────────────────────────┐
   第 9 步 api/ ───► │  入口写入 state：messages / user_id / role    │
                    └───────────────────┬─────────────────────────┘
                                        ▼
   ① guardrail_node(stage="input")  关键词检测（零 token）── 命中即短路（D2）
                                        │
                                        ▼
   ② router_node                    意图分类(LLM) + **权限注入(查表)** ──► route / permissions
                                        │
              ┌──────────────┬──────────┴─────────┬──────────────┐
              ▼              ▼                    ▼              ▼
   ③ data_node       ④ rag_node          ⑤ analysis_node   （ticket / final）
   NL→SQL→守卫→执行   检索+溯源            聚合解读+图表
   报错回喂重试       未就绪→refusals      仅内部角色
              └──────────────┴──────────┬─────────┴──────────────┘
                                        ▼
   ⑤ synthesis_node                 按角色三套模板合成（对客 / 内部 / 财务）
                                        │
                                        ▼
   ⑥ guardrail_node(stage="output")  确定性检查(词表+PII) + LLM 判定 ── 命中即替换话术
                                        │
                                        ▼
                                     出网
```

**每个节点「谁负责拦什么」**（这份对应关系比代码更重要）：

| 环节 | 拦得住 | 拦不住 / 需要别的环节 |
|---|---|---|
| `router` 的权限注入 | 把「角色 → 权限点」收成一处 | 权限**用没用**是各节点自己的事（`data` / `analysis` 自己查 `permissions`） |
| `data` 的守卫 + 执行 | 写语句、多语句、无 WHERE、超行数、白名单外表/列 | 「合法但查了别人的行」→ 由**行级过滤自检 + 程序覆写 `uid`** 兜住 |
| `data` 的降级 | 重试用尽后**不抛异常**，落 `refusals` | 「模型每次都生成合法但答非所问的 SQL」→ 属评测（第 16 步） |
| `rag` 的溯源 | （工具层）无 source 的命中被丢弃 | 「检索质量差」→ 属第 10 步的 rerank / chunk 策略 |
| `synthesis` 的三套模板 | 对客话术的篇幅与口吻、隐藏 SQL/审计字段 | 「模型把别人的数据说给这个客户」→ 由输出侧护栏的 LLM 判定兜住 |
| `guardrail` 输出侧 | 内部口径词、明文 PII、编造/越界（LLM 判定） | 它不是**唯一**防线：真正的硬边界仍是 SQL 守卫与只读角色（第 4 / 6 步） |

### 1.3 六个节点与 `GraphState` 的写入关系（谁写哪个键）

| 节点 | 读 | 写 |
|---|---|---|
| `guardrail_node(input)` | `messages` | `blocked` / `guardrail_stage` / `guardrail_rules` |
| `router_node` | `messages` / `user_id` / `role` | `route` / `route_confidence` / `route_reason` + **身份四件套**（`permissions` / `is_customer` / `role` / `user_id`） |
| `data_node` | `messages` / `user_id` / `role` / `permissions` | `sql` / `sql_attempts` / `rows` / `row_meta` / `refusals` |
| `rag_node` | `messages` | `docs` / `citations` / `refusals` |
| `analysis_node` | `messages` / `rows` / `permissions` | `analysis` / `chart_spec` / `refusals` |
| `synthesis_node` | `messages` / `role` / `permissions` / `rows` / `docs` / `analysis` / `refusals` | `answer` / `citations` |

## 2. Router Agent（意图分类 + 权限注入）

### 2.1 一句话职责与三条判据

输入：最后一条 **user** 消息 + 角色；输出：`route` / `route_confidence` / `route_reason` + 身份四件套。

`route` 的取值域（`state.ROUTES`，**只有这五个**）：

| route | 什么时候选它 | 谁来接着做 |
|---|---|---|
| `data` | 需要查**库里的具体业务数据**（订单、退款、库存、客户自己的记录） | `data_node` |
| `rag` | 需要查**知识库/文档/政策**（退货政策、保修条款、流程说明） | `rag_node`（第 10 步后端） |
| `analysis` | **对内**的聚合与解读（趋势、分布、对比、排行） | `analysis_node` |
| `ticket` | 要求**建工单 / 提交售后申请** | 第 6 步的 `create_ticket`（经 tools） |
| `final` | 不需要任何检索：寒暄、澄清、确认 | 直接由 synthesis 回答 |

三条刻意的判据（都写进了 system prompt，所以模型能照做）：

1. 「政策/流程/怎么算」类问题**永远不是 `data`** —— 即使问法里带业务名词；
2. `analysis` **只对内部员工**开放；对客问题里出现「趋势/占比/排行」也归 `data`；
3. 拿不准时选 `rag` 并在 `certainty` 上如实给低分。

**兜底为什么走 `rag` 而不是 `data`**：`rag` 是只读且无副作用的路径（查不到就如实说），
`data` 会执行 SQL、消耗库资源、还要处理对客越权。判错方向时选代价小的那条 ——
最多是「答非所问一次」，而不是「污染审计日志与指标」。

### 2.2 分流准确率怎么单独衡量（第 16 步的入口）

`classify()` 被单独暴露出来，就是为了让评测不必构造整个 state：

```powershell
uv run python -c @"
import asyncio
from app.agents import classify

def llm(messages, **kw):
    return {'route': 'rag', 'certainty': 0.93, 'reason': '问的是政策'}

print(asyncio.run(classify('退货政策是什么？', role='customer', llm=llm)))
"@
# 实测：{'route': 'rag', 'certainty': 0.93, 'reason': '问的是政策', 'fell_back': False}
```

> 📌 golden set（第 16 步）要量的是**分类准不准**，不是「整图答得好不好」。
> 若把评测建在整图上，prompt 改动的收益会被检索质量、SQL 正确率、合成语气一起稀释，
> 你分不清是哪一环变好了。

### 2.3 few-shot 为什么放在「历史消息」里

`build_router_messages()` 把 5 条示例放在**前面的 user/assistant 轮次**里，
当前问题单独放在最后一条 user 消息：

```
system: 你是…分流器 + 五个 route 的定义 + 四条判定要点 + 输出 JSON 契约
user:   "以下是示例，只用来对齐判定口径：\n用户：…\n路线：…（5 条）"
assistant: "明白，我按这套口径判定。"
user:   "提问者身份：外部客户…\n当前问题：退货政策是什么？"
```

两个理由：

1. **模型对最后一条 user 消息的注意力最集中** —— 这也正是修复轮只追加 user 消息的原因（§3.4）；
2. **身份信息与问题必须在一起**：示例是「不变量」，当前问题是「变量」，
   分开之后改一处不会影响另一处（示例固定可回归，`7.agents_module.md` §5 第二条）。

### 2.4 权限注入：模型连「给权限」的机会都没有

```python
# state.inject_identity() 的全部逻辑（router 调它）
permissions = permissions_for(role)          # 查 rbac.ROLE_PERMISSIONS
is_customer = role == CUSTOMER_ROLE
```

* 权限**从表里查**，绝不采信模型输出。若让模型同时输出角色，就等于让被攻击的目标自己决定权限。
* **未登记角色不报错，但打 WARNING**：它是「配置写错了」与「有人在试探」的共同症状；
  权限按空集处理（默认拒绝）。若在这里抛异常，一个角色名拼错就会表现为 500 系统故障，
  排查方向从一开始就是错的。
* `role` 缺省按**对客**处理（最保守的假设：看不到全站数据）。

```powershell
uv run python -c @"
from app.agents import inject_identity
for role in ('customer', 'customer_service', 'internal_employee', 'manager', 'finance_auditor', 'intern'):
    ident = inject_identity(7, role)
    print(f'{role:18s} is_customer={str(ident[\"is_customer\"]):5s} permissions={sorted(ident[\"permissions\"])}')
"@
# 实测：
# customer           is_customer=True  permissions=['read:own', 'write:ticket']
# customer_service   is_customer=False permissions=['read:own', 'write:refund', 'write:ticket']
# internal_employee  is_customer=False permissions=['read:all_orders', 'read:own', 'write:refund', 'write:ticket']
# manager            is_customer=False permissions=['read:all_orders', 'read:own', 'write:refund', 'write:ticket']
# finance_auditor    is_customer=False permissions=['read:all_orders', 'read:own', 'read:finance', 'write:ticket']
# intern             is_customer=False permissions=[]      ← 未登记角色：零权限（并打 WARNING）
```

### 2.5 手工试（最常用的一步）


## 3. Data Agent（NL→SQL → 校验 → 执行 → 报错重试）

### 3.1 四步链路，缺一不可

```
问题 + schema + few-shot
        │
        ▼
   ① 生成 SQL（LLM，temperature=0）
        │                         ┌── 校验失败：把**具体规则名 + 可照做的动作**回喂，
        ▼                         │    重新生成（最多 MAX_SQL_ATTEMPTS=3 次）
   ② validate_sql（第 4 步的守卫）─┤
        │  通过                    │
        ▼                         │
   ③ 行级过滤自检（对客必过）───────┘
        │  通过
        ▼
   ④ execute_readonly_query（第 6 步的工具；工具内部**再验一遍** SQL —— 纵深防御）
        ▼
      rows + meta（含 audit_id / row_count / truncated / tables / duration_ms）
```

### 3.2 schema 怎么进 prompt：**反射生成**，不手写

```powershell
uv run python -c "from app.agents.data import schema_text; print(schema_text())"
```

实测输出（本机）：

```
employees(emp_id, name, role, dept, level)
order_items(order_item_id, order_id, product_id, quantity, unit_price)
orders(order_id, user_id, status, total_amount, payment_method, created_at)

refunds(refund_id, order_id, user_id, amount, status, reason, created_at)

tickets(ticket_id, user_id, type, status, assignee_id, created_at)
users(user_id, name, level, created_at)
```

**为什么反射生成**：手写的 schema 会**悄悄过期** —— 加了一列之后模型永远不知道，
症状是「模型一直说没有这列」，而代码里明明有。反射生成让 schema 只有一处真相
（`Base.metadata`），8 张业务表与 `policy.ALLOWED_TABLES` 的对应关系由测试断言钉住。

**两处刻意的缺席（≠ 放行）**：

| 缺席的列 | 为什么 | 谁真正拦它 |
|---|---|---|
| `users.phone/email/address/id_card`、`stock_movements.operator_id` | 受保护列（`policy.PROTECTED_COLUMNS`） | `validate_sql` 的 `column_not_allowed` / `star_on_protected_table` |
| `refunds.idempotency_key`、`tickets.idempotency_key` | 写路径的内部实现细节（第 6 步的幂等键，取值是请求 id），没有业务含义却**可用于探测「某个请求是否发生过」** | 不进 prompt 是「第一英里的最小暴露」；要按幂等键排查请查审计日志 |

⚠️ 列进 prompt 只会让模型**反复尝试**、白耗重试预算；真正的拒绝在守卫里。
这就是「不列 ≠ 不拦」的意思 —— 别把 prompt 的干净误读成安全边界。

### 3.3 few-shot：4 条示例，每条示范一条守卫规则

```python
SQL_EXAMPLES = (
    ("我最近的三笔订单是什么状态？", "SELECT order_id, status, total_amount, created_at FROM orders WHERE user_id = :uid ORDER BY created_at DESC LIMIT :n"),
    ("订单 1024 什么时候下的？",    "SELECT order_id, created_at, status FROM orders WHERE user_id = :uid AND order_id = :oid"),
    ("我申请过几次退款？",          "SELECT count(*) AS refund_count FROM refunds WHERE user_id = :uid"),
    ("我买过的商品里有哪些类目？",    "SELECT DISTINCT p.category FROM order_items oi JOIN orders o ON o.order_id = oi.order_id JOIN products p ON p.product_id = oi.product_id WHERE o.user_id = :uid LIMIT :n"),
)
```

选例标准：① **都对客**（本系统最高频、也最容易被越权）；② 每条覆盖一条守卫规则
（行级过滤 / LIMIT / 参数绑定 / 聚合 / 主键等值），让「正确的形状」被反复示范。
示例里每个占位符后面还会自动补一句 `{'uid': <值>, 'n': <值>}`
（`_example_params()` 从 SQL 文本正则抽取，不维护第二份清单）——
否则模型会照抄 `:uid` 却不知道要绑值。

### 3.4 重试的砝码是「具体报错」，不是「再试一次」

这是 `7.agents_module.md` §5 第三条的落点，也是最容易被做歪的一处。
`RETRY_ACTIONS` 把守卫的**规则名**翻译成一句可照做的动作，然后回喂：

```python
RETRY_ACTIONS = {
    "missing_where": "缺少 WHERE 过滤条件：请补上**真实**的过滤（如 user_id / order_id / 时间范围），不要用 `WHERE 1=1`。",
    "trivial_where": "WHERE 是恒真条件（如 `1=1`、`'a'='a'`）：必须换成真实过滤列。",
    "missing_limit": "缺少 LIMIT：请加上 `LIMIT :n`（用绑定参数，不要写字面量）。",
    "limit_too_large": "LIMIT 的字面量超过上限：请改成绑定参数 `LIMIT :n`，由程序填值。",
    "not_read_only": "出现了写语句（INSERT/UPDATE/DELETE/DROP…）：这里只允许单条只读 SELECT。",
    …  共 13 条，**覆盖守卫的每一条规则**
}
```

为什么按规则名分支而不是把 `str(error)` 直接回喂：守卫的报文是给**运维**看的，
对模型信息密度很低 —— 一句「missing_where」不足以让它知道该怎么改。

**覆盖性由测试钉住**（`test_retry_actions_cover_every_guard_rule`）：它从 `sql_guard` 的
源码里正则抽出所有 `rule="..."`，再双向比对 `RETRY_ACTIONS`：

* 守卫有、表里没有 → 该规则会落到兜底话术（= 「笼统说再试一次」）；
* 表里有、守卫没有 → 死条目（规则改名后留下的化石，让人以为还支持）。

守卫将来新增规则时这条会红 —— 那正是提醒你回来补一行。

修复轮的 prompt 形状（**回显原文 + 一条指明问题的 user 消息**）：

```
…（system：schema + 硬约束 + few-shot）…
user:      问题：<原始问题>
assistant: {"sql": "SELECT order_id FROM orders LIMIT :n", "params": {"n": 5}}   ← 回显模型上次的原话
user:      你生成的 SQL 未通过安全校验。
           规则：missing_where
           程序报错：拒绝无 WHERE 的整表查询（防越权拖库 + 防全表扫描拖垮库）
           请针对性修改（不要原样重写）：缺少 WHERE 过滤条件：请补上**真实**的过滤…另外：对客查询**必须**带 `user_id = :uid` 绑定参数。
```

为什么回显成 **assistant 消息**而不是塞进一条 user 消息：维持正常的角色交替，
且让模型看到「这是我自己刚说的话」，比在 user 消息里引用它更不容易被它当成新指令。

### 3.5 对客身份：**程序覆写绑定值**，不采信模型

`validate_sql` 只回答「这段 SQL 长什么样」；它**不知道你是谁**。
`SELECT order_id FROM orders WHERE status = 'paid'` 完全合法，却会把别人的订单一并读出来。
所以对客路径在守卫之后还有一道**本节点自己的**检查（`customer_row_filter_error()`）：

| 判据 | 拒绝的样子 | 为什么 |
|---|---|---|
| 最外层 WHERE 里必须有 `user_id = 绑定参数` | `WHERE status = 'paid'` → 缺行级过滤 | `sql_guard` 只保证「有 WHERE 且不恒真」 |
| **必须是绑定参数**，不能是字面量 | `user_id = 1` → 拒绝 | 字面量意味着身份被写死在 SQL 文本里，模型可以写 1 而调用方是 2 |
| 必须落在**最外层** SELECT | 子查询里的 `user_id = :uid` 不算 | 外层仍可能全表扫 |

拦截后同样**回喂重写**（不直接降级）：这是可修复的问题，且回喂文本里带着
「必须用 `user_id = :uid`」这句可照做的动作。

**最关键的一步是绑定值的来源**：即使 SQL 形状完全正确，`params` 里的 `uid`
也要**由程序覆写**成鉴权结果：

```python
def _bind_customer_id(params, *, user_id, sql):
    bound = dict(params)
    if ":uid" in sql:
        bound["uid"] = user_id     # ← 模型给的 uid 一律丢弃
    return bound
```

为什么必须覆写：模型完全可能给出 `{"uid": 1}` 而当前用户是 2 ——
若照它的值绑定，守卫与行级过滤自检**都会通过**（形状对），但查出来的是别人的数据。

⚠️ 为什么这里可以用 `sqlglot` 解析（而 `db/queries.py` 坚持「过滤只有一处真相」）：
本函数**只读不生成 SQL** —— 它校验模型给的那条语句，不改写它。
唯一真相（WHERE 怎么写）仍在模型/调用方手里；一旦这里开始**改写** SQL
（比如自动补 WHERE），就会出现第二处 SQL 生成逻辑，那才是要防的。

### 3.7 行数上限：两层，且只有第二层拦得住参数化 LIMIT

| 层 | 位置 | 对手 | 行为 |
|---|---|---|---|
| ① 校验层 | `sql_guard._check_limit()` | `LIMIT 999999`（字面量） | 超 `policy.MAX_ROWS`（200）直接拒绝 |
| ② 执行层 | `sql_executor.clamp_bound_limit()` | `LIMIT :n`（运行期才定） | 夹到 `上限 + 1`，再 `fetchmany(上限 + 1)` |

`data_node` 额外把**向工具要的行数**收在 `DEFAULT_ROW_LIMIT = 50`
（`row_limit=` 只能调低，工具的绝对上限仍是 200）：
用户问「我的订单」时要的是答案不是数据导出。第一层的完整机制见
[`6.tools-runbook.md`](6.tools-runbook.md) §2.3，本步只负责**不把上限调宽**。

## 4. RAG Agent（检索接线 + 溯源）

### 4.1 为什么这个节点「薄得几乎只剩接线」

检索质量（chunk 策略、向量+关键词混合、RRF 融合、rerank）**全部属第 10 步** `rag/`。
本节点的职责只有四件：调工具、让 rerank 有地方发生、保住溯源、未就绪时不假装没有。
在 agent 层写任何检索逻辑，都会让第 10 步的调参变成「改两个地方」。

### 4.2 参数表

| 参数 | 说明 |
|---|---|
| `query` | 取自 `last_user_message(state)`（空 → 抛错，契约问题早暴露） |
| `top_k` | 默认 5，**夹到 `1..20`**（LLM 要「Top 500」不能让上下文/成本一起爆，E2） |
| `search` | 检索后端注入点；`None` = 用 `app/rag/retriever.py::hybrid_search`（第 10 步） |
| `min_score` | 相似度下限；**默认 `None`（不设阈值）** —— 阈值口径属第 10 步，写死在 agent 层等于把检索质量的调参权藏进来 |

### 4.3 `refusals` vs「0 条命中」：两种完全不同的结局

| 情况 | 本节点的处置 | 为什么 |
|---|---|---|
| `app/rag/` 不存在（第 10 步未落地）→ `ToolNotAvailableError` | 吞掉，写 `refusals`：`知识库检索暂不可用：…` | 这是「能力没接上」，用户该看到一句实话；落成空结果会被上层理解成「知识库里没有这条」 |
| 检索返回 0 条 | **不写 `refusals`**，`docs=[]` | 这是**数据事实**，由 synthesis 如实表述 |
| 命中里有条目没有 `source` | （工具层已经丢弃并打 WARNING）+ 计数进审计 `details.dropped` | 过滤只该有一处真相（`6.tools-runbook.md` §5.2） |

## 5. Synthesis Agent（按角色合成）

### 5.1 四个真实风险与各自的机制

| 风险 | 机制（不是「在 prompt 里请求它别这样」） |
|---|---|
| **编造**：上下文里没有的数据被顺着答下去 | **把材料边界写进 prompt**：查询 0 行就写「业务数据：无（本次没有查询，或查询结果为 0 行）」；检索为空就写「知识库片段：无」；有 `refusals` 就原样列成「本次**没有拿到**的材料（回答时如实说明，不许编造替代内容）」——模型编造往往不是因为它想撒谎，而是因为没人告诉它「这里没有材料」 |
| **越权叙述**：把内部口径说给客户 | 两套模板 + **材料过滤**：对客路径下 `_material_block(include_internal_details=False)` 根本不渲染 `sql` 与 `meta.audit_id` |
| **引用漂移**：复述文档名时会改写 | 模型只写**编号** `[1]`，由 `resolve_citations()` 映射回 `RetrievedDoc.citation()` |
| **对客话术过长** | 模板给出硬性数字（`CUSTOMER_MAX_CHARS = 300`），且被测试钉住 |

### 5.2 三套模板的优先级

```python
role_template(role, permissions):
    read:finance      → "finance"   金额带币种两位小数、标注口径、不写「约/大概」
    read:all_orders   → "internal"  专业简洁、可含数据表格、数字带口径
    其余              → "customer"  口语礼貌、≤300 字、不提内部术语
```

按**权限点**而不是角色名分支：`4.security.md` 已经把「能力」定义成权限点，
再写一遍角色白名单就是第二处真相。`permissions=None` 时**按角色现查**
（否则「只传角色」的调用方会把内部员工判成对客，症状是「内部功能用了对客话术」——
一种不报错、只会让人困惑的降级）。

### 5.4 引用编号为什么必须由程序映射

模型的复述会漂移（「退货政策.md」→「退货政策文档」），而编号不会。
`resolve_citations()` 只接受**越界检查通过的整数编号**：

* `[0]`、`[5]`（越界）、`"x"`、`None` → 丢弃；
* `True` → **丢弃**（`bool` 会隐式转成 1，模型偶尔把「引用了」写成布尔值，
  不排掉就会静默变成「引用了第 1 条」）。

## 6. Analysis Agent（对内聚合解读 + 可选图表）

### 6.1 与 data 的分工

`data` 回答「有哪些行」，`analysis` 回答「这些行说明什么」。
两个节点都读 `rows`，但**只有 analysis 允许对内** —— 它输出的不是一行数据而是一句判断。
权限判据用 router 注入的 `permissions`（含 `read:all_orders`），不是角色名字符串；
不足时**不抛异常也不静默返回空**，而是写 `refusals`：对客请求落到这里的正确处置是
「告诉他这件事需要内部身份」，不是 500。

### 6.2 三段式

1. **取数**：复用 `state["rows"]`（图里 data 刚查过就别重查）。没有数据 → `refusals`，
   **刻意不自己生成 SQL**（那会出现第二处 SQL 生成逻辑，而 SQL 生成只该有一处）。
2. **图表（可选）**：`build_chart_spec` 出纯函数 spec。选列规则简单可预测：
   `x` = 第一个**非数值**列，`y` = 第一个数值列；数据形状不合适就**不出图**并把原因记进 `caveats`。
3. **结论**：LLM 出 `headline` + `bullets` + `caveats`，prompt 硬要求「每条要点带数字」。

### 6.3 选列的三个「不出图」判据

| 情况 | 处置 | 为什么 |
|---|---|---|
| 行数 < `MIN_CHART_POINTS`（3） | 不出图 | 1~2 个点的图会让读者以为「只有这一项」 |
| 没有数值列（全是文本） | 不出图 | 硬凑一张图比没有图更危险 |
| 列值全是 `NULL` / 图表工具拒绝 | 不出图 + 记 `caveats` | 让「图出不来」把「结论也丢了」是过度反应 |

`bool` 刻意**不算**数值列：把 `True/False` 画成 0/1 的条形图是一条**看起来合理**的假数据。
`Decimal`（金额列，驱动原样返回）算数值列 —— 图表工具出口会转成 `float`
（只要比例关系），精确金额的比对回原始 `rows`（那里还是 `Decimal`）。

**为什么不让 LLM 挑列**：图表列名写错是本仓最常见的一类失败
（`build_chart_spec` 的报错信息里专门列了可用列）。
让确定性的代码挑、让模型只负责解读，能把这类失败从「偶发」变成「不发生」。

## 7. Guardrail Agent（输入/输出双向，横切）

### 7.1 两个阶段，两种判据

| | 输入侧（`stage="input"`） | 输出侧（`stage="output"`） |
|---|---|---|
| 判据 | 关键词/正则（第 4 步的 `security.guardrail`） | 词表 + PII 形态（确定性）→ LLM 判定（语义） |
| 成本 | 零 token，微秒级 | 一次额外 LLM 调用 |
| 位置 | 花任何钱（检索/SQL/模型）之前 | 出网之前 |
| 失败方向 | **fail-closed**（拦下） | 确定性检查 fail-closed；LLM 判定失败 **fail-open + WARNING** |

**输入侧是减速带而不是防线** —— `app/security/guardrail.py` 开篇就写明了：
它便宜、早、可回归；真正的兜底是 SQL 守卫与只读角色。
本步的职责是**把它挂在正确的位置**（router 之前）并在命中时短路。

### 7.2 输出侧：确定性检查在前，LLM 判定在后

**确定性检查（不花 token）**：

| 检查 | 对客路径 | 内部路径 | 为什么 |
|---|---|---|---|
| 内部口径词（`INTERNAL_TERMS`：列名、表名、SQL 片段、审计 id、权限点、节点名、`shopsage_readonly`） | **拦** | 只放行 | 内部同事读 `orders 表` 是正常工作需要（§5 第四条「对内可含数据表格」）；拦掉会让内部功能不可用 |
| 未脱敏 PII（手机号 / 身份证形态） | 拦 | **也拦** | 出口出现明文 PII 就是缺陷，与角色无关；`security/masking.py` 已经负责把它变成 `138****1234` |

⚠️ 两处**刻意的收窄**（都是误杀换来的）：

1. **业务词不进词表**：`订单` / `退款` / `工单` 正是对客回答必须出现的词，收进来等于把正常回答全拦掉；
2. **不收「16~19 位纯数字」（银行卡）**：主键 id 在很多系统里就是长数字，
   本仓的订单号/工单号是自增 bigint —— 收这条会把「订单 100000000000000001」判成银行卡。
   银行卡明文只可能来自用户粘贴的文本，由 `masking` 的值形态兜底在**上游**处理。

**LLM 判定（负责没有固定词表的那类问题）**：泄漏别人的数据、把「申请中」说成「已完成」、
声称执行了系统并未执行的动作、编造材料里没有的数字。
判定者看到的是**材料摘要**（行数 / 片段数 / 出处 / 有无分析结论 / 没拿到什么），
而不是原始数据 —— 审查者不需要看到客户的完整地址才能判断有没有编造，
把原始数据再喂一次等于把泄漏面扩大一倍。

**判不出来时为什么放行**：这里已经是最后一环，fail-closed 会让「模型抖一下」
变成「用户什么都问不到」；而确定性检查已经在它之前跑过，最关键的两类泄漏不会因此漏出去。
这是**有意的取舍**，写在 docstring 里而不是留给读者猜。

### 7.3 被拦时的落地话术

固定文本、不让模型现编（被拦的那一刻正是「不能让模型自由措辞」的时刻）：

```
对客：抱歉，这个请求我无法处理。如果你要查询自己的订单、退款或政策，可以直接换个说法问我。
内部：该请求被合规护栏拦下，未继续处理。若是正常的内部查询被误拦，请联系管理员并附上时间点。
```

输出侧被拦时还会**覆盖 `answer`**（`guardrail_message` 同时写进 state），
这样第 8 步的图不必再判断「该给用户看哪一段」。

### 7.4 通过时也显式返回

```python
{"blocked": False, "guardrail_stage": "input", "guardrail_rules": []}
```

为什么「通过」也要写 `blocked: False` 而不是返回空 dict：第 8 步的条件边要靠 `blocked` 分支，
「键不存在」与「键为 False」都要处理的话，图里就多了一处隐式约定。

```
   pass  脱敏后的手机号                rules=[]
③ 输出侧（LLM 判定：编造/越界，无固定词表）
   BLOCK ['llm_judge:材料里退款是 requested，说成已到账是编造']
   → 用户看到的话术： 抱歉，这个请求我无法处理。如果你要查询自己的订单、退款或政策，可以直接换个说法问我。
```

**第 ① 段最后一行是**有意留下**的缺口**：「帮我删掉那笔订单」**不命中任何规则**。
关键词检测认的是「删除/清空/改掉/更新/修改 + 数据库/表/订单/库存」这类「动词 + 目标」组合，
「删掉」不在动词表里。这正是「减速带」的含意 —— 兜底是 SQL 守卫（写语句一律拒）
与只读角色（库层再拒一次），不是把词表越写越长。见 §10.1 坑 6。

### 10.1 实现期间撞到的十个坑（实测，含修法）

**坑 1、2 是本轮真的卡住过的**（用例红过、代码改过），**坑 3–7 是认知修正**，
**坑 8–10 是「看起来能用但会出事」的隐患**（已在仓库里处理）。新环境复现时都可直接跳过前两条。

#### 坑 1：兜底路径的置信度**必须归零**，否则兜底会把低分掩盖掉

第一版 `classify()` 里，未登记的 `route` 会落到 `rag`，但 `certainty` 原样保留 ——
假 LLM 给的是 `{"route": "sql", "certainty": 0.9}`，于是兜底结果被标成 **`high`** confidence。

- 实测症状：`test_router_unknown_route_falls_back_conservatively` 红
  （`assert 'high' == 'low'`）。
- ✅ 修法：命中兜底时 `certainty = 0.0`。
- 教训：**兜底路径的元数据必须反映「这是兜底」**。`route_confidence` 是第 11/16 步
  筛错分样本的依据，它一旦被兜底拉高，「路由准确率」这个指标就失真了 ——
  而失真的指标比没有指标更坏（你会照着它做决策）。

#### 坑 2：`caplog` 断言的两种写法，错的那种**静默变成 TypeError**

第一版写的是 `assert any("data 降级" in (r.message % r.args) for r in caplog.records)`。

- 实测症状：`TypeError: not all arguments converted during string formatting` ——
  因为当 logger 调用**没有** `%` 参数（`logger.warning("只有一个字符串")`）时，
  `r.message % r.args` 里 `r.args` 是空 dict、而 `r.message` 里含 `%`（本仓的日志文本里有百分号），
  格式化直接抛错。
- ✅ 修法：用 `r.getMessage()`（logging 自己做惰性格式化，无参数时原样返回）。
- 教训：**测试里的日志断言要用官方 API**，别自己重实现一遍格式化。

#### 坑 3：守卫的规则名与「修复动作」是两张表，必须双向对齐

第一版把「规则名 → 修复动作」的映射写在函数体内、且没有覆盖性检查。
实测发现 `write_in_read`（守卫对「SELECT ... INTO / WITH ... AS (DELETE ...)」这条
读写混用语句的规则名）漏登记 —— 模型会收到兜底话术
「请按 PostgreSQL 只读查询的规范重写」，**而那正是「笼统说再试一次」的翻版**。

- ✅ 修法：映射提升为模块级 `RETRY_ACTIONS`，并加一条用例从 `sql_guard` 源码里
  正则抽出所有 `rule="..."` 做**双向**比对（守卫有表里没有 → 红；表里有没有守卫 → 红）。
- 实测：覆盖 13 条规则，与守卫规则集**完全相等**。
- 教训：**「新增规则时记得改另一处」这种约定不会自己守住** —— 要么让它在类型上不可能，
  要么让它在测试里必然变红。

#### 坑 4：输出侧词表收宽了会把**正常回答**拦掉

第一版 `INTERNAL_TERMS` 里放了 `sql`、`from orders`，还考虑过放 `表`、`订单`。
实测发现两类误杀：

1. `"sql"` 这个子串会命中 `PostgreSQL`、以及任何一句提到 SQL 的说明文字；
2. 「订单」「退款」是对客话术的正常成分（「您的订单已发货」），
   收进词表等于把正常回答全拦掉。

- ✅ 修法：词表只留**实现细节**（列名、表名、`select `、审计 id、权限点、节点名、引擎名、
  `litellm`、`prompt`），业务词一律不收。
- ✅ 同时给「有风险的形态」写了正反两条用例：
  `test_scan_internal_terms_does_not_block_business_words`（不许误杀）
  与 `test_scan_internal_terms_finds_table_and_sql_words`（必须拦得住）。
- 教训：**输出侧的词表要按「误杀」而不是「漏拦」来设计** ——
  漏拦还有下一层（LLM 判定），误杀会让用户直接问不到东西，而用户不会报告「我被误拦了」。

#### 坑 5：PII 规则里的「银行卡」会命中长数字主键

第一版照抄了 `security.masking._VALUE_PATTERNS` 的全部五条，包括 `^\d{16,19}$`（银行卡）。
在本仓，订单号/工单号是自增 `bigint` —— 一条内部回答里写「订单 100000000000000001」
就会被判成泄漏明文银行卡。

- ✅ 修法：输出侧只保留「手机号」与「身份证」两条形态；银行卡明文只可能来自用户粘贴的文本，
  由 `masking` 的值形态兜底在**上游**处理（出口这一层不必重复）。
- 教训：**同一套规则在不同位置的含义不同**。`masking` 面对的是「一行数据的某个字段」，
  出口护栏面对的是「一段自然语言」—— 后者必须容忍数字出现在句子里。

#### 坑 6：输入侧关键词是**减速带**，它的缺口要写进手册

实测：「帮我删掉那笔订单」**不命中任何规则**（`write_intent` 认的是
「删除/清空/改掉/更新/修改 + 数据库/表/订单/库存」，「删掉」不在动词表里）。

- 处置：**不修**。把这条写进用例（断言它 `blocked is False`）并注明
  「若这条也拦住了，说明第 4 步的规则表加宽了，请更新注释」。
- 理由：`security/guardrail.py` 开篇就写明它是减速带；真正的兜底是
  `validate_sql`（写语句一律拒）与只读角色（库层再拒一次）。把词表越写越长，
  换来的是误杀率上升和「以为挡住了」的错觉。
- 教训：**知道一个机制的边界，和实现它同样重要** —— 边界要写进手册和测试，
  而不是留在某个人的记忆里。

#### 坑 7：源码检查必须走 AST，纯文本匹配会把**文档**当成违规

本轮加「agent 不许绕过 `app.llm` 门面」的源码检查时，第一版写的是：

```python
if "litellm" in source or "openai." in source: offenders.append(path.name)
```

- 实测症状：`['agent_llm.py', 'guardrail.py', '__init__.py']` 三个文件全被判违规 ——
  而它们**恰恰是写明了「不要绕过 litellm 门面」的那几个文件**。
  同理，`assert "import langgraph" not in source` 会把文档字符串里
  「本包**不 import langgraph**」这句话当成证据。
- ✅ 修法：用 `ast.parse()` 只收集真正的 `Import` / `ImportFrom` 节点，注释与文档字符串天然不参与。
- 教训：**「检查代码里有没有 X」要检查的是语法结构，不是字节序列**。

#### 坑 8：`max_attempts=0` 必须是「零次机会」，不能是死循环或无限重试

第一版的重试循环写作 `for attempt in range(1, max_attempts + 1)`，
`max_attempts=0` 时循环体一次都不进、`reason` 为空串 —— 返回一个**没有原因的降级结果**，
排查时看到的是「查不到，但不知道为什么不查」。

- ✅ 修法：入口先判 `max_attempts < 1` 直接返回
  `DataPlan(ok=False, attempts=0, reason="重试预算为 0，未生成 SQL")`，
  并且**一次 LLM 都不调**（有用例断言 `llm.call_count == 0`）。
- 教训：**边界参数要显式返回「有原因的结果」**，而不是让循环自然落空。

#### 坑 9：`Decimal` / `datetime` 塞进 prompt 时**不能**走 `json.dumps`

`execute_readonly_query` 返回的是驱动原样值（金额是 `Decimal('2745.98')`）。
把它们 `json.dumps` 进 prompt 会直接 `TypeError`
（与 [`6.tools-runbook.md`](6.tools-runbook.md) §9.1 坑 6 同一个坑）。

- ✅ 修法：`format_rows()` 用 `str()` 渲染成紧凑的表格文本（模型只需要看懂值，
  不需要机器可解析的 JSON），并对 `Decimal`/`datetime` 各写一条用例。
- 教训：**JSON 化的责任在「出口」**；agent 到模型这一段是文本通道，不是 JSON 通道。

#### 坑 10：`analysis` 的权限判断不能只信 `state["permissions"]` 存在

第一版 `_has_internal_scope()` 只查 `state["permissions"]`。
但 `permissions_of()` 对「没写 `permissions` 的 state」是**按角色现查**的 ——
两者口径不一致时，会出现「单测里构造的 state 被拒、图里跑通的 state 通过」这种诡异差异。

- ✅ 修法：`_has_internal_scope()` 先查 `permissions`，取不到再按 `state["role"]` 查表
  （与 `permissions_of()` 同口径），两条路都收敛到「有没有 `read:all_orders`」。
- 教训：**「同一个判断在两处实现」迟早会漂移** —— 要么复用同一个函数，
  要么至少让口径显式写在一起（这里的做法是后者 + 注释说明为什么）。
