三条铁律：

1. **指标只在 `/metrics` 出、trace 只在 OTEL 出、LLM 账目只在 Langfuse 出 —— 不串味。**
   「QPS 也塞进 Langfuse」的症状是账单里混进一堆与模型无关的记录；
   「prompt 塞进指标标签」的症状是基数爆炸 + PII 出网。
   串味在代码上的表现是**同一个量有两个出口**，而两个出口必然漂移
   （漂移的看板比没有看板更危险：它会让人**以为**看见了）。

2. **埋点是旁路，永不改变控制流。** 本步所有写入路径都不抛异常，且 `tracing.span()`
   在异常时**原样重抛**。这条不是洁癖：第 8 步的断点重放依赖「节点异常穿透到回合驱动」
   （`app/graph/nodes.py::safe_node` 的 docstring 解释了为什么它刻意不 `try/except`）——
   一个会吞异常的埋点会让**重放静默失效**（症状是「用户看到兜底话术，但状态里没有断点」）。

3. **一个量只有一个写入方。** 两个名字可以并存（第 9 步的 `shopsage_api_*` 与第 11 步的
   `shopsage_*`），但每个名字只能由**一处**代码写。三个调用点各写一种计时口径，
   `TOOL_DURATION` 这个指标就**内部不可比**了 —— 而它看起来完全正常。

另一条（最容易被当成形式主义，实际最值钱）：**根 span 必须包住整个请求**。
本步第一版在请求结束后「补一条」根 span，它看起来完全合理（访问日志也在那里写）——
但那样每个节点 span 各自成了根，**每个节点一个 trace**，
「按 trace 查一次请求」这条排障路径彻底失效，而每个节点看起来都埋了点（§11.1 坑 4）。

## 1. 环境与前提

### 1.0 本步的链路（三条独立的出口）

```
                            ┌── 第 11 步 observability/ ──────────────────────────────┐
   一次请求                  │                                                          │
        │                    │  ① trace_span(...)  ──→  OTEL span（父子树）             │
        ▼                    │        │                                                 │
  ApiMiddleware ─────────────┤        └── 内存 exporter（环形 1000 条，§4.1）           │
   (根 span 包住整个请求)      │             └── 可选：OTLP/HTTP → Collector → jsonl     │
        │                    │                                                          │
        ├─ 图节点 ×8 ─────────┤  ② metrics.counter/observe ──→ prometheus_client        │
        │  (safe_node 一处)   │        └── MetricsRegistry → GET /metrics（文本 0.0.4）  │
        │                    │                                                          │
        ├─ llm_call ─────────┤  ③ langfuse_handler().record ──→ Langfuse generation     │
        │  (第 5 步门面)      │        └── token / cost / score（**没配密钥就关闭**）     │
        │                    │                                                          │
        ├─ execute_readonly_query ──┐                                                    │
        └─ retrieve_docs ───────────┘  都走 ①+②                                          │
                            └──────────────────────────────────────────────────────────┘
```

**每条出口「拦得住什么 / 拦不住什么」**：

| 出口 | 拦得住 | 拦不住 / 需要别的出口 |
|---|---|---|
| OTEL span | 「这一次为什么慢」——每一步的耗时与父子关系 | 长期趋势（span 是单次的；聚合是 Prometheus 的活） |
| 内存 exporter | 开发机上「没有 collector 也能看链路」 | 进程重启即丢（本机排障够用，长期存储要 OTLP） |
| Prometheus 指标 | 「一直很慢 / 越来越慢」——分位数、告警 | 单次请求（指标是聚合值，看不到那一次的细节） |
| Langfuse | 「花多少钱、质量如何」+ 与 trace 对账 | 系统级 QPS/延迟（那是 Prometheus 的活） |
| 属性白名单 | PII 出网（prompt / SQL 全文 / 用户 id） | 值本身的安全性（白名单里的字符串也会被截断到 200 字符） |
| `status_class` 折叠 | 基数爆炸（原始状态码 → 5 条序列） | 具体是 404 还是 429（要看日志，或按 endpoint 单独下钻） |

> ⚠️ **与 `11.observability.md` 的四处差异（有意为之，别当成写错了）**：
>
> 1. **`langfuse_handler` 不是 LangChain 的 `CallbackHandler`**（名字是契约，形态不是）。
>    Langfuse 4.x 把 LangChain 集成搬到了 `langfuse.langchain`，而它**只在装了顶层
>    `langchain` 包时才可导入** —— 本仓只装了 `langchain-core`（六个 Agent 是手写函数、
>    没有 `Runnable`），在模块顶层 import 它会让 `import app.observability` **直接失败**。
>    本仓一个 `Runnable` 都没有，`CallbackHandler` 那套本来也用不上（§7.1）。
> 2. **多了 `RETRIEVAL_DURATION` / `TOOL_OUTCOME` / `SPAN_ERRORS`**（文档没点名）。
>    理由是第 10 步交接的检索层与写路径工具同样需要被看见；文档点名的
>    `REQUEST_COUNT` / `AGENT_DURATION` / `SQL_DURATION` / `LLM_DURATION` / `LLM_TOKENS` / `LLM_COST` 一个都没少。
> 3. **OTLP 用 HTTP 而不是 gRPC**（`opentelemetry-exporter-otlp-proto-http`，
>    端口 **4318**）。只依赖 `httpx`，不需要 `grpcio`（少一个 ~50MB 的原生依赖）。
>    代价是**端点必须写全路径且端口不能写 4317** —— 配错的后果不是报错，而是
>    「trace 一条都不到」，所以 `tracing.normalize_otlp_endpoint` 把它变成启动期 WARNING（§11.1 坑 9）。
> 4. **`safe_node` 一处埋点覆盖 8 个节点**，而不是六个 Agent 各埋一次。
>    `safe_node` 是七个（`gate` 是第八个）节点唯一的共同入口，于是
>    「新增节点忘了埋点」这件事**不可能发生**，而六个 Agent 模块继续保持
>    「不知道可观测性存在」（「第 7 步的节点可独立测试」这条验收不受影响）。

### 1.4 配置面（5 个新配置项，全部「不配 = 不打扰业务」）

```powershell
uv run python -m scripts.observability_demo --scenario config
```

| 配置 | 默认 | 作用 | 配错的后果 |
|---|---|---|---|
| `OTEL_ENDPOINT` | **空** | 空 = span **只留进程内存**；填了才 OTLP/HTTP 外发 | 填成 4317（gRPC 端口）→ trace 一条都不到（有启动 WARNING） |
| `OBSERVABILITY_ENABLED` | `true` | `false` = 所有埋点退化成 no-op | 关掉后 `/metrics` 里的节点指标也没了（**有意的**，压测对照要看这个） |
| `SERVICE_NAME` | `shopsage-api` | 进 OTEL resource 与日志 | 多服务共用一个 collector 时区分不开 |
| `LANGFUSE_PUBLIC_KEY` / `_SECRET_KEY` | 空 | **两个都填才启用**；否则完全不构造 client | 只填一个 → 仍然关闭（不会半开） |
| `LANGFUSE_ENABLED` | `true` | 密钥配好了也能整体关掉上报 | — |

> ⚠️ `OTEL_ENDPOINT` 默认**留空**有一个很实际的理由：填了而 collector 没起时，
> 业务侧的 `BatchSpanProcessor` 会不断重试导出（只打日志、不阻塞请求，但日志会变吵），
> 而且每个 app 关闭时 `force_flush()` 都会等一个超时。开发机上「不留空」会让人以为服务变慢了。

## 3. `app/observability/metrics.py`：指标

### 3.1 为什么四个依赖都进**主**依赖（而不是 dev 组）

第 10 步为 `pypdf` 定过一个口径：**能被测试到的依赖才配当默认依赖**，而 PDF 分支是可选能力，
所以它进了 dev 组。本步的结论相反，逐条理由：

| 依赖 | 为什么是主依赖 |
|---|---|
| `opentelemetry-sdk` | **没有它就没有 span**。内存 exporter 也被它带着 —— 而「开发机上没 collector 时看链路」不是测试专属能力 |
| `opentelemetry-exporter-otlp-proto-http` | 外发能力；「配了端点才启用」由代码判断，不由依赖是否存在判断 |
| `prometheus-client` | `/metrics` 的文本格式**必须**与抓取端严格一致（手写文本最容易在「直方图 `_bucket` 的累计性」上出错，而那一错不报错、只让分位数变成无意义的数字） |
| `langfuse` | 文档 §2 的对外接口之一；**但它内部做了「没配密钥就完全不构造 client」**，所以不配密钥时它零开销（§7.1） |

造一个**独立的**指标实例（测试、演示、多租户隔离都用它）：

```powershell
uv run python -c @"
from app.observability import metrics as M
mm = M.new_metrics()
mm.counter(M.REQUEST_COUNT, {'endpoint': 'POST /api/chat', 'status_class': '2xx'})
for i in range(1, 101):
    mm.observe(M.AGENT_DURATION, i / 1000.0, {'node': 'router'})
k = 'shopsage_agent_duration_seconds{node=\"router\"}'
print('P50:', mm.histogram_quantile(k, 0.5))
print('P99:', mm.histogram_quantile(k, 0.99))
print('桶 :', M.buckets_of(mm, k))
"@
# 实测：P50: 0.05   P99: 0.09666666666666668
#       桶 : (0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0)
```

> ⚠️ **每个 `Metrics` 实例有自己的 `CollectorRegistry`**，全局 `REGISTRY` 一律不用。
> `prometheus_client` 默认往进程全局注册表注册，而 `register()` 遇到同名 collector 会抛
> `ValueError: Duplicated timeseries` —— 那会让「第二条用例」直接红，且报错指向注册表而不是被测代码
> （最难查的一类噪音）。第 9 步的 `MetricsRegistry` 就是为同一件事刻意不注册全局 `REGISTRY` 的。

### 3.2 桶边界：为什么两套而不是一套

`11.observability.md` §4 第 3 条说「用 histogram 而非平均值」。这句话只对了一半 ——
**桶的边界必须落在你会去问的那些量级上**：

* 一个节点耗时 30ms 与 60ms 的区别是有意义的（本地 SQL vs 本地检索），
  但用「0.1 / 0.5 / 1 / 5」的粗桶去量它们，两者落进同一个桶，分位数被**钉死在桶边界**上；
* 一次 LLM 调用 800ms 与 3s 的区别同样有意义，但用「0.01」起步的细桶去量，
  前 5 个桶永远是 0，白占序列（每条序列都要存 15 天）。

所以：**快路径**（节点/工具/SQL/检索）10ms~10s，**慢路径**（LLM）100ms~60s。
选桶按**系列名**判断（`_is_llm_series`），一处实现。

> ⚠️ 这条约束在**离线测试**里有个直接后果：被观测的系统耗时是微秒级（假模型、内存 saver），
> 沿用生产桶会让所有观测值落进第一个桶，于是「能算出 P99」这条用例变成
> 「在第一个桶上恒真」的空话（它会在任何实现下都通过，包括把 P99 算成 0 的错误实现）。
> 所以 `tests/observability/conftest.py` 的 `obs_metrics` 装置注入了**细桶**（最小 0.0001s）。

### 3.3 分位数只能**从桶里算**，不能在应用层算

`histogram_quantile()` 是 Prometheus 的设计意图，本模块给了等价的离线实现
（`Metrics.histogram_quantile`），给演示脚本与用例用。三条口径：

* **直方图的 `_bucket` 必须是累计值**（`le` 单调不减）。写反了不报错，只让分位数变成无意义的数字；
* **不同标签的观测必须互不污染**（`{node="fast"}` 与 `{node="slow"}` 各自的 P99）；
* **查不到的系列返回 `None` 而不是 0** —— 返回 0 会被当成「这一条一点都不慢」，
  于是「指标名写错」在图上表现为**完美的性能**（本仓最讨厌的一类静默错误）。

```powershell
uv run python -m scripts.observability_demo --scenario p99
```

### 3.4 基数的三道闸

`main.py` 第 9 步的注释里已经解释过「为什么状态码要折叠成 `2xx` / `4xx` / `5xx`」。
本步又加了两道：

| 闸 | 位置 | 防的是 |
|---|---|---|
| 名字写错 → **自动补 `_seconds`** | `Metrics._histogram_name` | 「同一个量被写成两条序列」（`prometheus_client` 内部也会补，但那让「用例查的名字」与「渲染的名字」可能不一致） |

## 4. `app/observability/tracing.py`：链路

### 4.1 `Telemetry` 为什么把三样东西绑在一起

`provider`（OTEL 的 `TracerProvider`）、`metrics`（注册表）、`exporter`（内存 span 记录器）
是**同一次配置的产物**。若分别做成模块级单例，「测试里换成内存 exporter」就要求同时改三处，
而漏改一处（比如忘了换 provider）的症状是「span 记录了，但记进了生产的那一份」—— 极难发现。

**两条关于全局状态的决定**：

1. **不给 OTEL 设全局 `TracerProvider`**。`set_tracer_provider()` 只生效一次
   （第二次静默失败），一旦用了，「测试里换一个 provider」就不可能 —— 本仓已经为同一类问题付过代价
   （第 9 步的 `MetricsRegistry` 刻意不注册全局 `REGISTRY`）。所以本模块**始终显式持有自己的 provider**。
2. **进程默认 + 请求根（`ContextVar`）**。`telemetry()` 先看请求根、再看进程默认。
   请求根由 `app/api/main.py` 的 lifespan 设一次，于是「这个 app 的 `/metrics`」与
   「这个 app 的埋点」**必然是同一份数据**（§11.1 坑 5 是本步实测到的反例）。

### 4.2 三种埋点方式 + span 命名规约

| 方式 | 用法 | 适合 |
|---|---|---|
| 装饰器 | `@trace_node("router")` / `@trace_tool("sql_query")` | 一个函数就是一步 |
| 上下文管理器 | `with trace_llm(model) as span:` | 一段代码、中途要补属性（LLM/检索/SQL） |
| 纯记录函数 | `telemetry().record_span(...)` | 只有「事后拿到的数字」 |

**装饰器同时吃同步与异步**（`inspect.iscoroutinefunction` 分派），且**保留 `__name__` 与
`__node_name__`** —— 后者不是形式主义：`app/graph/nodes.py::safe_node` 靠 `__node_name__`
决定「这个节点失败后是继续还是要中止」，装饰器把名字丢掉会让兜底策略**认错节点**。

**span 名前缀是一套分类**（`node.` / `tool.` / `sql.` / `llm.` / `retrieval.` / `http.`），
它决定了耗时进哪条指标（`_duration_series` 是唯一的映射处）：

```
node.router           → AGENT_DURATION{node="router"}
tool.create_ticket    → TOOL_DURATION{tool="create_ticket"}
sql.sql_query         → SQL_DURATION{tool="sql_query"}      ← 与 TOOL 分开（见下）
llm.call              → LLM_DURATION（无标签；模型在 LLM_TOKENS 上）
retrieval.search      → RETRIEVAL_DURATION
http.POST /api/chat   → （不记耗时指标；HTTP 的耗时由 shopsage_api_* 记）
```

> ⚠️ **SQL 为什么不用 `tool.` 前缀**：文档 §2 把 `SQL_DURATION` 与 `TOOL_DURATION` 列成了
> **两个**指标，而它们的处置完全不同 —— 「数据库慢」要加索引/改 SQL，「工具代码慢」要改代码。
> 混进一条序列的话，再精确的 P99 也回答不了「慢在哪」（而那正是这一层要回答的唯一问题）。

### 4.3 内存 exporter：为什么自己写、为什么有上限

`InMemorySpanExporter` 在**额外的包**里（`opentelemetry-sdk-test-utils`），而这里的情况与
`pypdf` 相反：「抓取 span 并断言」**不是测试专属能力** —— 开发机上没起 collector 时，
它是唯一能看见链路的方式（正是 `2.infra.md`「基础设施只起依赖、代码跑本机」这条拓扑带来的必然需求）。
所以本模块自带一个 30 行的 exporter（复用自己的 `SpanExporter` + `SpanProcessor` 基类，不装新包）。

两个刻意的实现选择：

* `export()` **永不抛**：OTEL 的 exporter 异常会被 provider 吞掉并打日志，
  但那会让「一条 span 的字段格式怪」升级成「不知道哪里在报错」；
* 记录是 **`MemorySpan`（纯数据）而不是 `ReadableSpan`**：后者身上挂着 `resource` /
  `instrumentation_scope` / 原始 context 对象（其中 `Context` 持有「当前活跃的 span」，
  **强引用整棵 trace**）。直接存它等于把已结束的 trace 钉在内存里 —— 这正是内存 exporter 泄漏的经典形态。

上限 `DEFAULT_MAX_RECORDS = 1000`，按时间淘汰最老的（不是清空：清空会让「刚跑完的请求反而没有记录」）。

### 4.4 属性白名单：`ALLOWED_ATTRIBUTES`

span 属性会进 trace UI、进日志、进外部 Langfuse。用黑名单（「排除 `sql` / `params` / `prompt`」）的话，
新增一个带 PII 的属性时**默认出网**。所以这里用**白名单**，且规则是：

* 键在白名单里 **且** 值是数字/布尔 → 保留（耗时、token、行数这类量不可能含 PII）；
* 键在白名单里但是字符串 → 保留并**截断到 200 字符**（防「合法键塞进一篇文章」）；
* 其余一律丢弃。

```powershell
uv run python -c @"
from app.observability.tracing import sanitize_attributes
print(sanitize_attributes({
    'node': 'router', 'rows': 12, 'stage': 'routing',
    'prompt': '用户的完整问题（含手机号）', 'sql': 'SELECT * FROM orders',
}))
"@
# 实测：{'node': 'router', 'rows': 12, 'stage': 'routing'}
```

### 4.5 span 的顺序：一个只有测试能发现的坑

`MemorySpanExporter.by_trace()` 按开始时间排序 —— 必须排，因为 exporter 的调用顺序
受 processor 与多线程影响，**不保证**等于时间顺序（不排的话火焰图会时对时错，比没有更误导）。

但**只按 `start_ns` 排是不够的**：OTEL 的 `start_time` 只有**微秒**精度，
而 `TracerProvider` 会把它向下取整到自己的时钟粒度 —— 于是「父 span + 它的第一个子 span」
经常得到**完全相同**的 `start_ns`（实测：`http.POST /api/chat` 与它的第一个子节点一模一样）。
这时只按 `start_ns` 排的结果由 exporter 的送出顺序决定，而**子先结束、先被送出**，
于是列表变成 `[子, 父]`：**火焰图里根节点跑到最下面，父子层级看起来是反的**。
现在第二排序键是「父 span 排在自己的子之前」（§11.1 坑 2）。

真 `create_app` + 假模型 + 内存 checkpointer，然后断言 span 与指标真的出现了 ——
因为「写了装饰器」不能证明「埋点生效了」，而那正是本步的验收标准。

### 5.3 `safe_node`：一处埋点覆盖八个节点

```python
# app/graph/nodes.py（第 11 步加了 with 那两行，其余不变）
async def node(state, config):
    del config
    with trace_span(f"node.{node_name}", kind="node", attributes={"node": node_name}) as handle:
        handle.set_attributes({"stage": str(state.get("route") or "")})
        return await fn(normalize_input(state))
```

三个理由：

1. **结构性成立**：`node_specs()` 把八个节点全交给 `safe_node` 包装，
   所以「新增节点忘了埋点」**不可能发生**（没有别的入口）；
2. **节点保持独立可测**：六个 Agent 模块的注入点里**没有** `telemetry=` 这种参数
   （第 7 步「节点可独立测试」这条验收不受影响）；
3. **异常仍然穿透**：`trace_span` 的 `with` 不吞异常，所以第 8 步的断点重放不受影响。

> ⚠️ **LLM 的 span 落在 `llm_call` 内部（`_call` 闭包）而不是外面**：`_call` 是被 tenacity
> 反复调用的那个闭包，所以**重试的每一次尝试各自一个 span**。
> 若把 span 开在 `llm_call` 外层，重试会被折叠成一条 —— 而「这次请求到底打了几次模型」
> 正是成本与延迟归因的关键（看不到重试次数，就看不出「退避把 P99 推高了」）。
> 用例：`test_llm_retry_produces_one_span_per_attempt`（断言恰好 2 条 + 第一条是 error）。

### 5.4 `_ToolCall`：为什么调用点**不能**自己传耗时

第一版让调用方传 `seconds=`，结果是三个调用点写了三种口径（有的含校验、有的不含），
于是 `TOOL_DURATION` 这个指标**内部不可比**。现在耗时由 `_ToolCall` 自己量，
口径只有一处：**`with` 块内的一切**。三个实际用法：

```python
# app/tools/ticket.py（写路径：唯一副作用出口）
with record_tool_call(tool=CREATE_TOOL) as call:
    with audit_tool_call(...) as handle:
        ...                                        # 权限闸 + 幂等插入
        call.outcome("idempotent_hit" if not created else "created", rows=1)

# app/tools/sql_executor.py（只埋**执行那一段**）
with record_sql_query(tool=TOOL_NAME) as call:
    try:
        with get_read_engine().connect() as conn: ...
    except SQLAlchemyError as exc:
        raise translate_db_error(...) from exc     # 异常穿透 → span 自动标 ERROR
    call.set_attributes({"rows": len(rows)})
    call.outcome("truncated" if truncated else "rows")

# app/tools/retriever.py（埋**整个调用**，含溯源过滤）
with record_retrieval(hits=0) as call:
    with audit_tool_call(...) as handle:
        ...
        call.outcome("degraded" if dropped_reasons else "hits", rows=len(docs))
```

**`outcome` 的取值必须是有限集合**（`created` / `idempotent_hit` / `truncated` / `rows` /
`hits` / `degraded`）—— 它是标签，而标签的每个新取值都是一条新的时间序列。
把自由文本（例如错误消息）当 outcome 就是基数爆炸。

**「幂等命中率」为什么值得单独一条指标**：一直命中说明上游在重复投递 ——
那是**故障信号**（A2 的幂等保护在工作），不该混进 `created` 被平均掉。
它是长期趋势问题，单条 trace 回答不了。

### 5.5 关闭埋点时**不能**把指标也关掉

`OBSERVABILITY_ENABLED=false` 时 span 退化成 no-op，于是「耗时」就没人量了 ——
而「临时关掉埋点排查性能」恰恰是想看性能的时候。所以 `_ToolCall.__exit__` 在
`telemetry().enabled` 为假时用自己量的耗时补一条观测
（用例：`test_disabled_telemetry_still_backfills_tool_duration`）。

#### 6.2.1 为什么这里**不能**用环境变量（两个都试过，都失败）

`prometheus.yml` 的 target 里写 `${SHOPSAGE_API_TARGET}` 或 `${SHOPSAGE_API_TARGET:-172.17.0.1:8000}`
**都不行**，而且**不报配置错**（`config -q` 通过、`promtool check config` 通过、日志干净）：

| 写法 | Prometheus 实际行为 | `lastError` |
|---|---|---|
| `${VAR:-1.2.3.4:8000}` | 整个字面量当主机名（`:-` 是 shell/compose 语法，2.x 不解析） | `invalid port ":8000%7D"` |
| `${VAR}` | 展开成**空主机名** → `http:///metrics` | `invalid URL escape "%7B"` |

根因是版本事实：**Prometheus 2.x 不替换 `static_configs` 里的环境变量** —— 配置文件的
环境变量展开在 2.x 只作用于 `external_labels`（靠 `expand-external-labels` 特性开关），
Prometheus 3.0 移除该 flag 后才成为默认行为
（[2.55 feature flags](https://prometheus.io/docs/prometheus/2.55/feature_flags/)、
[3.0 迁移指南](https://prometheus.io/docs/prometheus/3.9/migration/)）。
`%7B`/`%7D`（`{`/`}` 的 URL 编码）就是「没替换成功」的指纹。

同理 **`host.docker.internal` 在这套拓扑下也不可用**：compose 里配的
`extra_hosts: host.docker.internal:host-gateway` 只对 **Docker Desktop** 才等于「Windows 主机」；
原生 Docker Engine 会把它解析成 **Linux VM 自己**的网关（实测 `172.18.0.1`），
指向的仍是那台 Linux，不是 Windows。

> ➡️ **结论：这一版把地址写死。** 需要多环境复用就在部署期生成/替换这个文件，
> 或升级到 Prometheus 3.x。`scripts/check_infra.py` 现在会把 target 里任何
> `${...}`/`$VAR` 直接判为错误，避免这个坑再次静默复发。

## 7. Langfuse：LLM 的 token / 成本 / 质量

### 7.1 为什么不是 LangChain 的 `CallbackHandler`（版本事实）

`11.observability.md` §2 写的是 `from app.observability.langfuse_cb import langfuse_handler`。
**名称保留**（它是契约），但接口形态不同，原因是一个必须写清楚的版本事实：

> Langfuse 4.x 把 LangChain 集成搬到了 `langfuse.langchain`（旧的 `langfuse.callback` 已不存在），
> 而它**只在装了顶层 `langchain` 包时才可导入** —— 本仓只装了 `langchain-core`
> （六个 Agent 是手写函数，没有 `Runnable`），在模块顶层 import 它会让
> `import app.observability` **直接失败**。
> 而且 `CallbackHandler` 要挂在 `Runnable.invoke(callbacks=[...])` 上，本项目一个 `Runnable` 都没有。

于是落成一个**与调用点无关的门面**：

```python
handler = langfuse_handler()                        # 没配密钥 = 关闭，零开销
with handler.record(model="deepseek-chat") as rec:
    rec.tokens(prompt=1200, completion=380, total=1580)
    rec.cost(0.00042)
    rec.quality(name="answer_relevance", value=0.86)   # 配合 14.eval.md
```

### 7.2 离线看一次调用记了什么（**用假 client，零网络**）

```powershell
uv run python -m scripts.observability_demo --scenario langfuse
# 实测：
#   model           : deepseek-chat
#   tokens          : prompt=1200 completion=380 total=1580
#   cost_usd        : 0.00042
#   质量分（score）  : {"answer_relevance": 0.86, "faithfulness": 0.91}
#   observation id  : obs-demo-1
#   trace_context   : {'trace_id': 'd68e8a643fe2b5d212b95d58ec7ff233'}
#   上报类型        : generation（generation 才会进成本/延迟聚合）
#   usage_details   : {'input': 1200, 'output': 380, 'total': 1580}
#   未配置密钥时：enabled=False 原因='缺 public_key 或 secret_key'
#                 账目仍留在进程内：findings=1，开销 0.016ms（零网络）
```

### 7.3 四个必须成立的性质（每条都是实测踩出来的）

**① 没配密钥就完全关闭，连 client 都不构造。**
这条边界很窄但很重要：Langfuse 的构造函数用 `is None` 判断密钥，所以
`LANGFUSE_PUBLIC_KEY=""`（**空串，走环境变量**）会**绕过**那个判断，建出一个真的会连网重试的
client —— 实测构造花 **1.86s**、起 **4 个后台线程**、`flush()` 阻塞数秒。
而本仓 `.env` 里这两个键**就是空串**。所以 `from_settings` 自己看密钥、不全就返回空实现
（实测：关闭状态下 `record` + `flush` + `shutdown` + `score` 的总开销 **0.016ms**）。

**② 永不阻塞请求路径。** 实测（离线、端点不可达）：`flush()` 最短 **2.0s**、最长 **23.6s**；
**记过 score 之后 6~13s**（score 走 SDK 内部**另一条不受 `timeout` 约束的无上限队列**）。
而且 **SDK 注册了 `atexit` 钩子** —— 不主动 flush 也躲不掉（进程退出时照样付这个代价）。
所以：`record()` 只登记，网络导出交给后台线程；`timeout` 显式设成 **2s**（默认 5s 更久）；
并且给了 `LANGFUSE_ENABLED=false` 这个出口（见 §1.4 与该配置项的注释）。

**③ 永不抛异常。** LLM 记录失败不能影响这次调用 —— 它是旁路
（用例 `test_submit_never_raises_when_client_explodes`）。

**④ trace id 必须真的传下去，而且要校验形状。**
Langfuse 4.x 的 `trace_context` 在**非十六进制**的 id 上会 `int(x, 16)` 并抛
`ValueError`（实测：`"abc123defg"`、带横杠的 UUID 都直接崩）；而**短十六进制**
（`"abc123"`）会被**静默左补零**，得到一条**对不上账**的 trace（比不关联更坏：
看板上会有两条都「看起来对」的 trace）。
所以 `_trace_context()` 用 `^[0-9a-f]{32}$` 严格校验，不合格就**不传**。

### 7.4 「质量」必须记成 score（不是 metadata）

`quality()` 写的是 Langfuse 的 **score**：score 是里**能聚合、能画趋势、能按数据集筛选**的
一等公民，而 metadata 只是挂在单条 trace 上的一段 JSON。
把「答案质量 0.86」写进 metadata，等于把它变成一条只能人肉翻看的记录 ——
与 `14.eval.md` 要对齐「成本 vs 质量」的目标直接冲突。超范围的值被**夹住**到 `[0,1]`
（需要记原始分就用 `meta(raw_score=...)`）。

> ⚠️ **score 必须在 observation 的 `with` 块内发**。实测 `score_current_trace()` 依附
> 「当前活跃的 observation」，在块外调用它**不抛异常**（只打一条
> `Context error: No active span…`）然后静默返回 —— 症状是「质量分这条链看着配好了、
> 实际一条都不会到看板上」。用例用一个「块内/块外」探针钉住了这一点。

### 7.5 `done()` 必须幂等

生产路径在 `finally` 里记录，而 `record()` 的上下文管理器**退出时也会调一次** `done()` ——
两条路径叠在一起时，一次 LLM 调用会变成 Langfuse 里的**两条** generation，
于是「成本」与「调用次数」都翻倍（而看板看起来完全正常，只是数字偏大）。

### 7.6 与 OTEL 共用同一个 provider（两个系统对得上账）

`Langfuse(..., tracer_provider=telemetry.provider)` —— Langfuse 4.x 本身就是 OTEL 的实现，
共用 provider 之后，一次 LLM 调用在 Langfuse 里是 trace 的一个**子节点**（能顺着调用链看上下文），
而不是一条孤立记录。代价必须写清楚：**两个 exporter 挂在同一个 provider 上**
（我们的内存/OTLP + Langfuse 自己的），所以「Langfuse 端不可达」会让我们这一侧也多一条失败重试路径
—— 这正是它必须与 `otel_endpoint` 一样被**显式配置**、而不是默认打开的原因。

| 症状 | 最可能的原因 | 怎么确认 / 怎么修 |
|---|---|---|
| `/metrics` 里只有 `shopsage_api_*`，**没有** `shopsage_agent_*` | 埋点写进了**另一个注册表**（进程默认 vs app 注入） | `uv run python -m scripts.observability_demo --scenario series`；修法是让 `instrument._metrics()` 走 `telemetry().metrics`（§11.1 坑 5） |

## 11. 实现期间撞到的坑（实测，含修法）

### 11.1 十一个坑（前十个是实现期的，第十一个是交付前跑自查命令时发现的）

**坑 1：不可重入锁 + 自我调用 = 永久挂住（**最难查的一个**）。**
`telemetry()` 在持有 `_DEFAULT_LOCK` 的情况下调用 `configure_telemetry()` 来懒建，
而后者内部**又取了一次同一把锁** —— `threading.Lock` 不可重入，于是自己等自己。
症状**不是报错**，而是「第一次埋点调用永久挂住」：整条用例超时 150s 都没有任何输出。
定位手法是给探针脚本装一个看门狗线程 + `faulthandler.dump_traceback(all_threads=True)`：

```
Thread 0x00001d94 (most recent call first):
  File "app\observability\tracing.py", line 614 in configure_telemetry
  File "app\observability\tracing.py", line 692 in telemetry
  File "app\observability\tracing.py", line 750 in trace_span
  File "app\observability\instrument.py", line 221 in record_sql_query
  File "app\tools\sql_executor.py", line 204 in execute_readonly_query
```

**修法**：锁的范围收窄到「只保护读-改-写」—— `configure_telemetry` 里的赋值不加锁
（单次属性赋值在 CPython 里是原子的，且它是唯一的写方），`telemetry()` 也不在锁里调它。

**坑 2：同一起始时刻的父子，排序会反过来。**
OTEL 的 `start_time` 只有**微秒**精度且被 provider 向下取整，于是父 span 与它的第一个子 span
经常得到**完全相同**的 `start_ns`。此时按 `start_ns` 单独排序的结果由 exporter 的送出顺序决定，
而**子先结束、先被送出** → 列表是 `[子, 父]` → **火焰图里根节点跑到最下面**。
**修法**：第二排序键 = 「父 span 排在自己的子之前」（`span_id in {父 id 集合}`）。

**坑 3：`record_exception()` 不设 status。**
它只往 span 上加一个 `exception` **event**，**不改 status**。于是出错的 span 与正常 span
在 trace UI 里长得一模一样（status 都是 `unset`）——**看板上没有任何红**。
**修法**：`_OtelHandle.record_exception` 里显式补 `set_status(Status(StatusCode.ERROR, ...))`。

**坑 4：请求结束后「补一条」根 span → 每个节点一个 trace。**
第一版在 `finally` 里调 `record_request_span(...)`，它开一条新 span、立刻关掉。看起来完全合理
（访问日志也在那里写），但：① 它开在请求**结束之后**，不可能是任何节点 span 的父亲；
② 每个节点 span 因此各自成为根 → **每个节点一个 trace**，
「按 trace 查一次请求」这条排障路径彻底失效，而每个节点看起来都埋了点。
**修法**：在中间件里 `with trace_request_span(method, path)` **包住整段下游调用**；
WS 路径（中间件不管）在 `chat_stream` 里自己开一条包住整个消息循环。
用例：`test_root_span_and_node_spans_share_one_trace`。

**坑 5：埋点写进「进程默认注册表」，而 `/metrics` 渲染的是「app 的注册表」。**
两份不同的数据，**每一份看起来都正常** —— 症状是 `/metrics` 里有 `shopsage_api_*`、
节点级指标一条都没有。**修法**：`instrument._metrics()` 走 `telemetry().metrics`
（而 `create_app` 的 lifespan 把 app 的注册表交给了这个 app 的 telemetry），
再加一个 `ContextVar` 的「请求根」让「这次请求用哪一份」跟着请求走。

**坑 6：`prometheus_client` 的 `_created` 系列会污染输出。**
每个 Counter/Histogram 都会自动生成一条 `*_created` 时间戳 gauge：值在进程重启后**变小**，
而 Prometheus 看到 counter 变小会认为「回绕了」→ 每次重启凭空造一次假的 `rate()` 尖峰。
第 9 步定下的 `/metrics` 契约里也没有它。
**修法**：`PROMETHEUS_DISABLE_CREATED_SERIES=true`，且**必须在 import `prometheus_client` 之前设**
（模块顶部用 `os.environ.setdefault`）。

**坑 7：拼接两段指标文本时丢掉了末尾换行。**
`/metrics` 改成「渲染两个注册表并拼接」之后，当第二段为空时整体不以 LF 结尾 ——
浏览器里看完全正常，只有用例 `assert response.text.endswith("\n")` 会红
（Prometheus 抓取端会报 `unexpected end of stream`）。
**修法**：`health.metrics()` 里显式补一句「不以 LF 结尾就补上」。

**坑 8：对账工具本身错了 —— counter 的族名不带 `_total`。**
`prometheus_client` 把 `_total` **只放在样本名上**，`metric.name` 里没有
（`shopsage_requests` vs `shopsage_requests_total`）。于是 4 条 counter 被对账脚本判成「缺失」，
看起来像实现漏了指标。**修法**：用样本名前缀匹配（`name in samples or any(s.startswith(name + "_"))`）。

**坑 9：OTLP 端点配错不会报错，只是收不到 trace。**
`.env.example` 里原本写的是 `OTEL_ENDPOINT=http://localhost:4317` —— 4317 是 OTLP/**gRPC** 的
端口，而本项目用的是 **HTTP** exporter。配错的后果是 exporter 把 `/` 当路径发过去、
collector 返回 404，而 SDK 只在 DEBUG 级别记这件事。
**修法**：`normalize_otlp_endpoint()` ① 缺路径时补 `/v1/traces`；② 端口是 4317 时给一条
**启动期 WARNING**（能照着改）；并把 `.env` / `.env.example` 的默认值改成**留空**。

**坑 10：provisioned 看板的 datasource uid 不会自动改写。**
Grafana 给数据源分配的是**随机 uid**，而看板 JSON 里写的是 `"uid": "prometheus"` ——
症状是所有面板 "Datasource not found"，而数据源明明在列表里。
手点导入时 Grafana 会自动改写引用，所以这个坑**只在 provisioned 看板上出现**。
**修法**：在数据源 yml 里显式写 `uid: prometheus`，并在 `check_infra.py` 里做一次对账。

**坑 11：两条用在工作交付物里的 grep 自查，本身是错的。**
本手册 §9 第一版写的是两条 grep（一条查「指标标签里有没有 `user_id`」、
一条查「有没有绕过 `instrument` 的 `trace_span`」）。**第一次真的跑它们**（作者自己跑）就发现：

* 第一条报出 **15 处假阳性** —— 因为「`"user_id":` 出现在某一行」根本不等于
  「它是指标标签」。假阳性的代价不是「多看一眼」，而是**它会训练人忽略这条检查**
  （真正的违规混在里面时没人会去逐条核）；
* 第二条对**合法的**直接调用报错（`app/graph/nodes.py` 与 `app/llm/client.py`），
  于是它会诱导人加「例外列表」—— 而例外列表每多一条，纪律就多一个需要人记的漏洞。

**修法（两件事，都不是「把 grep 改得更精确」）**：

1. 把判据换成 **AST**（`scripts/check_observability.py`）：只检查「作为 `labels` 参数
   传给 `counter()` / `observe()` 的 dict 字面量」，于是 15 处假阳性一个不剩；
2. 把「例外」从**文档**里搬进**实现**：`instrument` 补上 `node_span()` / `embed_span()` /
   `llm_span()` 三个具名入口，`app/graph/nodes.py` 与 `app/llm/client.py` 改调它们 ——
   于是允许列表**为空**，检查变成一条真正的纪律。

顺带修了自检脚本自己的一个健壮性问题：带 BOM 的文件（`Set-Content -Encoding utf8`
存出来的）会让 `ast.parse` 抛 `SyntaxError: invalid non-printable character U+FEFF`，
第一版让异常冒出去 → **整条自检崩掉、一条问题都没报出来**
（「自检脚本自己崩了」比「没检查」更糟：它看起来像配置问题）。现在按 `utf-8-sig` 读，
且单个文件解析失败只记一条问题、继续检查其余文件。

> 这条坑的普适教训：**一个检查如果从没被跑过，它大概率是错的**。
> 交付前把文档里的每条自查命令**真的执行一遍**，比再读一遍文档有效得多。

### 11.2 三个「差点写错」的设计点（写下来备查）

1. **`_ToolCall` 的耗时绝不能由调用方传**：第一版让三个调用点各传 `seconds=`，
   结果是三种口径（含/不含校验、含/不含审计），`TOOL_DURATION` **内部不可比** ——
   而它看起来完全正常。现在由 `with` 块自己量，口径只有一处。
2. **`outcome` 是标签，不是自由文本**：错误消息当 outcome 就是基数爆炸。
   所以取值限制在有限集合（`created` / `idempotent_hit` / `truncated` / `rows` / `hits` / `degraded`）。
3. **`total_tokens` 不能自己加**：provider 的 `total` 可能含 reasoning / 缓存 token，
   `prompt + completion` 会与账单对不上（而「账单对不上」是成本看板失去信任的最快方式）。
   同理 **`cost_usd=None` 不能记成 0** —— 未知不等于零，记 0 会让成本**看起来完整、实际偏低**。

### 11.3 本步**没有**做的事（诚实的边界）

| 没做 | 为什么 | 什么时候补 |
|---|---|---|
| 逐 token 流式埋点 | 第 9 步 `chat.py` docstring 里点名的活；本步只把帧协议的位置留好 | 第 16 步（Web 端）之前 |
| trace 采样 | 全量记录更简单，而内存 exporter 有环形上限；采样会让「分位数」失真（采掉慢请求） | 有真实流量压力时 |
| 队列深度指标 | 出口（`QUEUE_DEPTH`）与 Grafana 面板**都已留好**，缺的是写它的队列 | 第 12 步 |
| 语义缓存的命中率 | 同上：缓存命中率要等缓存存在 | 第 13 步 |
| 评测分回填 | `langfuse_handler().score(trace_id=...)` 已经就绪（走 `create_score`） | 第 14 步 |
| 告警规则本体 | 记录规则（分位数）是原料，Alertmanager 属部署编排 | §19 部署 |
| `app/rag/retriever.py` 内部的子步骤 | 只埋了 `retrieve_docs`（工具层）。要在 `hybrid_search` 内部再分「向量腿/关键词腿/rerank」需要动第 10 步的 139 条用例基线 | 需要它时（收益与风险见下） |

> （`app/rag/retriever.py::Retriever`）。本步**刻意不进去**，因为那要改动第 10 步
> 刚验收完的 139 条用例的实现路径 —— 而第 10 步的 `RetrievalResult` 已经带了
> `vector_hits` / `keyword_hits` / `rerank_degraded` / `elapsed_ms` 这些分诊信息，
> 需要下钻时先看它（那是零风险的），确实不够再动检索层内部。
