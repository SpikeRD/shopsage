# Docker 运维手册：Linux 上怎么把这份代码真正跑起来（env.list 注入）

> **适用场景**：项目开发已完成，要在 **一台 Linux 服务器**上把 ShopSage **整套**（api / worker / web /
> postgres / redis / prometheus / grafana）用 Docker 跑起来，以及之后改完代码或配置**怎么重建、怎么重启**。
>
> **本文回答三个问题**：
> 1. 一次性部署：从空服务器到能打开页面，**按顺序跑哪几条命令**；
> 2. 环境变量怎么传：**全部走 `env.list`**，以及为什么不能靠 `.env`（§5）；
> 3. 改完之后：**跑哪一条**、为什么是那一条、跑完怎么确认生效（§6–§7）。
>
> 前置的依赖栈拓扑与开发期跨主机连法见 [`2.infra-runbook.md`](2.infra-runbook.md)；
> 可观测栈字段含义见 [`11.observability-runbook.md`](11.observability-runbook.md) §6；
> 生产形态的设计取舍见 [`../modules/2.infra.md`](../modules/2.infra.md) §4–§6。
>
> ⚠️ 本文所有命令**都在 Linux 服务器的仓库根执行**。开发机（Windows）没有 Docker，只能跑 `uv`。
>
> 📌 **本文是「待执行」手册，不是执行记录。** 跑通后按 §9 回填证据到对应模块文档第 8 节。

## 0. 30 秒速查：改了什么东西 → 跑哪条命令

**先判断改动属于哪一类，再抄命令。** 抄错了不会报错，只会「看起来重启了、其实没生效」——
这是本文存在的唯一理由。

| 改了什么 | 生效方式 | 命令（Linux，仓库根） | 会不会丢数据 |
|---|---|---|---|
| `env.list`（业务配置、密钥） | **容器重建**（env_file 只在创建容器时读） | `up -d --force-recreate api worker` | 不丢 |
| `env.list` 里的 `POSTGRES_*` | ⚠️ 只在**空数据卷**时生效一次 | 见 §6.2（要么进库改口令，要么 `down -v`） | `down -v` 会全丢 |
| `app/**` `.py`（业务代码） | 镜像重建 + 容器重建 | `up -d --build api worker`（改了模型再按 §4.3 补跑 migrate） | 不丢（卷不归镜像管） |
| `web/**`（前端） | 镜像重建 | `up -d --build web` | 不丢 |
| `pyproject.toml` / `uv.lock`（依赖变了） | 镜像依赖层变了 | `up -d --build`（**必须重建**，重启没用） | 不丢 |
| `web/package-lock.json` | 同上（`npm ci` 层） | `up -d --build web` | 不丢 |
| `env.list` 的 `DATABASE_URL` 等**运行期**变量 | 容器重建 | `up -d --force-recreate api worker` | 不丢 |
| `NEXT_PUBLIC_API_BASE`（前端后端地址） | ⚠️ **构建期**变量，**必须重新 build** | `up -d --build web`（重启无效！见 §5.2） | 不丢 |
| `infra/prometheus/**`（配置或规则） | 挂载是 bind mount，但 Prometheus **只在启动时读** | `up -d --force-recreate prometheus` | 不丢（卷保留；15d 历史还在） |
| `infra/grafana/provisioning/**` | 由 provisioning 应用 | `up -d --force-recreate grafana`（文件改动最慢 30s 也会自动同步，见 §7.3） | 不丢（但**历史改动**见 §7.3 的坑） |
| `infra/otel/otel-collector.yml` | 启动时读 | `--profile tracing up -d --force-recreate otel-collector` | 不丢（`/data/traces.jsonl` 在卷里） |
| `docker-compose.yml`（加减服务、端口、挂载） | compose 重新解析 YAML | `up -d`（**不是** `restart`） | 不丢 |
| 想彻底重来（配置状态脏了） | 删容器 + 删**数据卷** | `down -v && up -d` | ⚠️ **全丢**：库、Redis、Grafana 看板历史、Prometheus TSDB、HF 权重 |

> **一条铁律**：`docker compose restart` **不重新解析 `docker-compose.yml`、不重读 `env.list`**。
> 它的语义只是「对**现有**容器做 stop + start」（等价于 `docker compose stop && docker compose start`），
> 容器不会被重建，所以 YAML 里的字段变更（镜像、端口、挂载、环境变量）它一概看不见。
> 凡是「改了配置」的场合，用 `up -d`；要连字段变更一起吃掉，用 `up -d --force-recreate`。

> **第二条铁律**：**`env.list` 的改动只对「下一次创建的容器」生效**。
> 容器一创建，`os.environ` 就定型了 —— 这与 `.env` 是同一类语义（`1.config-guide.md` §1.7：
> 配置在进程启动时读一次），只是容器把「进程启动」换成了「容器创建」。

## 1. 这套部署长什么样：一张图看懂

```
                         Linux 服务器（一台机器，一个 compose 项目：shopsage）
  ┌───────────────────────────────────────────────────────────────────────────────┐
  │  docker compose -f docker-compose.yml --project-directory .                   │
  │                                                                               │
  │   web:3000 ──HTTP/WS──▶ api:8000 ──┬──▶ postgres:5432 (pgvector)              │
  │   (Next standalone)   (uvicorn)    ├──▶ redis:6379 (arq 队列 / 限流 / 缓存)     │
  │                                    └──▶ LLM API（出网）                        │
  │   worker ──(同一个镜像, arq)──▶ postgres / redis                               │
  │   migrate ──(同一个镜像, alembic upgrade head)──▶ postgres（一次性，跑完退出）    │
  │                                                                               │
  │   prometheus:9090 ──抓──▶ api:8000/metrics                                    │
  │   grafana:3000(宿主 3001) ──查──▶ prometheus:9090                              │
  │   otel-collector:4318 (可选, --profile tracing) ◀── api / worker 发 span       │
  │                                                                               │
  │   网络：shopsage (自定义 bridge)  卷：postgres_data / redis_data /             │
  │        prometheus_data / grafana_data / otel_data / hf_cache                  │
  └───────────────────────────────────────────────────────────────────────────────┘
```

**「一个业务镜像、三个角色」**（这是与开发栈最大的结构差异）：

| 服务 | 镜像 | 命令 | 为什么这样拆 |
|---|---|---|---|
| `migrate` | `shopsage-api` | `alembic upgrade head` | 迁移必须**先于** api 且**只跑一次**；放在 api 的 CMD 里会被多副本重复执行 |
| `api` | `shopsage-api` | `uvicorn app.main:app` | HTTP + WebSocket |
| `worker` | `shopsage-api` | `arq app.queue.worker.WorkerSettings` | 长任务常驻进程，与 api 独立扩缩/重启（`2.infra.md` §5） |
| `web` | `shopsage-web` | `node server.js` | Next `standalone` 产物，不含 `node_modules` 全量 |

> ⚠️ **同一个镜像跑 api 与 worker** 不只是省体积：它保证「入队用的任务名」与「消费用的实现」
> 是**同一份代码**。分开构建时最容易出的事故是「api 已更新、worker 还是旧版」，症状是
> 任务入队成功但永远执行不到（`12.queue-runbook.md` 的持久化契约问题）。

## 2. 前置条件（30 秒自检）

```bash
# ── Linux 服务器 ──
docker --version                 # 需要 24+（本文的 healthcheck / 语法都按 24+ 写的）
docker compose version           # 需要 v2.x（命令是 `docker compose`，**不是** `docker-compose`）
docker info | grep -E 'Server Version|Storage Driver'

# 当前用户能不能用 docker（不能就 sudo usermod -aG docker $USER 后**重新登录**）
docker ps >/dev/null && echo "docker OK"

# 磁盘：镜像 + 卷大约要 12–20 GB（含 2GB torch 与 3GB HF 权重）
df -h /var/lib/docker

# 出网：拉镜像 + 调 LLM + 首启下载 HF 权重
curl -sI https://registry-1.docker.io/v2/ | head -1
```

三条**必须先解决的**环境问题（不解决，后面每一步都会以看不懂的方式失败）：

| 症状 | 原因 | 修法 |
|---|---|---|
| `docker: command not found` / `permission denied` | 没装，或用户不在 `docker` 组 | 装 Docker Engine；`sudo usermod -aG docker $USER` 后**重新登录**（不重登不生效） |
| 仓库放在 VMware 共享文件夹（hgfs / 9p） | bind mount 的权限映射常导致容器读不到配置 | 仓库挪到 Linux 原生目录（`~/ShopSage`）。判据：`mount \| grep -E 'hgfs\|9p'` 不该包含仓库路径 |
| `port is already allocated` | 宿主机已有服务占用 8000/3000/9090/3001 | 改**仓库根 `.env`** 的 `API_PORT` / `WEB_PORT` / `PROMETHEUS_PORT` / `GRAFANA_PORT`（这些是 compose 插值变量，见 §6.4） |

## 3. 一次性部署：从空服务器到能打开页面

**完整顺序**（下面每一步都有「为什么不能跳过」）。假设仓库已 `git clone` 到 `~/ShopSage`。

### 3.1 同步代码 + 确认版本

```bash
cd ~/ShopSage

git status --short                # 期望无输出；不干净先想清楚那些改动要不要
git fetch --all --prune
git checkout main                 # 或你要部署的分支
git pull --ff-only                # --ff-only：分叉时立刻失败，而不是悄悄合出一个 merge commit

git log -1 --oneline              # 记下这个 SHA，回滚与证据回填都要用它
export IMAGE_TAG=$(git rev-parse --short HEAD)   # 后面 build/up 都用它（回滚开关，见 §8.4）
echo "部署版本：$IMAGE_TAG"
```

> ⚠️ `IMAGE_TAG` 这个变量是**本节的枢纽**：它让「镜像」和「某个 commit」一一对应。
> 不设它时镜像叫 `latest`，回滚就只能靠「记得上一次构建的是哪个提交」——那不叫回滚。

### 3.2 准备 `env.list`（**这是本手册的核心，别用 `.env`**）

```bash
cp env.list.example env.list
chmod 600 env.list                # 里面全是密钥
vi env.list                       # 按下面「最少要改的 8 项」逐条填
```

**最少必须改的 8 项**（其余可以先用默认值跑起来）：

| 键 | 为什么必须改 | 怎么取值 |
|---|---|---|
| `POSTGRES_PASSWORD` | 默认值是 `change-me-...`，生产不能用 | `openssl rand -hex 24` |
| `DATABASE_URL` | ⚠️ **必须与上一项的密码一致**，host 是 `postgres` 服务名 | 手工拼，见下方模板 |
| `JWT_SECRET` | `ENV=prod` 下缺失或短于 16 字符会**拒绝启动** | `openssl rand -hex 32` |
| `LLM_API_KEY` | `ENV=prod` 下缺失会拒绝启动 | 厂商控制台 |
| `LLM_FALLBACK_API_KEY` | 配了 `LLM_FALLBACK` 却没有它 → **拒绝启动** | 厂商控制台 |
| `DATABASE_READ_URL` / `SHOPSAGE_READONLY_PASSWORD` | 两处口令必须一致（§3.5 建角色用它） | `openssl rand -hex 32` |
| `API_CORS_ORIGINS` | 生产留空 = **不允许任何跨源**（页面会被浏览器拦掉） | 前端真实访问地址，如 `https://shopsage.example.com` |
| `GF_SECURITY_ADMIN_PASSWORD` | Grafana 管理入口 | `openssl rand -hex 16` |

`DATABASE_URL` 的写法（host 是**服务名** `postgres`，不是 localhost、也不是服务器 IP）：

```text
DATABASE_URL=postgresql://shopuser:<与 POSTGRES_PASSWORD 相同>@postgres:5432/shopsage
DATABASE_READ_URL=postgresql://shopsage_readonly:<与 SHOPSAGE_READONLY_PASSWORD 相同>@postgres:5432/shopsage
REDIS_URL=redis://redis:6379/0
```

> ⚠️ **`env.list` 的三条格式禁忌**（每条都踩过；细节见 `env.list.example` 文件头）：
> ① 值里不要写行内注释（`LLM_PRIMARY=x   # 说明` 会把注释算进值里）；
> ② 值里不要加引号（`env_file` 不剥引号，密码会真的带上两个引号）；
> ③ `KEY=VALUE` 一行一个，`=` 两边不留空格。
>
> 判据（不用起服务就能验格式）：
>
> ```bash
> grep -nE '^\s*[A-Za-z_][A-Za-z0-9_]*\s+=' env.list && echo "❌ 有空格，改掉" || echo "格式 OK"
> grep -nE '=\s*"' env.list && echo "❌ 有引号，去掉" || echo "无引号 OK"
> ```

### 3.3 校验 compose 与配置（**只读，什么都不启动**）

> ⚠️ **必须先有 `env.list`（§3.2）**：compose v2 在 `config` 阶段就会检查 `env_file:`
> 指向的文件是否存在，缺了会直接报
> `env file /home/xx/ShopSage/env.list not found`。
> 这不是「配置写错了」，只是还没建文件 —— 但很容易被误读成 compose 语法问题。

```bash
# ① compose 语法 + 变量替换（-q：静默，只回退出码）
docker compose -f docker-compose.yml --project-directory . config -q
echo "exit=$?"        # 期望 0；有输出=YAML/字段写错，按报错行号改

# ② 看「端口和环境变量渲染成了什么」（含密钥，别整段贴出去）
docker compose -f docker-compose.yml --project-directory . config \
  | grep -E 'published|target:|image:' | head -40

# ③ 配置自检脚本（仓库根，用本机 uv 环境跑；不需要 Docker）
uv run python -m scripts.check_infra
# 期望：逐项 OK，末尾「✅ 基础设施配置自检通过」
```

> ⚠️ **`scripts/check_infra.py` 在 Windows（GBK 控制台）上退出码可能是 1**：
> 它收尾那行 `print("✅ ...")` 会触发 `UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'`。
> **检查本身已经全部跑完并逐项打印了**，只是最后一行没打出来。
> 判据看**逐项 `OK` 行**，不要只看退出码；想让它干净退出就先设编码：
>
> ```bash
> # Linux 上本来就是 UTF-8，不会遇到；在 Windows 上手动跑时加这个
> export PYTHONIOENCODING=utf-8     # PowerShell: $env:PYTHONIOENCODING="utf-8"
> uv run python -m scripts.check_infra
> ```
>
> ⚠️ 这个脚本现在也检查**生产 compose 与 `prometheus.prod.yml`**（§5 的「生产 compose 结构」
> 一节）：服务缺 `image`/`build`、api/worker 没等 migrate、compose 里出现业务变量插值、
> prometheus 挂错配置文件 —— 这几类错误 `docker compose config -q` 都**不会**报，
> 只会在部署那一刻以看不懂的方式失败。

> ⚠️ `--project-directory .` **不能省，且必须在仓库根执行**（`2.infra-runbook.md` 坑 1、坑 2）：
> compose 的 `.env`（供 `${...}` 插值）与 bind mount 的相对路径**都按「项目目录」解析**。
> 少了这个参数，变量替换会**静默退回默认值**（不报错），bind mount 会指向不存在的路径 →
> Docker 自动建空目录再挂上去。

> ⚠️ 别直接 `config | head`：渲染结果里含**明文库密码**。要看就按上面的 `grep` 收窄。

### 3.4 构建镜像（**后端一个、前端一个，前端要传 build arg**）

```bash
# 后端（api / worker / migrate 共用）
docker build -f app/Dockerfile \
  -t "shopsage-api:${IMAGE_TAG}" -t shopsage-api:latest .

# 前端 —— ⚠️ NEXT_PUBLIC_API_BASE 是**构建期**参数，必须在这里给
docker build -f web/Dockerfile \
  --build-arg NEXT_PUBLIC_API_BASE="http://<服务器IP>:8000" \
  -t "shopsage-web:${IMAGE_TAG}" -t shopsage-web:latest .
```

**`NEXT_PUBLIC_API_BASE` 该填什么**：填**浏览器**能访问到的后端地址（不是容器名）。

| 部署形态 | 填什么 | 说明 |
|---|---|---|
| 直接暴露端口（最简单） | `http://<服务器IP>:8000` | 浏览器直连 api 的 8000；要放通防火墙 |
| 反代同域（推荐） | 留空，或 `https://shopsage.example.com` | 反代把 `/api` 与页面放在同一个域；见 `16-web-runbook.md` §9 |
| ⚠️ 写 `http://localhost:8000` | **只在「浏览器就跑在服务器本机」时才对** | 让同事从自己电脑打开页面 → 他的 localhost 是他自己的机器，必然连不上 |

> ⚠️ **为什么不能写容器名 `api:8000`**：这个值会被打包进**浏览器**执行的 JS，
> 而浏览器的 DNS 里没有 Docker 的服务名 —— 它只认从它自己机器能解析的地址。

> **构建期 vs 运行期**（容器化 Next 的头号坑，§5.2 有完整说明）：
> `NEXT_PUBLIC_*` 在 `next build` 时被**字面替换**进客户端 bundle。
> 所以**改 `env.list` 里的它 + 重启容器 = 无效**，必须重新 `docker build`。

> 💡 **不想手写 build 命令**：`docker-compose.yml` 里 web 的 `build.args` 已经接好了
> `${NEXT_PUBLIC_API_BASE}` 插值，所以下面这条等价、且更不容易漏参数（推荐用它）：
>
> ```bash
> NEXT_PUBLIC_API_BASE="http://<服务器IP>:8000" \
>   docker compose -f docker-compose.yml --project-directory . up -d --build web
> ```
>
> shell 前缀变量会被 compose 的 `${...}` 插值优先读到（优先于 `.env`），
> 所以它不会污染任何「容器内的环境变量」—— 这一点在 §5.1 有解释。
>
> ⚠️ **别用两种方式混着来**：先手动 `docker build`、再 `up -d --build`，
> 后者会用 compose 的默认值（`http://localhost:8000`）**重新构建一次**，把前者覆盖掉。

构建完立刻验两件事（不做的话，后面所有验证都可能是在测旧镜像）：

```bash
docker images | grep -E 'shopsage-(api|web)'
# 期望：两行，TAG 里既有 ${IMAGE_TAG} 也有 latest，且两者的 IMAGE ID 一致

# 镜像里没有密钥文件（这是最容易漏的一项）
docker run --rm --entrypoint sh "shopsage-api:${IMAGE_TAG}" -c \
  'ls -a /app | grep -E "^\.env$|^env\.list$" && echo "❌ 有密钥文件" || echo "✅ 无密钥文件"'

# 非 root 运行
docker run --rm "shopsage-api:${IMAGE_TAG}" id
# 期望：uid=10001(shopsage) gid=10001(shopsage)
```

### 3.5 启动整套（第一次）

```bash
# ① 先起依赖并等 healthy（migrate 依赖 postgres healthy 才能跑）
docker compose -f docker-compose.yml --project-directory . up -d --wait --wait-timeout 120 postgres redis
echo "exit=$?"        # 期望 0

# ② 跑迁移（migrate 是一次性服务：跑完就退出，退出码 0 才算成功）
#    注意：给了 COMMAND 时 compose 会**整体替换**服务的 command，不是追加
docker compose -f docker-compose.yml --project-directory . run --rm migrate
docker compose -f docker-compose.yml --project-directory . run --rm migrate alembic current
# 期望：current 与 `alembic heads` 一致

# ③ 起业务 + 观测栈（--build 顺带构建镜像；--wait 等全部 healthy）
docker compose -f docker-compose.yml --project-directory . up -d --build --wait --wait-timeout 240
echo "up exit=$?"     # 期望 0
```

> ⚠️ **`--wait` 与一次性服务（migrate）**：`up -d` 会把 `migrate` 也建出来跑一遍
> （它是 api/worker 的 `depends_on: service_completed_successfully` 依赖），跑完 `Exited (0)` 是**正常**的。
> 新版 compose 会把它算成「已完成」；**老版本**（v2.20 之前）可能因此让 `--wait` 返回非 0
> 并打印 `container shopsage-migrate exited (0)`。
>
> 判据：**只有当退出码不是 0 才是失败**。看到 `exited (0)` 却担心的话，改用分步顺序：
>
> ```bash
> docker compose -f docker-compose.yml --project-directory . up -d --build
> # 然后按 §3.7 用 `ps` 逐个确认 healthy（不依赖 --wait 的退出码）
> ```

> ⚠️ **迁移失败必须停下来看**，不要「先起 api 再说」。
> `alembic upgrade head` 失败时表结构停在旧版本，而 api 照常启动 —— 症状是
> 「登录 500」「查订单少列」这类**看起来像业务 bug** 的错误。判据：
>
> ```bash
> docker compose -f docker-compose.yml --project-directory . logs migrate | tail -30
> docker compose -f docker-compose.yml --project-directory . run --rm migrate alembic current
> # 期望：输出与 `alembic heads` 一致
> docker compose -f docker-compose.yml --project-directory . run --rm migrate alembic heads
> ```
>
> ⚠️ `run --rm migrate` 之后 `ps -a` 里看不到那个临时容器（`--rm` 会删掉它）；
> `up -d` 起的 migrate 容器则是 `Exited (0)` 留着看得到。两者都是正常的。

## 5. 环境变量：为什么全部走 `env.list`，以及两个必须知道的边界

### 5.1 三份「环境变量文件」的分工（**这是最容易搞混的一节**）

| 文件 | 谁读它 | 作用域 | 进 Git 吗 |
|---|---|---|---|
| `env.list` | **compose 的 `env_file:`** → 注入容器进程的 `os.environ` | Linux 全栈部署（api / worker / migrate / postgres / grafana） | ❌ 只提交 `env.list.example` |
| `.env`（仓库根） | ① compose 自己（做 `${...}` 插值）② 开发机上直接跑的 uv 进程 | 开发期（Windows）+ 部署拓扑参数 | ❌ |
| `.env.example` / `env.list.example` | 没人读，**是给人复制用的模板** | — | ✅ |

**三条由此推出的规则**：

1. **容器里的业务配置只来自 `env.list`**。镜像里没有 `.env`（`.dockerignore` 排除了），
   所以 `Settings` 的环境变量优先级链只剩第一档 —— 这正是 `2.infra.md` §5 的设计：
   容器里「环境变量是唯一来源，不存在覆盖」。
2. **`${...}` 插值读的是仓库根 `.env`，不是 `env.list`**。所以 compose 文件里
   只留「部署拓扑参数」（端口、`IMAGE_TAG`、`WITH_LOCAL_EMBEDDING`），
   **业务配置一个都不在 compose 里写** —— 否则同一个值有两个来源，必然漂移。
3. **`.env` 不要带到服务器上**。留着它不会立刻出错，但会让 `${...}` 插值
   **静默**取自开发机那份文件。判据：服务器仓库根不该有 `.env`。

> 💡 **唯一一个跨两边的变量**：`TZ`（compose 用它插值、也写进容器）。
> 它在两个地方都要有才算一致 —— 这是刻意的例外，因为它属于「部署拓扑」而不是「业务配置」。

> 💡 `docker-compose.yml` 里的 `environment: ENV=prod` **必须留着**：它覆盖 `env.list`
> 里的同名值（compose 优先级：`environment` > `env_file`）。少写它的后果是
> 「有人在本文件里把 `ENV` 改成了 dev 而容器照样按 prod 起来」这种反直觉状态；
> 反过来，`ENV=dev` 时 prod 的 fail-fast 与 CORS 收紧**全部不生效**。
>
> ⚠️ 把一套配置误当成另一套的典型症状：`up -d` 成功、容器 healthy、**业务配置全是默认值**
> （LLM key 空 → 500；`DATABASE_URL` 空 → prod fail-fast 直接退出）。
> 判据永远是「**进容器里看它真正读到的值**」，不是「文件我改了」：
>
> ```bash
> docker compose -f docker-compose.yml --project-directory . exec api \
>   env | grep -E '^(ENV|DATABASE_URL|REDIS_URL|LLM_PRIMARY|EMBEDDING_BACKEND)=' \
>   | sed -E 's#(://[^:]+:)[^@]*(@)#\1***\2#'
> ```

### 5.2 ⚠️ `NEXT_PUBLIC_*` 是**构建期**变量，不是运行期

这是容器化 Next 的头号坑，而且**不会报错**：

| 你以为 | 实际 |
|---|---|
| 改 `env.list` 的 `NEXT_PUBLIC_API_BASE` → 重启 web 容器 → 生效 | ❌ **完全无效**。Next 在 `next build` 时把它**字面替换**进 `客户端 JS 文件`，容器里根本没有这个变量可读 |
| 在 compose 的 `environment:` 里设它 → 生效 | ❌ 同样无效（浏览器拿到的是构建时写死的那份） |
| 必须重新 `docker build` | ✅ 唯一正确的改法 |

```bash
# 正确改法：改了它就必须带 --build，且要重建 web
docker compose -f docker-compose.yml --project-directory . up -d --build web
# 注：NEXT_PUBLIC_API_BASE 的默认值来自 compose 的 build.args 插值（${NEXT_PUBLIC_API_BASE}），
#     所以要么在仓库根 .env 里设它，要么直接改 compose，要么手动 docker build（§3.4）。
```

**怎么确认打进去的是哪个地址**（不用开浏览器）：

```bash
# 在构建产物里搜那个地址：搜到 = 就是它；搜不到 = 构建时没给这个 arg（用了默认值）
docker compose -f docker-compose.yml --project-directory . exec web \
  sh -c 'grep -rho "http://[a-zA-Z0-9._:-]*:8000" /app/.next/static | sort -u | head'
```

> ⚠️ `web/src/lib/config.ts` 有一个**自动纠正**：当 `NEXT_PUBLIC_API_BASE` 指到「页面自己」
> （同源）时，代码会改用 `http://127.0.0.1:8000` 并在页面上给一条提示。
> 所以「指向写错」在页面上表现为一条黄条提示 + 连不上后端，而不是彻底白屏 ——
> 但那个纠正值在别人的电脑上同样连不上，**别把它当成修好了**。

### 5.3 哪些变量是「只能在首次启动时生效一次」的

| 变量 | 生效时机 | 改它的正确姿势 |
|---|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | **数据卷为空时初始化一次** | 进库 `ALTER USER` / 重建卷（⚠️ 删数据）。见 §6.2 |
| `GF_SECURITY_ADMIN_PASSWORD` | `grafana_data` 卷为空时 | 进 Grafana UI 改，或 `docker exec` 用 `grafana-cli admin reset-admin-password` |
| `NEXT_PUBLIC_API_BASE` | **构建期** | 重新 build（§5.2） |
| `WITH_LOCAL_EMBEDDING` | **构建期**（build arg） | 重新 build（§6.3） |
| 其余（`LLM_*` / `EMBEDDING_*` / `RAG_*` / `API_*` / `OTEL_*`） | 容器创建时 | `up -d --force-recreate api worker` |

## 6. 场景 B：逐个服务的坑

### 6.1 代码热更新：容器里**没有** `--reload`

开发期的 `uvicorn --reload` 是宿主机跑代码时的便利。容器里的 CMD **不带** `--reload`
（`app/Dockerfile`），所以改 `.py` 必须 `up -d --build`。这是刻意的：
带 reload 的镜像会额外装 watchfiles、且在生产上「改文件即重启」不是想要的行为。

想临时开发调试（不建议在生产机上做）：

```bash
docker compose -f docker-compose.yml --project-directory . run --rm -p 8001:8000 \
  -v "$PWD/app:/app/app" api \
  uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

### 6.2 改了 `POSTGRES_PASSWORD` 却不生效（**最经典的一个**）

postgres 的初始化变量**只在数据卷为空时生效一次**。卷已存在时：

- 改 `env.list` 的 `POSTGRES_PASSWORD` → 库里的口令**不变**，但 api 拿新口令去连 → 认证失败；
- 症状：`api` 反复重启，日志 `password authentication failed for user "shopuser"`。

两种修法：

```bash
# ① 进库改口令（不丢数据，推荐）
docker compose -f docker-compose.yml --project-directory . exec postgres \
  psql -U shopuser -d shopsage -c "ALTER USER shopuser WITH PASSWORD '新口令';"
# 然后把 env.list 的 DATABASE_URL / DATABASE_READ_URL 也改成新口令，
# 再 up -d --force-recreate api worker

# ② 清空重建（⚠️ 数据全丢：库、向量、账号、订单）
docker compose -f docker-compose.yml --project-directory . down -v
docker compose -f docker-compose.yml --project-directory . up -d
```

> ⚠️ 只改 `POSTGRES_PASSWORD` 而忘了 `DATABASE_URL`（或反过来）是同一类事故的另一半。
> `env.list` 里把它们放在一起就是为了让「一起改」变成最省事的做法。

### 6.3 `EMBEDDING_BACKEND=local` 与 `WITH_LOCAL_EMBEDDING` 必须一致

| 配置 | 镜像 | 结果 |
|---|---|---|
| `EMBEDDING_BACKEND=local` + `WITH_LOCAL_EMBEDDING=true` | 含 sentence-transformers + torch | ✅ 正常 |
| `EMBEDDING_BACKEND=local` + `WITH_LOCAL_EMBEDDING=false` | 不含 | ❌ **服务能起来、`/health` 全绿**，第一次检索才报错，且图会降级成「没有依据的回答」 |
| `EMBEDDING_BACKEND=litellm` + `WITH_LOCAL_EMBEDDING=true` | 含（白装 2GB） | ⚠️ 能跑，只是镜像大、构建慢 |

**为什么默认是 `local` + `true`**：迁移把向量表维度**写死成 `vector(1024)`**
（`app/rag/schema.py::VECTOR_DIM`，有测试对账），而 1024 维的默认选择就是本地 `bge-m3`。
要用 1536 维的 `text-embedding-3-small`，必须**改迁移 + 重灌全部向量**，那不是「换个配置项」。

```bash
# 确认容器里到底有没有装（不要靠猜）
docker compose -f docker-compose.yml --project-directory . exec api \
  python -c "import sentence_transformers as s; print('sentence-transformers', s.__version__)"
# ModuleNotFoundError = 构建时没给 WITH_LOCAL_EMBEDDING=true
```

> ⚠️ `EMBEDDING_DIM` / `RAG_VECTOR_DIM` 与迁移里的 `vector(n)` 三者必须相等。
> 不一致时的**最坏**形态不是报错，而是「维度恰好相同但向量空间不相容」——
> 检索看着正常、结果全是乱的，掉分时你会先去怀疑 prompt（`5.llm-runbook.md` §7.6）。

### 6.4 端口冲突与改端口

compose 里的宿主端口都可以用仓库根 `.env` 的变量改（**插值读 `.env`**）：

```bash
# 仓库根 .env（只在服务器上临时用；不是 env.list）
API_PORT=18000
WEB_PORT=13000
GRAFANA_PORT=13001
PROMETHEUS_PORT=19090
```

改完 `up -d`。⚠️ **改了 `WEB_PORT` 就要同步改 `NEXT_PUBLIC_API_BASE` 与 `API_CORS_ORIGINS`**
（一个给浏览器找后端，一个告诉后端允许哪个来源），否则页面必然连不上。

### 6.5 整栈停止：`stop` / `down` / `down -v` 的区别（**别用错**）

| 命令 | 容器 | 网络 | 命名卷（数据） | 镜像 | 什么时候用 |
|---|---|---|---|---|---|
| `docker compose ... stop` | 停止（保留） | 保留 | **保留** | 保留 | 临时停机，之后 `start` 回来 |
| `docker compose ... down` | **删除** | **删除** | **保留** | 保留 | 改完 compose、要干净重建（推荐） |
| `docker compose ... down -v` | **删除** | **删除** | ⚠️ **删除** | 保留 | 真的要清空重来 |
| `docker compose ... down --rmi local` | 删除 | 删除 | 保留 | **删除本地构建的** | 想连镜像一起清掉 |

```bash
cd ~/ShopSage
docker compose -f docker-compose.yml --project-directory . down        # ✅ 安全：数据留着
docker compose -f docker-compose.yml --project-directory . down -v     # ⚠️ 会删 shopsage_* 全部数据
```

> **`down -v` 会删掉什么**：postgres 的库（含 pgvector 向量表、种子数据、账号）、
> Redis 的 AOF（含 arq 队列与死信相关的键）、Prometheus 最近 15 天的 TSDB、
> Grafana 的本地状态、以及 **`hf_cache`（约 3GB 的模型权重，要重新下载）**。
> 「我只是重建个容器」时**不要加 `-v`** —— 重建镜像/重建容器**从来不删卷**。

```bash
# 确认卷还在（名字由 compose 顶层 name: shopsage 决定）
docker volume ls | grep shopsage
```

### 6.6 ⚠️ 多 worker：`--workers` 默认 1，别随手改成 4

`app/Dockerfile` 的 CMD 是 `--workers 1`，注释里给了完整理由。摘要：

- uvicorn 的 `--workers N` 是「一个进程 fork 出 N 个」共享同一个监听端口；
- `prometheus_client` 的注册表是**进程内**的 → 每次 `GET /metrics` 由**随机一个** worker 应答；
- 于是 Prometheus 抓到的计数在 N 份之间跳变，记录规则里的 `sum by (le, node)` **静默低估**。

要真上多副本，需要先启用 `prometheus_client` 的 multiprocess 模式
（`PROMETHEUS_MULTIPROC_DIR` + `MultiProcessCollector`）—— **本仓未做**。
在那之前，「横向扩容」的正确做法是**多起几个 api 容器**（每个 `--workers 1`），
而不是改 `--workers`：前者每个容器是一个独立 scrape target，指标天然不混。

> ⚠️ 但本仓的 `docker-compose.yml` 给 api 写了固定的 `container_name: shopsage-api`，
> 所以 **`--scale api=2` 会直接报错**（名字冲突）。要多副本，得先删掉那行 `container_name`，
> 然后：
>
> ```bash
> # 需要先删掉 compose 里 api 的 container_name（否则报 "container name already in use"）
> docker compose -f docker-compose.yml --project-directory . up -d --scale api=2
> docker compose -f docker-compose.yml --project-directory . ps api
> ```
>
> 同时 Prometheus 的 target 得改成服务名 `api:8000`（Docker DNS 会返回所有副本的 IP，
> Prometheus 会为每个 IP 生成一个 target）—— 这正好是 `prometheus.prod.yml` 现在的写法。

### 6.7 只重启业务进程（容器内）

```bash
# 重启单个服务（不重建、不重读 env.list —— 只在你确认配置没变时用）
docker compose -f docker-compose.yml --project-directory . restart api

# 真要看它什么时候起来的
docker compose -f docker-compose.yml --project-directory . ps -q api \
  | xargs docker inspect --format '{{.State.StartedAt}} restarts={{.RestartCount}}'
```

> ⚠️ `RestartCount` 一直在涨 = 容器在**崩溃循环**里。先看日志，别急着重启：
>
> ```bash
> docker compose -f docker-compose.yml --project-directory . logs --tail=80 api
> # 最常见的两条：
> #   「ENV=prod 缺少必填配置: database_url, llm_api_key」→ env.list 没被读到（§5.1）
> #   「password authentication failed」→ 口令与库不一致（§6.2）
> ```

## 7. 场景 C：只改了 `infra/` 下的配置（不重建镜像）

适用：改了 `infra/prometheus/**`、`infra/grafana/provisioning/**`、`infra/otel/**`。

### 7.1 Prometheus：配置只在启动时读

```bash
# 标准做法：重建容器（最省事、语义最清楚）
docker compose -f docker-compose.yml --project-directory . up -d --force-recreate prometheus

# 备选：热重载（不重启进程；compose 里已开 --web.enable-lifecycle）
curl -X POST http://localhost:9090/-/reload
```

> ⚠️ **生产用的是 `infra/prometheus/prometheus.prod.yml`**，不是开发那份
> `prometheus.yml`。两份的差别只有 scrape 地址口径：
>
> | 文件 | 业务在哪 | target 写什么 |
> |---|---|---|
> | `prometheus.yml`（dev 栈） | Windows 开发机的 uv 进程 | Windows 在 VMware 网段的**网卡 IP**（写死，实测 `192.168.1.13:8000`） |
> | `prometheus.prod.yml`（本文件） | 同栈的 `api` 容器 | **服务名 `api:8000`** |
>
> 改错了不会报错，只会 target 永久 down。判据见 §7.2 第 ② 条。

> ⚠️ `docker compose restart prometheus` 也能让新配置生效（它重启即重读配置文件），
> 但它**绕过了 compose 的变更检测**：如果这次改动同时动了 YAML 里的字段
> （换了镜像 tag、改了端口/挂载、加了环境变量），`restart` 一概看不见。
> 所以「只改配置内容」两种都行，**「改了 YAML」一律用 `up -d --force-recreate`**。

### 7.2 三个「配置真的生效了吗」的证据（不能只看 healthy）

`healthy` 只证明「进程活着 + 探针通了」，**不证明配置对**。下面三条才证明配置进了容器：

```bash
# ① 容器里看到的确实是仓库里的新文件
docker compose -f docker-compose.yml --project-directory . exec prometheus \
  sh -c 'ls -l /etc/prometheus/ /etc/prometheus/rules/; head -5 /etc/prometheus/prometheus.yml'

# ② Prometheus：配置没被拒 + 规则真的加载了 + 目标在抓
docker compose -f docker-compose.yml --project-directory . exec prometheus \
  promtool check config /etc/prometheus/prometheus.yml

curl -s http://localhost:9090/api/v1/targets | grep -o '"health":"[a-z]*"' | sort | uniq -c
# 期望：prometheus 与 shopsage-api 两个 job 都是 up

curl -s 'http://localhost:9090/api/v1/rules?type=record' | grep -o '"name":"shopsage:[a-z0-9_]*"' | sort -u
# 期望：能看到 shopsage:agent_p99_5m 等记录规则（0 条 = rule_files 没挂上/写错）

# ③ Grafana：数据源与看板是 provisioned 进来的（不是手点的）
curl -s -u admin:<GF_SECURITY_ADMIN_PASSWORD> http://localhost:3001/api/datasources | grep -o '"uid":"[^"]*"' | sort -u
# 期望：包含 "uid":"prometheus"   ← 少了它 = 看板全部面板 "Datasource not found"
curl -s -u admin:<GF_SECURITY_ADMIN_PASSWORD> 'http://localhost:3001/api/search?type=dash-db' | grep -o '"title":"[^"]*"'
# 期望：能看到「ShopSage · 可观测性（第 11 步）」
```

> ⚠️ **只看 `uniq -c` 是不够的**：它只说「有几个 up」，不说**是哪一个** down、也不说**为什么**。
> 一个 up 一个 down 时务必看 `scrapeUrl` 和 `lastError`：
>
> ```bash
> curl -s 'http://localhost:9090/api/v1/targets?state=any' \
> | python3 -c 'import json,sys
> for t in json.load(sys.stdin)["data"]["activeTargets"]:
>     print(f"{t[\"labels\"][\"job\"]:<14} {t[\"health\"]:<5} {t[\"scrapeUrl\"]}")
>     if t.get("lastError"): print(f"    lastError: {t[\"lastError\"]}")'
> ```

### 7.3 Grafana：provisioning 会自动应用

数据源与看板由 `infra/grafana/provisioning/**` 声明，Grafana 起来时应用。provider 的实际配置
（`infra/grafana/provisioning/dashboards/shopsage.yml`）是
`allowUiUpdates: true` / `disableDeletion: false` / `updateIntervalSeconds: 30`，于是：

- **改看板 JSON → 最多 30 秒自动同步**，通常**不用重启**；
- **重命名 / 增删看板文件** → 直接重建容器最干脆（不必等轮询）：

```bash
docker compose -f docker-compose.yml --project-directory . up -d --force-recreate grafana
```

> ⚠️ **删掉看板文件 ≠ Grafana 里看板消失**：`disableDeletion: false` 只表示「允许从 UI 删」，
> 文件消失时 Grafana **不会**帮你删掉已 provision 的看板 —— 它留在库里、只是不再被同步。
> 症状是「旧看板一直在、改了名字也没用」。要么在 UI 里手动删，要么 `down -v` 重置（⚠️ 会删数据）。
> 反过来，`allowUiUpdates: true` 意味着**你会被 UI 上的临时改动骗到**：它不写回文件，
> 而文件一旦变动（30s 内轮询到）就会把 UI 上的改动盖掉。想固化就改 JSON。
>
> ⚠️ 看板 JSON 必须位于 `provisioning/dashboards/` **之内**：provider 的 `path`
> 就是 `/etc/grafana/provisioning/dashboards` 这个容器内路径。
> 放到别处（例如另起 `infra/grafana/dashboards/`）不会报错，只会**静默挂成空目录** → 「数据源在、看板不见了」。

### 7.4 OTel Collector：默认不启动

```bash
# 起它（profile 一开，之后所有 up -d 都会带上它）
docker compose -f docker-compose.yml --project-directory . --profile tracing up -d otel-collector
# 改了 otel-collector.yml 之后
docker compose -f docker-compose.yml --project-directory . --profile tracing up -d --force-recreate otel-collector
# 验证：看它有没有在收 span（业务侧 OTEL_ENDPOINT 必须指向 4318 才会发）
docker compose -f docker-compose.yml --project-directory . exec otel-collector tail -n 20 /data/traces.jsonl
```

> ⚠️ **`env.list` 里 `OTEL_ENDPOINT` 默认是注释掉的**，因为 collector 是 profile 门控的。
> 配了地址却没起 collector 时，业务侧 `BatchSpanProcessor` 会不断重试连接
> （只打日志、不阻塞请求，但日志变吵）。要么两边都配，要么两边都别配。
>
> ⚠️ 端口：**4318 = OTLP/HTTP**（业务用的是这条），4317 = gRPC。
> 写成 4317 不会报错，只是 **trace 一条都不到**（`app/observability/tracing.py` 会打成启动期 WARNING）。

## 8. 场景 D：构建、镜像与回滚

### 8.1 镜像标签策略（回滚开关）

```bash
SHA=$(git rev-parse --short HEAD)     # 下文用 SHA 当 tag，比 latest 多一条信息
docker build -f app/Dockerfile -t "shopsage-api:$SHA" -t shopsage-api:latest .
```

- `shopsage-api:latest` 是**部署用**的（`docker-compose.yml` 的默认 `IMAGE_TAG`）；
- `shopsage-api:$SHA` 是**可追溯 + 可回滚**的（`IMAGE_TAG` 环境变量就吃它）。

> ⚠️ **`IMAGE_TAG` 是 compose 插值变量，读的是仓库根 `.env` 或命令前缀**，不是 `env.list`：
>
> ```bash
> # 两种写法等价，选一种并保持一致
> IMAGE_TAG="$SHA" docker compose -f docker-compose.yml --project-directory . up -d
> # 或者写进仓库根 .env（见 §5.1：`.env` 只该放部署拓扑参数）
> echo "IMAGE_TAG=$SHA" >> .env
> ```
>
> 不设它时一律用 `latest` —— 于是「现在跑的是哪个提交」这个问题就答不上来了。
> 查当前容器用的镜像 ID：`... ps -q api | xargs docker inspect --format '{{.Config.Image}}'`。

生产上更常见的形态是「在 CI 的 Linux runner 构建 → push registry → 服务器 pull」：

```bash
# CI runner
docker build -f app/Dockerfile -t registry.example.com/shopsage-api:$SHA .
docker push registry.example.com/shopsage-api:$SHA

# 服务器（不构建，只拉；compose 里把 build: 去掉、image 指向 registry 即可）
docker pull registry.example.com/shopsage-api:$SHA
docker tag registry.example.com/shopsage-api:$SHA shopsage-api:latest
docker compose -f docker-compose.yml --project-directory . up -d --pull always api worker
```

### 8.2 构建快的条件（为什么第一次慢、后面快）

`app/Dockerfile` 分了三层缓存：

1. 基础镜像层（`python:3.12-slim`）；
2. `uv` 二进制层；
3. **依赖层** —— 只由 `pyproject.toml` + `uv.lock` 决定（`COPY` 在 `uv sync` **之前**）。

于是「只改 `.py`」时依赖层命中缓存，重建几十秒内结束；改了 `uv.lock` 才重装依赖（分钟级）。

```bash
# 想强制不用任何缓存重建（排查「缓存里塞了旧代码」时用）
docker compose -f docker-compose.yml --project-directory . build --no-cache api

# 想先拉一次基础镜像拿补丁版
docker compose -f docker-compose.yml --project-directory . build --pull api
```

> ⚠️ **`--no-cache` 不该是日常操作**：动辄十几分钟，而且会掩盖「为什么缓存没命中」这个真问题。

### 8.3 镜像卫生（四个必查项）

```bash
# ① 没有密钥（history 里能看到命令与 ENV；本文件不写任何 ENV 密钥）
docker history "shopsage-api:${IMAGE_TAG}" | head -20

# ② 没有 .env / env.list（.dockerignore 排除；漏掉的后果是密钥固化进镜像层）
docker run --rm --entrypoint sh shopsage-api:latest -c 'ls -a /app | grep -E "\.env|env\.list" || echo "✅ 无密钥文件"'

# ③ 不是 root 运行
docker run --rm shopsage-api:latest id        # 期望 uid=10001(shopsage)

# ④ 体积（api 约 1.5–2.5 GB 含 torch；不含 torch 时约 400 MB）
docker images | grep shopsage
```

### 8.4 回滚

```bash
# 镜像还在，改回旧 tag 再 up 即可（比 git revert + 重新构建快得多）
docker tag "shopsage-api:<旧SHA>" shopsage-api:latest
IMAGE_TAG=<旧SHA> docker compose -f docker-compose.yml --project-directory . up -d --force-recreate api worker

# ⚠️ 数据库迁移【不会】跟着回滚：alembic upgrade head 是单向的。
#    破坏性迁移（删列/改类型）必须自己准备 downgrade 或数据备份，见 3.db-runbook.md §3。
```

## 10. 故障速查（按「症状 → 原因 → 修法」）

### 10.1 起不来 / 起来但不可用

| 症状 | 最可能的原因 | 怎么确认 | 修法 |
|---|---|---|---|
| `up -d` 报 `service "xxx" has neither an image nor a build context` | compose 文件里那个服务既没 `image:` 也没 `build:` | `... config \| grep -A3 'xxx:'` | 补上；本仓的 api/worker/migrate 共用 `x-app-base` 锚点 |
| `api` 反复重启，日志 `ENV=prod 缺少必填配置: database_url, llm_api_key` | `env.list` 没被读到（文件不存在 / 名字不对 / 内容格式错） | `... exec api env \| grep DATABASE_URL` 看有没有 | 确认 `env.list` 在仓库根、`docker compose config` 里能看到 `env_file` 指向它 |
| `api` 反复重启，`password authentication failed for user "shopuser"` | 口令与库不一致（改了 `POSTGRES_PASSWORD` 但卷已存在） | `... logs api \| grep -i auth` | §6.2：进库 `ALTER USER`，并同步 `DATABASE_URL` |
| `api` 起不来，`ENV=prod 未配置 JWT_SECRET` | `env.list` 缺 `JWT_SECRET` 或短于 16 字符 | `... logs api \| grep JWT` | `openssl rand -hex 32` 填进去，`up -d --force-recreate api` |
| `migrate` 退出码非 0 | 迁移脚本错 / 库版本比 head 新 / 连接串错 | `... logs migrate \| tail -30` | 按报错改；⚠️ **不要**先起 api 绕过 |
| `port is already allocated` | 宿主端口被占 | `ss -lntp \| grep -E '8000\|3000\|9090\|3001'` | 改 `.env` 的 `API_PORT`/`WEB_PORT`/…（§6.4） |
| 容器起来了但 `curl localhost:8000` 不通 | 端口没映射 / 进程绑了 127.0.0.1 | `... ps`；`... exec api ss -lntp` | CMD 里必须是 `--host 0.0.0.0`（本仓已如此） |
| `page cannot be reached` 但 web 容器 healthy | `PORT`/`HOSTNAME` 不对（standalone server 读它们） | `... logs web` | compose 里已设 `PORT=3000`、`HOSTNAME=0.0.0.0` |

### 10.2 页面能用但功能坏

| 症状 | 最可能的原因 | 怎么确认 | 修法 |
|---|---|---|---|
| 页面打开，控制台 `Failed to fetch`（**没有状态码**） | ① 跨源被浏览器拦；② 后端地址写错；③ 服务没起 | 看 `API_CORS_ORIGINS` 是否包含**地址栏里那个 origin** | 补上（含协议/端口，`localhost` 与 `127.0.0.1` 算两个）；`up -d --force-recreate api` |
| 页面能用 HTTP 但**流式一定失败** | `NEXT_PUBLIC_API_BASE` 指到了页面自己（同源）；Next 不代理 WS upgrade | 页面上会有黄条提示（`web/src/lib/config.ts` 的自动纠正） | 重新 build web 并把 base 指到后端（§5.2） |
| 改了 `NEXT_PUBLIC_API_BASE` 但页面没变 | 它是**构建期**变量 | `exec web sh -c 'grep -rho "http://[^ \"]*:8000" /app/.next/static \| sort -u'` | `up -d --build web`（重启无效） |
| 登录 401 且确认口令正确 | 库里的账号口令是旧散列/账号被停用 | `... exec api python -m scripts.demo_accounts` 或查 `accounts` 表 | 重灌演示账号（`scripts.seed`）或按 `4.security-runbook.md` 处理 |
| 回答总是「没有依据」/ 检索不到 | 语料没灌；或 `EMBEDDING_BACKEND=local` 但镜像没装依赖 | `... run --rm api python -m scripts.load_knowledge_base --dry-run`；`exec api python -c "import sentence_transformers"` | 灌语料；或按 §6.3 重建镜像 |
| `/api/kb` 返回空列表 / 404 | 前端镜像里没有 `docs/kb`（Dockerfile 的 `COPY docs/kb /docs/kb` 漏了，或 workdir 变了） | `... exec web ls /docs/kb` | 修 `web/Dockerfile`（workdir `/app` → 必须放在 `/docs/kb`），重建 web |
| 修改后行为没变 | ① 改的是另一份文件副本；② 该服务没被重建；③ bind mount 路径不对（挂的是空目录） | `... exec <svc> cat <容器内路径>` 看内容对不对 | `up -d --force-recreate <svc>`；路径核对见 `2.infra-runbook.md` 坑 2 |

### 10.3 监控栈

| 症状 | 最可能的原因 | 怎么确认 | 修法 |
|---|---|---|---|
| Prometheus 起不来，日志只提 `rule_files` | `/etc/prometheus/rules` 没挂进容器 | `... exec prometheus ls /etc/prometheus/rules` | 补上 `./infra/prometheus/rules:/etc/prometheus/rules:ro`（**少了它 Prometheus 是启动失败，不是警告**） |
| Prometheus 起来了，规则查询 0 条 | 规则文件 YAML 写错或路径不对 | `... exec prometheus promtool check rules /etc/prometheus/rules/shopsage.yml` | 按报错改 rules；再 `--force-recreate prometheus` |
| target down，`lastError` 是 `no such host` | 生产用了开发那份 `prometheus.yml`（target 是 Windows IP） | `... exec prometheus grep -n 'targets: \[' /etc/prometheus/prometheus.yml` | 生产必须挂 `prometheus.prod.yml`（target = `api:8000`） |
| target down，`refused` 秒回 | target 写了 `localhost`（那是容器自己） | 同上 | 改成服务名 `api:8000` |
| `scrapeUrl` 里出现 `%7B`/`%7D` | `targets` 里写了 `${VAR}` —— **Prometheus 2.x 不替换它** | 同上 | 把地址写死或换 `prometheus.prod.yml`；`scripts/check_infra.py` 会把这类写法判为错误 |
| Grafana 没有数据源 | 挂载路径少了 `infra/` → **静默挂空目录，不报错** | `... logs grafana \| grep -i provision` | 修路径；`up -d --force-recreate grafana` |
| 看板全部面板 "Datasource not found"，数据源却在列表里 | 数据源没钉 `uid`（看板 JSON 里写的是 `uid: prometheus`） | `curl -u admin:... http://localhost:3001/api/datasources \| grep uid` | 数据源文件里补 `uid: prometheus`；重建 grafana |
| 看板消失了（数据源还在） | 看板 JSON 不在 provider 的 `path` 之内 → 静默空目录 | `... exec grafana ls /etc/grafana/provisioning/dashboards/` | 把 JSON 放回 `infra/grafana/provisioning/dashboards/` |
| 删掉看板文件后旧看板还在 | Grafana **不会**因文件消失而删除已 provision 的看板 | Grafana UI 里搜旧标题 | 手动在 UI 删除；或 `down -v` 重置（⚠️ 删数据） |
| otel-collector 起不来 / 业务日志一直重试连接 | collector 在 `tracing` profile 里，不 `--profile` 就不起 | `... ps` 里有没有它 | `--profile tracing up -d otel-collector`；或把 `OTEL_ENDPOINT` 注释掉 |
| trace 一条都不到 | `OTEL_ENDPOINT` 写成了 4317（gRPC）或缺 `/v1/traces` | `... logs api \| grep -i otel` | 用 `http://otel-collector:4318`（代码会自动补 `/v1/traces`） |

### 10.4 构建与依赖

| 症状 | 最可能的原因 | 怎么确认 | 修法 |
|---|---|---|---|
| 改了依赖（`pyproject.toml`/`uv.lock`）但镜像里没变 | 只重启了容器，没重建镜像；或 Docker 命中了依赖层缓存而 lock 没被复制进去 | `... run --rm --entrypoint python api -c "import <包名>, sys; print(<包名>.__version__, sys.executable)"` | `up -d --build`；确认 Dockerfile 里 `COPY pyproject.toml uv.lock ./` 在 `uv sync` **之前** |
| `uv sync --locked` 在镜像里失败 | `uv.lock` 与 `pyproject.toml` 不一致（本地改了依赖没提交 lock） | 报错会点名 lock 过期 | 本地 `uv lock` → 提交 `uv.lock` → 重新构建（**这正是 `--locked` 想要的失败**） |
| 构建报 `/bin/sh^M: bad interpreter` 之类 | 提交时被 CRLF 污染（Windows 开发） | `file app/Dockerfile` / `git ls-files --eol app/Dockerfile` | 加 `.gitattributes`（`*.sh text eol=lf`、`Dockerfile text eol=lf`）后重新检出 |
| 构建上下文巨大、构建很慢 | `.dockerignore` 没排除 `.venv/` `.git/` `.hf-cache/` | `docker build` 第一步的 "transferring context" 体积 | 补 `.dockerignore`（本仓已有，见文件注释） |
| `COPY docs/kb` 报 `not found` | `.dockerignore` 里用了「先全排 `docs/*`、再放行 `!docs/kb`」的写法 | `docker build --no-cache` 的报错行 | 改成逐条排除 `docs/runbook/` 等（本仓已如此） |
| `web` 构建在 `COPY .next/standalone` 失败 | `next.config.ts` 缺 `output: "standalone"` | `web/next.config.ts` 里搜 `standalone` | 加回来（本仓已加） |
| `web` 构建 `npm ci` 失败 | `package-lock.json` 与 `package.json` 不一致 | 报错会点名 | 本地 `npm install` 后提交 `package-lock.json`；**不要**在 Dockerfile 里改成 `npm install` |
| `ModuleNotFoundError: sentence_transformers` | 构建时没给 `WITH_LOCAL_EMBEDDING=true`，但 `EMBEDDING_BACKEND=local` | §6.3 的 `import` 检查 | 带 build arg 重建（§3.4） |
| `PermissionError: ... /.cache` 或 HF 下载失败 | `HF_HOME` 不可写（容器内不是 10001 属主），或无出网 | `... exec api ls -ld /app/.hf-cache` | 确认 `hf_cache` 卷挂着、属主是 `shopsage`（Dockerfile 已 chown） |

### 10.5 通用排查入口

```bash
# 所有服务的状态 + 退出码
docker compose -f docker-compose.yml --project-directory . ps -a

# 一个服务的最近日志（先看这个，别猜）
docker compose -f docker-compose.yml --project-directory . logs --tail=100 --no-log-prefix api

# 事件流（OOM、healthcheck 失败、反复重启都在这里）
docker events --filter 'label=com.docker.compose.project=shopsage' --since 10m

# 容器里手动跑一条命令（不要 ssh 进容器，用 exec）
docker compose -f docker-compose.yml --project-directory . exec api python -c "from app.config import get_settings; print(get_settings().env)"
```

## 11. 记住这十二条（面试/复述用）

1. **`docker compose restart` ≠ 应用新配置**：它只 stop/start 已有容器，不重新解析 YAML、不重读 `env.list`。
   改配置一律 `up -d`；要连字段变更一起吃掉就 `--force-recreate`。
2. **`up -d` 是声明式的、`restart` 不是**：`up` 会把「compose 描述期望状态」和实际状态对齐
   （多出来的容器删掉、变了的重建），这才是「重建」的正确入口。
3. **重建镜像/重建容器从来不删数据卷**：数据丢只发生在 `down -v`。所以「我要重建」时**别顺手加 `-v`**。
4. **环境变量分三份文件，各喂各的**：`env.list` → 容器进程；`.env` → compose 插值 + 开发机进程；
   `*.example` → 给人复制。混用的症状是「容器 healthy、配置全是默认值」。
5. **`NEXT_PUBLIC_*` 是构建期变量**：改它必须重新 build。容器化 Next 的头号坑，且**不会报错**。
6. **迁移单独一个服务，不放在 api 的 CMD 里**：多副本会抢锁；而且迁移失败应该**阻断发布**
   （`depends_on: service_completed_successfully` 正是这个语义）。
7. **镜像标签就是回滚开关**：用 `git SHA` 打 tag，回滚是 `docker tag` + `up -d`，
   比 `git revert` + 重新构建快得多。但**数据库迁移不回滚**。
8. **bind mount 的「源不存在」在 Docker 里是静默失败**：不会报「文件不存在」，而是**建个空目录挂上去**
   —— 于是 Prometheus 报 `not a directory`、Grafana 报「没有数据源」，根因都在 compose 的相对路径
   （相对路径按 `--project-directory` 解析，写全 `-f ... --project-directory .`）。
9. **配置进容器 ≠ 配置生效**：`healthy` 只说明进程活着。真正的证据是
   `promtool check config`、`/api/v1/rules` 里有你写的规则、`/api/v1/targets` 是 up。
10. **`${VAR}` 不是「到处都能用」的语法**：compose 只替换 **compose 文件**；挂进容器的 YAML 由
    **容器里的程序自己**决定要不要替换 —— **Prometheus 2.x 只替换 `external_labels`**，
    `static_configs` 里的 `${...}` 既不替换也不报错。判据永远是「**进容器里看它真正读到的值**」。
11. **`--workers N` 会让指标失真**：prometheus_client 是进程内的，N 个 worker 共享端口时
    每次抓取由随机一个应答 → 计数在 N 份之间跳变 → 记录规则静默低估。
    横向扩容的正确做法是**多起容器**，不是调 `--workers`（除非先上 multiprocess 模式）。
    ⚠️ 但要多副本得先删 compose 里 api 的 `container_name`（否则名字冲突），见 §6.6。
12. **同一镜像多角色优于多镜像**：api/worker/migrate 共用一个镜像，
    保证「入队用的任务名」与「消费用的实现」是同一份代码（分开构建必出「worker 还是旧版」）。
