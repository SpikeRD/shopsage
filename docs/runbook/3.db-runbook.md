## 2. 写 `app/db/`：连接、会话、池

### 2.1 连接串方言：装了哪个驱动，URL 就写哪个（最容易翻车的一处）

`DATABASE_URL`（`.env`）与「SQLAlchemy 用的 URL」可以不同，因为纯 `psycopg.connect()` 不认识 SQLAlchemy 方言：

| 驱动 / 用途 | URL 形式 | 谁吃它 |
|---|---|---|
| libpq 原生（psycopg3、psql、DBeaver） | `postgresql://user:pw@host:5432/db` | `psycopg.connect()`、`psql` |
| SQLAlchemy 2.x + psycopg3（**本仓选定**） | `postgresql+psycopg://user:pw@host:5432/db` | `create_engine()` |
| SQLAlchemy 2.x + psycopg2 | `postgresql+psycopg2://...` | `create_engine()` |
| SQLAlchemy 2.x + asyncpg（异步方案） | `postgresql+asyncpg://...` | `create_async_engine()` |

**结论**：`.env` 里保持不带方言的 `postgresql://...`（psql/探活能用），在 `session.py` 里由代码补方言，例如：

```python
url = settings.database_url.replace("postgresql://", "postgresql+psycopg://", 1)
```

> ✅ **本机实测（可复现）**：`sqlalchemy.engine.make_url("postgresql://u:p@h:5432/db").get_dialect().driver`
> 返回 **`psycopg2`** —— 也就是说**光写 `postgresql://` 默认走 psycopg2**。所以「`.env` 里的串直接喂给
> `create_engine()`」在只装了 psycopg3 的环境里必然报错：实测报 `ModuleNotFoundError: No module named 'psycopg2'`。
> 方言写对之后，实测 `engine.dialect.name/driver` = `postgresql/psycopg`、`engine.dialect.dbapi.__name__` = `psycopg`，
> 池类型是 `QueuePool`、`pool.size()` = 5、`pool._max_overflow` = 10 —— 即下面 §2.3 的参数确实生效。

报错长这样就是写错了：`ModuleNotFoundError: No module named 'psycopg2'`（URL 是 `+psycopg2` 而依赖里只有 psycopg3，
**或者你给的是不带方言的裸 `postgresql://`**）、`Can't load plugin: sqlalchemy.dialects:postgresql.psycopg2`。

> [`3.db.md`](../modules/3.db.md) 第 3 节写的是「`psycopg`（异步驱动，可选 `asyncpg`）」—— 本手册按**同步**路径给流程
> （`create_engine` / `SessionLocal` / `get_db`，与该文档第 2 节的对外接口一致）。
> 以后要走异步（FastAPI 全异步）：把 `create_engine` 换成 `create_async_engine` + `AsyncSession`，
> 此时 **URL 必须** `postgresql+asyncpg://`（或 `postgresql+psycopg://` 的 async 变体），池参数与 `get_db` 写法一并要改。

### 2.3 `session.py`：池参数 + 读写两个入口

```python
# app/db/session.py（骨架，按需调整；关键是池参数与两个入口都在这里）
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

from app.config import get_settings

_settings = get_settings()


def _url(url: str) -> str:
    """给 SQLAlchemy 补上方言；已带方言时原样返回。"""
    return url.replace("postgresql://", "postgresql+psycopg://", 1)


def _make_engine(url: str):
    return create_engine(
        url,
        # 池：显式设上限（C1：连接不被打爆）
        pool_size=5,          # 常驻连接数 ≈ 每个 worker 的并发 SQL 数
        max_overflow=10,      # 峰值临时额度；超了会阻塞到 pool_timeout 再抛错
        pool_timeout=30,      # 借不到连接时最多等多久（秒）
        pool_recycle=1800,    # 连接最长寿命（秒），防中间设备静默断连
        pool_pre_ping=True,   # 借出前先 ping，踢掉死连接（见 3.db.md §5）
        echo=False,           # 排障时临时 True，看真实 SQL
        connect_args={"options": "-c TimeZone=UTC"},
    )


# 读写分离是「能力」，不是「必须一开始就上」（3.db.md §4 第 2 条）：
# 现在两者可以指向同一个库；负载上来后只需改只读那条的 URL（或挂只读副本）即可切换。
_write_url = _url(_settings.database_url)
_read_url = _url(getattr(_settings, "database_read_url", "") or _settings.database_url)

engine = _make_engine(_write_url)          # 兼容 3.db.md 的 `from app.db.session import engine`
_read_engine = _make_engine(_read_url)     # 读路径引擎（见下）
_session_factory = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)
SessionLocal = _session_factory            # 兼容 `SessionLocal`


def get_write_engine():
    """写路径引擎（工单/退款等预定义 service，不经 LLM 动态 SQL）。"""
    return engine


def get_read_engine():
    """读路径引擎（Text-to-SQL 只读白名单走这里）。"""
    return _read_engine


def get_db():
    """FastAPI 依赖：每请求一个会话，用完必还。"""
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

> `autoflush=False` 是 FastAPI 场景的常见选择：避免查询前隐式 flush 造成意外写库。
> `_read_engine` / `engine` 用的是同一套 `_make_engine` 参数（读路径的池可以更小、写路径更小也行，看压测再调）。
> 注意 `connect_args={"options": "-c TimeZone=UTC"}` 是**会话级**设置（只影响本连接），
> 与库的 `timezone` 参数是两回事；本仓种子数据都是 UTC 存储，跨时区展示在第 16 步（web）做转换。

**怎么估池参数**（`3.db.md` §5）：

- `pool_size ≈ 每 worker 的并发 SQL 数`；`max_overflow` 是峰值临时额度，**真实上限 = `pool_size + max_overflow`**。
- 4 个 uvicorn worker × (5 + 10) = 60 个连接 —— 还要核对 Linux VM 上 PostgreSQL 的 `max_connections`（默认 100）
  与**其它客户端**（psql、DBeaver、第 16 步的 Web、第 12 步的队列 worker）共同占用，别一把梭。
- 池太小：请求在 `pool_timeout` 后抛 `TimeoutError: QueuePool limit of size 5 overflow 10 reached`；
  池太大：把库的连接数/内存打爆。**宁可排队，不要把库拖垮。**

改两处，**不要把连接串写进 `alembic.ini`**（那是把密码抄第二遍，必然漂移、也容易误提交）：

```python

import app.db.models  # noqa: F401  ← 必须 import，否则 target_metadata 里没有表，autogenerate 会生成空迁移

config.set_main_option("sqlalchemy.url", get_settings().database_url.replace("postgresql://", "postgresql+psycopg://", 1))
target_metadata = Base.metadata
```

```ini
# alembic.ini：把原来的 sqlalchemy.url 那行清空/注释掉，避免两处真相
# sqlalchemy.url =
```

> `alembic.ini` 里默认的 `sqlalchemy.url = driver://user:pass@localhost/dbname` 是**占位符**，
> 不改它会得到 `ModuleNotFoundError: No module named 'driver'` —— 这是新手最常撞的一条。

### 3.2 生成首版迁移

```powershell
uv run alembic revision --autogenerate -m "init business tables"
# 期望：alembic/versions/<hash>_init_business_tables.py 生成，输出里列出 8 张表的 create_table
# ⚠️ 一定要打开这个文件看一眼：autogenerate 只懂「模型有、库里没有」的差异，
#    索引/约束/服务端默认值/命名约定 都可能漏，漏了就手工补。
```

自检（第 3 步验收「迁移可重复执行」的一半）：

```powershell
uv run alembic current     # 期望：空（还没 upgrade）或当前 revision
uv run alembic history     # 期望：线性历史，只有一条 <base> -> <hash>
```

## 5. 行级过滤与只读视图（D1 的数据库兜底）

`3.db.md` §4 第 3 条把「对客路径不会越权」的实现钉在 **SQL 层**（`WHERE user_id = :当前用户`），
不是应用层 `if` 过滤。第 4 步（`4.security.md`）的白名单表名也来自这里的 schema，所以本步要把「对客查询封装」做出来：

```python
# app/db/queries.py（骨架）
from sqlalchemy import select

from app.db.models import Order
from app.db.session import get_read_engine


def get_orders_for_customer(user_id: int, limit: int = 50):
    """对客订单查询：行级过滤 + 强制 LIMIT，走只读引擎。"""
    stmt = (
        select(Order)
        .where(Order.user_id == user_id)   # ← 行级过滤，永远带
        .order_by(Order.created_at.desc())
        .limit(limit)                       # ← 结果行数截断（C1）
    )
    with get_read_engine().connect() as conn:      # 只读引擎 → 不落写库
        return conn.execute(stmt).all()
```

### 5.1 越权自测（D1 的最小证据，本机可跑）

```powershell

"@
# 期望：OK: 行级过滤生效（...）
```

### 5.3 只读视图（可选加固，与「只读白名单」配套）

对客路径**只通过视图/只读角色**取数，可以从数据库层再兜一层（应用写错也越不出去）：

```sql
-- 在迁移里建视图与只读角色（示意；是否落地按 4.security.md 的设计定）
CREATE OR REPLACE VIEW v_customer_orders AS
  SELECT order_id, user_id, status, total_amount, created_at FROM orders;

-- 只读角色：只给 SELECT，且只给视图与允许的表
CREATE ROLE shopsage_readonly LOGIN PASSWORD '<只读口令>';
GRANT SELECT ON v_customer_orders TO shopsage_readonly;
-- 注意：默认 public schema 在新版 PostgreSQL 已收紧，但历史库要显式 REVOKE 掉不需要的授权
```

> 取舍：视图+只读角色是**纵深防御**（D1 的第二道闸），但会让「行级过滤」出现两个落点
> （视图里写死 `WHERE user_id = current_setting('app.user_id')` 或由应用参数化）。
> 本项目第 3 步**默认只做应用层封装里的行级过滤**，视图按需加 —— 加的话要让 SQL 里的过滤**只有一处真相**，
> 否则「视图已过滤」和「应用忘了过滤」两个假设会互相掩护。

## 6. 连接池上限验证（C1，本机可跑的简化版）

`3.db.md` §7 的 `test_pool_limits_connections`：高并发下连接数不超过 `pool_size + max_overflow`。

```python
# tests/test_db_pool.py
# 需要真库（Linux VM 可达）—— 池上限是「和数据库之间的连接数」，没有库就无从观测。
import concurrent.futures as cf
import threading

from sqlalchemy import text

from app.db.session import engine


def test_pool_never_checks_out_more_than_capacity():
    """并发借连接：**同时借出**的连接数不超过 pool_size + max_overflow，且用完都还回池。"""
    cap = engine.pool.size() + engine.pool._max_overflow   # 真实上限 = 5 + 10 = 15
    lock = threading.Lock()
    peak = 0

    def hold() -> None:
        nonlocal peak
        with engine.connect() as conn:            # 借出 → 持有 → 自动还回
            conn.execute(text("select 1"))
            with lock:
                peak = max(peak, engine.pool.checkedout())

    with cf.ThreadPoolExecutor(max_workers=cap * 3) as ex:   # 45 个并发去抢 15 个连接
        for f in [ex.submit(hold) for _ in range(cap * 3)]:
            f.result()                            # 借不到时会等 pool_timeout，超时才抛 TimeoutError

    assert peak <= cap, f"连接借出峰值 {peak} 超过池上限 {cap}"
    assert engine.pool.checkedout() == 0, "有连接没还回池 —— 典型 session/connection 泄漏"
```

> 想看到池真的「拦住」而不是碰巧没超，把 `max_workers` 拉到 `cap * 3` 并观察 `peak` 恰好顶到 `cap`；
> 若要复现**排队超时**，临时把 `pool_size=1, max_overflow=0, pool_timeout=1` 再跑，
> 期望 `sqlalchemy.exc.TimeoutError: QueuePool limit of size 1 overflow 0 reached`。

```bash
# ── 执行位置：VMware-Linux（能直接数连接，最直接的 C1 证据）──
# 一边在 Windows 侧跑上面的并发用例（或压测脚本），一边在这里数：
docker compose -f infra/docker-compose.dev.yml --project-directory . \
  exec postgres psql -U shopuser -d shopsage -c \
  "SELECT usename, COALESCE(client_addr::text,'local') AS client, count(*) FROM pg_stat_activity
   WHERE datname='shopsage' GROUP BY 1,2 ORDER BY 3 DESC;"
# 期望：Windows 侧应用那一条的 count <= pool_size + max_overflow（每个进程各自一套池）
#       还能看到「谁连过来的」（client_addr 是 Windows 侧经 VMware NAT 过来的源地址）
```

**证据怎么算过**（`3.db.md` 第 8 节第二条验收）：

| 观察 | 结论 |
|---|---|
| 并发下 `count(连接)` 稳定 ≤ 池上限，且请求全部成功 | ✅ 池上限生效 |
| 出现 `TimeoutError: QueuePool limit ... reached` | 池太小或**有 session 泄漏**（`get_db` 没 `close`）→ 先查泄漏再加池 |
| 连接数超过上限且持续上涨 | 有人在 `create_engine` 之外自己 `psycopg.connect()` 裸连，没走池 → 收口到 `app/db/session.py` |
| 压测后连接数不回落 | 泄漏；用 `checkedout() == 0` 用例兜住 |

> 真正的压测（QPS / P99 / 库 CPU）属第 6 步（`6.tools.md`）与第 12 步（`11.observability.md`）的活；
> 第 3 步只要证明「池有上限、连接不泄漏」即可，别在这里堆压测报告。

| 症状 | 最可能的原因 | 怎么确认 | 修法 |

## 9. 记住这七个坑（面试/复述用）

1. **`POSTGRES_*` 与 `DATABASE_URL` 是两套消费者**（compose 初始化 vs 应用连接），必须同步改；
   而且 `POSTGRES_*` **只在数据卷为空时生效一次** —— 「改了密码不生效」几乎都是这条。
2. **URL 方言与驱动必须配对**：`postgresql://` 给 psql/psycopg 原生，`postgresql+psycopg://` 给 SQLAlchemy；
   写错的表现是 `ModuleNotFoundError: No module named 'psycopg2'`，而不是「连不上库」——
   因为裸 `postgresql://` 在 SQLAlchemy 里的默认驱动就是 psycopg2（本机实测）。
3. **连接池必须有上限**：真实上限 = `pool_size + max_overflow`；池太小排队超时、池太大拖垮库，
   跨主机还要乘以 worker 数并核对库的 `max_connections`。
4. **`pool_pre_ping=True` 是跨主机场景的刚需**：VMware NAT/中间设备会静默丢掉空闲连接，
   没有 pre-ping 就会「从池里拿到死连接」报 `server closed the connection unexpectedly`。
5. **行级过滤必须在 SQL 层**（`WHERE user_id = :me`）而非应用层 `if`：应用层过滤＝先查全表再截断，
   既慢又可能在中间环节泄露。验证要看**数据库侧**（`pg_stat_statements`），不能只看代码。
6. **迁移要能双向跑**：`upgrade`/`downgrade` 都可重复执行才算过；`env.py` 忘了 import 模型 =
   静默生成空迁移；禁止 `create_all()` 与 Alembic 混用（会打架出 `already exists`）。
7. **`downgrade base` 会连数据一起删**：种子数据灌完后再回滚，演示环境就空了 ——
   重来要「回滚 → 升级 → 重跑种子」三步走，别用 `DROP SCHEMA` 一把梭。
