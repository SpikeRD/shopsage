## 2. 写 `app/db/`：连接、会话、池

### 2.1 连接串方言：装了哪个驱动，URL 就写哪个（最容易翻车的一处）

`DATABASE_URL`（`.env`）与「SQLAlchemy 用的 URL」可以不同，因为纯 `psycopg.connect()` 不认识 SQLAlchemy 方言：

| 驱动 / 用途 | URL 形式 | 谁吃它 |
|---|---|---|
| libpq 原生（psycopg3、psql、DBeaver） | `postgresql://user:pw@host:5432/db` | `psycopg.connect()`、`psql` |
| SQLAlchemy 2.x + psycopg3（**本仓选定**） | `postgresql+psycopg://user:pw@host:5432/db` | `create_engine()` |
| SQLAlchemy 2.x + psycopg2 | `postgresql+psycopg2://...` | `create_engine()` |
| SQLAlchemy 2.x + asyncpg（异步方案） | `postgresql+asyncpg://...` | `create_async_engine()` |

**结论**：`.env` 里保持不带方言的 `postgresql://...`（psql/探活能用），在 `session.py` 里由代码补方言，例如：

```python
url = settings.database_url.replace("postgresql://", "postgresql+psycopg://", 1)
```

> ✅ **本机实测（可复现）**：`sqlalchemy.engine.make_url("postgresql://u:p@h:5432/db").get_dialect().driver`
> 返回 **`psycopg2`** —— 也就是说**光写 `postgresql://` 默认走 psycopg2**。所以「`.env` 里的串直接喂给
> `create_engine()`」在只装了 psycopg3 的环境里必然报错：实测报 `ModuleNotFoundError: No module named 'psycopg2'`。
> 方言写对之后，实测 `engine.dialect.name/driver` = `postgresql/psycopg`、`engine.dialect.dbapi.__name__` = `psycopg`，
> 池类型是 `QueuePool`、`pool.size()` = 5、`pool._max_overflow` = 10 —— 即下面 §2.3 的参数确实生效。

报错长这样就是写错了：`ModuleNotFoundError: No module named 'psycopg2'`（URL 是 `+psycopg2` 而依赖里只有 psycopg3，
**或者你给的是不带方言的裸 `postgresql://`**）、`Can't load plugin: sqlalchemy.dialects:postgresql.psycopg2`。

> [`3.db.md`](../modules/3.db.md) 第 3 节写的是「`psycopg`（异步驱动，可选 `asyncpg`）」—— 本手册按**同步**路径给流程
> （`create_engine` / `SessionLocal` / `get_db`，与该文档第 2 节的对外接口一致）。
> 以后要走异步（FastAPI 全异步）：把 `create_engine` 换成 `create_async_engine` + `AsyncSession`，
> 此时 **URL 必须** `postgresql+asyncpg://`（或 `postgresql+psycopg://` 的 async 变体），池参数与 `get_db` 写法一并要改。

### 2.3 `session.py`：池参数 + 读写两个入口

```python
# app/db/session.py（骨架，按需调整；关键是池参数与两个入口都在这里）
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

from app.config import get_settings

_settings = get_settings()


def _url(url: str) -> str:
    """给 SQLAlchemy 补上方言；已带方言时原样返回。"""
    return url.replace("postgresql://", "postgresql+psycopg://", 1)


def _make_engine(url: str):
    return create_engine(
        url,
        # 池：显式设上限（C1：连接不被打爆）
        pool_size=5,          # 常驻连接数 ≈ 每个 worker 的并发 SQL 数
        max_overflow=10,      # 峰值临时额度；超了会阻塞到 pool_timeout 再抛错
        pool_timeout=30,      # 借不到连接时最多等多久（秒）
        pool_recycle=1800,    # 连接最长寿命（秒），防中间设备静默断连
        pool_pre_ping=True,   # 借出前先 ping，踢掉死连接（见 3.db.md §5）
        echo=False,           # 排障时临时 True，看真实 SQL
        connect_args={"options": "-c TimeZone=UTC"},
    )


# 读写分离是「能力」，不是「必须一开始就上」（3.db.md §4 第 2 条）：
# 现在两者可以指向同一个库；负载上来后只需改只读那条的 URL（或挂只读副本）即可切换。
_write_url = _url(_settings.database_url)
_read_url = _url(getattr(_settings, "database_read_url", "") or _settings.database_url)

engine = _make_engine(_write_url)          # 兼容 3.db.md 的 `from app.db.session import engine`
_read_engine = _make_engine(_read_url)     # 读路径引擎（见下）
_session_factory = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)
SessionLocal = _session_factory            # 兼容 `SessionLocal`


def get_write_engine():
    """写路径引擎（工单/退款等预定义 service，不经 LLM 动态 SQL）。"""
    return engine


def get_read_engine():
    """读路径引擎（Text-to-SQL 只读白名单走这里）。"""
    return _read_engine


def get_db():
    """FastAPI 依赖：每请求一个会话，用完必还。"""
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

> `autoflush=False` 是 FastAPI 场景的常见选择：避免查询前隐式 flush 造成意外写库。
> `_read_engine` / `engine` 用的是同一套 `_make_engine` 参数（读路径的池可以更小、写路径更小也行，看压测再调）。
> 注意 `connect_args={"options": "-c TimeZone=UTC"}` 是**会话级**设置（只影响本连接），
> 与库的 `timezone` 参数是两回事；本仓种子数据都是 UTC 存储，跨时区展示在第 16 步（web）做转换。

**怎么估池参数**（`3.db.md` §5）：

- `pool_size ≈ 每 worker 的并发 SQL 数`；`max_overflow` 是峰值临时额度，**真实上限 = `pool_size + max_overflow`**。
- 4 个 uvicorn worker × (5 + 10) = 60 个连接 —— 还要核对 Linux VM 上 PostgreSQL 的 `max_connections`（默认 100）
  与**其它客户端**（psql、DBeaver、第 16 步的 Web、第 12 步的队列 worker）共同占用，别一把梭。
- 池太小：请求在 `pool_timeout` 后抛 `TimeoutError: QueuePool limit of size 5 overflow 10 reached`；
  池太大：把库的连接数/内存打爆。**宁可排队，不要把库拖垮。**

## 3. Alembic：建表、改表、可重复执行

### 3.1 初始化（一次）

```powershell
# ── 执行位置：Windows 开发机，仓库根 ──
uv run alembic init alembic
# 生成：alembic.ini + alembic/env.py + alembic/versions/
```

改两处，**不要把连接串写进 `alembic.ini`**（那是把密码抄第二遍，必然漂移、也容易误提交）：

```python
# alembic/env.py（要点）
from app.config import get_settings
from app.db.base import Base
import app.db.models  # noqa: F401  ← 必须 import，否则 target_metadata 里没有表，autogenerate 会生成空迁移

config.set_main_option("sqlalchemy.url", get_settings().database_url.replace("postgresql://", "postgresql+psycopg://", 1))
target_metadata = Base.metadata
```

```ini
# alembic.ini：把原来的 sqlalchemy.url 那行清空/注释掉，避免两处真相
# sqlalchemy.url =
```

> `alembic.ini` 里默认的 `sqlalchemy.url = driver://user:pass@localhost/dbname` 是**占位符**，
> 不改它会得到 `ModuleNotFoundError: No module named 'driver'` —— 这是新手最常撞的一条。

### 3.2 生成首版迁移

```powershell
uv run alembic revision --autogenerate -m "init business tables"
# 期望：alembic/versions/<hash>_init_business_tables.py 生成，输出里列出 8 张表的 create_table
# ⚠️ 一定要打开这个文件看一眼：autogenerate 只懂「模型有、库里没有」的差异，
#    索引/约束/服务端默认值/命名约定 都可能漏，漏了就手工补。
```

自检（第 3 步验收「迁移可重复执行」的一半）：

```powershell
uv run alembic current     # 期望：空（还没 upgrade）或当前 revision
uv run alembic history     # 期望：线性历史，只有一条 <base> -> <hash>
```

### 3.3 升级 / 回滚（可重复执行 = 本步硬验收）

```powershell
uv run alembic upgrade head      # 期望：Running upgrade  -> <hash>, init business tables
uv run alembic current           # 期望：<hash> (head)

# 库侧核对：8 张表 + alembic_version 都在
# ── 执行位置：VMware-Linux（或 Windows 上有 psql 客户端也行，host 用 <Linux-IP>）──

#       + alembic_version（共 9 行）
```

**可重复执行**（`3.db.md` 第 8 节第一条验收）要这样验，而不是只看一次 upgrade 成功：

## 5. 行级过滤（SQL 层过滤；只读视图/角色见 §5.3 决策记录）

`3.db.md` §4 第 3 条把「对客路径不会越权」的实现钉在 **SQL 层**（`WHERE user_id = :当前用户`），
不是应用层 `if` 过滤。第 4 步（`4.security.md`）的白名单表名也来自这里的 schema，所以本步要把「对客查询封装」做出来：

```python
# app/db/queries.py（骨架）
from sqlalchemy import select

from app.db.models import Order
from app.db.session import get_read_engine


def get_orders_for_customer(user_id: int, limit: int = 50):
    """对客订单查询：行级过滤 + 强制 LIMIT，走只读引擎。"""
    stmt = (
        select(Order)
        .where(Order.user_id == user_id)   # ← 行级过滤，永远带
        .order_by(Order.created_at.desc())
        .limit(limit)                       # ← 结果行数截断（C1）
    )
    with get_read_engine().connect() as conn:      # 只读引擎 → 不落写库
        return conn.execute(stmt).all()
```

### 5.2 「SQL 真的带 WHERE 吗」——看数据库侧，别信代码

```bash
# ── 执行位置：VMware-Linux，仓库根 ──
# 开统计（一次即可）
docker compose -f infra/docker-compose.dev.yml --project-directory . \
  exec postgres psql -U shopuser -d shopsage -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"

# 跑一次 Windows 侧的 §5.1，然后在库侧查最近的对客查询语句
# ⚠️ ① 不要 left(query, 120)：长语句的 WHERE 就在 120 字符之后，会被截掉 → 误判成「不带 WHERE」
#    ② 不要用 `query ILIKE '%user_id%'` 当判据：它匹配语句**全文**，
#       `SELECT DISTINCT orders.user_id FROM orders LIMIT $1`（挑种子数据的装置查询）
#       因为 SELECT 列表里有 user_id 这个**列名**也会命中，可它根本没有行级过滤
docker compose -f infra/docker-compose.dev.yml --project-directory . \
  exec postgres psql -U shopuser -d shopsage -c \
  "SELECT queryid, calls, rows, (query ILIKE '%WHERE%') AS has_where, query
   FROM pg_stat_statements WHERE query ILIKE '%from orders%' ORDER BY calls DESC;"
# 期望：由 app/db/queries.py 出口发出的那条形如
#   SELECT orders.order_id, ..., orders.created_at FROM orders
#   WHERE orders.user_id = $1::BIGINT ORDER BY ... LIMIT $2::INTEGER          ← has_where = t
#
# 判读口诀（缺一步就会被上面两个坑带偏）：
#   「带 user_id 列名 ≠ 带 WHERE user_id；带 LIMIT ≠ 带行级过滤」
#   1. 看 has_where = t，并且确认是 `WHERE ... user_id = $n`（不是别的 WHERE）；
#   2. 看 queryid：同一条 SQL 的参数被归一化 → 同一个 queryid。
#      「挑种子数据的装置查询」与「业务出口语句」是**两个不同的 queryid**，别混为一谈；
#   3. 看 calls：与「跑了一次 §5.1 / 跑了一次 pytest」同频的是装置查询；
#      随业务请求持续上涨的才是业务路径。
#
# 想确认「某条语句到底是谁发的」：复跑一次可疑动作，再看这条 queryid 的 calls 是否 +1：
docker compose -f infra/docker-compose.dev.yml --project-directory . \
  exec postgres psql -U shopuser -d shopsage -c \
  "SELECT calls, rows, query FROM pg_stat_statements WHERE queryid = <上一步的 queryid>;"
# 期望：calls +1 的那条就是元凶。
# 拿不到调用栈时，退用 §2.3 的 `echo=True` 或引擎级事件打印 Python 侧的真实 SQL + 调用栈，最直接。
#
# 结论怎么算过：带 `WHERE orders.user_id = ` 的语句 = 干净的对客路径；
#   出现 `has_where = f` 且**不在**下面豁免清单里 → 对客路径有裸查询，D1 没兜住，回去收口到 queries.py。
```

**已知「不带 WHERE」语句的豁免清单**（实测逐条确认过，别再把它们当违规；也**别**拿它当判据的豁免分支，
判据本身按 queryid 锚定，天然不会误伤——清单只用于人工分诊）：

| 语句 | 来源 | 为什么可以不带 WHERE |
|---|---|---|
| `SELECT DISTINCT orders.user_id FROM orders LIMIT $1` | `tests/test_db_queries.py::_two_users_with_orders` | 只挑「有订单的用户 id」当前置条件（否则过滤测试会因空集假通过），不返回订单内容 |
| `information_schema.tables` / `pg_extension` 查询 | `tests/db_helpers.py`、`scripts/db_check.py::snapshot` | 结构自检与扩展探测，不碰业务行 |
| `compare_metadata` 的 introspection | `alembic/env.py`（`revision --autogenerate`） | 迁移期比对结构，只读元数据 |

> `pg_stat_statements` 需要 `shared_preload_libraries` 才能在**实例级**生效；上面的 `CREATE EXTENSION`
> 只是把视图建出来，若 `SELECT` 报「must be loaded via shared_preload_libraries」，就在开发 compose 的
> postgres 服务加 `command: ["postgres", "-c", "shared_preload_libraries=pg_stat_statements"]` 并重建容器
> （⚠️ 与 `POSTGRES_INITDB_ARGS` 一样，这类实例参数改动要重启容器；数据卷不用删）。
> 拿不到该视图时，退用 `echo=True` 打印真实 SQL（§2.3 的 `echo`）作为等效证据，并在证据里写清用的是哪种方式。

### 5.3 只读视图与只读角色 —— **决策记录：第 3 步不实现**

> **结论**：第 3 步**不建** `v_customer_orders` 视图、**不建** `shopsage_readonly` 角色。
> 行级过滤的唯一落点是 `app/db/queries.py`；数据库层的纵深防御（只读角色）推迟到**第 4 步**
> （[`4.security.md`](../modules/4.security.md)）与 `app/tools/sql_executor.py` 一起做。
> 本仓现状可核对：`alembic/versions/` 里只有 8 张表 + 索引 + 约束，全仓无 `CREATE VIEW` / `CREATE ROLE` / `GRANT`。

**为什么不做过滤视图**（四条理由，都不是偷懒）：

1. **会制造第二处真相**：过滤若同时写在视图和 `queries.py` 里，「视图已过滤」和「应用忘了过滤」两个假设
   会互相掩护——而现在的判据（`assert_row_filtered()` 编译期检查 + §5.2 的 queryid 锚定）之所以能一巴掌拍死
   裸查询，前提正是**过滤只有一个落点**。
2. **会话变量方案与连接池打架**：视图里写 `WHERE user_id = current_setting('app.user_id')` 就得在每个连接上
   `SET app.user_id`，而 `QueuePool` 的连接是借出/复用/`pool_recycle` 回收的（§2.3）——忘了 SET 或 SET 错，
   就会**串号**（上一个请求的 user_id 留给下一个请求）。这比「应用忘了 WHERE」更隐蔽、更难复现。
3. **参数化方案等于没加固**：`WHERE user_id = :uid` 仍由应用传参时，视图只是包了个壳，多一层要维护的 DDL，
   安全性没有任何增量。
4. **真危险的那条路径视图帮不上忙**：第 4/6 步的 Text-to-SQL 自由 SQL 由 `validate_sql()`（sqlglot AST）
   强制注入 `WHERE user_id`——LLM 的 SQL 照样必须被应用层拦住，数据库视图不是这条路径的防线。

**只读角色为什么值得做（但放在第 4 步）**：它才是真正的数据库层兜底——即使 `validate_sql()` 被绕过，
**写操作在数据库层直接报权限错误**。当前 `get_read_engine()` 未设 `DATABASE_READ_URL` 时与写引擎是**同一个**
（§2.4 ③），也就是说「只读路径」目前只在命名上是只读的。第 4 步要做的清单：

1. `.env` 加只读 DSN（如 `DATABASE_READ_URL=postgresql://shopsage_readonly:...@<Linux-IP>:5432/shopsage`）
   并进 `Settings`，让 `get_read_engine()` 真正落到只读连接；
2. `app/tools/sql_executor.py` 的 Text-to-SQL 执行**强制**走只读引擎；
3. 角色与授权从迁移里**剥离**（密码不进 Git）：用参数化迁移或一次性 bootstrap 脚本
   （`CREATE ROLE ... LOGIN PASSWORD :pw` / `GRANT SELECT ON <白名单表>` / 显式 `REVOKE` 掉不需要的授权）；
4. 确认 `scripts/seed.py`、`scripts/db_check.py` 仍走写角色，别被「收口到只读引擎」误伤；
5. 验收用例：用只读 DSN 执行 `DELETE FROM orders` / `CREATE TABLE t(...)` 必须报权限错误
   （写进 `tests/security/`，属 `4.security.md` §8 的证据）。

> ⚠️ 两条容易踩的认知：**只读角色不解决「读到别人的行」**（那是 D1 行级过滤的授权粒度），它只解决「写不进去」；
> 而**视图也不解决「写」**。两者是两件事，别互相替代。

**视图的触发条件**（满足任一再做，且必须保证过滤只有一处真相）：
出现第二个必须直接读表的消费者 / 要把过滤下沉到 DBA 可控层面 / 明确的列裁剪与行安全策略（RLS）需求。
做的时候对称：迁移里 `CREATE OR REPLACE VIEW`、`downgrade` 里 `DROP VIEW`，并同步 §5.2 的判据与豁免清单。

> 参考写法（**当前不落地**，仅存档；`4.security.md` 定稿后再决定是否启用）：
>
> ```sql
> CREATE OR REPLACE VIEW v_customer_orders AS
>   SELECT order_id, user_id, status, total_amount, created_at FROM orders;
>
> CREATE ROLE shopsage_readonly LOGIN PASSWORD '<只读口令>';   -- 口令不进迁移，见上第 3 条
> GRANT SELECT ON v_customer_orders TO shopsage_readonly;
> -- 注意：默认 public schema 在新版 PostgreSQL 已收紧，但历史库要显式 REVOKE 掉不需要的授权
> ```

## 6. 连接池上限验证（C1，本机可跑的简化版）

`3.db.md` §7 的 `test_pool_limits_connections`：高并发下连接数不超过 `pool_size + max_overflow`。

```python
# tests/test_db_pool.py
# 需要真库（Linux VM 可达）—— 池上限是「和数据库之间的连接数」，没有库就无从观测。
import concurrent.futures as cf
import threading

from sqlalchemy import text

from app.db.session import engine


def test_pool_never_checks_out_more_than_capacity():
    """并发借连接：**同时借出**的连接数不超过 pool_size + max_overflow，且用完都还回池。"""
    cap = engine.pool.size() + engine.pool._max_overflow   # 真实上限 = 5 + 10 = 15
    lock = threading.Lock()
    peak = 0

    def hold() -> None:
        nonlocal peak
        with engine.connect() as conn:            # 借出 → 持有 → 自动还回
            conn.execute(text("select 1"))
            with lock:
                peak = max(peak, engine.pool.checkedout())

    with cf.ThreadPoolExecutor(max_workers=cap * 3) as ex:   # 45 个并发去抢 15 个连接
        for f in [ex.submit(hold) for _ in range(cap * 3)]:
            f.result()                            # 借不到时会等 pool_timeout，超时才抛 TimeoutError

    assert peak <= cap, f"连接借出峰值 {peak} 超过池上限 {cap}"
    assert engine.pool.checkedout() == 0, "有连接没还回池 —— 典型 session/connection 泄漏"
```

> 想看到池真的「拦住」而不是碰巧没超，把 `max_workers` 拉到 `cap * 3` 并观察 `peak` 恰好顶到 `cap`；
> 若要复现**排队超时**，临时把 `pool_size=1, max_overflow=0, pool_timeout=1` 再跑，
> 期望 `sqlalchemy.exc.TimeoutError: QueuePool limit of size 1 overflow 0 reached`。

```bash
# ── 执行位置：VMware-Linux（能直接数连接，最直接的 C1 证据）──
# 一边在 Windows 侧跑上面的并发用例（或压测脚本），一边在这里数：
docker compose -f infra/docker-compose.dev.yml --project-directory . \
  exec postgres psql -U shopuser -d shopsage -c \
  "SELECT usename, COALESCE(client_addr::text,'local') AS client, count(*) FROM pg_stat_activity
   WHERE datname='shopsage' GROUP BY 1,2 ORDER BY 3 DESC;"
# 期望：Windows 侧应用那一条的 count <= pool_size + max_overflow（每个进程各自一套池）
#       还能看到「谁连过来的」（client_addr 是 Windows 侧经 VMware NAT 过来的源地址）
```

**证据怎么算过**（`3.db.md` 第 8 节第二条验收）：

| 观察 | 结论 |
|---|---|
| 并发下 `count(连接)` 稳定 ≤ 池上限，且请求全部成功 | ✅ 池上限生效 |
| 出现 `TimeoutError: QueuePool limit ... reached` | 池太小或**有 session 泄漏**（`get_db` 没 `close`）→ 先查泄漏再加池 |
| 连接数超过上限且持续上涨 | 有人在 `create_engine` 之外自己 `psycopg.connect()` 裸连，没走池 → 收口到 `app/db/session.py` |
| 压测后连接数不回落 | 泄漏；用 `checkedout() == 0` 用例兜住 |

> 真正的压测（QPS / P99 / 库 CPU）属第 6 步（`6.tools.md`）与第 12 步（`11.observability.md`）的活；
> 第 3 步只要证明「池有上限、连接不泄漏」即可，别在这里堆压测报告。

## 7.1 实现期间撞到的五个新坑（实测，含修法）

这四条是「照着手册做」时真正卡住过的地方，全部已修在仓库里；新环境复现时可以直接跳过。

### 坑 1：`alembic.ini` 里写中文 → `UnicodeDecodeError: 'gbk' codec can't decode byte 0xac`

```
File "alembic/util/compat.py", line 130, in read_config_parser
    return file_config.read(file_argument, encoding="locale")
UnicodeDecodeError: 'gbk' codec can't decode byte 0xac in position 561: illegal multibyte sequence
```

Alembic 用 **`encoding="locale"`** 读 `alembic.ini`。zh-CN Windows 的 locale 编码是 **GBK**，
而 ini 文件是 UTF-8 且含中文注释 → 迁移命令在**读配置阶段**就崩，跟数据库一点关系都没有。

- ⚠️ **`$env:PYTHONUTF8=1` 不管用**（实测确认）：UTF-8 模式不改变 `"locale"` 的取值。
- ✅ 修法：**`alembic.ini` 保持纯 ASCII**（中文说明搬到 `alembic/README`）——这也是本仓的做法，文件头有注释说明原因。
- 校验办法：`python -c "print(sum(b>127 for b in open('alembic.ini','rb').read()))"` 应为 `0`。

### 坑 2：`literal_binds` 只能给离线模式 → `Can't use literal_binds setting without as_sql mode`

第一版 `env.py` 把 `literal_binds=True` / `dialect_opts` 无条件塞进 `context.configure()`，
于是**在线**的 `alembic revision --autogenerate` 直接失败（只有 `--sql` 离线模式才允许这两项）。
修法：`env.py` 的 `_configure()` 按「是否离线」分别组装选项（`connection is None` 时才加这两项）。

### 坑 3：`--autogenerate` 会生成**空迁移**，而库停在旧版本时还会生成**错误 diff**

- 库与模型一致时，`--autogenerate` 会产出一个 upgrade/downgrade 都是 `pass` 的文件，污染迁移历史；
- 数据库不是 head 时，它会拿**旧结构**跟新模型比对，生成一堆错误 diff（甚至重复建表）。

修法：`env.py` 里加了 `_process_revision_directives` 护栏 —— 空迁移直接拒绝并提示原因，
库不是 head 时要求先 `alembic upgrade head`；确实需要空迁移时用
`alembic -x allow_empty=true revision --autogenerate -m "..."` 显式绕过（已实测两条路径）。

> 顺带踩到一个 API 混淆：钩子拿到的 `context` 是 **MigrationContext**，只有
> `get_current_heads()` / `.script`；而 `get_x_argument()` / `get_context()` 属于 **EnvironmentContext**（env 模块级那个）。
> 名字很像，混用就 `AttributeError: 'MigrationContext' object has no attribute 'get_context'`。
> `-x` 参数因此在模块级读一次存进 `X_ARGS` 再给钩子用。

### 坑 4：`pg_stat_statements` 「装了扩展」≠「能查到数据」

`CREATE EXTENSION pg_stat_statements` 在本机**可以成功**（`pg_available_extensions` 里有它），
但 `shared_preload_libraries` 仍是空串 —— 查询会报
`pg_stat_statements must be loaded via shared_preload_libraries`。
要真正用它，得给 compose 的 postgres 服务加 `command: ["postgres", "-c", "shared_preload_libraries=pg_stat_statements"]`
并**重建容器**（数据卷不必删）。⚠️ 这一步会重启依赖服务，确认没人在用再做。

所以 §5.2 的库侧证据在**当时**是跳过：`tests/test_db_queries.py::test_live_sql_contains_row_filter`
在没有该视图时 `pytest.skip`。等效证据用引擎级 `echo=True` 打印真实 SQL，或直接用
`queries.py` 的 `assert_row_filtered()`（编译期检查，已在 CI 里跑）。

> ✅ **状态更新（本次分诊实测）**：这台 Linux VM 上 `shared_preload_libraries` 已经配好，
> `pg_stat_statements` 可用。`test_live_sql_contains_row_filter` 已**真跑并 PASS**（不再 skip）：
> `uv run pytest tests/test_db_queries.py -k live_sql -v` → `PASSED`。
> 也就是说 §5.2 现在有**真实的库侧证据**，不必再退到 `echo=True`；判定细节见 §7.1 坑 5。

> ⚠️ 另注意 `pg_stat_statements.track` 默认是 `top`：**只记顶层语句**，函数/嵌套里的语句不记。
> 分诊「某条语句是谁发的」时临时开成 `all`（`ALTER SYSTEM SET pg_stat_statements.track = 'all';`
> 后 `SELECT pg_reload_conf();`），否则会漏语句、误以为「没有裸查询」。

### 坑 5：把「全文含 `user_id`」当判据 → 装置查询被误判成越权裸查询

这条是**判据**的坑，不是代码的坑。照 §5.2 分诊时实测撞到：按老写法
`SELECT calls, rows, left(query, 120) ... WHERE query ILIKE '%user_id%'` 查，得到两条，一条带
`WHERE`、一条不带，看起来像「对客路径有裸查询」。把完整语句拉出来（不截断）后真相是两个不同 queryid：

| queryid | calls | has_where | 完整语句 | 归属 |
|---|---|---|---|---|
| `-7807791628461212022` | 3 | **t** | `SELECT orders.order_id, ..., created_at FROM orders WHERE orders.user_id = $1::BIGINT ORDER BY created_at DESC, order_id DESC LIMIT $2::INTEGER` | 真·对客出口 `app/db/queries.py::get_orders_for_customer` |
| `343036595678306220` | 3 | **f** | `SELECT DISTINCT orders.user_id FROM orders LIMIT $1::INTEGER` | `tests/test_db_queries.py::_two_users_with_orders`（挑「有订单的用户」当前置条件） |

两个错都在判据上：

1. **`left(query, 120)` 截断**：长语句的 `WHERE` 正好落在 120 字符之后，被截掉 → 看着就像没带 WHERE。
2. **`query ILIKE '%user_id%'` 匹配全文**：第二条因为 `SELECT` 列表里有 `user_id` 这个**列名**而命中，
   可它是「挑种子数据的装置查询」，只返回用户 id 列表，按设计就不该带行级过滤；
   顺带它**带 `LIMIT` 却没有任何过滤**——`LIMIT` 属 C1 结果截断，与 D1 行级过滤是两回事，不能互相替代。

**修法**（已落地）：

- §5.2 的核对 SQL 改成输出 `queryid / calls / rows / has_where / query` 五列、**不截断**，
  并给出判读口诀「**带 user_id 列名 ≠ 带 WHERE user_id；带 LIMIT ≠ 带行级过滤**」+ 三步判读
  （看 `has_where` → 看 `queryid` 归属 → 看 `calls` 与业务请求是否同频）+ 已知豁免清单；
- `tests/test_db_queries.py::test_live_sql_contains_row_filter` 改成 **queryid 锚定**：
  调一次 `get_orders_for_customer()`，比较调用前后的 queryid 快照，只对「本次引入/`calls` 上涨」的
  语句断言；业务路径零容忍（必须匹配 `WHERE\s+orders\.user_id\s*=`），不带过滤的语句只允许命中
  `UNFILTERED_STMT_EXEMPTIONS`。这样装置查询天然不会误伤，真裸查询也漏不掉；
- 同时把本次这两条真实语句抄成不依赖数据库的用例（`LIVE_SQL_*` + 三条纯逻辑测试），
  避免下次又被截断/列名匹配带偏。

> 教训：**库侧核对要说的是「哪条路径发的语句」，不是「语句里有没有某个词」。** 判据要锚定
> `queryid` 与调用栈（`echo=True` / 引擎级事件），并按 queryid、calls 归并，别按关键字捞一批再一刀切断言。
> ⚠️ 这几条用例不要在 `pytest-xdist`（`-n`）下并发跑，别的 worker 的 orders 语句会混进快照。

## 9. 记住这八个坑（面试/复述用）

1. **`POSTGRES_*` 与 `DATABASE_URL` 是两套消费者**（compose 初始化 vs 应用连接），必须同步改；
   而且 `POSTGRES_*` **只在数据卷为空时生效一次** —— 「改了密码不生效」几乎都是这条。
2. **URL 方言与驱动必须配对**：`postgresql://` 给 psql/psycopg 原生，`postgresql+psycopg://` 给 SQLAlchemy；
   写错的表现是 `ModuleNotFoundError: No module named 'psycopg2'`，而不是「连不上库」——
   因为裸 `postgresql://` 在 SQLAlchemy 里的默认驱动就是 psycopg2（本机实测）。
3. **连接池必须有上限**：真实上限 = `pool_size + max_overflow`；池太小排队超时、池太大拖垮库，
   跨主机还要乘以 worker 数并核对库的 `max_connections`。
4. **`pool_pre_ping=True` 是跨主机场景的刚需**：VMware NAT/中间设备会静默丢掉空闲连接，
   没有 pre-ping 就会「从池里拿到死连接」报 `server closed the connection unexpectedly`。
5. **行级过滤必须在 SQL 层**（`WHERE user_id = :me`）而非应用层 `if`：应用层过滤＝先查全表再截断，
   既慢又可能在中间环节泄露。验证要看**数据库侧**（`pg_stat_statements`），而且要按 **queryid 锚定**
   ——「带 user_id 列名」不等于「带 WHERE user_id」（§7.1 坑 5）。
6. **纵深防御要挑对工具**：行级过滤只放**一处真相**（`queries.py`），视图会制造第二处；
   真正该加的数据库层兜底是**只读角色**（写不进去），它和「读到别人的行」是两件事（§5.3 决策记录）。
7. **迁移要能双向跑**：`upgrade`/`downgrade` 都可重复执行才算过；`env.py` 忘了 import 模型 =
   静默生成空迁移；禁止 `create_all()` 与 Alembic 混用（会打架出 `already exists`）。
8. **`downgrade base` 会连数据一起删**：种子数据灌完后再回滚，演示环境就空了 ——
   重来要「回滚 → 升级 → 重跑种子」三步走，别用 `DROP SCHEMA` 一把梭。
