# 环境迁移验收文档（ShopSage · 新机器）

> **用途**：仓库整体迁移到一台新 Windows 开发机后，按本文**逐步**确认「环境是否可用」，并把每步的**实测证据**回填到第 6 节。
>
> **与既有文档的关系**：本文不是替代 `docs/runbook/`，而是它们的**验收总入口** —— 每一步都指向对应的实操手册，
> 出问题时回手册查细节，本文只负责「按顺序走一遍 + 判定通过/不通过」。
>
> **适用拓扑**（与 `2.infra-runbook.md` 一致）：Windows 开发机跑代码，**依赖栈（PostgreSQL + pgvector / Redis / Prometheus / Grafana）在另一台 Linux 机器上**，本机**不需要 Docker**。

### 第 2 步：uv 缓存与虚拟环境

#### 2.1 先确认 uv 缓存问题（**迁移后最容易踩的一条**）

```powershell

```

**本次实测**：

```text

  cause: failed to open file `C:\Users\任志皓\AppData\Local\uv\cache\.lock`: 拒绝访问。 (os error 5)
```

❌ **不通过（环境问题，非项目问题）**。修法就是 1.2 节的 `$env:UV_CACHE_DIR`：

```powershell
$env:UV_CACHE_DIR = "$PWD\.uv-cache"; uv python list   # 不再报错
```

#### 2.2 虚拟环境可用性

```powershell
uv run python --version
```

**本次实测**：`Python 3.12.15` ✅

> ⚠️ **迁移要点**：`.venv` 是**从旧机一起搬过来的**，`pyvenv.cfg` 里写着旧机的绝对路径：
> `home = C:\Users\<用户名>\AppData\Roaming\uv\python\cpython-3.12-windows-x86_64-none`。
> 本次两台机器**用户名恰好相同**（`任志皓`）所以能直接用；**用户名不同就会直接坏掉**。
> 稳妥做法是迁移后执行 `uv sync --locked` 重建（见下），不要依赖搬过来的 `.venv`。

#### 2.3 环境与锁文件一致性（**迁移验收的关键一条**）

```powershell

```

**期望**：两条都 `exit=0`。

**本次实测**：

| 命令 | 退出码 | 输出 |
|---|---|---|
| `uv lock --check` | **0** ✅ | `Resolved 174 packages` |
| `uv sync --locked` | **0** ✅ | `Checked 133 packages in 5ms` |

✅ **通过** —— 说明新机上的依赖环境与 `uv.lock` **完全一致**，没有缺包/多包/版本漂移。

#### 2.4 仓库子目录的写入限制（**本会话特有，务必分辨**）

本会话的受限 shell **不能写仓库子目录**，但根目录可以。实测各目录探针结果：

| 目录 | 受限 shell 下写入 | 说明 |
|---|---|---|
| 仓库根 `.` | ✅ 可以 | 根上有沙箱写入授权 |
| `.venv` / `.uv-cache` / `.npm-cache` / `.vscode` / `.pytest-tmp` | ✅ 可以 | 迁移后新建的，继承了授权 |
| `docs/` / `web/` / `app/` / `tests/` / `scripts/` / `infra/` … | ❌ **拒绝访问** | 迁移前就在的目录，**没有**继承到授权 |

用 `icacls` 对账可以直接看出差别：

```powershell
icacls <仓库根>          # 有 S-1-4-...:(OI)(CI)(W,D,DC) 这一条
icacls <仓库根>\docs     # 没有这一条
```

**这会制造三类假红**（都与代码无关）：

1. `npm run typecheck` 报 `EPERM ... tsconfig.tsbuildinfo`；
2. `npm run build` **卡死不动**（不是编译失败，是写不进 `.next`）；
3. pytest 报 `PytestCacheWarning: could not create cache path`，以及 `tests/test_config.py` 那 6 条 `tmp_path` 用例 `PermissionError`。

> 📌 **判定口径**：这三类全部记为**环境限制**，不计入项目质量。放宽权限后重跑，前端两条**全部通过**（见第 7 步）。

#### HF 缓存的**两个坑**（本次实测定性，且有误导性）

这两个坑的共同特征是：**服务能起来、`/health` 全绿、单测也过**，但**第一次真检索才炸** ——

> ⚠️ **三个必须记住的分诊要点**（本次都实际踩过，前两条差点导致误报）：
>
> 1. **`curl.exe` 在本会话被沙箱拦死**：连 `http://127.0.0.1:8000/health` 都返回 `http=000`。
>    所以**不要用 curl 的失败当网络证据** —— 要用 `.NET`/`httpx` 做对照。
> 2. **`.NET`（`Invoke-WebRequest`）会走 Windows 系统代理，Python `httpx` 默认只认 `HTTPS_PROXY` 环境变量**。
>    两者行为不同，不能互相推断。本次实测**显式设 `HTTPS_PROXY` 也无效**，直连同样无效 ——
>    正是靠这组对照才排除「网络被封」的误判，最终定位到推理上游。
> 3. **「连接超时」不等于「网络不通」**：本例真正的原因是**服务端受理了请求却不下发内容**。
>    判据是拿一个**必然被拒的请求**（空 body → 422、错路径 → 404）去证明「链路是通的」。
