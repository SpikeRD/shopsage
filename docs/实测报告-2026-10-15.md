## P0-1 · 登录接口的限流**完全没生效**（暴力破解无上限）

**严重度**：P0（安全）
**位置**：`app/api/middleware.py:57-68`（`LIMITED_SCOPES`）

### 现象

登录接口配置了全项目最严的额度（`app/api/ratelimit.py:111`，`auth.login = 10 次 / 300 秒`），
但实测 **40 次连续错误登录全部返回 401，一次 429 都没有**：

```text
POST /api/auth/login x40 (configured limit 10/300s): {401: 40}
POST /api/auth/refresh x40 (configured limit 60/300s): {401: 40}
```

对照：同样口径下 `/api/chat` 是**正常生效**的（30 次后开始 429）：

```text
POST /api/chat (limit 30/60) -> Counter({401: 30, 429: 6})
```

### 根因

限流要生效需要**三处登记**（`middleware.py:64` 自己写了这条纪律）：

1. `scope.SCOPE_BY_ROUTE`（用哪个 scope 名）→ ✅ 有 `auth.login` / `auth.refresh`
2. `ratelimit.DEFAULT_RULES`（默认额度）→ ✅ 有 `10/300` 与 `60/300`
3. `middleware.LIMITED_SCOPES`（**中间件要不要限**）→ ❌ **缺 `auth.login` / `auth.refresh`**

中间件只在 `(method, path) in LIMITED_SCOPES` 时才调 `_check_limit`（`middleware.py:160`），
而 `LIMITED_SCOPES` 里只有 `/api/chat`、`/api/chat/approve`、`/api/tasks`。
于是登录/刷新**根本没进限流分支** —— 配的额度和 scope 名全是摆设。

`/health` 也不在 `LIMITED_SCOPES` 里，但那是**有意设计**（探针不该吃配额），
登录接口显然不是同一类意图。

### 为什么测试没发现

现有用例只断言了**单向包含**（`tests/api/test_api_contracts.py:189`）：

```python
assert LIMITED_SCOPES <= set(SCOPE_BY_ROUTE)   # 限流的路径必须有 scope
```

这条能拦住「限流了但没 scope」，**拦不住「有 scope、有额度、却没登记限流」** ——
方向反了。`tests/api/test_tasks.py:311` 只对 `/api/tasks` 做了正向断言，
登录接口没有任何等价断言。

### 影响

- `.env` 里写的 `RATE_LIMIT_CHAT=30/60` 这类配置对登录**完全不生效**；
- 密码爆破只受「Argon2id 计算耗时」这一个天然限速，没有额度上限；
- 项目文档（`.env.example`、`scope.py` 注释）明确声称「不限流等于给暴力破解无限次尝试」，
  **实现与文档不符**。

### 修复

```python
# app/api/middleware.py
LIMITED_SCOPES: Final[frozenset[tuple[str, str]]] = frozenset(
    {
        ("POST", "/api/chat"),
        ("POST", "/api/chat/approve"),
        ("POST", "/api/tasks"),
        # 变更 001：账号接口必须显式登记，否则额度配了也不生效（实测 P0）
        ("POST", "/api/auth/login"),
        ("POST", "/api/auth/refresh"),
    }
)
```

**并补一条「反向」用例**，把这类漏登记变成测试失败：

```python
def test_every_scoped_route_is_actually_enforced() -> None:
    """每条登记了 scope 的业务路由都必须在 LIMITED_SCOPES 里，否则额度是摆设。"""
    from app.api.middleware import LIMITED_SCOPES
    from app.api.scope import SCOPE_BY_ROUTE, UNLIMITED_PATHS
    for route in SCOPE_BY_ROUTE:
        assert route in LIMITED_SCOPES, f"{route} 有 scope 但中间件不限流（额度不生效）"
    assert not (UNLIMITED_PATHS & {p for _, p in LIMITED_SCOPES})
```

## P0-2 · 对客 SQL 行级过滤可被绕过 → **跨租户读别人的订单**

**严重度**：P0（安全 / 数据越权）
**位置**：`app/agents/agent_llm.py:259-301`（`customer_row_filter_error`）

### 现象

对客路径的「只能查自己」靠两道检查：`validate_sql`（守卫）+ `customer_row_filter_error`（行级过滤）。
实测这条 SQL **两道都放行**：

```sql
SELECT order_id, user_id FROM orders WHERE user_id = :uid OR user_id = 3 LIMIT 10
```

```text
1) validate_sql -> ALLOWED
2) customer_row_filter_error -> PASS (no error)
```

同一函数的其他绕过形态也被放行：

| SQL（调用者 user_id=2） | 结果 |
|---|---|
| `WHERE user_id = :uid` | ✅ 正确放行 |
| `WHERE user_id = :uid OR user_id = 3` | ❌ **错误放行** |
| `WHERE user_id = :uid AND 1=1` | ❌ **错误放行** |
| `WHERE status='pending' AND user_id = :uid` | ✅ 放行（合理） |

### 根因

`customer_row_filter_error` 的判据只有两条（`agent_llm.py:272-275`）：

> ① 存在一个列名 `user_id` 的比较，且等号右边是**参数占位符**；
> ② 该比较必须落在最外层 SELECT 的 WHERE 里。

它检查的是「**形状**」（有没有 `user_id = :占位符`），**从不检查语义**
（这个条件是否真的把结果限定到了当前用户）。`_equalities()` 遍历所有 `EQ` 节点，
只要**任意一个**满足就 `return None`（放行），
因此 `A OR B` 里只要 A 是合规形状，B 无论是 `user_id = 3`、
`user_id IN (1,2,3)`、还是别的字面量，都一并放行。

`validate_sql` 也帮不上忙：它明确「不知道你是谁」（`agent_llm.py:263`），
只要求 WHERE 存在且不恒真 —— `user_id = :uid OR user_id = 3` 两条都满足。

**注意**：`data.py:420-433` 的 `_bind_customer_id` 确实防住了「模型谎报绑定值」
（强制把 `:uid` 覆写成鉴权得到的 user_id）—— 这一层是对的。
但它防不住「SQL 文本里**额外写死**一个越权条件」，因为那部分不走绑定参数。

### 影响

- 客户 A 可以构造提问（如「帮我查 user_id=3 的订单」）诱导模型生成 `OR` 条件，
  或直接由模型自由发挥时命中该形态，**读到其他客户的订单/金额/地址**；
- 这是 D1（行级过滤）的核心承诺，也是本项目「对客/对内两条业务线」隔离的基础；
- 由于图有降级兜底，越权成功时**不会报错**，答案看起来完全正常。

### 修复

把「形状检查」升级为「**语义检查**」——最外层 WHERE 的**整个条件**必须等价于
「只允许 `user_id = :uid`」这一种形态：

```python
def customer_row_filter_error(sql: str, *, user_id: int) -> str | None:
    ...
    condition = where.this
    # ① 顶层只允许 AND 组合（OR 会把范围扩大，直接拒）
    if _contains_or(condition):
        return _row_filter_hint(user_id, "最外层 WHERE 含 OR：无法保证只查本人数据")
    # ② 收集所有 user_id 的等值对，必须恰好一个、且右侧是占位符
    equalities = [v for c, v in _equalities(condition) if c.name.lower() == "user_id"]
    if len(equalities) != 1:
        return _row_filter_hint(user_id, f"`user_id` 等值条件有 {len(equalities)} 个（必须恰好 1 个）")
    if not isinstance(equalities[0], sqlglot.exp.Placeholder):
        return _row_filter_hint(user_id, "`user_id` 必须用绑定参数比较")
    # ③ 其余条件里不许再出现 user_id 的其它比较（IN / > / != 等）
    if _other_user_id_comparisons(condition):
        return _row_filter_hint(user_id, "除等值外还有其它 `user_id` 比较，无法保证范围")
    return None
```

更稳的兜底（建议同时做）：**不依赖模型写 WHERE**，而是在守卫通过后由程序
**强制包一层**：`SELECT * FROM (<model sql 去掉 user_id 条件>) t WHERE t.user_id = :uid`，
或对客路径统一走 `app/db/queries.py` 的固定查询出口。

**回归用例**（`tests/security/` 加）：

```python
@pytest.mark.parametrize("sql", [
    "SELECT order_id FROM orders WHERE user_id = :uid OR user_id = 3",
    "SELECT order_id FROM orders WHERE user_id = :uid OR TRUE",
    "SELECT order_id FROM orders WHERE user_id = :uid AND user_id != 2",
    "SELECT order_id FROM orders WHERE user_id = :uid UNION SELECT order_id FROM orders WHERE user_id = 3",
])
def test_cross_tenant_sql_is_rejected(sql: str) -> None:
    assert customer_row_filter_error(sql, user_id=2) is not None
```

## P1-1 · 知识库为空时缓存的答案会**永久顶着「已灌库」继续被返回**

**严重度**：P1（正确性 / 数据一致性）
**位置**：`app/cache/corpus.py:124-137`（`bump`）+ `app/cache/invalidate.py:150-163`

### 现象（实测复现）

1. 迁移后知识库是**空的**（`rag_documents=0`、`rag_chunks=0`，见 P2-3）；
2. 此时问「退货政策是怎么规定的？」→ 走 RAG、**答案无任何出处**，并被写进语义缓存；
3. 灌完知识库（8 文档 / 61 片）后再问**同一句话**，仍然返回那条无出处的旧答案：

```text
第一次（空库）：citations=0   ← 被缓存
灌库后连问 4 次：citations=0   ← 全部命中旧缓存
```

直接查缓存表，这条记录 `hit_count=10`：

```text
1 | customer:2 | 退货政策是怎么规定的？ | cits=  (空) | rev= 1 | active=True | hits=10
```

### 根因

缓存失效的第三级是「知识库版本」（`corpus_revision`）。入库时
`bump_after_ingest` 会带着 `document_version` 调 `store.bump(version=..., force=False)`，
而 `bump()` 的逻辑是（`corpus.py:134-137`）：

```python
if version is not None and not force:
    current = self.current()
    if int(version) == current:
        return current          # ← 版本号相同就「不 bump」
```

它想表达的是「**同一份文档**重复入库不算变化」。
但实际传进来的是 `rag_documents.version`（**每份文档各自的版本号**），
不是全局知识库版本 —— 两者是**不同的量纲**。

实测证明（当时 `corpus_revision=1`）：

```text
Simulating bump_after_ingest for a NEW document whose rag_documents.version == 1:
  bump(version=1, force=False) -> 1
  corpus_revision after      = 1   <-- 未变化，缓存没被失效
For contrast, a document whose version == 2:
  bump(version=2, force=False) -> 2
  corpus_revision after      = 2
```

即：**任何 `rag_documents.version` 恰好等于当前 `corpus_revision` 的新文档/变更，
都不会推进版本号**。首次全量灌库尤其容易撞上（新文档 version 普遍是 1）。

### 影响

- 「推了新文档但缓存不失效」→ 用户长期拿到旧答案/无出处答案；
- 症状**极难归因**：接口 200、`/health` 全绿、日志无异常，只是答案悄悄不对；
- 与 `issues/002` 记录的「静默降级」是同一类最危险的失败模式。

### 修复

让 `bump` 只做「无条件 +1」，把「是否需要 bump」的判断交给**调用方**，
并用**正确量纲**的输入判断。最小改动：

```python
# app/cache/corpus.py
def bump(self, *, by: str = "", force: bool = True) -> int:
    """把版本 +1。默认**无条件**推进（版本号是缓存失效的开关，不是幂等标记）。"""
    # 删掉 `version == current` 的短路；重复入库的去重在 ingest 侧做（按内容哈希）
```

或在保留签名兼容的前提下，把短路条件改成「文档内容哈希未变」而不是「version 数字相同」。
**另外必须**：给 `cache_semantic_entries` 加一条「`corpus_revision` 与当前版本不符即不命中」的断言用例，
并在灌库脚本结束时**显式 `force=True` bump 一次**。

## P1-2 · 前端**从不使用刷新令牌** → 30 分钟后硬性掉线

**严重度**：P1（功能 / 用户体验）
**位置**：`web/src/lib/session.ts:133-164`（`ensureFreshToken`）

### 现象

`session.ts` 完整实现了刷新逻辑（含提前 60s 续期、失败清干净），
`api.ts:271` 也实现了 `postRefresh`，**但全项目没有任何地方调用它们**：

```text
grep "ensureFreshToken" web/src  → 只在 session.ts 定义处
grep "postRefresh"      web/src  → 只在 api.ts 定义处 + session.ts 定义处
```

唯一的引用出现在**测试**里（`web/tests/session.test.ts`），
即「功能被测试覆盖得很完整，但从未接线到应用」。

实际请求路径（`useChatStream.ts:130`、`SideNav.tsx:118`）都是直接
`readSession()` 拿到 `token` 就用，401 时没有任何续期重试。

### 影响

- 登录时**确实存了**刷新令牌（`writeSessionPair`，`session.ts:88`），但永远不会用；
- 访问令牌 30 分钟到期 → 用户被踢回登录页，与文档承诺的
  「刷新令牌 14 天有效、用户无感续期」**完全不符**；
- 更糟的是用户看到的是「莫名其妙掉线」，因为刷新令牌明明还在 localStorage 里。

### 修复

在**统一的请求出口**接上续期，而不是散落在每个组件：

```ts
// web/src/lib/api.ts —— 所有带令牌的请求走这一个包装
async function authorizedFetch(path: string, token: string, init?: RequestInit) {
  let response = await fetch(apiUrl(path), { ...init, headers: authHeaders(token) });
  if (response.status === 401) {
    const fresh = await ensureFreshToken(entryOf(path), browserStorage());
    if (fresh && fresh !== token) {
      response = await fetch(apiUrl(path), { ...init, headers: authHeaders(fresh) });
    }
  }
  return response;
}
```

WS 通道同理：握手前先 `await ensureFreshToken(...)`，避免用即将过期的令牌建连。
⚠️ 注意避免**并发 401 触发并行刷新**（多个请求同时刷新会互相作废刷新令牌）——
用一个模块级 `Promise` 去重。

## P1-3 · 管理员可以把口令设成 **1 个字符**

**严重度**：P1（安全 / 策略缺失）
**位置**：`app/api/schemas.py:489-490`、`:519`

### 现象（实测）

```text
POST /api/admin/accounts {"identifier":"probe_x","password":"x", ...}
  -> 201 Created        ← 1 个字符的口令被接受
POST /api/auth/login {"identifier":"probe_x","password":"x"}
  -> 200 拿到令牌       ← 并且真的能登录
```

空串被拒（`min_length=1` 拦下），但 `"x"`、`"a"`、`"  "` 这类都通过。

### 根因

`schemas.py` 里只有长度下限 1：

```python
password: str = Field(min_length=1, max_length=200, description="初始口令（由管理员告知本人）")
new_password: str = Field(min_length=1, max_length=200)
```

项目对**其它**配置项都是 fail-fast 且写清理由的（如限流表达式、
`API_CORS_ORIGINS` 的 `*`），唯独口令强度没有任何约束，
也没有「至少 8 位」这类最低要求。

### 影响

- 管理员开账号时误设/偷懒设弱口令，等于给该账号开了后门；
- 登录接口限流目前还**失效**（P0-1），弱口令 + 无限次尝试叠加 = 可直接爆破；
- 与项目自身「表白名单、fail-fast、默认拒绝」的安全纪律不一致。

### 修复

在 `schemas.py` 用 pydantic 约束，并在 `accounts.py` 再做一次（防绕过 API 层）：

```python
MIN_PASSWORD_LENGTH: Final[int] = 12

password: str = Field(min_length=MIN_PASSWORD_LENGTH, max_length=200,
                      description=f"初始口令（至少 {MIN_PASSWORD_LENGTH} 位）")
```

同时建议加一条弱口令黑名单（`password` / `123456` / 与 identifier 相同等），
错误信息**不要回显口令本身**。

## P2-1 · 知识库**默认是空的** → 开箱即用的 RAG 全部无出处

**严重度**：P2（可用性 / 首次体验）
**位置**：数据状态，非代码

### 现象

全新环境按 README 走完 `alembic upgrade head` + `scripts.seed` 之后，
知识库表是空的：

```text
rag_documents 0
rag_chunks    0
corpus_stats: docs=0 chunks=0
```

此时所有知识库类问题都走 RAG 但**零出处**（模型自由发挥）：

```text
Q=退货政策是怎么规定的？  route=rag  citations=0
Q=我的订单到哪了？        route=data citations=0
Q=物流一般几天到？        route=rag  citations=0
```

灌库后立刻恢复（同一句话 4 条出处、答案带 `[2][3][4][5]` 角标）：

```text
灌库后：citations=['docs/kb/退货政策.md #c7e2d41...', ... 共 4 条]
```

### 影响

- 新克隆仓库的人**第一眼看到的就是「AI 胡说八道、没有依据」**；
- `scripts.seed` 灌了业务数据但**不灌知识库**，而 README 把
  `load_knowledge_base` 列在「跑完全量回归后必须重灌」—— 措辞像是可选项，
  实际是**首次使用的必要步骤**；
- 与 P1-1 叠加：空库期间问过的问题会被**缓存下来**，灌库后继续返回无出处答案。

### 修复

1. README 的「首次启动」把 `uv run python -m scripts.load_knowledge_base`
   列为**必做步骤**（不是「跑完回归后重灌」）；
2. 建议让 `scripts.seed` 增加 `--with-kb` 或直接调用灌库，
   或让 `db_check` 把「知识库为空」列为**警告**（现在只统计业务表）；
3. 更稳的做法：RAG 节点在**检索到 0 条**时，不要静默给一段无出处的答案，
   而应输出「知识库暂无相关内容」这类**可识别的话术**，避免污染缓存与误导用户。

## P2-2 · `MemoryRateLimitStore` 的键**永不回收**（降级路径内存泄漏）

**严重度**：P2
**位置**：`app/api/ratelimit.py:189-236`

### 现象

```text
distinct keys tracked after 1000 one-shot callers: 1000
-> keys are never evicted (deque drains but dict entry stays)
```

`hit()` 会把窗口外的时间戳 `popleft()` 掉，但 `self._hits[key]` 这个**字典条目一直留着**。
匿名请求按来源 IP 分桶（`caller_bucket`），所以每个新 IP 都会永久新增一个键。

### 影响

- Redis 不可用时降级到内存实现（这是**设计内**的路径，`open_rate_limiter` 会告警）；
- 多副本下每个副本各存一份，长期运行 + 大量来源 IP（或伪造 IP 的扫描）→ 内存持续增长；
- 单条 `deque` 最多 `limit` 个浮点数，所以增长是**键数量**而非单键体积，
  但对「无限新增 IP」的攻击面没有上限。

### 修复

在 `hit()` 里顺手清理空键（成本极低）：

```python
with self._lock:
    hits = self._hits.get(key)
    if hits is None:
        hits = self._hits[key] = deque()
    while hits and hits[0] <= cutoff:
        hits.popleft()
    if not hits:
        # 窗口内没有任何访问 → 这个键可以立刻回收
        ...
```

更彻底的做法：定期扫一遍把空 `deque` 删掉，或用 `cachetools.TTLCache` 给键加 TTL。
另建议给键总数设一个上限（超过就 LRU 淘汰），避免被 IP 洪水打爆。

## P2-3 · 护栏的 LLM 判定会因 `max_tokens=200` 截断而**静默放行**

**严重度**：P2
**位置**：`app/agents/guardrail.py:276-288`

### 现象

实测日志里反复出现：

```text
LLM 返回内容为空但 finish_reason=length（被 max_tokens 截断）：
  model=deepseek-flash completion_tokens=200
guardrail 的 LLM 判定失败，按放行处置（确定性检查已先行）：... not_json / empty
```

护栏（输出侧最后一道）判定失败时**默认放行**（`guardrail.py:281`），
理由是「确定性检查（阻断词 + PII）已经跑过」。

### 影响

- 设计取舍是**有意的且写进了 docstring**，本身不算错；
- 但 `max_tokens=200` 对 `deepseek-flash` 这类**推理模型**偏紧：
  它先花 token 在 reasoning 上，实测 `completion_tokens=200` 正好顶满且 `content` 为空；
- 结果是「LLM 语义审查」这道防线**高频失效**，实际只剩确定性检查在兜底，
  而调用方/运维无法从接口层面感知（只有日志里一条 WARNING）。

### 修复

1. 把 `max_tokens` 提到 512~800（`guardrail.py:278`）——
   `client.py:203-211` 那条告警本来就是在提示这件事；
2. 给「judge 不可用」加一个**可观测的计数指标**（现在只有日志），
   让「语义审查失效率」能在 `/metrics` 上被看到；
3. 若失效率持续偏高，考虑对高风险 route（`ticket`/退款）改为 **fail-closed**，
   只对低风险只读问答保持 fail-open。

## P2-4 · 测试套件有 1 条**非幂等**用例（本地必红、CI 必绿）

**严重度**：P2（CI 可信度 / 测试隔离）
**位置**：`tests/api/test_cors.py:77-85`

> ⚠️ **本条我最初判成了「配置优先级倒置的产品 bug」，实测后**否定了这个结论**。
> 配置优先级是**正确**的。这里如实记录更正过程与真正的根因，因为它仍然是一个需要修的问题。

### 现象

```text
FAILED tests/api/test_cors.py::test_prod_defaults_to_no_cross_origin
  assert ['http://loca...68.1.13:3000'] == []
1 failed, 1750 passed, 50 skipped
```

### 根因（已实测定位）

**配置优先级本身是对的**。实测三种情形：

```text
① 进程 env 与 .env 都有、且值不同  → 进程 env 赢（正确）
② 只有 .env 有                    → .env 值（正确）
③ 两者都没有 + ENV=prod           → []（正确，prod 默认生效）
```

第 ③ 条实测：

```text
after pop API_CORS_ORIGINS from os.environ + ENV=prod:
  cors_origins(Fake) -> []            # ✅ prod 默认正确
```

**真正的原因有两个叠加**：

1. **`litellm` 在 import 时调用 `load_dotenv()`，把整个 `.env` 注入 `os.environ`**
   （实测：`import litellm` 之前 `os.environ["API_CORS_ORIGINS"]` 是 `None`，
   import 之后变成 `.env` 里的值；而进程环境变量被保留，所以优先级语义没错）：

   ```text
   before litellm: None
   after  litellm: 'http://localhost:3000,http://127.0.0.1:3000,...'
   ```

2. 于是 `monkeypatch.delenv("API_CORS_ORIGINS")` **删不掉 `.env` 提供的值** ——
   删了 `os.environ` 里的副本之后，`_env_value` 的第 2 步
   `getattr(settings, "api_cors_origins")` 仍然能拿到 `.env` 的值：

   ```text
   delenv 之后： _env_value(...) -> 'http://localhost:3000,...192.168.1.13:3000'
   ```

也就是说：**本仓的 `.env` 显式定义了 `API_CORS_ORIGINS`，
而这条用例的前提是「没配置过」** —— 前提被仓库自己的 `.env` 破坏了。

### 影响

- **本地必红、CI 必绿**（CI 没有 `.env`，前提成立，用例通过）——
  这类「只在开发者机器上红」的失败最容易被当成环境问题忽略；
- 它**掩盖了真实信号**：任何人看到 `1 failed` 都会先怀疑自己改坏了东西；
- 顺带暴露一个值得写进文档的事实：**`.env` 会被 `litellm` 注入进程环境**，
  所以「改 `.env` 后要不要重启」这类问题里，`os.environ` 的快照可能已经过期。

### 修复

让用例**显式**控制前提，而不是依赖「`.env` 里恰好没有这个键」：

```python
def test_prod_defaults_to_no_cross_origin(monkeypatch) -> None:
    monkeypatch.setenv("ENV", "prod")
    monkeypatch.delenv("API_CORS_ORIGINS", raising=False)
    # 用「显式 settings」表达前提：这个对象没有 api_cors_origins 字段
    class _NoCors:
        env = "prod"
    assert cors_origins(_NoCors()) == []
```

或者更贴近真实：临时把 `env_file` 指向一个不含该键的文件再构造 `Settings`。
**注意不要**改成断言 `.env` 的值 —— 那会把「配置优先级」这条被测语义丢掉。

另外建议在 `tests/conftest.py` 里加一条 autouse fixture，
把仓库 `.env` 会泄漏进 `os.environ` 的 `API_*` 键清干净，
让所有配置类用例都变成 hermetic（现在只有这一条暴露了问题）。
